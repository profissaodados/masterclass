Toda linha do seu Data Warehouse tem duas identidades. Você sabia?

Todo produto, cliente ou loja já chega com um código próprio, criado lá no sistema de origem — o SKU do ERP, o CPF do cadastro, a placa do carro. Essa é a chave natural. Mas dentro de um Data Warehouse, ela quase nunca é usada como identidade principal. Em vez disso, o próprio warehouse cria uma chave nova, artificial e sem significado nenhum — a surrogate key (chave substituta) — só para identificar aquela linha ali dentro. Parece redundante à primeira vista, mas é uma das decisões mais importantes — e mais mal compreendidas — de toda modelagem dimensional. Hoje vamos destrinchar exatamente por que ela existe, como ela é gerada, e o que ela resolve que a chave natural, sozinha, nunca conseguiria.

O ERP é dono da primeira. O Data Warehouse é dono da segunda — e é ela que o fato vai usar.
Fundamentos
🪪 Primeiro, o básico: o que é uma Chave Natural?

Uma chave natural (também chamada de business key, "chave de negócio") é um identificador que já existe fora do Data Warehouse, criado por algum sistema de origem — o ERP, o CRM, o e-commerce — para diferenciar seus próprios registros. Ela carrega significado para o negócio: um SKU identifica um produto no catálogo, um CPF identifica uma pessoa perante a Receita, uma placa identifica um carro perante o Detran.

🧸 SKU de produto
Código de catálogo criado pelo ERP da loja. Ex: SKU-1001.
🪪 CPF de cliente
Documento criado pela Receita Federal, não pelo seu sistema.
🏷️ Código de barras
Criado por um padrão global (GS1/EAN), reconhecido em qualquer loja do mundo.
🎒
Pensando como criança

A chave natural é como o seu nome de batismo: alguém de fora te deu esse nome, ele tem significado, e você nasceu com uma versão dele. O problema é que nomes podem se repetir (duas "Marias" na mesma escola), podem mudar (casamento, apelido) e às vezes uma pessoa é cadastrada em duas escolas diferentes com nomes escritos de um jeito ligeiramente diferente. Uma chave que vem "de fora" nunca é 100% confiável para identificar alguém com precisão total, para sempre.

O Gatilho de Tudo
❓ O problema: por que não usar a chave natural direto?

Se a chave natural já existe, por que não usá-la também como chave primária da dimensão no Data Warehouse? Na prática, quatro problemas aparecem — e qualquer um deles já seria motivo suficiente.

♻️ 1. Reaproveitamento de código
Sistemas de origem reciclam códigos descontinuados. Um SKU cancelado em 2024 pode ser reaproveitado em 2026 para um produto completamente diferente.
🔀 2. Colisão entre sistemas
Ao juntar duas lojas (física + online) num Data Warehouse único, cada uma tem seu próprio ERP — e ambas podem ter usado, por acaso, o mesmo código para produtos diferentes.
🕰️ 3. Precisa de histórico (SCD)
Se um cliente muda de cidade e você quer guardar as duas versões (Tipo 2), a chave natural (id_cliente) se repete em várias linhas — ela não pode mais ser a chave primária sozinha.
🐌 4. Performance de join
Chaves naturais costumam ser VARCHAR, às vezes compostas por mais de uma coluna (ex: loja + SKU) — mais pesadas para indexar e cruzar do que um inteiro simples.

Veja o problema nº 1 acontecendo de verdade: o SKU 1001 foi descontinuado em 2024 e, sem querer, reaproveitado em 2026 para um brinquedo totalmente diferente:

A surrogate key é exatamente o que evita isso: cada cadastro do código 1001 vira uma linha própria, com sua própria chave.

A Solução
🔑 O que é, de fato, uma Surrogate Key?

Uma surrogate key ("chave substituta" ou "chave sub-rogada") é um identificador artificial, gerado pelo próprio Data Warehouse — não pelo sistema de origem — cujo único objetivo é identificar, de forma única e permanente, uma linha (ou uma versão de uma linha) dentro de uma tabela de dimensão. Ela normalmente é um número inteiro sequencial (1, 2, 3...), mas também pode ser um hash ou um UUID, como veremos adiante.

🎫
Analogia

É como o crachá de visitante que você recebe na portaria de um prédio. Ele ganha um número (1, 2, 3...) que não tem nada a ver com quem você é — é só o jeito que aquele prédio tem de te diferenciar dos outros visitantes enquanto você está lá dentro. Seu RG continua sendo seu RG (a chave natural, válida em qualquer lugar). O crachá (a surrogate key) só existe, só tem sentido, e só é gerado dentro daquele prédio.

Ralph Kimball resume as regras de uma boa surrogate key em quatro palavras:

1️⃣ Simples
Uma única coluna, nunca composta por várias colunas de origem.
🚫 Sem significado
O valor em si não deve carregar informação de negócio — é só um rótulo.
🏭 Gerada pelo DW
Nasce dentro do próprio Data Warehouse, nunca copiada de um sistema de origem.
🔒 Durável
Uma vez atribuída a uma linha, nunca muda e nunca é reaproveitada em outra.

⚠️ Armadilha comum: criar uma surrogate key "inteligente" — por exemplo, reservar os números 100–199 para brinquedos e 200–299 para eletrônicos. Isso parece prático, mas transforma a surrogate key numa segunda chave natural disfarçada: no dia em que a loja de brinquedos passar de 99 produtos, ou um produto mudar de categoria, o esquema quebra. A surrogate key precisa continuar burra e sem significado — é isso que a torna à prova do futuro.

Mecânica
⚙️ Como ela funciona na prática

A dimensão guarda as duas chaves lado a lado: a surrogate key como chave primária, e a chave natural apenas como mais um atributo (guardada só para rastreabilidade — "qual era o código lá na origem?"). Já a tabela fato aponta exclusivamente para a surrogate key, nunca para o código de origem.

sqlcopiarCREATE TABLE dim_produto ( sk_produto INTEGER PRIMARY KEY, -- surrogate key: gerada pelo DW codigo_sku VARCHAR(20), -- chave natural: só um atributo agora nome VARCHAR(100), categoria VARCHAR(50) ); CREATE TABLE fato_venda ( sk_produto INTEGER REFERENCES dim_produto(sk_produto), -- aponta pra SK, nunca pro SKU data_venda DATE, quantidade INTEGER, valor_total DECIMAL(10,2) );

💡 Guardar a chave natural como atributo (não como PK) é o que permite rastrear a origem de qualquer linha — útil para debugar um pipeline ou responder "qual SKU do ERP virou este produto aqui?" — sem abrir mão de nenhum dos benefícios da surrogate key.

Mecânica
🏭 Como uma Surrogate Key nasce

Quando um produto novo chega do sistema de origem, o pipeline de carga (ETL/ELT) segue sempre a mesma lógica, batizada por Kimball de "surrogate key pipeline": procurar se aquele natural key já apareceu antes e, se não, gerar uma chave nova.

Existem três formas comuns de fazer o passo 3 — gerar o valor da nova chave. Cada uma tem um jeito de pensar bem diferente:

🔢 Sequencial
Um contador central (SEQUENCE/IDENTITY/SERIAL) entrega o próximo número inteiro: 1, 2, 3... O método clássico, mais usado em Data Warehouses tradicionais.
🧮 Hash
Aplica-se uma função (MD5/SHA256) sobre a chave natural (+ sistema de origem). O mesmo produto sempre gera o mesmo hash — sem precisar de um contador central.
🎲 UUID / GUID
Um valor aleatório gigante (gen_random_uuid()), praticamente impossível de colidir, gerado em qualquer lugar sem falar com ninguém.

Conexão Essencial
🕰️ Surrogate Key e SCD Tipo 2 — melhores amigos

Sem surrogate key, o SCD Tipo 2 (guardar o histórico completo de mudanças criando uma linha nova a cada versão) seria impossível de implementar de forma limpa. Se a chave primária da dimensão fosse a chave natural (id_cliente), nenhuma tabela relacional aceitaria duas linhas com a mesma id_cliente = 101 — chave primária não pode se repetir. A surrogate key resolve isso: cada versão de Maria ganha sua própria sk_cliente, enquanto o id_cliente (chave natural) continua o mesmo em todas.

Casos que só existem por causa da SK
🧩 Casos especiais

Como a surrogate key não depende de nenhum sistema de origem, ela permite três truques que uma chave natural, sozinha, jamais permitiria.

❓ 1. A linha "Desconhecido" (sk = -1)
Às vezes uma venda chega no fato antes do cadastro do cliente correspondente terminar de carregar (um atraso chamado late-arriving dimension), ou o campo realmente veio vazio na origem. Como toda linha do fato precisa de uma surrogate key válida, cria-se uma linha reservada especial para representar "ainda não sei quem é":
sk_cliente (PK)id_cliente (natural)nomecidade
-1NULL(Desconhecido)(Desconhecido)
1001101MariaRecife
Isso só é possível porque -1 é apenas um número artificial — tentar fazer o mesmo com um CPF "desconhecido" seria estranho e ambíguo.
📅 2. A exceção da Dim Tempo
Kimball aceita, como exceção prática, usar uma "smart key" na dimensão de tempo — um inteiro como 20260728 (AAAAMMDD) como surrogate key. Funciona porque datas nunca mudam de versão nem são reaproveitadas, e o valor ainda é legível e ordena naturalmente.
🧩 3. Mini-dimensão
Atributos que mudam demais (ex: "faixa de gasto no mês") ganham sua própria tabelinha com sua própria surrogate key, referenciada por uma segunda chave estrangeira no fato — evita que a dimensão principal exploda em linhas.

Mão na Massa
💻 Os 3 métodos em SQL (DuckDB / Postgres)

Abaixo, o mesmo produto novo (SKU-1001, "Boneca Estelar") ganhando uma surrogate key pelos três métodos — e, no final, o padrão de "lookup" usado num pipeline real para nunca gerar uma chave duplicada para o mesmo produto.

1Sequencial — SEQUENCE / IDENTITY
O método clássico: um contador central entrega o próximo inteiro disponível.
sql · duckdbcopiarCREATE SEQUENCE seq_sk_produto START 1; CREATE TABLE dim_produto ( sk_produto BIGINT PRIMARY KEY DEFAULT nextval('seq_sk_produto'), codigo_sku VARCHAR, nome VARCHAR ); INSERT INTO dim_produto (codigo_sku, nome) VALUES ('SKU-1001', 'Boneca Estelar'); SELECT * FROM dim_produto; -- sk_produto: 1 | codigo_sku: SKU-1001 | nome: Boneca Estelar
2Hash — MD5 da chave natural
O mesmo produto, em qualquer worker paralelo, sempre calcula o mesmo hash — sem precisar consultar um contador central.
sql · duckdbcopiarSELECT md5('ERP_ONLINE' || '-' || 'SKU-1001') AS sk_produto, 'SKU-1001' AS codigo_sku, 'Boneca Estelar' AS nome; -- sk_produto: 8f4e1c9a... (mesmo hash sempre que rodar com o mesmo input)
3UUID — valor aleatório globalmente único
Gerado sem consultar nada nem ninguém — ótimo quando várias origens inserem ao mesmo tempo.
sql · duckdbcopiarSELECT uuid() AS sk_produto, 'SKU-1001' AS codigo_sku, 'Boneca Estelar' AS nome; -- sk_produto: 3fa85f64-5717-4562-b3fc-2c963f66afa6
4O padrão real: lookup antes de gerar (nunca duplicar a SK do mesmo natural key)
Este é o "surrogate key pipeline" de verdade: só gera uma chave nova para quem ainda não existe na dimensão.
sql · duckdbcopiar-- staging_produto = o que chegou hoje da origem INSERT INTO dim_produto (codigo_sku, nome) SELECT s.codigo_sku, s.nome FROM staging_produto s LEFT JOIN dim_produto d ON d.codigo_sku = s.codigo_sku WHERE d.sk_produto IS NULL; -- só insere quem realmente é novo -- depois, o fato faz o lookup da SK a partir do código natural INSERT INTO fato_venda (sk_produto, data_venda, quantidade, valor_total) SELECT d.sk_produto, v.data_venda, v.quantidade, v.valor_total FROM staging_venda v JOIN dim_produto d ON d.codigo_sku = v.codigo_sku;

✅ Note que fato_venda nunca guarda codigo_sku diretamente — o JOIN acontece uma vez, na carga, e o resultado (a surrogate key) é o que fica gravado para sempre no fato.

Checklist
✅ Boas Práticas
🔑 A surrogate key é sempre uma única coluna
Nunca componha a chave primária com várias colunas de origem — se hoje a natural key é composta (ex: loja + SKU), a surrogate key ainda assim é uma coluna só.
📎 Guarde a chave natural como atributo
Nunca descarte o código de origem — mantenha-o como coluna comum, para rastreabilidade e para o lookup do pipeline.
🚫 Nunca reaproveite uma surrogate key
Uma vez usada para uma linha, aquele valor nunca deve ser reatribuído a outra — mesmo que a linha original seja "apagada" logicamente.
🧠 Não codifique significado nela
Resista à tentação de fazer faixas de valores "significarem" categoria, região ou tipo. Isso recria o problema que a surrogate key veio resolver.
❓ Sempre tenha uma linha "Desconhecido"
Reserve uma surrogate key fixa (ex: -1 ou 0) para representar dados ausentes ou ainda não carregados — nunca deixe o fato com uma chave estrangeira nula.
⚙️ Escolha o método pelo formato do pipeline
Carga única e sequencial → sequencial. Paralela e idempotente → hash. Distribuída e sem coordenação → UUID.
