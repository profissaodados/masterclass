Dados fragmentados, uma pergunta só

BI Conversacional é a ideia de perguntar aos seus dados em português — "quais clientes compraram e depois reclamaram?" — e receber uma resposta certa, na hora, mesmo que essa resposta esteja escondida em três sistemas diferentes que nunca conversaram entre si. Por trás da mágica não existe adivinhação: existe um LLM (um modelo de linguagem) que traduz sua pergunta em SQL de verdade, guiado por um mapa de como os dados se conectam, e um motor como o DuckDB que executa essa consulta cruzando as fontes na hora. Nesta aula, vamos abrir essa caixinha em gráficos, comparações e exemplos bem visuais — como se estivéssemos explicando para uma criança de 8 anos.

Fundamentos
🤔 O Que É BI Conversacional?

"BI" é sigla de Business Intelligence — o conjunto de ferramentas e processos que transforma dados brutos em respostas para decisões de negócio. Durante décadas, isso significou construir dashboards: telas fixas, com gráficos prontos, para perguntas que alguém já previu com antecedência. O BI Conversacional muda essa lógica: em vez de você ir até um dashboard pronto, você faz a pergunta — com suas próprias palavras — e um agente de IA descobre, na hora, onde estão os dados e como combiná-los para responder.

📊 BI Tradicional
Alguém desenha um dashboard antes de você precisar dele. Se a pergunta não estava prevista, é preciso pedir para um time de dados construir algo novo — e esperar.
💬 BI Conversacional
Você pergunta em linguagem natural no momento em que precisa. Um LLM traduz a pergunta em SQL, um motor executa contra as fontes, e a resposta chega em segundos.
🗺️ O Segredo Não É Mágica
É um mapa semântico bem feito + um LLM que segue esse mapa + um motor de consulta (como o DuckDB) que sabe federar várias fontes ao mesmo tempo.
🧒 Explica pra criança

Imagine que você tem um amigo tradutor que mora dentro do computador. Você fala "quero saber quantos brinquedos o João comprou", e ele não inventa uma resposta — ele vai até as gavetas certas, conta de verdade, e te conta o número exato. Ele só faz isso direito se alguém já tiver explicado pra ele onde fica cada gaveta e como elas se conectam. É disso que esta aula trata!

O Problema Real
📇 A Herança Silenciosa: Três Cartórios na Mesma Cidade

Imagine três cartórios numa mesma cidade: um registra nascimentos, outro imóveis, outro empresas abertas. Cada um funciona perfeitamente sozinho. Mas a pergunta "quais moradores que compraram um imóvel também abriram uma empresa?" é impossível de responder — porque cada cartório usa um jeito diferente de identificar a mesma pessoa, e nenhuma ponte foi construída entre eles. Isso é exatamente o que acontece dentro de uma empresa com CRM, ERP e sistema de Suporte.

🧒 Explica pra criança

É como se seu melhor amigo tivesse um apelido diferente em cada lugar: a vó chama de "Zezinho", a escola chama de "José" e o time de futebol chama de "Camisa 9". Se alguém perguntar "quantos gols o Zezinho fez na escola?", ninguém consegue responder direto — é preciso primeiro descobrir que os três nomes são a mesma pessoa.

A pergunta de negócio impossível — isoladamente

"Quais clientes de Varejo compraram e depois abriram chamados? Mostre total gasto e quantidade de chamados." — o segmento "Varejo" só existe no CRM, "quanto gastou" só existe no ERP, "abriu chamado" só existe no Suporte. Nenhuma fonte sozinha responde. É preciso cruzar as três ao mesmo tempo — e é exatamente isso que o BI Conversacional automatiza.

A Peça Mais Importante
🗺️ O Mapa Semântico: O Que o LLM Precisa Saber

Um LLM sozinho não sabe que cod_cli no ERP é a mesma coisa que id_cliente no CRM. Alguém precisa entregar esse conhecimento por escrito — isso é o contexto semântico (ou "mapa executivo"): um texto que descreve schema, relações e armadilhas antes de qualquer pergunta ser feita.

📐 Schema das Tabelas
Quais tabelas existem, quais colunas cada uma tem e o que cada coluna significa de verdade — não só o nome técnico.
🔗 Regras de Junção
Como cruzar as fontes: crm.id_cliente = erp.cod_cli, crm.id_cliente = suporte.cliente_ref. Sem isso, o LLM "chuta" o join errado.
🧮 Dicas de Agregação
Avisos para evitar armadilhas de contagem — por exemplo, qual coluna usar num COUNT(DISTINCT ...) para não contar a coisa errada.
🔒 Restrições de Segurança
Deixar explícito que só é permitido SELECT — nenhuma escrita, nenhuma alteração de dado é aceitável vinda de SQL gerado por IA.
🧒 Explica pra criança

É como dar um mapa do tesouro para o tradutor antes de ele sair procurando. Sem o mapa, ele pode até encontrar alguma coisa — mas pode ser a caixa errada. Com o mapa certo ("o baú de brinquedos do João fica no quarto azul, não no verde"), ele acha exatamente o que você pediu.

Frase que resume tudo

"O LLM é tão bom quanto o mapa que você entrega." Com 300 tabelas corporativas de nomes crípticos, um mapa semântico ruim ou incompleto torna esse problema exponencialmente mais difícil — não é sobre o modelo ser mais "inteligente", é sobre o mapa ser mais completo.

Confiança & Controle
🛡️ Segurança: Somente Leitura

Um LLM gera texto — inclusive texto que parece SQL perigoso. Antes de qualquer comando gerado tocar o banco de dados, uma etapa de validação verifica: o comando começa com SELECT ou WITH (para CTEs)? Se contiver INSERT, DELETE, DROP, UPDATE ou ALTER em qualquer lugar, é bloqueado antes de rodar.

O Motor por Baixo do Capô
🦆 DuckDB Como Federador: Consultar Sem Copiar

"Federar" significa consultar várias fontes como se fossem uma só, sem duplicar os dados num lugar central. É a diferença entre a abordagem clássica de Data Warehouse (copiar tudo antes) e a abordagem de federação (consultar direto, na hora). Compare os dois caminhos abaixo.

🏗️ Abordagem Clássica (Copiar Primeiro — ETL)
1. Extrair dados de cada fonte
2. Transformar e padronizar
3. Carregar num Data Warehouse central
4. Consultar a cópia (não a fonte original)
🦆 Federação com DuckDB (Consultar Direto)
1. Pergunta chega em linguagem natural
2. DuckDB se conecta a cada fonte, na hora
3. Executa o SQL cruzando as fontes sem copiar
4. Resultado combinado retorna na mesma consulta
👆 Clique em qualquer bloco
Compare o caminho dos dados nos dois modelos, passo a passo.

💡 Federação não substitui o Data Warehouse em todos os casos — pipelines de ETL continuam essenciais para dados que precisam de histórico, qualidade tratada e alta performance repetida. Mas para perguntas ad hoc, que ninguém previu, esperar um pipeline novo ser construído pode levar dias; federar com DuckDB responde em segundos.

💡 Limites e Riscos: Onde Isso Pode Quebrar

Nenhuma tecnologia resolve problema de fundação sozinha. Três pontos merecem atenção séria antes de colocar isso em produção:

🎯 Confiança no SQL Gerado
Um SQL pode ser sintaticamente válido mas semanticamente errado — roda sem erro e devolve um número, só que o número responde a pergunta errada. Em produção: conexão somente leitura, allowlist de tabelas, validação do plano de execução.
🗺️ Qualidade do Mapa Semântico
Contexto incompleto ou dicas erradas geram respostas "certas no formato, erradas no significado". Com centenas de tabelas de nomes crípticos, isso piora exponencialmente.
🏚️ Herança Não Resolvida
Chaves inconsistentes, datas em formatos diferentes, duplicatas — tudo isso continua lá embaixo. A IA multiplica a qualidade da base: para cima se ela é boa, para baixo se ela é ruim.
🧒 Explica pra criança

É como usar uma lanterna forte pra ver dentro de um quarto bagunçado. Com a lanterna você enxerga a bagunça muito melhor e muito mais rápido — mas a lanterna, sozinha, não arruma o quarto. Alguém ainda precisa guardar os brinquedos no lugar certo.

A frase que resume a virada

"A camada cognitiva não conserta a fundação, ela ilumina o estado dela." A mudança real trazida pelo BI Conversacional não é tecnológica — é de governança: pela primeira vez, a IA força a organização a responder, com clareza, o que os dados realmente significam.

Use APENAS estas views e colunas: - clientes(customer_id, customer_unique_id, customer_city, customer_state) - pedidos(order_id, customer_id, order_status, order_purchase_timestamp, order_delivered_customer_date, order_estimated_delivery_date) - itens_pedido(order_id, order_item_id, product_id, seller_id, price, freight_value) - pagamentos(order_id, payment_type, payment_installments, payment_value) - avaliacoes(order_id, review_score, review_comment_message) - produtos(product_id, product_category_name) - vendedores(seller_id, seller_city, seller_state) Regras de junção: - pedidos.customer_id = clientes.customer_id - itens_pedido.order_id = pedidos.order_id - itens_pedido.product_id = produtos.product_id - itens_pedido.seller_id = vendedores.seller_id - pagamentos.order_id = pedidos.order_id - avaliacoes.order_id = pedidos.order_id Dicas de agregação: - "Faturamento" ou "total vendido" = SUM(itens_pedido.price) — não payment_value, que inclui frete e pode estar parcelado. - Um pedido pode ter várias linhas em itens_pedido (vários produtos) — some, não conte linhas. - "Quantidade de pedidos" = COUNT(DISTINCT order_id), nunca COUNT(*) em itens_pedido. - Tempo de entrega = order_delivered_customer_date - order_purchase_timestamp. Regras de segurança: - Gere APENAS comandos SELECT ou WITH. Nunca INSERT, UPDATE, DELETE, DROP ou ALTER. - Responda SOMENTE com o SQL, sem explicações, sem markdown. """
Antes de rodar: veja o SQL que o LLM deve gerar para cada pergunta
FunçãoResponsabilidade
montar_conexao()Cria views do DuckDB apontando direto para os 7 CSVs do Olist — sem importar nada
limpar_sql()Remove cercas de markdown (```sql) que o modelo às vezes insere na resposta

Passo 4 — O script completo: agente_bi_olist.py
pythoncopiarimport sys import re import duckdb import ollama CAMINHO_DADOS = "./dados_olist" def montar_conexao(): # DuckDB lê os CSVs direto do disco — sem CREATE TABLE, sem import prévio con = duckdb.connect(database=":memory:") con.execute(f""" CREATE VIEW clientes AS SELECT * FROM read_csv_auto('{CAMINHO_DADOS}/olist_customers_dataset.csv'); CREATE VIEW pedidos AS SELECT * FROM read_csv_auto('{CAMINHO_DADOS}/olist_orders_dataset.csv'); CREATE VIEW itens_pedido AS SELECT * FROM read_csv_auto('{CAMINHO_DADOS}/olist_order_items_dataset.csv'); CREATE VIEW pagamentos AS SELECT * FROM read_csv_auto('{CAMINHO_DADOS}/olist_order_payments_dataset.csv'); CREATE VIEW avaliacoes AS SELECT * FROM read_csv_auto('{CAMINHO_DADOS}/olist_order_reviews_dataset.csv'); CREATE VIEW produtos AS SELECT * FROM read_csv_auto('{CAMINHO_DADOS}/olist_products_dataset.csv'); CREATE VIEW vendedores AS SELECT * FROM read_csv_auto('{CAMINHO_DADOS}/olist_sellers_dataset.csv'); """) return con def limpar_sql(texto): return re.sub(r"```sql|```", "", texto).strip() def validar_sql(sql): sql_upper = sql.upper() if not (sql_upper.startswith("SELECT") or sql_upper.startswith("WITH")): return False proibidos = ["INSERT", "UPDATE", "DELETE", "DROP", "ALTER", "ATTACH"] return not any(p in sql_upper for p in proibidos) def pergunta_para_sql(pergunta, modelo="llama3.1"): prompt = f"{CONTEXTO_SEMANTICO}\n\nPergunta: {pergunta}\nSQL:" resposta = ollama.chat( model=modelo, messages=[{"role": "user", "content": prompt}], options={"temperature": 0}, # determinístico, sem "criatividade" ) sql = limpar_sql(resposta["message"]["content"]) if not validar_sql(sql): raise ValueError(f"SQL bloqueado por segurança:\n{sql}") return sql def agente_bi(pergunta, modelo="llama3.1"): con = montar_conexao() sql = pergunta_para_sql(pergunta, modelo) print(f"\n🧠 SQL gerado:\n{sql}\n") return con.execute(sql).df() def main(): pergunta = sys.argv[1] if len(sys.argv) > 1 else \ "Quais os 5 estados com maior valor total de frete pago pelos clientes?" resultado = agente_bi(pergunta) print(resultado.to_string(index=False)) if __name__ == "__main__": main()

Deu errado? Problemas comuns
🔌 Connection refused
O Ollama não está rodando. Deixe ollama serve ativo num terminal (ou confirme que já roda em segundo plano) antes de chamar o script.
📁 CSV não encontrado
Confirme que CAMINHO_DADOS aponta exatamente para a pasta onde os arquivos do Olist foram extraídos.
🧩 Coluna inexistente no SQL
O mapa semântico está incompleto — adicione a coluna faltante à descrição da view correspondente em CONTEXTO_SEMANTICO.
🐢 Resposta muito lenta
Troque para um modelo menor (ollama pull qwen2.5:3b) ou verifique se há aceleração de GPU disponível.
Do Protótipo à Produção
✅ Boas Práticas
🔒 Conexão somente leitura
Não confie só na validação de texto — conecte o agente ao banco com credenciais que fisicamente não conseguem escrever nada.
📋 Allowlist de tabelas
Restrinja explicitamente quais tabelas/views o agente pode enxergar — nunca exponha o banco inteiro por padrão.
🧪 Validar o plano de execução
Além de checar o texto do SQL, valide o plano (EXPLAIN) antes de rodar — pega comandos disfarçados que a regex simples deixaria passar.
📖 Versionar o mapa semântico
Trate o contexto semântico como código: revisão, versionamento e testes — é a peça que mais decide a qualidade das respostas.
👀 Auditar amostras de SQL
Revise periodicamente uma amostra de perguntas e SQLs gerados — é como você percebe cedo um join errado ou uma dica de agregação faltando.
💰 Monitorar custo e latência
Cada pergunta dispara uma chamada de LLM + uma consulta federada — acompanhe tempo de resposta e custo por pergunta, especialmente com fontes remotas.
