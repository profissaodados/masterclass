Toda ferramenta pergunta a mesma coisa. Toda ferramenta deveria ouvir a mesma resposta.

O dbt Semantic Layer é uma camada que fica entre os seus modelos dbt (já prontos, testados, no warehouse) e todas as ferramentas que consomem números — Tableau, Power BI, Hex, Google Sheets, Slack, Python. Em vez de cada ferramenta reescrever sua própria fórmula de "receita" ou "ticket médio", você define essas métricas uma única vez, em YAML, e todo mundo que perguntar "qual foi a receita?" recebe exatamente a mesma resposta — calculada na hora, sempre a partir da fonte. O motor por trás disso se chama MetricFlow, e é ele quem traduz a pergunta de negócio em SQL para o seu warehouse.

O Gatilho de Tudo
❓ O problema: cada ferramenta "sabe" calcular receita à sua maneira

Imagine uma loja com dados de pedidos no warehouse. O time de BI monta um dashboard no Tableau e escreve SUM(order_total). O time de Growth monta uma planilha no Excel e copia os valores manualmente, sem excluir reembolsos. O time de Produto usa o Power BI e escreve a fórmula excluindo pedidos cancelados. Três pessoas, três ferramentas, três números diferentes — todos chamados de "receita". Ninguém está mentindo de propósito: cada um só reimplementou a regra de negócio do seu próprio jeito, porque não existia um lugar único onde essa regra estivesse escrita.

🗣️
Pensando como criança

É como perguntar "quantos doces você tem?" para três amigos que contam de jeitos diferentes: um conta só os doces inteiros, outro conta os pedaços separados, outro nem sabia que tinha uns doces guardados na gaveta. As três respostas estão "certas" do jeito de cada um — mas só uma delas é a resposta combinada, a que todo mundo concordou em usar.

Clique nas ferramentas abaixo e veja como a mesma pergunta — "qual foi a receita?" — gera respostas diferentes, até a última opção, onde todas passam a usar a métrica definida no Semantic Layer:

⚠️ O Semantic Layer não inventa uma métrica nova — ele obriga todo mundo a concordar com uma única definição, escrita em código, versionada e testada como qualquer outra parte do pipeline dbt.

Fundamentos
🧠 Então, o que é exatamente o Semantic Layer?

Ele é uma tradução. De um lado, você tem tabelas no warehouse — fct_orders, dim_customers — cheias de linhas e colunas cruas. Do outro lado, você tem perguntas de negócio: "qual foi a receita em março, por região?". O Semantic Layer é o dicionário que conecta as duas pontas: ele sabe que "receita" significa sum(order_total), que "região" vem da tabela de clientes, e que para juntar as duas coisas é preciso usar o customer_id. Toda vez que alguém pergunta, o MetricFlow lê esse dicionário e escreve o SQL certo, na hora, para o seu warehouse.

📖 Sem Semantic Layer
A "tradução" mora na cabeça de cada analista, espalhada em dashboards, planilhas e queries soltas. Muda a pessoa, muda a fórmula.
📐 Com Semantic Layer
A tradução mora em YAML versionado, ao lado dos seus modelos dbt. Muda a pessoa, a fórmula continua a mesma.
⚙️ MetricFlow
O "tradutor" de verdade: lê o YAML e compila SQL válido para Snowflake, BigQuery, Databricks, Postgres, DuckDB e outros.

💡 O Semantic Layer não substitui seus modelos dbt — ele é construído em cima deles. Um semantic_model sempre aponta para um ref() de um modelo que já existe e já passou pelos seus testes normais.

A peça central
🧩 Semantic Models — a ficha técnica de um modelo dbt

Um semantic model é um arquivo YAML que descreve um modelo dbt em termos que o MetricFlow entende: quais colunas servem para identificar e juntar registros (entities), quais colunas servem para agrupar e filtrar (dimensions), e quais colunas servem para agregar em números (measures). Cada semantic model aponta para exatamente um modelo dbt via ref() — normalmente uma tabela fato ou dimensão que já vive nos seus marts.

🧾
Analogia

É como a ficha técnica de um brinquedo de montar: ela não é o brinquedo em si (isso já é o modelo dbt), mas diz onde estão os encaixes (entities), quais peças têm cores/categorias (dimensions) e quantas peças de cada tipo vêm na caixa (measures). Sem a ficha técnica, você até tem as peças — mas não sabe como elas se conectam.

yamlcopiarsemantic_models: - name: orders description: "Um pedido feito na loja." model: ref('fct_orders') defaults: agg_time_dimension: ordered_at entities: # quem se conecta com quem - name: order_id type: primary - name: customer_id type: foreign dimensions: # o que descreve/agrupa - name: ordered_at type: time type_params: time_granularity: day - name: order_status type: categorical measures: # o que se agrega em número - name: order_total agg: sum expr: order_total - name: orders agg: count expr: order_id

✅ Repare que este YAML não recalcula nada sozinho — ele só rotula colunas que já existem em fct_orders. O trabalho pesado de transformação continua sendo feito pelo modelo dbt de sempre.

Peça 1 de 3
🔗 Entities — os encaixes que permitem juntar tabelas sozinhas

Uma entity é uma chave: uma coluna que identifica um registro (primary), referencia outro registro (foreign) ou identifica um registro de forma não-exclusiva num certo grão (unique). É a partir das entities que o MetricFlow descobre, sozinho, como fazer o JOIN entre dois semantic models — você nunca escreve esse join manualmente numa consulta de métrica.

🧲
Analogia

Entities são como os plugues de encaixe do Lego: cada peça tem um tipo de encaixe, e duas peças com encaixes compatíveis se juntam sem que você precise explicar como. O semantic model "pedidos" tem um encaixe customer_id (foreign); o semantic model "clientes" tem o mesmo encaixe como customer_id (primary). Quando você pede uma métrica de pedidos agrupada por região do cliente, o MetricFlow simplesmente encaixa as duas peças.

Veja o join acontecendo: ao pedir a métrica revenue agrupada por customer_id__region, o MetricFlow segue o encaixe customer_id automaticamente entre os dois semantic models:

🟦 primary
Identifica 1 registro por linha no modelo — a chave "dona" do semantic model. Ex: customer_id em customers.
🟨 foreign
Referencia a chave primária de outro semantic model. Ex: customer_id em orders, apontando de volta para customers.
🟩 unique
Identifica um registro de forma única, mas não é a chave "dona" do modelo — útil quando existe mais de um identificador válido.
Peça 2 de 3
📅 Dimensions — os adjetivos que agrupam e filtram

Uma dimension é qualquer coluna usada para agrupar, filtrar ou fatiar um número — nunca para somar. Existem dois tipos: categorical (texto/categoria, como status do pedido ou região do cliente) e time (uma data ou timestamp, com uma granularidade declarada — dia, semana, mês, trimestre, ano).

🏷️
Analogia

Dimensions são as etiquetas coloridas numa caixa de brinquedos: "vermelho", "grande", "comprado em março". Elas não dizem quantos brinquedos existem — só ajudam a separar o monte em grupos menores antes de contar.

🏷️ Categorical
Uma categoria fixa: order_status, region, customer_type. Serve para GROUP BY e para filtros do tipo "só os pedidos 'completed'".
🕰️ Time
Uma data com granularidade declarada: ordered_at em day. É a partir dela que o MetricFlow sabe truncar para month, quarter ou year quando pedido.

Uma mesma dimensão de tempo pode ser consultada em granularidades diferentes, sem reescrever nada — o MetricFlow faz o DATE_TRUNC por você:

Granularidade pedidaordered_at originalComo aparece agrupado

week2026-03-142026-03-09 (semana que contém o dia)

💡 Para referenciar uma dimensão que vive num semantic model diferente daquele da sua métrica, usa-se a sintaxe entidade__dimensão — por exemplo, customer_id__region ao consultar a métrica revenue, que mora em orders. É a mesma "trilha" de join explicada na seção de Entities.

Peça 3 de 3
🧮 Measures — o ingrediente cru, antes de virar receita

Uma measure é uma agregação simples sobre uma coluna: soma, contagem, contagem distinta, mínimo, máximo, média. Ela ainda não é uma métrica de negócio — é só o número cru, pronto para ser usado como ingrediente. A métrica é quem decide como esse ingrediente vira um prato (uma métrica simples usa 1 measure; uma métrica ratio combina 2).

🥣
Analogia

Measures são os ingredientes na despensa: "2 xícaras de açúcar", "3 ovos". Uma metric é a receita pronta: "bolo de chocolate" usa açúcar, ovos e chocolate numa proporção específica. Ninguém serve "açúcar" como prato — mas todo prato começa com ingredientes medidos.

Os tipos de agregação (agg) mais usados numa measure:

Σ sum
Soma os valores. Ex: order_total.
# count
Conta linhas. Ex: número de pedidos.
#! count_distinct
Conta valores únicos. Ex: clientes distintos.
x̄ average
Média simples dos valores.
↕ min / max
Menor ou maior valor da coluna.

O caminho completo, do ingrediente cru até o prato servido — order_total (coluna) vira a measure order_total (soma), que vira a metric revenue (a receita de negócio que qualquer ferramenta consulta):

🧱 coluna: order_total → 🧮 measure: order_total (agg: sum) →
📐 metric: revenue
type: simple
O produto final
📐 Metrics — a receita que vira número de negócio

Uma metric é a definição oficial de negócio, construída a partir de uma ou mais measures (ou até de outras metrics). Existem 5 tipos, cada um resolvendo um jeito diferente de combinar ingredientes:

yamlcopiarmetrics: - name: revenue label: "Receita" type: simple type_params: measure: order_total - name: orders label: "Pedidos" type: simple type_params: measure: orders - name: average_order_value label: "Ticket médio" type: ratio type_params: # ratio combina 2 metrics já definidas, não measures cruas numerator: revenue denominator: orders

🌐Consumidores
📊 Tableau 📈 Hex / Mode / Sigma 🔢 Google Sheets / Excel 💬 Slack 🐍 Python / Notebooks
🧑‍💻 dbt Core + MetricFlow
Você define e valida semantic models e metrics localmente, e consulta pela CLI (mf query / dbt sl query) direto do seu terminal — ótimo para desenvolver e testar as definições.
☁️ dbt Cloud — API hospedada
Expõe a mesma definição via API (GraphQL e JDBC/ODBC) para qualquer ferramenta externa se conectar — é essa API que Tableau, Hex ou uma planilha realmente consultam em produção.

Uma consulta real de métrica, pedindo receita e pedidos agrupados por mês e por região do cliente:

bashcopiardbt sl query --metrics revenue,orders --group-by metric_time__month,customer_id__region # o MetricFlow traduz isso, sozinho, em algo como: SELECT DATE_TRUNC('month', o.ordered_at) AS metric_time__month, c.region AS customer_id__region, SUM(o.order_total) AS revenue, COUNT(o.order_id) AS orders FROM fct_orders o JOIN dim_customers c ON o.customer_id = c.customer_id GROUP BY 1, 2;

✅ Ninguém escreveu esse JOIN à mão — o MetricFlow o inferiu a partir das entities customer_id declaradas nos dois semantic models, exatamente como visto na seção de Entities.

Uma pausa honesta
🌱 "Então o mercado ainda não está pronto pra isso?"

Não exatamente — é mais preciso dizer que a dor que a Semantic Layer resolve é real e validada (todo mundo já viveu o problema de "receita" divergente entre ferramentas, visto lá na seção "O Problema"), mas a distribuição específica do dbt Labs ainda é nova. O MetricFlow só virou parte do dbt Core em meados de 2023 — pouco mais de 2 anos de vida. Integrações nativas de BI historicamente levam anos para se espalhar pelo ecossistema inteiro, ferramenta por ferramenta.

🗺️
Analogia

É como um idioma novo, recém-inventado: por mais útil que seja, cada país (cada ferramenta de BI) precisa decidir aprender esse idioma, treinar tradutores (construir um conector) e assinar acordos antes de conseguir conversar nele. Enquanto isso, um idioma que todo mundo já fala — como o "SQL de um banco Postgres" — dispensa esse processo inteiro. Ninguém precisa aprender nada novo pra usar um idioma que já sabia.

Um detalhe técnico explica boa parte do "gap": o dbt Labs escolheu expor a Semantic Layer via uma API nova (GraphQL + um driver JDBC próprio, Arrow Flight SQL) em vez de imitar um protocolo que as ferramentas já falam. Isso significa que cada fornecedor de BI precisa construir um conector dedicado, um acordo de cada vez:

FerramentaConector nativo?Como funciona hoje
TableaunativoConector dbt Semantic Layer embutido no próprio app
Google Sheets / ExcelnativoExtensão oficial publicada pela dbt Labs
Hex / Mode / SigmanativoParceiros certificados, conector dedicado
Power BIcontornoFonte de dados "Script Python" + SDK dbtsl — importação/refresh, não é consulta ao vivo

💡 Um concorrente direto, o Cube.dev, tomou a decisão oposta: expõe as métricas como se fosse um banco Postgres comum, então qualquer ferramenta com driver Postgres — incluindo Power BI e Metabase — já conecta sem esperar integração nenhuma. É o mesmo problema de distribuição, resolvido com uma escolha de protocolo diferente.

🌎 Então o mercado não rejeitou o conceito de metrics layer — ele só ainda não decidiu qual protocolo vai virar padrão. Enquanto isso não se resolve, a lista de ferramentas com suporte nativo só tende a crescer.

A peça invisível
🕰️ Time Spine — o calendário que nunca falta um dia

Métricas cumulative e comparações período a período (como "crescimento mês a mês") precisam de uma tabela auxiliar com uma linha para cada dia do calendário — mesmo os dias sem nenhum pedido. Essa tabela se chama time spine (geralmente metricflow_time_spine), e é o que garante que um mês sem vendas apareça como "R$ 0", em vez de simplesmente sumir do gráfico.

📆
Analogia

É como um diário com uma página para cada dia do ano, mesmo os dias em que nada de especial aconteceu. Se seu diário só tivesse páginas para os dias em que você escreveu algo, ficaria impossível saber quantos dias realmente se passaram entre duas anotações — o time spine é esse diário completo, sem nenhuma página faltando.

❌ Sem time spine
Uma métrica cumulativa de "receita nos últimos 30 dias" pode pular dias sem pedido, distorcendo médias e fazendo o gráfico "andar mais rápido" do que devia.
✅ Com time spine
Todo dia do período aparece, com ou sem pedido — a janela de 30 dias é sempre 30 linhas de calendário, nunca 30 linhas de "dias com venda".

Checklist
✅ Boas Práticas
🗣️ Nomeie do jeito que o negócio fala
Prefira revenue a sum_order_total_usd_v2 — o nome da métrica é o contrato com quem vai usá-la, não um detalhe de implementação.
🧱 Measures simples, metrics compostas
Evite duplicar measures para cada métrica; prefira poucas measures bem definidas e componha ratio/derived em cima delas.
🕰️ Sempre declare agg_time_dimension
Todo semantic model baseado em fatos precisa de uma dimensão de tempo padrão — é ela que alimenta o metric_time universal usado nas consultas.
🔗 Modele joins com entities, não com SQL manual
Se você está escrevendo um JOIN à mão numa consulta de métrica, provavelmente falta uma entity — deixe o MetricFlow inferir o caminho.
📆 Mantenha um time spine sempre atualizado
Sem ele, métricas cumulativas e comparações período a período podem pular dias silenciosamente.
👀 Trate metrics.yml como código crítico
Uma mudança nessa definição muda o número que todo mundo vê — exija revisão de PR como em qualquer mudança de schema de produção.
🌱 Comece pequeno
2 ou 3 semantic models e 4 ou 5 métricas essenciais já resolvem o maior problema (números divergentes) — cresça aos poucos a partir daí.
🧪 Teste métricas como testa modelos
Compare o resultado de uma métrica nova com uma query manual conhecida antes de publicá-la para os consumidores.
