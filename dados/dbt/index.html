Transformação de dados como engenharia de software

dbt (data build tool) é uma ferramenta de transformação que permite times de dados escreverem lógica em SQL (com um toque de Jinja) e transformá-la em tabelas e views versionadas, testadas e documentadas — direto dentro do data warehouse. Criado em 2016 por Tristan Handy na Fishtown Analytics (hoje dbt Labs), o dbt não extrai nem carrega dado nenhum: ele assume que os dados brutos já estão no warehouse (o trabalho de ferramentas como Fivetran, Airbyte ou Stitch) e cuida exclusivamente do T de ELT — aplicando ao SQL analítico práticas que a engenharia de software já usava há décadas: controle de versão, testes automatizados, modularidade e documentação gerada a partir do próprio código.

Fundamentos
🛠️ O que é o dbt e que problema ele resolve?

Antes de ferramentas como o dbt, transformar dados brutos em tabelas prontas para análise costumava significar um emaranhado de stored procedures gigantes, scripts Python soltos ou planilhas de ETL visual — sem versionamento claro, sem testes automáticos e sem documentação confiável de onde cada número vinha. O dbt ataca esse problema tratando SQL como código de verdade: cada transformação é um arquivo .sql guardado em um repositório Git, com dependências explícitas entre si, testável e documentável como qualquer módulo de software.

📝 SQL-first
Um model dbt é, no fundo, um SELECT. Não é preciso aprender uma linguagem de pipeline nova — só SQL, mais um pouco de Jinja para reaproveitar lógica.
🧪 Testável por padrão
Regras como "essa coluna nunca é nula" ou "esse ID é único" viram testes declarativos em YAML, rodados automaticamente antes de confiar no dado.
📖 Documentado a partir do código
dbt docs generate lê o próprio projeto e produz um site navegável com o grafo de dependências entre todas as tabelas.
DimensãoAbordagem tradicional (stored procs / scripts soltos)Com dbt
VersionamentoFrequentemente manual, fora de um repositório GitTodo o projeto vive em Git, com pull requests e histórico
TestesAd hoc, muitas vezes inexistentesTestes declarados em YAML, rodados a cada execução

Origem

Criado em 2016 por Tristan Handy dentro da consultoria Fishtown Analytics — que em 2022 se renomeou para dbt Labs após o produto se tornar o foco principal da empresa. É também o dbt que popularizou o termo "analytics engineer": o profissional que aplica boas práticas de engenharia de software (versionamento, testes, CI/CD, modularidade) ao trabalho tradicionalmente feito por analistas de dados em SQL.

Onde ele entra
🔄 ETL Tradicional vs. ELT Moderno

No modelo ETL (Extract, Transform, Load), a transformação acontecia fora do banco de destino — em um servidor de ETL dedicado — antes dos dados serem carregados já prontos. No modelo ELT (Extract, Load, Transform), que se tornou dominante com a chegada de warehouses colunares baratos e elásticos (BigQuery, Snowflake, Redshift...), os dados brutos são carregados primeiro, sem transformação, e só depois transformados dentro do próprio warehouse — usando o poder de processamento que ele já tem. O dbt é a ferramenta que assumiu essa última etapa. Clique nos blocos para comparar o caminho do dado em cada modelo.

🏭 ETL Tradicional
Extract — conecta nas fontes
Transform — servidor de ETL dedicado
Load — carrega já pronto no destino
🚀 ELT Moderno (dbt entra aqui)
Extract & Load — Fivetran / Airbyte / Stitch
Dado bruto pousa no warehouse
Transform — dbt roda SQL dentro do warehouse
👆 Clique em qualquer bloco
Compare onde a transformação acontece em cada modelo, e por que isso importa para o dbt.

💡 Essa inversão de ordem (carregar bruto, transformar depois) só ficou prática quando warehouses colunares passaram a oferecer processamento elástico e barato o bastante para rodar transformações pesadas dentro deles, sem precisar de um cluster de ETL separado. O dbt não compete com Fivetran/Airbyte (o "EL") nem com orquestradores como Airflow (que podem disparar o dbt) — ele é especificamente a camada de T.

As Formas de Rodar
🏗️ dbt Core, dbt Cloud e dbt Fusion

"dbt" não é uma coisa só — é uma linguagem de projeto (arquivos .sql + .yml) que pode ser executada por diferentes motores. Entender a diferença entre eles evita confusão comum entre quem está começando.

💻 dbt Core
CLI open source (licença Apache 2.0), instalado via pip install dbt-core + o adapter do seu warehouse. Roda local, em CI ou orquestrado por Airflow/Dagster — sem custo de licença.
☁️ dbt Cloud
Plataforma SaaS gerenciada pela dbt Labs: IDE no navegador, agendador de jobs, hospedagem da documentação, CI integrado e um catálogo de metadados — sobre a mesma base do dbt Core.
⚡ dbt Fusion
Novo motor de execução (em Rust) lançado pela dbt Labs, com parsing e compilação nativos muito mais rápidos que o Core em Python, além de checagem de erros de SQL antes de rodar no warehouse.

Mão na Massa
📁 Anatomia de um Projeto dbt

Um projeto dbt é, literalmente, uma pasta versionada em Git. A raiz sempre tem um dbt_project.yml — o arquivo que declara o projeto e configura como cada pasta de models/ deve ser materializada.

meu_projeto_dbt/
dbt_project.yml ← configuração do projeto
models/
staging/
stg_orders.sql
_staging.yml ← docs + tests
marts/
fct_orders.sql
tests/ ← testes singulares
macros/ ← Jinja reutilizável
seeds/ ← CSVs versionados
snapshots/ ← histórico tipo SCD2
packages.yml ← dependências (dbt_utils...)
dbt_project.yml — o essencial
yamlcopiarname: 'meu_projeto_dbt' version: '1.0.0' profile: 'meu_projeto_dbt' # onde os models compilados/rodados vivem model-paths: ["models"] seed-paths: ["seeds"] # materialização padrão por pasta models: meu_projeto_dbt: staging: +materialized: view marts: +materialized: table

💡 Configurações com prefixo + (como +materialized) se aplicam a todos os models daquela pasta e subpastas — evitando repetir a mesma configuração em cada arquivo .sql individualmente.

A Unidade Básica
🧱 Models: um SELECT vira uma tabela

Um model dbt é simplesmente um arquivo .sql dentro de models/ contendo um único SELECT — sem CREATE TABLE, sem INSERT. O dbt é quem decide, na hora de rodar, como transformar esse SELECT em objeto real no warehouse (view, tabela...). O nome do arquivo vira o nome da tabela/view.

models/staging/stg_orders.sql
sqlcopiarSELECT id AS order_id, customer_id, order_date, status, CAST(amount AS DECIMAL(10,2)) AS amount_usd FROM {{ source('raw_shop', 'orders') }}
O que o dbt executa de fato (após compilar + materializar como view)
sql compiladocopiarCREATE OR REPLACE VIEW analytics.staging.stg_orders AS ( SELECT id AS order_id, customer_id, order_date, status, CAST(amount AS DECIMAL(10,2)) AS amount_usd FROM raw_shop.orders );
📄 Um arquivo = um model
Cada .sql em models/ vira um único objeto no warehouse — o nome do arquivo (sem extensão) é o nome da tabela/view.
🗣️ Só SELECT, nada de DDL
Você nunca escreve CREATE TABLE ou INSERT à mão — o dbt gera o DDL/DML certo com base na materialização configurada.
🌍 Ciente do ambiente
O mesmo código roda em dev (schema pessoal) ou produção — o dbt resolve o schema de destino a partir do profile ativo, sem editar o SQL.
O Coração do dbt
🕸️ ref(), source() e o Grafo de Dependências (DAG)

Em vez de escrever o nome físico de uma tabela (analytics.staging.stg_orders), um model dbt referencia outro model com a função Jinja {{ ref('stg_orders') }}, e uma tabela bruta declarada como fonte com {{ source('raw_shop', 'orders') }}. É a partir de todo ref()/source() usado no projeto que o dbt monta automaticamente um DAG (grafo acíclico dirigido): ele sabe exatamente qual model depende de qual, e roda todos na ordem certa — em paralelo sempre que possível. Clique nas camadas abaixo para ver como um pedido de venda percorre o grafo.

🗄️ Sources

raw_shop.customers
🧹 Staging
stg_orders
stg_customers
⚙️ Intermediate
int_orders_joined
🎯 Marts
fct_orders
dim_customers
👆 Clique em qualquer nó do grafo
Veja o SQL/config daquele model e quem ele referencia via ref()/source().
🔀 Ordem de execução automática
Rodar dbt run executa os models na ordem topológica do DAG — nunca antes de suas dependências terem sido materializadas.
🎯 Execução seletiva
dbt run --select fct_orders+ roda só um model e tudo que depende dele (downstream) — útil para não reprocessar o projeto inteiro.

💡 Usar ref() em vez do nome físico da tabela também é o que permite ao dbt trocar o schema de destino conforme o ambiente (dev/prod) sem tocar em uma linha de SQL — e é a base de recursos como testes de freshness em sources e execução incremental do CI (seção "Build & CI" mais à frente).

Como o SELECT Vira Objeto
🏭 Materializations

A materialization decide como o dbt transforma o SELECT de um model num objeto físico no warehouse. É configurável por model, pasta ou projeto inteiro ({{ config(materialized='table') }} no topo do arquivo, ou no dbt_project.yml). Escolha uma abaixo para ver o SQL gerado e as implicações.

Rodando Só o Necessário
⏭️ Incremental Models na Prática

Recalcular uma tabela de bilhões de linhas do zero a cada execução desperdiça tempo e crédito de computação. Um model incremental usa a macro {{ is_incremental() }} para, nas execuções seguintes à primeira, processar apenas as linhas novas ou alteradas — inserindo (ou fazendo merge) delas na tabela já existente, em vez de reconstruir tudo.

models/marts/fct_orders.sql
sqlcopiar{{ config( materialized='incremental', unique_key='order_id', incremental_strategy='merge' ) }} SELECT * FROM {{ ref('stg_orders') }} {% if is_incremental() %} -- só roda a partir da 2ª execução: WHERE updated_at > (SELECT MAX(updated_at) FROM {{ this }}) {% endif %}
🔁 Estratégias de incremental
appendSó insere as linhas novas — sem checar duplicatas.
mergeUpsert por unique_key: atualiza se existe, insere se não.
delete+insertApaga as partições/chaves afetadas e reinsere.
insert_overwriteSubstitui partições inteiras (comum em BigQuery/Spark).
Simule: quantas linhas precisam ser processadas em cada execução?
Total de linhas na tabela50.000.000
Linhas novas/alteradas desde a última execução80.000
O que Torna SQL Reutilizável
✨ Jinja & Macros

Puro SQL não tem variáveis, laços ou funções reutilizáveis — cada consulta é um texto isolado. O dbt compila cada model através do motor de templates Jinja2 antes de rodar, o que adiciona a esse SQL: variáveis, condicionais, laços e macros (funções reutilizáveis que retornam SQL).

macros/cents_to_dollars.sql — uma macro reutilizável
sql + jinjacopiar{% macro cents_to_dollars(coluna) %} ({{ coluna }} / 100)::numeric(16,2) {% endmacro %}
Usando a macro dentro de um model
sqlcopiarSELECT order_id, {{ cents_to_dollars('amount_cents') }} AS amount_usd FROM {{ ref('stg_orders') }}
🔁 {% for %} — gera SQL repetitivo
Um laço Jinja pode gerar um SUM(CASE WHEN ...) por categoria a partir de uma lista, evitando copiar/colar a mesma linha dezenas de vezes.
🔀 {% if %} — SQL condicional
Compila um trecho de SQL diferente dependendo de uma variável — como no exemplo do is_incremental() da seção anterior.
📦 Macros de pacotes
Pacotes como o dbt_utils distribuem macros prontas (ex: dbt_utils.date_spine(), dbt_utils.star()) que qualquer projeto pode instalar e usar.

💡 Tudo entre {{ }} e {% %} é resolvido em tempo de compilação, antes de qualquer SQL chegar ao warehouse — rode dbt compile para ver exatamente o SQL puro que será enviado, sem nenhum Jinja restante.

Confiança no Dado
🧪 Tests: Genéricos e Singulares

Testes no dbt não testam código — testam dados. Um teste é uma consulta que deve retornar zero linhas; se retornar alguma, o teste falha. Existem dois tipos: genéricos (reutilizáveis, declarados em YAML sobre uma coluna) e singulares (um arquivo .sql customizado em tests/ para uma regra de negócio específica). Clique em cada teste genérico embutido.

👆 Clique em um teste
Veja como declará-lo em YAML e o que ele verifica.
Teste singular — tests/order_amount_nao_negativo.sql
sqlcopiar-- falha se ESTA consulta retornar qualquer linha SELECT order_id, amount_usd FROM {{ ref('fct_orders') }} WHERE amount_usd < 0

💡 dbt build roda models e testes juntos, respeitando o DAG: se stg_orders falhar num teste, o dbt pula (em vez de rodar) tudo que depende dele — evitando propagar dado ruim rio abaixo no grafo.

Dados que Não Vêm de um Source
🌱 Seeds & 📸 Snapshots

Dois recursos para situações que ref()/source() sozinhos não cobrem: dados de referência pequenos e mantidos à mão, e o histórico de como uma linha mutável mudava ao longo do tempo.

🌱 Seeds — CSVs pequenos versionados em Git
Tabelas de referência que raramente mudam (mapeamento de código de país, lista de feriados, faixas de CEP) vivem como .csv em seeds/ e viram tabela com dbt seed — sem depender de um sistema de origem externo.
bashcopiar$ dbt seed # lê seeds/paises.csv e cria/atualiza analytics.paises
📸 Snapshots — histórico tipo SCD Tipo 2
Tabelas de origem costumam guardar só o estado atual (ex: status de um pedido). Um snapshot dbt tira "fotos" periódicas e grava colunas dbt_valid_from/dbt_valid_to, preservando o histórico completo de mudanças — o mesmo conceito de SCD Tipo 2.
sqlcopiar{% snapshot orders_snapshot %} {{ config( strategy='timestamp', unique_key='order_id', updated_at='updated_at' ) }} SELECT * FROM {{ source('raw_shop','orders') }} {% endsnapshot %}
A Ponte com o Dado Bruto
📡 Sources & Freshness

Um source declara, em YAML, onde vivem as tabelas brutas que o EL (Fivetran, Airbyte...) já carregou — dando um nome lógico a elas para uso em {{ source(...) }}, em vez de espalhar o schema físico por todo o projeto.

models/staging/_sources.yml
yamlcopiarsources: - name: raw_shop database: raw schema: shop tables: - name: orders loaded_at_field: _loaded_at freshness: warn_after: {count: 12, period: hour} error_after: {count: 24, period: hour}
⏱️ dbt source freshness
dbt source freshness checa se a linha mais recente daquela tabela chegou dentro do prazo esperado — sinalizando warn ou error quando o pipeline de carga está atrasado, antes mesmo do dbt rodar qualquer transformação sobre dado velho.
Combinado com source() em vez do nome físico da tabela, isso também permite rastrear no grafo de onde cada model puxa dado bruto — visível no gráfico de linhagem gerado pela documentação.
Convenção de Projeto
🏛️ Camadas: Staging → Intermediate → Marts

A comunidade dbt convergiu para um padrão de três camadas dentro de models/ — não é obrigatório, mas é a convenção mais usada em projetos de médio/grande porte.

🧹 Staging (stg_)
Um model por tabela de origem. Só limpeza leve: renomear colunas, converter tipos, padronizar nomes — sem juntar tabelas. Materializado como view (barato, sempre atual).
⚙️ Intermediate (int_)
Blocos de construção: joins e lógica de negócio intermediária que serão reaproveitados por mais de um mart. Não é exposto diretamente para ferramentas de BI.
🎯 Marts (fct_ / dim_)
Tabelas finais, voltadas ao negócio — fatos (fct_orders) e dimensões (dim_customers), no vocabulário de modelagem dimensional (Kimball). Materializado como table ou incremental.

💡 A regra prática mais citada: staging nunca faz join, marts nunca referenciam um source() diretamente (sempre passam por staging) — isso mantém o DAG legível e evita que a mesma lógica de limpeza seja duplicada em vários lugares do projeto.

Checklist
✅ Boas Práticas
🧹 Staging nunca faz join
Mantenha a limpeza de dado bruto isolada de qualquer lógica de negócio — um model por tabela de origem, sem JOIN.
🏷️ Nomeie por convenção
stg_, int_, fct_, dim_ deixam o propósito de cada model óbvio só pelo nome, sem abrir o arquivo.
🧪 Teste toda chave primária
No mínimo, unique + not_null na chave de cada mart — é o teste mais barato com o maior retorno de confiança.
📦 Trave versões de pacotes
Fixe a versão de dependências em packages.yml (ex: dbt_utils) — evita quebras silenciosas quando um pacote lança uma versão nova.

⚠️ dbt não extrai nem carrega dados de sistemas de origem, e não substitui um orquestrador de pipelines completo — ele assume que o dado bruto já chegou ao warehouse e que algo (Airflow, dbt Cloud, cron) vai chamá-lo. Tentar usar o dbt como ferramenta de EL ou como scheduler geral é forçar a ferramenta para fora do que ela foi desenhada para fazer.
