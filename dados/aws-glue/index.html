O ETL que tira o servidor do caminho — e ainda organiza seu catálogo

AWS Glue é um serviço de ETL (Extract, Transform, Load) totalmente gerenciado e serverless, lançado pela AWS em 2017. Por baixo, ele roda Apache Spark (ou Python puro, ou Ray) sem que você precise provisionar, configurar ou desligar um único cluster — a AWS sobe os recursos quando o job começa e derruba quando termina. Mas o Glue é mais do que só "Spark gerenciado": ele também é dono do Data Catalog, o repositório central de metadados (compatível com o Hive Metastore) que o Athena, o Redshift Spectrum, o EMR e o próprio Glue usam para saber o que existe no seu data lake e onde. Nesta aula vamos abrir cada peça: Crawlers, DynamicFrames, Jobs, DPUs, Glue Studio, Bookmarks, orquestração, Data Quality e Schema Registry.

Fundamentos
🧩 O que é o AWS Glue?

Antes do Glue, montar um pipeline de ETL em um data lake exigia provisionar e manter um cluster Hadoop/Spark (via EMR, por exemplo) ligado o tempo todo ou sob demanda, além de manter manualmente um catálogo de metadados descrevendo schemas, partições e localizações dos arquivos. O AWS Glue resolve as duas coisas ao mesmo tempo: fornece o motor de processamento sem servidor para gerenciar e centraliza o conhecimento sobre os dados num catálogo compartilhado por todo o ecossistema de analytics da AWS. É a cola (literalmente, glue) entre onde os dados estão (S3, RDS, DynamoDB, Redshift...) e as ferramentas que os consultam (Athena, Redshift Spectrum, EMR, QuickSight).

☁️ Serverless
Não existe cluster para provisionar, aplicar patch, escalar ou desligar. Você define workers e a AWS sobe/derruba a infraestrutura por trás de cada execução de job.
🗂️ Data Catalog
Repositório central e persistente de metadados — databases, tabelas, colunas, partições — compatível com a API do Hive Metastore.
🕷️ Crawlers
Processo que varre uma fonte de dados, infere schema automaticamente e popula (ou atualiza) tabelas no Data Catalog sem intervenção manual.
⚙️ Jobs
A unidade de execução do ETL em si — scripts Spark (Scala/Python), Python Shell puro, ou Ray — orquestrados por triggers e workflows.
A ideia em uma frase

O Glue separa duas responsabilidades que, num data lake sem ferramenta dedicada, ficam soltas e desatualizadas: saber o que existe (o Data Catalog, mantido por Crawlers) e processar/transformar (os Jobs, rodando Spark gerenciado). Qualquer outro serviço AWS de analytics consulta o mesmo catálogo — então uma tabela catalogada uma vez fica visível para Athena, Redshift Spectrum e EMR sem trabalho extra.

O Cérebro Compartilhado
📚 Data Catalog: databases, tabelas e partições

O Data Catalog organiza metadados numa hierarquia familiar para quem já usou o Hive Metastore: databases (agrupamentos lógicos) contêm tabelas, e cada tabela aponta para uma localização física (geralmente um prefixo no S3) e descreve colunas, tipos e partições. Nenhum dado é copiado para dentro do Catalog — ele guarda só o metadado, apontando para onde os dados de fato vivem.

🔗 Quem consulta o mesmo Catalog
  • Amazon Athena — usa o Catalog como seu metastore padrão para SELECT ... FROM database.tabela
  • Redshift Spectrum — cria external schemas apontando para databases do Catalog
  • Amazon EMR — pode configurar o Hive Metastore para usar o Glue Data Catalog em vez de um metastore local
  • SageMaker / EMR Serverless / Lake Formation — reaproveitam as mesmas definições de tabela
Por que isso importa na prática

Uma única execução de Crawler sobre um novo diretório do S3 é o suficiente para que essa tabela apareça imediatamente disponível no Athena, no Redshift Spectrum e em jobs Glue seguintes — sem redigitar schema em três lugares diferentes. É essa centralização que dá ao Data Catalog seu papel de "fonte da verdade" de metadados no ecossistema analítico da AWS.

Descoberta Automática
🕷️ Crawlers: inferindo schema sem esforço manual

Um Crawler se conecta a uma fonte de dados (tipicamente um prefixo no S3), amostra os arquivos, usa classifiers (embutidos ou customizados) para identificar o formato (CSV, JSON, Parquet, ORC, Avro...) e infere colunas, tipos e partições. O resultado é escrito automaticamente como uma tabela nova — ou atualizado numa tabela existente, se o schema mudou.

🧩 Classifiers
Reconhecem o formato dos dados por assinatura ou conteúdo. O Glue já vem com classifiers embutidos (JSON, CSV, Parquet, Avro, ORC, XML...) e permite criar classifiers customizados via regex ou Grok para formatos proprietários.
📁 Particionamento Hive
Pastas no padrão chave=valor/ (ex: ano=2024/mes=01/) são detectadas automaticamente e viram colunas de partição na tabela — a mesma técnica usada por Athena, Spark e Presto para pruning.
🔄 Atualização incremental
Um Crawler pode ser configurado para rodar em schedule e apenas processar prefixos novos/alterados, evitando reprocessar o dataset inteiro a cada execução.

⚠️ Crawlers custam por hora de execução, e datasets com milhões de arquivos pequenos podem deixá-los lentos e caros. Em pipelines maduros, uma prática comum é criar/atualizar a tabela via código (API do Glue Data Catalog ou CREATE TABLE no Athena) e reservar o Crawler só para descoberta inicial ou fontes realmente variáveis.

A Abstração do Glue
🔄 DynamicFrame vs. DataFrame

Um Spark DataFrame exige um schema fixo e único para todas as linhas — ótimo quando os dados já são limpos e homogêneos, mas frágil diante de dados semiestruturados reais (JSON de APIs, logs, fontes que evoluem com o tempo). O Glue introduz o DynamicFrame: uma abstração equivalente, mas que tolera schema flexível por linha — cada registro pode ter campos ausentes, tipos diferentes para o mesmo campo, ou campos extras — sem quebrar o job.

Experimente: registros JSON com schema inconsistente
Registros de entrada (schema varia entre eles)
😖 DataFrame (schema único e rígido)
✅ DynamicFrame (schema flexível por linha)
🧪 ResolveChoice
Transform que resolve colunas com tipos ambíguos (ex: valor ora int, ora string) — escolhendo um tipo, convertendo tudo (cast) ou separando em colunas distintas (make_cols).
📤 Relationalize
"Achata" estruturas JSON aninhadas e arrays em múltiplas tabelas relacionais (com chaves estrangeiras sintéticas) — útil para carregar dados semiestruturados num DW relacional.
🔁 toDF() / fromDF()
Conversão nos dois sentidos entre DynamicFrame e DataFrame — comum começar em DynamicFrame (schema flexível na leitura) e converter para DataFrame assim que o schema já estiver estável, para aproveitar toda a API do Spark SQL.

💡 Internamente, o DynamicFrame é implementado sobre o DataFrame do Spark — ele adiciona uma camada de metadados (o schema flexível) e transforms específicos do Glue, mas ainda roda no mesmo motor de execução distribuído do Spark por baixo. A escolha entre um e outro é sobre quando você quer lidar com a variação de schema: no início da leitura (DynamicFrame) ou depois de já ter normalizado tudo (DataFrame).

Onde o Código Roda
⚙️ Tipos de Job

Nem todo processamento precisa de um cluster Spark distribuído. O Glue oferece três tipos de job, cada um pensado para uma escala e um perfil de carga diferente.

🐘 Quando escolher Spark
Datasets que não cabem confortavelmente em uma única máquina, transformações que se beneficiam de paralelismo (joins grandes, agregações sobre bilhões de linhas), ou quando o pipeline já usa DynamicFrame/transforms do Glue.
🐍 Quando escolher Python Shell
Tarefas que não precisam de processamento distribuído: mover um arquivo, chamar uma API, validar uma condição antes de disparar o job Spark, rodar um script pandas sobre um CSV pequeno. Muito mais barato por ter apenas frações de DPU.
Capacidade & Custo
🖥️ Workers, DPUs e a Calculadora de Custo

Uma DPU (Data Processing Unit) é a unidade de capacidade de computação do Glue — cada DPU equivale a 4 vCPUs e 16 GB de RAM. Em vez de escolher instâncias EC2 manualmente, você escolhe um tipo de worker e quantos workers o job usa; a AWS provisiona e cobra por DPU-hora (faturado por segundo, com mínimo de 1 minuto).

G.1X
1 DPU (4 vCPU, 16 GB) por worker. Padrão para a maioria dos jobs de ETL.
G.2X
2 DPUs (8 vCPU, 32 GB) por worker. Para jobs com uso intensivo de memória (shuffles grandes, ML).
G.4X / G.8X
4 ou 8 DPUs por worker — cargas ainda mais intensivas em memória, disponíveis para Glue 3.0+.
G.025X
1/4 de DPU por worker. Pensado para jobs de baixo volume, minimizando custo ocioso.

📈 Auto Scaling
A partir do Glue 3.0, jobs Spark podem escalar workers dinamicamente durante a execução — a AWS monitora as fases do plano Spark e ajusta a capacidade, evitando pagar por workers ociosos em fases sequenciais do job (ex: leitura de poucos arquivos antes de um shuffle grande).
⚡ Flex Execution
Modo de execução mais barato (mas com start-up menos previsível, usando capacidade ociosa da AWS) para jobs não urgentes — ex: cargas batch noturnas que toleram alguns minutos extras de espera para começar.

Carga Incremental
🔖 Job Bookmarks: processando só o que é novo

Sem nenhum controle, rodar o mesmo job de novo reprocessaria todos os arquivos da fonte, gerando duplicatas. O Job Bookmark é o mecanismo do Glue para lembrar, entre execuções, quais arquivos (ou registros de uma tabela JDBC, via coluna de controle) já foram processados — permitindo que cada execução trate apenas o que chegou desde a última vez.

Experimente: rode o mesmo Job duas vezes com Bookmark habilitado

⚠️ O Bookmark rastreia arquivos por caminho + timestamp de última modificação (em fontes S3) — sobrescrever um arquivo já processado com o mesmo nome pode não disparar reprocessamento, e apagar o bookmark (--job-bookmark-option job-bookmark-disable ou reset manual) reprocessa a fonte inteira. Vale testar esse comportamento antes de depender dele em produção.

Quem Dispara o Quê
🔀 Triggers & Workflows

Um pipeline raramente é um único job isolado — normalmente é uma sequência: Crawler descobre → Job A limpa → Job B agrega → Crawler final cataloga o resultado. Triggers disparam jobs individuais (por schedule, sob demanda, ou quando outro job/crawler termina), e um Workflow agrupa múltiplos jobs, crawlers e triggers num grafo de orquestração visualizável como uma unidade só.

👆 Clique em uma etapa do workflow
Cada etapa pode ser um Crawler, um Job ou um Trigger — condicionado ao sucesso (ou falha) da etapa anterior.
⏰ Schedule Trigger
Dispara em um horário/cron fixo — ex: "todo dia às 02:00", equivalente a uma expressão cron do EventBridge.
✅ Conditional Trigger
Dispara quando um ou mais jobs/crawlers anteriores terminam com sucesso (ou falha) — a peça que encadeia etapas dentro de um Workflow.
🖱️ On-Demand Trigger
Disparado manualmente ou via API/CLI/SDK — útil para reprocessamentos pontuais ou integração com um orquestrador externo (Step Functions, Airflow).

💡 Para orquestrações mais complexas — com lógica condicional rica, retries customizados, ou integração com serviços fora do Glue — é comum colocar o AWS Step Functions por cima dos Workflows do Glue, chamando StartJobRun via API em vez de depender só dos Triggers nativos.

Confiança nos Dados
✅ AWS Glue Data Quality

Glue Data Quality permite declarar regras de qualidade usando a DQDL (Data Quality Definition Language) — uma sintaxe declarativa que roda dentro do próprio job, avaliando cada regra contra os dados reais e podendo bloquear a carga de linhas que falham.

Amostra ilustrativa fixa: email tem 1 valor vazio em 4 (75% completude, abaixo do limite de 95%) e status tem o valor "cancelado", fora do conjunto permitido — por isso essas duas regras falham.
📏 Completeness
Percentual de valores não-nulos numa coluna — a regra mais comum para garantir que campos obrigatórios realmente vieram preenchidos.
🔑 Unicidade & Referência
IsUnique para chaves primárias e ReferentialIntegrity para checar se chaves estrangeiras de fato existem na tabela referenciada.
🚦 Ação em caso de falha
Regras podem apenas alertar (log/CloudWatch) ou interromper o job, evitando que dados que falharam nos critérios cheguem à camada de consumo.
Contratos de Dados em Streaming
🗂️ Glue Schema Registry

Diferente do Data Catalog (metadados de tabelas em lote), o Schema Registry gerencia schemas de mensagens de streaming (Kafka, Kinesis, MSK) em formatos como Avro, JSON Schema e Protobuf — validando compatibilidade antes que produtores publiquem uma mudança que quebraria consumidores existentes.

🔒 Modos de compatibilidade
ModoPermite
BACKWARDNovo schema lê dados escritos com o schema anterior
FORWARDSchema anterior consegue ler dados escritos com o novo
FULLCompatível nos dois sentidos simultaneamente
NONESem validação — qualquer mudança é aceita (arriscado)
🎯 Por que isso importa
Sem um registry, um produtor de eventos pode renomear ou remover um campo e só descobrir o problema quando um consumidor já em produção quebra ao ler a mensagem nova. O Schema Registry rejeita a publicação de um schema incompatível antes que ela aconteça, transformando um incidente de produção num erro de validação no momento do deploy.
Alcançando Outras Fontes
🔌 Connections & Rede (VPC)

Para ler ou escrever em fontes que não são o S3 — RDS, Redshift, bancos on-premises via VPN/Direct Connect, ou qualquer JDBC — um Job Glue precisa de uma Connection: credenciais, driver e, quando a fonte está numa VPC privada, informações de sub-rede e security group para que o Glue suba ENIs (Elastic Network Interfaces) dentro dessa VPC.

🗝️ Credenciais via Secrets Manager
Boas práticas recomendam referenciar um segredo do AWS Secrets Manager na Connection, em vez de embutir usuário/senha em texto plano no job.
🌐 ENIs elásticas
Ao rodar contra uma fonte em VPC, o Glue provisiona ENIs temporárias nas sub-redes configuradas — é comum precisar liberar essas sub-redes/security groups no lado do banco de destino.
🔗 Conectores de terceiros
O AWS Marketplace oferece conectores prontos (Snowflake, MongoDB, SAP, Salesforce...) reutilizáveis como Connections do Glue, sem escrever o driver JDBC/customizado na mão.
Quanto Custa
💰 Modelo de Precificação

O Glue segue o princípio pay-per-use: você paga pela capacidade efetivamente consumida durante a execução, não por um cluster ocioso esperando o próximo job.

ComponenteCobrado porObservação
Jobs Spark / StreamingDPU-hora (faturamento por segundo)Mínimo de 1 minuto por execução
Jobs Python ShellDPU-hora (frações de DPU)Ideal para tarefas leves — muito mais barato que um job Spark mínimo
CrawlersDPU-hora durante a execução do crawlerCusto cresce com o volume/quantidade de arquivos amostrados
Data CatalogArmazenamento de metadados + requisiçõesPrimeiro 1 milhão de objetos e requisições/mês costuma estar na camada gratuita
Data QualityDPU-hora adicional durante a avaliação das regrasRoda como parte (ou extensão) do job que a invoca

✅ Como não há infraestrutura ociosa entre execuções, jobs que rodam poucas vezes ao dia (ETL batch noturno, por exemplo) tendem a custar uma fração do que um cluster EMR permanente custaria — a troca é aceitar a latência de subir/derrubar recursos a cada execução (tipicamente alguns minutos de "cold start").

Panorama
📊 AWS Glue vs. EMR vs. Athena vs. Step Functions

Esses serviços não competem entre si — na prática, um pipeline maduro na AWS costuma usar vários ao mesmo tempo, cada um no papel para o qual foi desenhado.

ServiçoCategoriaGerenciamentoMelhor para
AWS GlueETL + CatálogoTotalmente serverlessPipelines de transformação com metadados centralizados
Amazon EMRCluster Spark/HadoopVocê controla o cluster (ou EMR Serverless)Cargas Spark customizadas, controle fino de configuração, jobs de longa duração
Amazon AthenaConsulta SQL ad hocTotalmente serverlessConsultas pontuais direto no S3 via SQL, sem mover dados

Um fluxo comum combinando todos

Step Functions orquestra o pipeline inteiro → dispara um Crawler Glue para descobrir dados novos → dispara um Job Glue para limpar e agregar → grava Parquet particionado no S3 → e o resultado final vira consultável instantaneamente no Athena, porque a tabela já está no mesmo Data Catalog.

Checklist
✅ Boas Práticas
📦 Grave em Parquet particionado
Sempre que possível, grave a saída dos jobs em Parquet particionado (ex: por data) — reduz custo e tempo de consultas subsequentes no Athena/Redshift Spectrum.
🔖 Habilite Job Bookmarks desde o início
Ativar o bookmark só depois que o job já rodou algumas vezes sem ele é mais trabalhoso do que configurar corretamente desde a primeira execução.
🧵 Dimensione workers com folga, não excesso
Comece com poucos workers e observe métricas de CPU/memória no CloudWatch antes de escalar — DPUs ociosas custam da mesma forma que DPUs em uso.
🗝️ Segredos no Secrets Manager
Nunca embuta credenciais de Connections em texto plano nos argumentos do job — referencie um segredo gerenciado.
🐍 Use Python Shell para tarefas leves
Um job Spark mínimo ainda paga o custo de subir um cluster gerenciado — para checagens simples, um Python Shell com fração de DPU é ordens de magnitude mais barato.
🕷️ Não abuse de Crawlers recorrentes
Prefira atualizar o Data Catalog via API/código quando o schema é previsível, reservando Crawlers para descoberta inicial ou fontes que mudam de forma imprevisível.

⚠️ Glue não é a ferramenta certa para processamento transacional (OLTP) nem para consultas interativas de baixíssima latência — ele é uma ferramenta de ETL em lote (ou streaming). Para consultas ad hoc, combine com Athena; para servir dashboards em tempo real, considere serviços com latência sub-segundo dedicados.
