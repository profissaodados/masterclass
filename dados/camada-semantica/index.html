A camada que garante que "receita" signifique a mesma coisa em todo lugar

Uma camada semântica (semantic layer) é uma camada de abstração entre o dado bruto — tabelas em um data warehouse ou lakehouse — e as ferramentas que o consomem. Ela traduz colunas e joins em conceitos de negócio (métricas, dimensões, entidades), definidos uma única vez, como código, e reaproveitados por qualquer ferramenta de BI, notebook, planilha ou agente de IA que precise consultá-los. O objetivo não é armazenar dado novo — é garantir que "receita", "churn" ou "usuários ativos" tenham exatamente a mesma fórmula não importa quem pergunte, ou de onde a pergunta venha.

Fundamentos
🧩 O que é uma Camada Semântica?

Pense nela como um dicionário de negócio traduzido em código: em vez de cada dashboard, notebook ou planilha escrever seu próprio SUM(amount) - SUM(refund) para chegar em "receita líquida", a definição existe em um único lugar — a camada semântica — e todo o resto apenas pergunta por ela pelo nome. A camada não guarda os dados: ela guarda a lógica de como calculá-los a partir das tabelas que já existem no warehouse, e traduz essa lógica em SQL na hora da consulta.

📖 Dicionário de negócio
Mapeia termos como "receita", "cliente ativo" ou "taxa de churn" para colunas, agregações e joins concretos nas tabelas do warehouse — uma tradução entre a linguagem do negócio e o SQL físico.
🧮 Métricas como código
A lógica vive em arquivos versionados (YAML, LookML, Malloy...), revisáveis em Pull Request, testáveis em CI — não escondida dentro de um dashboard que só uma pessoa sabe editar.
🔌 Independente da ferramenta
A mesma métrica é consultada via SQL, API REST, GraphQL ou driver JDBC/ODBC — o que ganhou o apelido de "headless BI": a lógica sem uma interface própria fixa, servida a qualquer front-end.

Origem

O termo remonta às "universes" (universos semânticos) da Business Objects, criada em 1990 — uma das primeiras ferramentas a separar explicitamente "o que o usuário de negócio pergunta" de "o SQL que roda no banco". Cubos OLAP dos anos 90-2000 (Microsoft Analysis Services, Oracle Essbase) seguiram lógica parecida, porém pré-processada e rígida. A onda atual — headless BI — nasce por volta de 2020 com Cube e o LookML do Looker (2012), ganhando força com o lançamento do dbt Semantic Layer em 2022, puxada por stacks modernos onde múltiplas ferramentas (BI, Python, IA) precisam falar a mesma língua de métricas.

Por que ela existe
🔥 Metric Sprawl: quando "receita" tem 5 respostas diferentes

Todo time de dados já viveu essa reunião: o time de marketing diz que a receita de junho foi R$ 1,31 milhão, o financeiro diz R$ 1,25 milhão, e o notebook do cientista de dados calcula R$ 1,20 milhão — todos consultando "a mesma" tabela de pedidos. Ninguém está errado tecnicamente: cada um escreveu um SUM() ligeiramente diferente — um inclui reembolsos, outro não; um converte moeda na data do pedido, outro na data do pagamento; um filtra pedidos cancelados, outro esqueceu. Esse fenômeno tem nome: metric sprawl — a mesma métrica de negócio, redefinida de forma independente (e ligeiramente divergente) em cada ferramenta que a usa.

🧨 Sem Camada Semântica — cada ferramenta define à sua moeda
Quatro consumidores, quatro fórmulas de "receita" escritas de forma independente — pequenas diferenças de filtro e escopo temporal que ninguém nota até um número não bater numa reunião.
✅ Com Camada Semântica — uma definição, muitos consumidores
A mesma métrica revenue, definida uma vez na camada semântica, é a que todos os quatro consultam — não existe uma segunda fórmula para divergir.

Onde ela Vive no Stack
🏗️ Arquitetura: entre o Warehouse e quem consome

Sem camada semântica, cada ferramenta de consumo conversa diretamente com as tabelas brutas do warehouse, escrevendo sua própria lógica de agregação. Com uma camada semântica, essa lógica sai das ferramentas e passa a viver numa camada intermediária: as ferramentas param de perguntar "some a coluna amount onde status != 'cancelled'" e passam a perguntar, de forma declarativa, por "a métrica revenue, agrupada por mês". 💡 Na prática, a camada semântica atua como um compilador: recebe uma pergunta declarativa ("revenue por mês, filtrado por region = 'BR'") e a traduz para SQL otimizado, aplicando os joins corretos entre as tabelas de fatos e dimensões automaticamente. Blocos de Construção
📐 Componentes de um Modelo Semântico

Independente da ferramenta escolhida, quase toda camada semântica é construída a partir do mesmo punhado de conceitos — os nomes variam (LookML chama de "views" e "explores", MetricFlow chama de "semantic models"), mas a ideia por trás é a mesma.

📏 Medida / Measure
Uma coluna agregável de uma tabela — SUM(amount), COUNT(order_id), AVG(session_duration). É o ingrediente bruto a partir do qual métricas são construídas.
🏷️ Dimensão
Um atributo para agrupar ou filtrar — categórico (status, country) ou temporal (order_date com granularidade dia/semana/mês).
🔑 Entidade / Chave
Identifica um registro e conecta modelos entre si — order_id, customer_id — a base para o motor resolver joins automaticamente sem que cada consulta precise escrevê-los.
Exemplo: um modelo semântico completo (sintaxe estilo dbt MetricFlow)
yamlcopiarsemantic_models: - name: orders model: ref('fct_orders') entities: - name: order_id type: primary - name: customer_id type: foreign dimensions: - name: order_date type: time type_params: time_granularity: day - name: status type: categorical measures: - name: order_total agg: sum expr: amount - name: order_count agg: count expr: order_id

Métricas como Código
📝 Modelagem Declarativa

A diferença mais prática de trabalhar com camada semântica: em vez de copiar e colar um CTE de SQL em cada novo dashboard, você referencia uma métrica pelo nome. A definição vive em um arquivo versionado — revisável em Pull Request, testável, com histórico de mudanças no Git — não escondida dentro de um dashboard.

Sem camada semântica — o mesmo CTE, copiado em cada dashboard
sql (dashboard A)-- dashboard de marketing SELECT DATE_TRUNC('month', order_date) AS mes, SUM(amount) - SUM(refund_amount) AS receita FROM fct_orders WHERE status != 'cancelled' GROUP BY 1; -- o dashboard B, do financeiro, reescreve -- essa mesma lógica de um jeito ligeiramente diferente
Com camada semântica — uma definição, referenciada pelo nome
yaml (definido uma vez)copiarmetrics: - name: revenue type: simple type_params: measure: order_total_net filter: "{{ Dimension('order__status') }} != 'cancelled'" # qualquer consumidor pede só isto: # metrics=["revenue"], group_by=["metric_time__month"]

Uma Segunda Interpretação
🕸️ Medallion Semântico: Camada Semântica como Grafo de Conhecimento

Até aqui, "camada semântica" significou metrics layer: garantir que uma métrica como revenue tenha a mesma fórmula em qualquer ferramenta. Mas o termo tem uma segunda vida na indústria, vinda da tradição de semantic web: uma camada que garante que as relações entre entidades — não os números — sejam um fato explícito e navegável, em vez de lógica de JOIN que existe só enquanto a consulta roda. É essa leitura que dá nome ao Medallion Semântico: estender a arquitetura Bronze/Silver/Gold com uma quarta camada, focada em significado.

📏 Camada Semântica como Metrics Layer
O que vimos até aqui (dbt Semantic Layer, Cube, LookML). Resolve: "receita" calculada diferente em cada ferramenta. Unidade de consistência: a fórmula de uma métrica.
🕸️ Camada Semântica como Grafo de Conhecimento
O que vemos nesta seção (RDF, triplas, SPARQL). Resolve: relação entre entidades some depois que a consulta termina. Unidade de consistência: a relação entre duas entidades.

O Medallion tradicional organiza o dado por qualidade: Bronze (cru) → Silver (limpo, tipado) → Gold (pronto para análise). O Medallion Semântico acrescenta uma quarta etapa, focada em significado:

pipelineBronze → dado cru Silver → dado limpo Gold → dado pronto para análise Semantic → dado conectado por significado

💡 A camada Semantic não substitui o Gold — ela nasce a partir dele. O Gold continua sendo o dado curado e confiável; a camada semântica pega esse dado e transforma relações hoje implícitas (escondidas dentro de um JOIN) em fatos explícitos, gravados como parte do próprio dado.

O problema que motiva isso: tabelas Gold podem estar corretas, bem tipadas e com métricas batendo — e um agente de IA ainda assim tropeçar numa pergunta simples como "quem é esse profissional?", porque responder de verdade exige conectar profissional, vínculo empregatício, estabelecimento e município. Essa conexão existe hoje só dentro do SQL de um JOIN: nasce quando a consulta roda, e desaparece logo depois. Para um analista experiente que já conhece o domínio, tudo bem. Para uma máquina, cada coluna pode parecer uma ilha isolada.

A decisão central da modelagem: o vínculo precisa virar entidade (reificação)

É tentador ligar profissional direto ao estabelecimento. Mas um profissional pode ter múltiplos vínculos (CLT 40h num lugar, PJ 12h em outro) — se CBO, tipo de contrato e carga horária ficarem pendurados direto no profissional, os atributos de vínculos diferentes se misturam, e a carga horária de um contrato pode se combinar com o tipo de outro. Reificação é tratar essa relação como uma entidade própria, com identidade e atributos dela mesma.

Com o vínculo reificado, a modelagem em Turtle (a sintaxe textual mais comum para RDF) fica assim para um profissional com um único vínculo:

turtlecopiar@prefix sus: <https://saude.gov/ontologia/> . <https://saude.gov/profissional/10001> a sus:Profissional ; sus:temVinculo <https://saude.gov/vinculo/10001_2077469> . <https://saude.gov/vinculo/10001_2077469> a sus:Vinculo ; sus:comEstabelecimento <https://saude.gov/cnes/2077469> ; sus:exerceCBO "225125" ; sus:tipoVinculo "CLT" ; sus:cargaHoraria 40 .

Profissional 10001

Município 530010

Cada seta é uma tripla — sujeito → predicado → objeto. As linhas pontuadas dentro do bloco Vínculo (▸) também são triplas: o objeto ali é um literal (texto/número), não outra entidade — por isso não viram uma nova caixa no grafo.

Vocabulário: os termos por trás de um grafo de conhecimento
👆 Clique em um termo
RDF, IRI, tripla, SPARQL e reificação — os cinco conceitos que sustentam essa abordagem.

Na prática, um laboratório simples reaproveita o que a aula já cobriu: o Gold continua em Parquet, lido com DuckDB; a diferença é uma etapa de projeção que transforma as linhas em triplas RDF e as consulta com SPARQL em vez de SQL.

pythoncopiarimport duckdb from rdflib import Graph, Namespace, Literal from rdflib.namespace import RDF SUS = Namespace("https://saude.gov/ontologia/") con = duckdb.connect() vinculos = con.sql("SELECT * FROM read_parquet('gold_vinculos.parquet')").fetchall() g = Graph() for prof, cnes, cbo, tipo, carga in vinculos: vinc = SUS[f"vinculo/{prof}_{cnes}"] g.add((SUS[f"profissional/{prof}"], SUS.temVinculo, vinc)) g.add((vinc, SUS.comEstabelecimento, SUS[f"cnes/{cnes}"])) g.add((vinc, SUS.cargaHoraria, Literal(int(carga)))) g.serialize("sus.ttl", format="turtle") # consulta: carga horária total do profissional 10001 print(g.query(""" PREFIX sus: <https://saude.gov/ontologia/> SELECT (SUM(?carga) AS ?total) WHERE { <https://saude.gov/ontologia/profissional/10001> sus:temVinculo ?v . ?v sus:cargaHoraria ?carga . } """))
🏗️ Em produção: Iceberg/Delta como origem
O padrão continua o mesmo — Gold confiável → projeção semântica → grafo consultável — só que o job de projeção lê de Iceberg/Delta em vez de Parquet local, e materializa incrementalmente, não do zero a cada execução.
📉 Nem tudo vira tripla
O grafo não deve replicar o lakehouse inteiro — o dado denso e volumoso continua lá. Só as relações relevantes para navegação, explicabilidade e raciocínio de agentes valem a materialização.
🔄 Sincronização é trabalho contínuo
Se o Gold muda, o grafo precisa acompanhar — versionamento da ontologia, validação de IRIs e linhagem entre Gold e Semantic viram responsabilidades novas, não só uma migração única.

⚠️ O Medallion Semântico não é mágica: exige modelagem de domínio (decidir o que é entidade, relação ou atributo — nenhuma ferramenta faz isso sozinha), tem custo de escala (materializar grafo a partir de bilhões de linhas é caro) e risco de governança (uma ontologia malfeita produz um grafo bonito e errado — pior que uma tabela confusa, porque passa uma falsa sensação de organização).

A Fronteira Atual
🤖 Camada Semântica + Agentes de IA

Um agente de IA que gera SQL diretamente sobre centenas de tabelas brutas tende a alucinar joins, escolher a coluna errada entre várias parecidas, ou simplesmente reinventar sua própria fórmula de "receita" — exatamente o mesmo problema de metric sprawl, só que automatizado. Apontar o agente para a camada semântica em vez do schema bruto resolve boa parte disso: em vez de "escreva um SELECT sobre 200 tabelas", o agente recebe um menu curado de métricas e dimensões já nomeadas, descritas e testadas — e só precisa escolher entre elas. É o mesmo racional do Medallion Semântico visto na seção anterior, só que resolvendo relações em vez de métricas: um agente que percorre Profissional → temVínculo → Estabelecimento como fatos explícitos erra muito menos do que um que precisa adivinhar qual coluna faz o join.

🎯 Menos alucinação
Um punhado de métricas com nome e descrição de negócio é muito mais fácil de escolher corretamente do que centenas de colunas e tabelas ambíguas.
🔒 Governança preservada
O agente fica sujeito às mesmas regras (filtros, permissões, definições) que um analista humano — a resposta do bot no Slack bate com o dashboard oficial.
🗣️ Linguagem natural, consulta estruturada
O agente traduz a pergunta em linguagem natural para uma chamada estruturada à camada semântica (via API/MCP), não para SQL livre contra o warehouse.

💡 Esse é o racional por trás de servidores MCP (Model Context Protocol) para camada semântica, como o do dbt e o de Cube: eles expõem as métricas já definidas como ferramentas que um agente de IA pode chamar diretamente, em vez do agente precisar reconstruir a lógica de negócio do zero a cada pergunta. Mas atenção: o agente só é tão preciso quanto a documentação da camada semântica — métrica sem descrição clara de negócio continua sendo escolhida errado, só que agora com mais confiança.

Checklist
✅ Boas Práticas
📚 Documente cada métrica
Descrição de negócio, dono, e a fórmula em português claro — é isso que faz humanos e agentes de IA escolherem a métrica certa.
🧪 Teste métricas como código
Valide em CI que uma mudança no modelo upstream não alterou silenciosamente o resultado de uma métrica já publicada.
🔁 Uma métrica, uma definição
Resista à tentação de criar uma "revenue_v2" paralela — corrija ou versione a definição original em vez de duplicá-la.
🕒 Cuidado com granularidade temporal
Combinar métricas com time grains diferentes (diário vs. mensal) sem ajuste explícito produz números sutilmente errados.

⚠️ Camada semântica não substitui uma boa modelagem de dados. Ela consome modelos já limpos e bem estruturados (star schema, tabelas de fatos e dimensões bem definidas) — se o dado de origem está sujo ou mal modelado, a camada semântica só vai formalizar e distribuir esse problema mais rápido, não corrigi-lo.
