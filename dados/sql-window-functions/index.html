E se cada linha pudesse espiar as vizinhas, sem sumir do resultado?

Toda função de agregação que você já conhece — SUM, AVG, COUNT — tem um "defeito": ao usá-las com GROUP BY, várias linhas viram uma só. Você ganha o total, mas perde o detalhe. As Window Functions (funções de janela) resolvem exatamente isso: elas calculam algo olhando para um grupo de linhas ao redor — a "janela" — mas devolvem o resultado ao lado de cada linha original, sem apagar nenhuma. É a diferença entre perguntar "qual o total da turma?" (uma resposta só) e perguntar "qual o total da turma, escrito do lado da nota de cada aluno?" (uma resposta por aluno). Hoje vamos destrinchar a sintaxe OVER(), as quatro grandes famílias de função, e construir a intuição com muito exemplo visual.

Fundamentos
🪟 Primeiro, o básico: o que é uma "janela"?

Imagine você sentado no banco de um ônibus. Você tem o seu lugar — ninguém tira você dele — mas, olhando pela janela ao seu lado, você também enxerga quem está sentado perto: quem está na frente, quem está atrás, quantas pessoas tem no ônibus todo. Uma window function faz exatamente isso com uma linha de uma tabela: ela deixa a linha onde está, mas permite que essa linha "veja" um grupo de linhas ao redor — a janela — e calcule algo com base nelas (uma soma, uma posição, o valor do vizinho...).

🚌
Pensando como criança

Pensa numa fileira de crianças sentadas numa mesa redonda para um lanche. Cada criança continua com o próprio prato — ninguém divide o lanche com ninguém — mas cada uma consegue olhar para o prato de quem está do lado e responder perguntas tipo "quantos biscoitos tem essa mesa toda?" ou "quem comeu mais que eu?". Isso, sem que ninguém precise sair do próprio lugar. É exatamente isso que OVER() faz: mostra a "mesa" (a janela) para cada linha, sem misturar os pratos.

Veja isso literalmente: cada assento do ônibus é uma linha da tabela. A criança do assento 2 (destacada) consegue ver quem está do lado — essa é a "janela" dela:

A Sintaxe
🔬 Anatomia do OVER()

Toda window function segue o mesmo esqueleto: uma função (agregada, de ranking ou de posição) seguida da palavra-chave OVER, que abre parênteses com até três ingredientes opcionais — quem entra em cada janela (PARTITION BY), em que ordem as linhas são processadas dentro da janela (ORDER BY), e quantas linhas vizinhas entram no cálculo (o frame, com ROWS/RANGE BETWEEN). Passe o olho pelas partes abaixo — cada uma vai ganhar sua própria seção daqui a pouco.

SUM(valor) OVER ( PARTITION BY regiao ORDER BY mes ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW )
① A função
SUM(valor) — o cálculo que você quer fazer. Pode ser uma agregada (SUM, AVG, COUNT...), uma de ranking (RANK, ROW_NUMBER...) ou de posição (LAG, LEAD...).
② PARTITION BY (opcional)
Divide as linhas em grupos independentes — "recomeça a janela" a cada grupo. Sem isso, a tabela inteira é uma janela só.
③ ORDER BY (opcional)
Define a ordem em que as linhas de cada janela são processadas — essencial para totais acumulados, ranking e LAG/LEAD.
④ Frame (opcional)
Recorta quantas linhas vizinhas entram no cálculo: todas até agora, só as 2 anteriores, a janela inteira... Sem isso, cada função tem um padrão próprio.

💡 Só a função + OVER() vazio já é válido — significa "a janela é a tabela inteira" (ou a partição inteira, se houver PARTITION BY). ORDER BY e o frame são os únicos verdadeiramente opcionais dentro dos parênteses.

Ingrediente 1 de 3
🍰 PARTITION BY — fatiando sem esconder

PARTITION BY divide as linhas em grupos, exatamente como o GROUP BY faria — a diferença é que ninguém desaparece. Cada grupo (partição) calcula seu resultado de forma totalmente independente dos outros grupos, mas todas as linhas originais continuam no resultado final, uma por uma.

🏫
Analogia

É como dividir a turma em times para uma gincana: cada time soma os próprios pontos, sem misturar com o time vizinho — mas no final, a lista de chamada continua com o nome de todo mundo, um do lado do resultado do seu time.

Repare como SUM(valor) OVER (PARTITION BY regiao) soma só as vendas da própria região de cada vendedor — a "caixa" Norte nunca enxerga o que acontece na caixa Sul:

🟣 partição: regiao = 'Sul'

sqlcopiarSELECT vendedor, regiao, mes, valor, SUM(valor) OVER (PARTITION BY regiao) AS total_regiao FROM vendas ORDER BY regiao, vendedor, mes;
⚖️ vs GROUP BY
GROUP BY regiao devolveria só 2 linhas (Norte e Sul). PARTITION BY regiao devolve as 12 linhas originais, cada uma carregando o total da própria região.
🧩 Sem PARTITION BY
Se você omitir o PARTITION BY, existe apenas uma janela: a tabela inteira. SUM(valor) OVER() traria o total geral (1.790) em toda linha.
Ingrediente 2 de 3
📶 ORDER BY dentro da janela

O ORDER BY de dentro do OVER() não ordena as linhas do resultado final (quem faz isso é o ORDER BY do fim da query) — ele define a ordem de processamento dentro de cada janela. Isso muda tudo para cálculos que "olham para trás", como totais acumulados, ranking e LAG/LEAD: sem ORDER BY, não existe "antes" nem "depois".

🍦
Analogia

É como uma fila do caminhão de sorvete: só faz sentido perguntar "quantos sorvetes já foram vendidos até agora?" se todo mundo souber quem chegou primeiro. O ORDER BY dentro do OVER() é o que estabelece essa fila.

Veja a mesma pergunta — "total acumulado da Ana" — com e sem ORDER BY dentro do OVER():

❌ Sem ORDER BY — cada linha "vê" tudo de uma vez
mesvalorSUM() OVER (PARTITION BY vendedor)

Fev150380
Mar130380
Todo mês mostra o mesmo total (380) — não existe noção de "até aqui".
✅ Com ORDER BY mes — acumula aos poucos
mesvalorSUM() OVER (... ORDER BY mes)

Cada mês soma só o que já aconteceu até ele — um total acumulado de verdade.

⚠️ Pegadinha comum: ao adicionar ORDER BY dentro de OVER() para uma função agregada, o frame padrão muda de "toda a partição" para "do início até a linha atual" — é exatamente isso que transforma uma soma total num total acumulado. Voltamos nisso na seção de Frame.

Família 1 de 4
➕ Funções agregadas como window function

As mesmas funções que você usa com GROUP BY — SUM, AVG, COUNT, MIN, MAX — funcionam como window function bastando trocar o GROUP BY por um OVER(...). O resultado de cada uma aparece ao lado de cada linha, não substituindo o grupo inteiro por uma única linha.

vendedormesvalorSUM (total região)AVG (média região)MAX (melhor mês região)COUNT (qtd vendas região)
AnaJan100670111,72006
AnaFev150670111,72006
BrunoFev200670111,72006
sqlcopiarSELECT vendedor, mes, valor, SUM(valor) OVER (PARTITION BY regiao) AS total_regiao, AVG(valor) OVER (PARTITION BY regiao) AS media_regiao, MAX(valor) OVER (PARTITION BY regiao) AS melhor_mes_regiao, COUNT(*) OVER (PARTITION BY regiao) AS qtd_vendas_regiao FROM vendas;
O caso mais pedido: "% do total"

Uma pergunta clássica de dashboard — "que fatia do total da região essa venda representa?" — vira uma conta trivial dividindo o valor da linha pelo SUM() OVER() da mesma linha, sem nenhum JOIN ou subquery:

sqlcopiarSELECT vendedor, mes, valor, ROUND(100.0 * valor / SUM(valor) OVER (PARTITION BY regiao), 1) AS pct_da_regiao FROM vendas; -- Carla, Mar, 300 → 300 / 1120 = 26.8% de tudo que a região Sul vendeu
Família 2 de 4
🥇 Funções de Ranking

Quatro funções respondem "qual a posição desta linha dentro da janela?" — mas cada uma trata empates de um jeito diferente. É a pergunta mais comum de todas ("top 3 de cada região", "melhor vendedor do mês"), então vale a pena entender bem a diferença.

🏁
Analogia — uma corrida com empate

Imagine uma corrida onde dois corredores empatam em 2º lugar. ROW_NUMBER é o fiscal apressado que dá um número único pra cada um (2º e 3º), nem que seja por sorteio. RANK é o fiscal justo: dá 2º lugar pros dois, mas o próximo corredor vira 4º (o "3º lugar" fica pulado, reservado pro empate). DENSE_RANK também dá 2º pros dois, só que o próximo já é o 3º — sem pular números. NTILE(n) nem olha para empates: só quer dividir todo mundo em n grupos de tamanho parecido, tipo separar a turma em "quartis" de nota.

A tabela toda, ranqueada por valor (do maior pro menor) dentro de cada região — repare no empate de 150 na região Norte:

regiaovendedormesvalorROW_NUMBER()RANK()DENSE_RANK()NTILE(2)
NorteBrunoFev2001111
NorteAnaFev1502221
NorteBrunoMar1503221
NorteAnaMar1304432
NorteAnaJan1005542
NorteBrunoJan906652
🔢 ROW_NUMBER()
Sempre única, 1, 2, 3, 4... mesmo com empate de valor — quem vem primeiro depende da ordem de desempate (ou é arbitrário se não houver).
🥈 RANK()
Empatados recebem a mesma posição, e a próxima posição pula (150 e 150 empatam em 2º, o próximo vai direto pra 4º).
🎖️ DENSE_RANK()
Empatados recebem a mesma posição, mas a próxima posição não pula (150 e 150 empatam em 2º, o próximo é 3º).
sqlcopiarSELECT regiao, vendedor, mes, valor, ROW_NUMBER() OVER (PARTITION BY regiao ORDER BY valor DESC) AS posicao_unica, RANK() OVER (PARTITION BY regiao ORDER BY valor DESC) AS posicao_com_furo, DENSE_RANK() OVER (PARTITION BY regiao ORDER BY valor DESC) AS posicao_sem_furo, NTILE(2) OVER (PARTITION BY regiao ORDER BY valor DESC) AS metade FROM vendas ORDER BY regiao, posicao_unica;

✅ O uso mais comum de ROW_NUMBER() na vida real: pegar o "top N por grupo". Envolva a query acima numa WITH e filtre WHERE posicao_unica <= 2 para ter os 2 melhores meses de cada região — sem subquery de agregação, sem JOIN.

Família 3 de 4
⏮️ LAG e LEAD — olhando os vizinhos

LAG(coluna, n) traz o valor de n linhas atrás (dentro da mesma partição e ordem); LEAD(coluna, n) traz o valor de n linhas à frente. Sem n, o padrão é 1 — "o vizinho imediato". É a base de qualquer cálculo de "variação em relação ao período anterior".

🚶
Analogia

Numa fila do banco, LAG é virar a cabeça pra trás e perguntar "quem tá logo atrás de mim?" (na verdade, é o contrário — pergunta quem está na sua frente na ordem de chegada). LEAD é olhar pra frente e perguntar "quem vem depois de mim?". Os dois só fazem sentido porque a fila tem uma ordem — de novo, o ORDER BY dentro do OVER().

Vendas da Carla (Sul), mês a mês — cada linha "espia" o mês anterior (LAG) e o mês seguinte (LEAD):

mesvalorLAG(valor,1)LEAD(valor,1)variação vs mês anterior
Jan120— (não existe)→ 100—
Fev100← 120→ 300-16,7%
Mar300← 100— (não existe)+200%
sqlcopiarSELECT vendedor, mes, valor, LAG(valor, 1) OVER (PARTITION BY vendedor ORDER BY mes) AS valor_mes_anterior, LEAD(valor, 1) OVER (PARTITION BY vendedor ORDER BY mes) AS valor_mes_seguinte, ROUND(100.0 * (valor - LAG(valor,1) OVER (PARTITION BY vendedor ORDER BY mes)) / LAG(valor,1) OVER (PARTITION BY vendedor ORDER BY mes), 1) AS pct_variacao FROM vendas;

⚠️ Quando não existe linha anterior (Janeiro é o primeiro mês) ou seguinte (Março é o último), LAG/LEAD devolvem NULL por padrão — mas aceitam um terceiro argumento com um valor default, tipo LAG(valor, 1, 0), se você preferir zero a nulo.

Família 4 de 4
📌 FIRST_VALUE, LAST_VALUE e NTH_VALUE

Em vez de "n linhas atrás/à frente" como o LAG/LEAD, essas três funções olham para posições fixas dentro da janela: a primeira linha, a última linha, ou a linha na posição n — sempre respeitando o ORDER BY e o frame configurados.

🏆
Analogia

Numa corrida com pódio, FIRST_VALUE é sempre apontar para quem chegou em 1º lugar, LAST_VALUE aponta pra quem chegou por último, e NTH_VALUE(coluna, 2) aponta especificamente pra quem ficou em 2º lugar — não importa em qual linha da tabela você está, a resposta é sempre a mesma pessoa fixa daquele grupo.

Toda linha da região Sul passa a carregar quem fez o melhor e o pior mês, sem sair da própria linha:

vendedormesvalorFIRST_VALUE (melhor mês da região)LAST_VALUE (pior mês da região)
CarlaJan120300 (Carla/Mar)100 (Carla/Fev)
CarlaMar300300 (Carla/Mar)100 (Carla/Fev)
DiegoJan200300 (Carla/Mar)100 (Carla/Fev)
sqlcopiarSELECT vendedor, mes, valor, FIRST_VALUE(valor) OVER (PARTITION BY regiao ORDER BY valor DESC ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS melhor_mes_regiao, LAST_VALUE(valor) OVER (PARTITION BY regiao ORDER BY valor DESC ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS pior_mes_regiao FROM vendas;

⚠️ Pegadinha clássica: LAST_VALUE sem o frame explícito (ROWS BETWEEN ... AND UNBOUNDED FOLLOWING) usa o frame padrão do ORDER BY, que vai só "até a linha atual" — isso faz LAST_VALUE devolver, erradamente, o próprio valor da linha em vez do último da janela inteira. É o motivo nº1 de gente reportar "bug" no LAST_VALUE que na verdade é o frame errado.

O Detalhe que Muda Tudo
🖼️ Frame: ROWS vs RANGE — quantas linhas entram na janela?

O frame é a moldura que recorta exatamente quais linhas, dentro da partição já ordenada, participam do cálculo daquela linha. As opções mais comuns: UNBOUNDED PRECEDING (desde o início), CURRENT ROW (a linha atual), N PRECEDING/N FOLLOWING (n linhas antes/depois) e UNBOUNDED FOLLOWING (até o fim).

🔦
Analogia

Pense numa lanterna que anda junto com você numa fila de brinquedos numerados no chão. "Do começo da fila até onde estou" ilumina tudo que já passou (bom pra total acumulado). "Só eu e o brinquedo logo antes" ilumina uma janelinha pequena que anda junto com você (bom pra média móvel). O tamanho do facho de luz é o frame.

A mesma coluna SUM(valor) OVER (ORDER BY mes ...), mudando só o frame — repare como o resultado muda completamente com os mesmos dados:

Frame: UNBOUNDED PRECEDING AND CURRENT ROW (acumulado)
mesvalorresultado

Fev150250
Mar130380
Frame: 1 PRECEDING AND 1 FOLLOWING (janela de 3, centrada)
mesvalorresultado

sqlcopiar-- acumulado: soma tudo desde o início da partição até a linha atual SUM(valor) OVER (PARTITION BY vendedor ORDER BY mes ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) -- janela móvel: soma só a linha anterior + atual + próxima SUM(valor) OVER (PARTITION BY vendedor ORDER BY mes ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING)

💡 ROWS conta linhas físicas (sempre exatamente N vizinhas). RANGE conta valores lógicos do ORDER BY — então, com datas, RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW pega "os últimos 7 dias de calendário", mesmo que isso signifique 3 linhas numa semana e 9 em outra (dias sem venda não somam linha).

A Comparação que Fecha o Conceito
⚖️ Window Function vs GROUP BY

Os dois agrupam linhas e aplicam uma função agregada — a diferença inteira está em o que acontece com as linhas depois. É a pergunta que resume tudo o que vimos até aqui.

❌ GROUP BY regiao — colapsa em 2 linhas
regiaoSUM(valor)
Norte670
Sul1120
Perdemos o detalhe de vendedor e mês — só sobrou o total por região.
✅ SUM(valor) OVER (PARTITION BY regiao) — mantém 12 linhas
regiaovendedormesvalortotal_regiao
NorteAnaJan100670
NorteBrunoFev200670
...............
Cada venda individual continua visível, e também sabe o total da própria região.
📉 GROUP BY
Uma linha por grupo. Ótimo quando você só quer o resumo (dashboard executivo, relatório final).
📊 Window Function
Uma linha por registro original, com contexto extra. Ótimo quando você precisa do detalhe e do resumo juntos (ex: "quanto essa venda representa do total?").
🤝 Podem coexistir
É possível usar window function sobre o resultado de um GROUP BY — cada motor processa GROUP BY/HAVING antes de OVER() na ordem lógica de execução.

✅ Regra prática: se a pergunta é "quanto é X, no total?" → GROUP BY. Se a pergunta é "quanto é X, e como cada linha se compara a esse X?" → window function.

Aplicação Prática
💡 4 problemas do dia a dia, resolvidos com window function
1Top-N por grupo — "as 2 melhores vendas de cada região"
sqlcopiarWITH ranqueado AS ( SELECT *, ROW_NUMBER() OVER (PARTITION BY regiao ORDER BY valor DESC) AS rn FROM vendas ) SELECT regiao, vendedor, mes, valor FROM ranqueado WHERE rn <= 2;
2Deduplicação — "manter só o registro mais recente por vendedor"
O mesmo truque do Top-N, só que com rn = 1 — clássico para limpar duplicatas de uma tabela cadastral bagunçada.
sqlcopiarWITH deduplicado AS ( SELECT *, ROW_NUMBER() OVER (PARTITION BY vendedor ORDER BY mes DESC) AS rn FROM vendas ) SELECT vendedor, regiao, mes, valor FROM deduplicado WHERE rn = 1;
3% do total sem subquery — "peso de cada venda no total da equipe"
sqlcopiarSELECT vendedor, mes, valor, ROUND(100.0 * valor / SUM(valor) OVER (), 1) AS pct_do_total_geral FROM vendas ORDER BY pct_do_total_geral DESC;
4Crescimento mês a mês — "quanto cada vendedor cresceu (ou caiu) em relação ao mês anterior"
sqlcopiarSELECT vendedor, mes, valor, valor - LAG(valor) OVER (PARTITION BY vendedor ORDER BY mes) AS variacao_absoluta, ROUND(100.0 * (valor - LAG(valor) OVER (PARTITION BY vendedor ORDER BY mes)) / LAG(valor) OVER (PARTITION BY vendedor ORDER BY mes), 1) AS variacao_pct FROM vendas ORDER BY vendedor, mes;

💻 Construindo tudo do zero no DuckDB

Abaixo, a tabela vendas usada a aula inteira é criada do zero e cada família de window function é aplicada sobre ela, em scripts numerados que podem ser colados e rodados em sequência no DuckDB.

1Criar e popular a tabela vendas
sql · duckdbcopiarCREATE TABLE vendas ( vendedor VARCHAR, regiao VARCHAR, mes VARCHAR, valor DECIMAL(10,2) ); INSERT INTO vendas VALUES ('Ana', 'Norte', 'Jan', 100), ('Ana', 'Norte', 'Fev', 150), ('Ana', 'Norte', 'Mar', 130), ('Bruno', 'Norte', 'Jan', 90), ('Bruno', 'Norte', 'Fev', 200), ('Bruno', 'Norte', 'Mar', 150), ('Carla', 'Sul', 'Jan', 120), ('Carla', 'Sul', 'Fev', 100), ('Carla', 'Sul', 'Mar', 300), ('Diego', 'Sul', 'Jan', 200), ('Diego', 'Sul', 'Fev', 190), ('Diego', 'Sul', 'Mar', 210);
2Total e % por região (agregada como window function)
sql · duckdbcopiarSELECT vendedor, regiao, mes, valor, SUM(valor) OVER (PARTITION BY regiao) AS total_regiao, ROUND(100.0 * valor / SUM(valor) OVER (PARTITION BY regiao), 1) AS pct_regiao FROM vendas ORDER BY regiao, vendedor, mes;
3Total acumulado por vendedor, mês a mês
sql · duckdbcopiarSELECT vendedor, mes, valor, SUM(valor) OVER (PARTITION BY vendedor ORDER BY mes ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS acumulado FROM vendas ORDER BY vendedor, mes; -- nota: no DuckDB, "Jan" < "Fev" < "Mar" alfabeticamente não bate com a ordem real — -- na vida real, use uma coluna de data ou um número de mês (1,2,3) para o ORDER BY
4Ranking dentro da região (ROW_NUMBER, RANK, DENSE_RANK)
sql · duckdbcopiarSELECT regiao, vendedor, mes, valor, ROW_NUMBER() OVER (PARTITION BY regiao ORDER BY valor DESC) AS rn, RANK() OVER (PARTITION BY regiao ORDER BY valor DESC) AS rk, DENSE_RANK() OVER (PARTITION BY regiao ORDER BY valor DESC) AS drk FROM vendas ORDER BY regiao, rn;
5LAG/LEAD — variação percentual mês a mês por vendedor
sql · duckdbcopiarSELECT vendedor, mes, valor, LAG(valor) OVER (PARTITION BY vendedor ORDER BY mes) AS mes_anterior, ROUND(100.0 * (valor - LAG(valor) OVER (PARTITION BY vendedor ORDER BY mes)) / LAG(valor) OVER (PARTITION BY vendedor ORDER BY mes), 1) AS pct_variacao FROM vendas ORDER BY vendedor, mes;
6Top-2 por região com CTE + ROW_NUMBER
sql · duckdbcopiarWITH ranqueado AS ( SELECT *, ROW_NUMBER() OVER (PARTITION BY regiao ORDER BY valor DESC) AS rn FROM vendas ) SELECT regiao, vendedor, mes, valor FROM ranqueado WHERE rn <= 2 ORDER BY regiao, rn; -- Norte: Bruno/Fev (200), Ana/Fev (150) ou Bruno/Mar (150) — empate real, resultado pode variar -- Sul: Carla/Mar (300), Diego/Mar (210)

✅ Repare que nenhum desses scripts precisou de JOIN, subquery correlacionada ou GROUP BY — window function costuma ser a forma mais curta e mais rápida de resolver esse tipo de pergunta.

Checklist
✅ Boas Práticas
🎯 Sempre que possível, use PARTITION BY
Sem ele, a janela é a tabela inteira — fácil de esquecer e obter um total geral quando você queria um total "por grupo".
📶 Desconfie de funções que "olham para trás" sem ORDER BY
LAG, LEAD, ranking e totais acumulados exigem uma ordem bem definida — sem ORDER BY (ou com um ORDER BY ambíguo, com empates), o resultado pode variar entre execuções.
🖼️ Declare o frame explicitamente em FIRST_VALUE/LAST_VALUE
O frame padrão ("do início até a linha atual") quase nunca é o que você quer para essas duas funções — declare ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING manualmente.
🚫 Window function não pode ir direto no WHERE
Como OVER() é calculado depois do WHERE na ordem lógica da query, filtrar por ela exige uma CTE/subquery (ou QUALIFY, em bancos que suportam).
⚡ Uma boa janela pode substituir vários JOINs
Perguntas como "top-N por grupo" ou "% do total" que antes exigiam subquery correlacionada ou auto-join geralmente ficam mais simples e mais rápidas com window function.
🔢 ROW_NUMBER ≠ RANK — escolha com intenção
Use ROW_NUMBER quando precisa de unicidade garantida (paginação, dedup); use RANK/DENSE_RANK quando empates devem aparecer como empates de verdade (colocação de prova, pódio).
