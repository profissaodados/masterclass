Cada projeto Python merece sua própria caixinha de brinquedos

Um venv (ambiente virtual) é uma pastinha isolada, criada pelo próprio Python, que guarda uma cópia própria do interpretador e uma prateleira própria de pacotes instalados — separada de tudo o que existe no resto do computador. Assim, o projeto A pode usar Django 3 e o projeto B pode usar Django 5 ao mesmo tempo, na mesma máquina, sem um brigar com o outro. Nesta aula vamos abrir essa pastinha por dentro, criar, ativar, instalar pacotes e ver — de um jeito bem visual — por que isso é praticamente obrigatório em qualquer projeto Python sério.

Fundamentos
🎒 O que é um ambiente virtual?

Quando você instala o Python no seu computador, ele vem com um único lugar global onde todos os pacotes (bibliotecas) ficam guardados. Se você não fizer nada especial, todo comando pip install que você digitar vai cair exatamente nesse mesmo lugar — não importa em qual projeto você está trabalhando. Um venv resolve isso: é um Python "de mentirinha", criado dentro da pasta do seu projeto, com sua própria lista de pacotes instalados, totalmente separada da instalação global.

🧒🧸
Explicando para uma criança
Imagina que Python é uma casa com uma caixa de brinquedos na sala, que todo mundo da família usa. Se o irmão mais velho troca uma peça de LEGO por outra versão diferente, a irmã mais nova que estava montando outra coisa com aquela mesma peça… fica sem a peça certa! Um venv é dar pra cada criança (cada projeto) a sua própria caixinha de brinquedos, só dela, com suas próprias peças. Ninguém mexe na caixinha do outro, e ninguém briga.
O problema
💥 O caos de não usar venv

Imagine dois projetos no mesmo computador: o Projeto A (um sistema antigo) precisa de Django==3.2, e o Projeto B (um sistema novo) precisa de Django==5.0. Sem ambientes virtuais, os dois tentam guardar o pacote no mesmo lugar — e só cabe uma versão por vez. Instalar um projeto desinstala o outro sem avisar. Veja a diferença ao vivo:

Experimente: instale os dois projetos com e sem venv
Isso tem nome

Esse problema é tão comum que tem apelido: "dependency hell" (o inferno das dependências). Ele acontece porque, sem isolamento, existe uma única pasta site-packages compartilhada por tudo que você roda no computador.

Conceito central
📦 Isolamento: a ideia por trás de tudo

Um venv não duplica o computador inteiro — ele isola só o que importa para o Python. Entender exatamente o que fica separado e o que continua compartilhado é a chave para nunca mais se confundir.

🔒 Fica isolado (só desse projeto)
  • Os pacotes instalados com pip install
  • A versão de cada pacote instalado
  • Os comandos/scripts que vêm com pacotes (ex: flask, black, pytest)
  • A versão do pip usada para instalar
🌍 Continua compartilhado (com o SO)
  • O interpretador Python em si (o venv referencia a instalação base)
  • Bibliotecas do sistema operacional (ex: drivers, libc)
  • Variáveis de ambiente que não são de Python
  • Arquivos do seu código-fonte (o venv não guarda seu .py)
🎒✏️
Explicando para uma criança
A caixinha de brinquedos é sua, mas a casa onde ela fica ainda é a mesma casa da família. O venv não copia a casa inteira — ele só te dá uma caixinha nova, com as peças (pacotes) que você escolheu colocar nela.
Passo 1
🏗️ Criando um venv

Criar um venv é um único comando, embutido no próprio Python (módulo venv da biblioteca padrão desde o Python 3.3 — não precisa instalar nada extra). Você escolhe um nome de pasta, e o Python monta a caixinha inteira para você.

bash python -m venv venv # cria a pasta "venv/" com o ambiente # em alguns sistemas Linux, o comando é "python3" python3 -m venv venv
Experimente: rode a criação e veja a pastinha nascer

Que nome de pasta usar?

Qualquer nome funciona — o comando só precisa de um caminho. Na prática, a comunidade usa muito venv, .venv (oculto, começa com ponto) ou env. O importante é escolher um e sempre ignorá-lo no Git (mais sobre isso na seção de boas práticas).

Dúvida comum
🐍 Uma versão de Python por venv

O venv não instala nem gerencia versões do Python — ele só empresta uma cópia leve do interpretador que já existia no computador no momento em que você rodou o comando. Se você criou com python3.11 -m venv venv, esse venv fica "casado" com o Python 3.11 para sempre. Ter várias versões instaladas no sistema é trabalho de outra ferramenta — o venv só entra depois, para isolar os pacotes de cada uma delas.

🧃🏭
Explicando para uma criança
O venv é a caixinha de brinquedos, não a fábrica de brinquedos. Ele não cria um Python do zero — ele só pega emprestado, na hora em que nasce, uma cópia do Python que já estava na prateleira da casa. Se você quer um Python "novinho" diferente, primeiro precisa trazer essa versão pra casa (com outra ferramenta) — o venv só sabe empacotar o que já existe.
Experimente: escolha uma versão "instalada" na máquina e veja o venv nascer preso a ela
meu_projeto — zsh
🔒 Essa versão fica fixada para sempre neste venv. Para usar outra, você não "atualiza" — cria um venv novo, a partir de outro interpretador.
🧰 Quem instala versões diferentes de Python
  • pyenv — o mais usado, instala e alterna entre várias versões
  • Homebrew: brew install python@3.11 (macOS)
  • Instalador oficial em python.org, um por versão
  • No Windows, o py launcher lista as versões instaladas
🎒 Quem isola pacotes dentro de uma versão já instalada
  • venv — pega o interpretador indicado e cria a caixinha
  • Não baixa, não compila e não atualiza a versão do Python
  • Um projeto pode ter vários venvs, um por versão que precisar testar
  • Trocar de versão = criar outro venv, nunca "converter" o existente

Na prática, as duas ferramentas trabalham juntas

O fluxo comum é: 1) use pyenv (ou similar) para ter a versão de Python que o projeto precisa instalada na máquina; 2) use python3.x -m venv venv apontando pra essa versão para isolar os pacotes. Sim — dá pra ter Python 3.9, 3.11 e 3.13 convivendo na mesma máquina, cada um com seus próprios venvs, sem nenhum conflito.

Passo 2
🔑 Ativando e desativando

Criar o venv não é suficiente — ele só "vale" enquanto está ativado. Ativar muda, temporariamente, para onde o terminal aponta quando você digita python ou pip: em vez de usar a instalação global, ele passa a usar a cópia de dentro da sua caixinha.

🍎🐧 macOS / Linux
source venv/bin/activate
🪟 Windows (PowerShell)
venv\Scripts\Activate.ps1

Estrutura interna
🔬 Anatomia da pasta venv

Abra a pasta venv/ e você vai encontrar sempre a mesma receitinha, em toda instalação Python do mundo. Clique em cada parte para entender o que ela faz:

📄 pyvenv.cfg
📁 bin/ (Scripts\ no Windows)
🐍 python / python3
🔑 activate
📦 pip
📁 lib/python3.x/site-packages/
📁 include/
📄 pyvenv.cfg
Um arquivo de texto simples que diz de onde esse venv "nasceu": o caminho do Python base usado para criá-lo, a versão do Python e se os pacotes do sistema estão visíveis (include-system-site-packages). É a certidão de nascimento do ambiente.
🗂️
Explicando para uma criança
A pasta bin/ (ou Scripts/) é a portinha de entrada da caixinha — é por ali que você "entra" nela ao ativar. A pasta site-packages é a prateleira onde ficam todos os brinquedos (pacotes) que você já colocou lá dentro.

Reprodutibilidade
📝 requirements.txt: a lista de compras do projeto

Um venv fica só na sua máquina — não vai para o Git. Para outra pessoa (ou o servidor de produção) recriar exatamente os mesmos pacotes, usamos um arquivo de texto simples chamado requirements.txt: uma lista com o nome e a versão de cada pacote.

1️⃣ Gerar a lista (no seu computador)
pip freeze > requirements.txt
Isso lê tudo que está instalado no venv ativo e escreve num arquivo, um pacote por linha.
2️⃣ Instalar a lista (em outra máquina)
pip install -r requirements.txt
Cria um venv novo e vazio, ativa, roda esse comando — e ele instala tudo de uma vez, nas versões certas.

Na prática
🎨 Múltiplos projetos, múltiplos venvs

Aqui está o payoff de tudo isso: quatro projetos bem diferentes, com dependências que nem se falam, convivendo tranquilos no mesmo computador — cada um com sua própria caixinha.

Ferramentas do ecossistema
⚖️ venv vs. virtualenv vs. conda vs. poetry

venv não é a única ferramenta de isolamento — só é a que já vem de fábrica com o Python. Conhecer as alternativas ajuda a escolher a certa para cada situação.

Explicando para uma criança
Todo mundo aqui faz a mesma coisa básica: dar uma caixinha só sua. O venv é a caixinha que já vem de brinde dentro do Python. As outras são caixinhas "de luxo", com recursos extras, vendidas separadamente.

Checklist final
✅ Boas práticas
Faça sempre

✅ Crie um venv por projeto, nunca compartilhe entre projetos diferentes
✅ Adicione a pasta do venv ao .gitignore logo de cara
✅ Gere e mantenha um requirements.txt (ou pyproject.toml) atualizado
✅ Use um nome padrão no time inteiro (ex: .venv) para todo mundo saber onde olhar
✅ Atualize o pip logo após criar: pip install --upgrade pip

Nunca faça

❌ Commitar a pasta venv/ no Git (ela pode ter centenas de MB)
❌ Copiar/colar uma pasta de venv para "reaproveitar" em outro projeto ou máquina
❌ Instalar pacotes de projeto com o venv desativado (vai parar no global sem você perceber)
❌ Misturar pip e conda no mesmo ambiente sem saber o que está fazendo
❌ Deixar o time inteiro sem saber qual versão de Python o projeto espera
