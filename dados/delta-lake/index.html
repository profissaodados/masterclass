A pasta de Parquet que ganhou memória e regras

Delta Lake é uma camada de formato de tabela (table format), open-source, criada em 2019 pela Databricks, que fica por cima de arquivos Parquet comuns. Sozinho, um monte de arquivos Parquet numa pasta não sabe se uma escrita terminou, não impede duas pessoas de se atrapalharem escrevendo ao mesmo tempo, e não lembra como os dados eram ontem. O Delta Lake resolve tudo isso com uma ideia simples e poderosa: um diário de bordo que registra, em ordem, cada mudança feita na tabela. Nesta aula vamos abrir esse diário por dentro — com muitos desenhos, comparações e demos que você pode clicar.

Motivação
😵 O problema: um data lake sem Delta

Um "data lake" cru é, na prática, uma pasta cheia de arquivos Parquet num sistema de arquivos (HDFS, S3, ADLS...). Isso funciona bem para leitura simples, mas quebra assim que você precisa de algo que qualquer banco de dados trivial já resolve há décadas.

🧒 Explicando para uma criança

Imagine uma caixa de brinquedos compartilhada na escola. Não tem caderno de regras, não tem nome escrito em nada, e várias crianças mexem nela ao mesmo tempo. Se alguém for guardar 5 brinquedos e for chamado no meio do caminho, a caixa fica pela metade — e a próxima criança que olhar não sabe se aquilo é "normal" ou se a arrumação foi interrompida. O Delta Lake é como colocar um caderno de registro do lado da caixa: toda vez que alguém mexe nela, escreve exatamente o que fez, numerado em ordem — e só depois de escrever no caderno a mudança "conta" de verdade.

🧨 Sem atomicidade
Um job que escreve 1000 arquivos pode falhar no arquivo 600. Um leitor concorrente pode enxergar uma tabela parcialmente escrita — dados incompletos, sem aviso nenhum.
👻 Sem isolamento
Enquanto um job reescreve arquivos, outra query pode ler uma mistura de arquivos antigos e novos ao mesmo tempo — um estado que nunca existiu de verdade.
🚫 Sem UPDATE/DELETE fácil
Arquivos Parquet são imutáveis. Mudar uma linha significaria reescrever o arquivo inteiro manualmente, coordenando com todo mundo que possa estar lendo.
📐 Sem controle de schema
Nada impede alguém de jogar um arquivo com colunas diferentes na mesma pasta. O erro só aparece muito depois, na query que quebra.
A sacada do Delta Lake

Adicionar, ao lado dos arquivos Parquet, uma pasta especial chamada _delta_log/ que guarda um log de transações ordenado. Nenhum leitor ou escritor confia "no que está na pasta" — todo mundo confia no que o log diz que está válido. É essa indireção que traz ACID, time travel e todo o resto. Vamos ver como, passo a passo.

Fundamento
💡 A grande sacada: Parquet + Log de Transações

Delta Lake não substitui o Parquet — ele o abraça. Os dados continuam sendo arquivos .parquet normais, lidos por qualquer engine (Spark, DuckDB, Trino...). A novidade é a pasta _delta_log/: uma sequência de arquivos JSON numerados, cada um representando uma transação (um commit) — o único lugar onde a "verdade" sobre o que existe na tabela é definida.

Cada .json é um commit imutável e numerado sequencialmente. Ele lista quais arquivos foram adicionados (add) e quais deixaram de valer (remove) naquela transação. É só isso — e é o suficiente para reconstruir qualquer versão da tabela.

🧒 Explicando para uma criança

Pense no _delta_log como o diário de bordo de um navio. O capitão nunca apaga uma página antiga — se algo mudou, ele escreve uma página nova contando o que mudou, com data e número. Para saber como o navio está hoje, você lê o diário do começo ao fim (ou pega um resumo recente). Para saber como ele estava há 3 semanas, você simplesmente para de ler no ponto certo do diário. Os "arquivos Parquet" são a carga do navio — o diário é o que diz oficialmente o que está a bordo.

👆 Clique em qualquer arquivo
Cada arquivo de dado só "existe" oficialmente se algum commit do log o referencia com uma ação add. É assim que um leitor sabe, sem adivinhar nada, exatamente quais arquivos formam a versão atual da tabela.

💡 Repare que os arquivos de dados não têm nome sequencial nem legível — só o log sabe o que cada um significa. Isso é proposital: o log é a única fonte da verdade. Um arquivo Parquet "solto" na pasta que nenhum commit referencia (por exemplo, sobrado de uma escrita que falhou) é simplesmente invisível para qualquer leitor Delta, mesmo estando fisicamente ali no disco.

O Cérebro da Tabela
📜 Dentro de um commit do log

Cada arquivo .json do _delta_log é uma lista de ações, uma por linha (formato NDJSON). Veja um commit de exemplo que cria a tabela e insere as duas primeiras linhas de vendas:

00000000000000000000.jsoncopiar{"commitInfo":{"timestamp":1717000000,"operation":"CREATE TABLE","isBlindAppend":true}} {"protocol":{"minReaderVersion":1,"minWriterVersion":2}} {"metaData":{"id":"9f1c...","format":{"provider":"parquet"},"schemaString":"{produto,pais,valor,...}","partitionColumns":[]}} {"add":{"path":"part-00000-a1b2.snappy.parquet","size":2048,"modificationTime":1717000,"dataChange":true}} {"add":{"path":"part-00001-c3d4.snappy.parquet","size":1984,"modificationTime":1717000,"dataChange":true}}
⚙️ protocol
Versões mínimas de leitor/escritor exigidas para entender este commit — é como o Delta adiciona funcionalidades novas sem quebrar leitores antigos.
📋 metaData
O schema da tabela, colunas de particionamento e configurações. Reescrito sempre que o schema muda (evolução de schema).
➕ add
"Este arquivo Parquet agora faz parte da tabela." Pode incluir estatísticas min/max por coluna, usadas depois para pular arquivos em filtros.
➖ remove
"Este arquivo não faz mais parte da tabela." O arquivo continua no disco (tombstone) até o VACUUM apagar de verdade.
🧾 commitInfo
Metadados de auditoria: quem fez, quando, qual operação (INSERT, MERGE, DELETE...) — é o que alimenta DESCRIBE HISTORY.

✅ Repare que o log nunca guarda "linhas" de dado — só nomes de arquivos e metadados. Isso mantém os arquivos JSON pequenos mesmo em tabelas gigantescas, porque quem guarda os valores de fato continua sendo o Parquet.

A Garantia Central
🔒 Transações ACID: tudo ou nada

Um commit do Delta só é válido se o arquivo .json correspondente for escrito por completo, de uma vez (usando operações atômicas do sistema de armazenamento, como "criar se não existir"). Isso garante as quatro letras de ACID:

⚛️ Atomicidade
A transação inteira acontece ou nada acontece. Nunca existe um estado "meio commitado".
✅ Consistência
Toda escrita passa pelas regras de schema antes de virar um commit válido.
🕶️ Isolamento
Leitores sempre veem um snapshot completo e consistente — nunca uma mistura de estados.
💾 Durabilidade
Uma vez que o .json foi escrito, o commit existe para sempre no log — mesmo que o processo caia logo em seguida.

É como apostar numa moeda: ou dá cara, ou dá coroa — nunca "meio cara, meio coroa". Escrever os 3 arquivos de dados é só preparação, como separar os brinquedos antes de guardar. Se a luz acabar antes disso, os brinquedos preparados ficam largados no chão — mas o caderno continua dizendo a mesma coisa de antes, então ninguém percebe nada de errado.

Performance do Log
📸 Checkpoints: um resumo para não reler tudo

Depois de milhares de commits, reconstruir o estado da tabela lendo todos os JSONs desde o início ficaria cada vez mais lento. Por padrão, a cada 10 commits, o Delta escreve um checkpoint.parquet: uma foto consolidada de "quais arquivos valem agora", num formato Parquet rápido de ler. Um leitor novo só precisa: achar o checkpoint mais recente + reler os poucos commits JSON depois dele.

Qualidade de Dados
🛡️ Schema Enforcement & Evolution

Por padrão, o Delta rejeita qualquer escrita cujo schema não bate com o da tabela (coluna a mais, faltando, ou de tipo diferente). É o oposto do "aceita qualquer coisa" dos data lakes crus. Quando a mudança é intencional, você opta explicitamente por evoluir o schema.

🧒 Explicando para uma criança

É como um formulário de matrícula da escola: se falta o campo "nome" ou alguém escreve a idade no campo do telefone, a secretária devolve o formulário na hora, antes de arquivar. Só se você marcar a caixinha "quero adicionar um campo novo pra todo mundo" (mergeSchema) é que a escola aceita um formulário com uma pergunta extra — e completa com "não informado" nas matrículas antigas.

Upsert
🔀 MERGE INTO: update e insert em um só comando

MERGE INTO compara uma tabela alvo com uma fonte de mudanças (novo lote, CDC, etc.) usando uma chave, e decide linha a linha: se a chave já existe, atualiza (UPDATE); se não existe, insere (INSERT). É o coração de pipelines incrementais e upserts.

Copy-on-Write
✏️ UPDATE & DELETE: como mudar um arquivo imutável

Parquet não permite editar bytes existentes. Por padrão, o Delta resolve isso com copy-on-write: para um DELETE ou UPDATE, ele localiza os arquivos Parquet que contêm linhas afetadas, reescreve um arquivo novo já sem/com a mudança, marca o arquivo antigo como remove no log e adiciona o novo como add — tudo em um único commit atômico.

Experimente: DELETE FROM vendas WHERE pais = 'Portugal'

Ainda não executado
Arquivos com linhas de Portugal serão reescritos sem elas; arquivos sem nenhuma linha de Portugal nem são tocados.

💡 Uma otimização mais recente, Deletion Vectors, evita reescrever o arquivo inteiro: em vez disso, grava um pequeno "mapa de bits" marcando quais linhas ignorar na leitura (merge-on-read). Mais rápido para deletes/updates pequenos e frequentes, ao custo de os leitores precisarem entender esse mapa.

Múltiplos Escritores
⚔️ Controle de concorrência otimista

E se dois processos tentam escrever ao mesmo tempo? O Delta usa controle de concorrência otimista: cada escritor lê a versão atual, prepara sua transação, e tenta "reivindicar" o próximo número de versão com uma operação atômica do armazenamento (ex: "criar arquivo só se ele não existir"). Se alguém já reivindicou esse número, há conflito — e o escritor perdedor decide se pode tentar de novo com base no que mudou.

Manutenção
🧹 OPTIMIZE & Z-ORDER

Escritas frequentes (streaming, micro-batches) tendem a criar muitos arquivos pequenos — ótimo para escrever rápido, péssimo para ler depois (overhead de abrir milhares de arquivos). OPTIMIZE reescreve arquivos pequenos em arquivos maiores e bem compactados, usando o mesmo mecanismo de add/remove que já vimos.

Z-ORDER: agrupando valores parecidos fisicamente

Sem ordenação, valores de região e categoria ficam espalhados aleatoriamente entre arquivos — um filtro por região precisa abrir quase todos. Z-ORDER BY (regiao, categoria) agrupa combinações parecidas nos mesmos arquivos, potencializando o pruning por min/max (o mesmo princípio dos row groups do Parquet).

Cada bloco é um arquivo; a cor representa a região predominante dentro dele. Repare como o Z-ORDER concentra cores iguais no mesmo arquivo.
Limpeza Física
🗑️ VACUUM: apagando de verdade

Arquivos marcados como remove continuam ocupando espaço em disco — eles só deixam de contar para a versão atual da tabela, mas ainda existem para permitir time travel. VACUUM apaga fisicamente arquivos órfãos mais antigos que um período de retenção (padrão: 7 dias / 168 horas).

Recurso Avançado
🔄 Change Data Feed (CDF)

Com delta.enableChangeDataFeed = true, cada UPDATE/DELETE/MERGE passa a gerar também um registro linha a linha do que mudou, consultável via table_changes() — perfeito para alimentar pipelines incrementais (CDC) sem reprocessar a tabela inteira.

💡 Repare nas duas linhas geradas por um único UPDATE: update_preimage (o valor antigo) e update_postimage (o valor novo) — é isso que permite a um consumidor downstream saber exatamente o que mudou, não só o estado final.

Panorama
⚖️ Delta Lake vs. Iceberg vs. Hudi vs. Parquet puro

Os três formatos de tabela resolvem o mesmo problema central (ACID + versionamento por cima de arquivos colunares), com filosofias diferentes de log e ecossistema.

O conceito guarda-chuva: Lakehouse

Todos os três formatos existem para viabilizar o Lakehouse: um data lake barato baseado em arquivos colunares, com as garantias transacionais que antes só bancos e data warehouses ofereciam. A escolha entre eles hoje é mais sobre ecossistema e engines usadas do que sobre capacidade técnica — os três convergiram para conjuntos de features muito parecidos.

🐍 Delta Lake na prática

Do dia a dia com PySpark até inspecionar o histórico de commits, sem precisar de cluster nenhum com delta-rs e DuckDB.

sqlcopiarDESCRIBE HISTORY vendas; SELECT * FROM vendas VERSION AS OF 2; OPTIMIZE vendas ZORDER BY (regiao, categoria); VACUUM vendas RETAIN 168 HOURS;

Checklist
✅ Boas práticas
🧹 Rode OPTIMIZE com regularidade
Especialmente em tabelas alimentadas por streaming ou micro-batches — arquivos pequenos se acumulam rápido e degradam leitura. Agende OPTIMIZE periódico, não só quando notar lentidão.
📐 Combine particionamento com Z-ORDER
Particione por colunas de baixa cardinalidade e padrão de filtro estável (ex: data), e use ZORDER BY para as colunas de filtro adicionais de alta seletividade.
🗑️ Nunca zere a retenção do VACUUM sem necessidade
VACUUM ... RETAIN 0 HOURS pode quebrar leituras concorrentes em andamento e destrói o time travel além do ponto de corte. Mantenha ao menos os 7 dias padrão.
🔄 Use Change Data Feed para pipelines incrementais
Antes de reprocessar tabelas inteiras a cada execução, avalie se enableChangeDataFeed + table_changes() resolve o caso de forma muito mais barata.
