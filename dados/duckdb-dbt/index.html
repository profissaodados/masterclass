Um organiza o SQL. O outro executa na velocidade da luz.

dbt (data build tool) é a ferramenta que transforma um monte de arquivos .sql soltos em um projeto organizado, testado e documentado — ele decide a ordem certa de rodar cada transformação, mas não guarda nem processa nenhum dado sozinho. DuckDB é o motor que efetivamente executa esse SQL, rápido, local, sem servidor. Juntos, formam um ambiente de desenvolvimento de dados completo que roda inteiro dentro do seu notebook — sem custo de nuvem, sem esperar fila de cluster, com o mesmo fluxo de trabalho que times gigantes usam em produção.

Motivação
🍝 O Problema: SQL Espaguete

Antes do dbt, um pipeline analítico costumava virar uma pilha de scripts .sql soltos numa pasta, rodados manualmente ou por um cron obscuro, sem ninguém saber ao certo qual script depende de qual, o que quebra se uma tabela de origem mudar, e se algum número da tabela final está mesmo certo. Cada analista reescreve a mesma lógica de "limpar a coluna de data" em três lugares diferentes.

🧸 Explicando fácil

Imagina uma cozinha onde cada cozinheiro tem sua própria receita de molho de tomate, escrita num guardanapo, guardada num bolso diferente. Ninguém sabe qual guardanapo é o mais atual, nem em que ordem as panelas precisam ir ao fogo. O dbt é o livro de receitas organizado da cozinha: cada receita (model) fica escrita uma única vez, numerada, com a ordem certa de preparo — e qualquer cozinheiro novo consegue seguir sem perguntar nada a ninguém.

😵 Sem dbt
Scripts soltos, ordem de execução decorada de cabeça, lógica de negócio copiada e colada em vários arquivos, nenhum teste automático, documentação (se existir) desatualizada em algum wiki separado do código.
✅ Com dbt
Cada transformação é um arquivo .sql versionado no Git, a ordem de execução é calculada automaticamente a partir de quem referencia quem, testes rodam a cada execução, e a documentação nasce do próprio código.
Fundamentos
📖 O Que é o dbt?

dbt (data build tool) é uma ferramenta de linha de comando de código aberto que cuida exclusivamente do T em ELT (Extract, Load, Transform). Ele não extrai dados de um sistema de origem, não os carrega no banco — assume que os dados já chegaram em algum lugar consultável (um schema no seu warehouse, ou arquivos que o DuckDB enxerga). A partir daí, dbt organiza, versiona, testa e documenta a transformação desses dados brutos em tabelas prontas para análise, usando apenas SQL (mais um pouco de Jinja, um templating simples).

📥 Extract
Puxar dados do sistema de origem (API, banco transacional, planilha). Fora do escopo do dbt — ferramentas como Fivetair, Airbyte ou um script cuidam disso.
📤 Load
Colocar esses dados brutos em algum lugar consultável via SQL. Também fora do escopo do dbt — pode ser um warehouse, ou simplesmente arquivos Parquet/CSV que o DuckDB lê direto.
🔧 Transform — aqui mora o dbt
Pegar o dado bruto já carregado e transformá-lo com SELECTs organizados, testados e documentados, até virar tabelas prontas para BI.

💡 Isso é uma virada em relação ao ETL tradicional (Transform antes de carregar): no ELT moderno, carrega-se o dado bruto primeiro — barato de armazenar — e a transformação acontece depois, dentro do próprio motor de banco, usando o poder de processamento dele. É exatamente aqui que o DuckDB se encaixa perfeitamente: um motor analítico rápido, disponível na hora, para o "T" do dbt rodar em cima.

A Dupla
🤝 Por Que dbt + DuckDB é uma Combinação Perfeita

O dbt precisa de um motor SQL por trás para de fato rodar as consultas que ele organiza — esse motor é plugável, chamado de adapter (Snowflake, BigQuery, Postgres, Databricks...). O dbt-duckdb é o adapter que conecta o dbt ao DuckDB. Como o DuckDB não exige servidor, credenciais nem custo de nuvem, essa combinação vira o ambiente ideal para aprender, prototipar e desenvolver pipelines dbt inteiros na sua própria máquina — o mesmo projeto, depois, roda sem alterar um único model contra um warehouse de verdade em produção.

A Peça Fundamental
🧩 Models: Sua Primeira Transformação

Um model é, na essência, um arquivo .sql com um único SELECT dentro. O dbt pega esse SELECT e decide sozinho se ele vira uma VIEW ou uma TABLE no banco — você nunca escreve CREATE TABLE à mão. A mágica está na função {{ ref('outro_model') }}: em vez de escrever o nome físico da tabela, você referencia outro model pelo nome do arquivo — e é essa referência que o dbt usa para descobrir a ordem certa de execução.

🧸 Explicando fácil

{{ ref('stg_pedidos') }} é como escrever "use o resultado da receita 'molho de tomate'" em vez de "use a panela vermelha da prateleira 3". Não importa onde a panela vermelha estava ontem — o dbt sempre acha a receita certa, na versão mais atual, e prepara ela antes de você precisar dela.

models/staging/stg_pedidos.sql — o que você escreve
sqlcopiarwith source as ( select * from {{ source('loja_bruta', 'pedidos') }} ) select id_pedido, id_cliente, data_pedido::date as data_pedido, valor_total from source
SQL compilado — o que o DuckDB de fato executa
sql compiladowith source as ( select * from "dev"."main"."pedidos" ) select id_pedido, id_cliente, data_pedido::date as data_pedido, valor_total from source

💡 {{ source(...) }} aponta para dado bruto que já existe no banco (não foi criado por um model dbt). {{ ref(...) }} aponta para outro model dbt. Essa distinção é o que permite ao dbt distinguir "onde o pipeline começa" de "o que ele mesmo construiu".

O Coração do dbt
🕸️ O Grafo (DAG): Como os Models se Conectam

Cada vez que um model usa {{ ref('outro_model') }}, ele cria uma seta num grafo de dependências — o DAG (Directed Acyclic Graph, grafo acíclico dirigido). O dbt lê todas essas setas antes de rodar qualquer coisa e calcula sozinho a ordem correta: nada roda antes do que ele depende, e tudo que pode rodar em paralelo, roda em paralelo. 🧸 Explicando fácil

Pense numa esteira de montagem de LEGO: primeiro vêm as peças soltas (fontes brutas), depois elas são separadas por cor e limpas (staging), depois montadas em pedaços maiores (intermediate), até virarem o castelo pronto (marts). Ninguém tenta encaixar o telhado antes de ter as paredes — o dbt garante essa ordem sozinho, olhando as setas do grafo.

A Decisão Mais Importante de Cada Model
🏗️ Materializations

Materialization é a resposta à pergunta "esse SELECT vira o quê, de fato, no banco?". O dbt oferece quatro estratégias — a escolha certa depende do tamanho da tabela, de quantas vezes ela é consultada, e de quanto custa reprocessá-la do zero.

Dados de Referência
🌱 Seeds: CSV Vira Tabela

Um seed é um arquivo CSV pequeno, versionado dentro do próprio projeto (pasta seeds/), que o dbt carrega como tabela com o comando dbt seed. Ideal para dados de referência que não mudam com frequência e não vêm de nenhum sistema de origem — uma tabela de câmbio, um de-para de categorias, uma lista de feriados.

seeds/categorias.csv
csvcopiarid_categoria,nome_categoria 1,Eletrônicos 2,Livros 3,Casa & Cozinha 4,Esportes
Carregar e usar
bash + sqlcopiar$ dbt seed # cria/atualiza a tabela "categorias" -- num model, referencia como qualquer outro: select * from {{ ref('categorias') }}

⚠️ Seeds não substituem source(): são para dados pequenos e estáticos mantidos pelo próprio time de dados, não para carregar volumes grandes vindos de um sistema de origem — isso é papel da etapa de Load, fora do dbt.

Histórico Automático
📸 Snapshots: Capturando Mudanças (SCD Tipo 2)

Tabelas de origem costumam guardar só o estado atual — se o endereço de um cliente muda, o valor antigo é sobrescrito e perdido para sempre. Um snapshot do dbt tira uma "foto" periódica dessa tabela e, quando percebe uma mudança, insere uma nova linha em vez de sobrescrever — preservando o histórico completo no formato SCD Tipo 2 (com dbt_valid_from / dbt_valid_to).

snapshots/clientes_snapshot.sql
sqlcopiar{% snapshot clientes_snapshot %} {{ config( target_schema='snapshots', unique_key='id_cliente', strategy='timestamp', updated_at='atualizado_em' ) }} select * from {{ source('loja_bruta','clientes') }} {% endsnapshot %}
Simular uma nova execução do snapshot

💡 É a mesma técnica ensinada na aula de SCD (Slowly Changing Dimensions) — o snapshot do dbt é justamente uma implementação automatizada de SCD Tipo 2 rodando em cima do seu SQL, sem você escrever a lógica de comparação de hash na mão.

SQL que se Repete Vira Função
🪄 Jinja & Macros

dbt compila cada model através do Jinja, uma linguagem de templates. Isso habilita variáveis, condicionais ({% if %}), loops ({% for %}) e, principalmente, macros — funções reutilizáveis escritas em SQL+Jinja, chamadas em qualquer model como se fossem funções nativas.

❌ Sem macro — lógica repetida em 3 models
sqlcopiarselect (valor_centavos / 100.0)::decimal(10,2) as valor_reais from {{ ref('stg_pedidos') }} -- a mesma conta copiada em stg_pagamentos.sql -- e em fct_pedidos.sql também
✅ Com macro — escrito uma vez, usado sempre
sqlcopiar-- macros/centavos_para_reais.sql {% macro centavos_para_reais(coluna) %} ({{ coluna }} / 100.0)::decimal(10,2) {% endmacro %} -- em qualquer model: select {{ centavos_para_reais('valor_centavos') }} as valor_reais from {{ ref('stg_pedidos') }}
🧸 Explicando fácil

Uma macro é um carimbo: em vez de desenhar a mesma estrelinha à mão em 20 folhas, você faz um carimbo de estrelinha uma vez e carimba nas 20. Se um dia a estrelinha precisar mudar de formato, você troca o carimbo — não as 20 folhas.

Documentação que Nasce do Código
📚 Docs & Lineage Graph

Descrições de models e colunas vivem em arquivos schema.yml, ao lado do próprio código SQL — nunca num wiki separado que ninguém atualiza. O comando dbt docs generate lê esses YAMLs mais o próprio DAG e monta um site estático navegável, com o lineage graph: o mesmo grafo que vimos na seção do DAG, mas clicável, com a descrição de cada coluna.

models/staging/schema.yml
yamlcopiarmodels: - name: stg_pedidos description: "Pedidos limpos, 1 linha por pedido" columns: - name: id_pedido description: "Chave única do pedido" tests: - unique - not_null
Gerar e servir o site de documentação
bashcopiardbt docs generate dbt docs serve # abre localhost com o lineage graph # interativo + descrições de cada coluna

✅ Nenhuma ferramenta externa de catálogo é obrigatória para começar: o próprio dbt docs já entrega busca, descrições e o grafo de linhagem completo, gerado 100% a partir do que já está no projeto.

Do Zero ao Fim
🔨 Exemplo Completo: Um Pipeline, Cinco Formatos Diferentes

Essa é a demonstração mais forte da dupla: o mesmo projeto dbt lê Parquet, CSV, JSON, Excel e até uma tabela de um banco SQLite anexado — sem ETL prévio, sem converter nada para um formato comum antes. O DuckDB lê cada arquivo com sua função nativa (read_parquet, read_csv_auto, read_json_auto, read_xlsx, ATTACH), e o dbt só organiza em que ordem e como essas fontes se juntam.

🧸 Explicando fácil

É como fazer um bolo com ingredientes que chegaram de lugares bem diferentes: a farinha veio num saco lacrado (Parquet), o leite numa caixinha comum (CSV), os ovos soltos numa caixa (JSON), o açúcar numa lata de rótulo bonito (Excel) e o fermento foi emprestado da vizinha (uma tabela de outro banco, anexada). O cozinheiro (DuckDB) não liga de onde cada um veio — ele só mistura tudo na tigela certa, na hora certa, seguindo a receita que o dbt escreveu.

Seis fontes, seis formatos — clique para ver como cada uma entra no projeto

O Mesmo Projeto, Dois Mundos
🆚 Dev Local (DuckDB) vs. Produção (Warehouse)

A ideia central: os models não mudam nada ao trocar de motor. Só o target escolhido no profiles.yml muda — e com ele, para onde o SQL compilado é enviado.

Dev — target local, DuckDB
yamlcopiaroutputs: dev: type: duckdb path: 'dev.duckdb' target: dev
Prod — target na nuvem, mesmo projeto
yamlcopiaroutputs: prod: type: snowflake account: "{{ env_var('SF_ACCOUNT') }}" database: analytics target: prod
bashcopiar$ dbt build # usa "dev" (DuckDB) por padrão $ dbt build --target prod # mesmíssimos models, rodando no warehouse
Dimensão🦆 Dev local (DuckDB)☁️ Produção (warehouse)
Custo por execuçãoZeroCréditos de computação / $

Ordem de grandeza ilustrativa para o tempo de um dbt build completo num projeto pequeno/médio durante o desenvolvimento — não um benchmark.
Mas tem uma pergunta que essa troca de target não responde sozinha: no exemplo completo da aula, as fontes eram cinco formatos de arquivo diferentes (Parquet, CSV, JSON, Excel, SQLite). Em dev, o próprio DuckDB lê qualquer um deles direto do disco — ele faz, sozinho, o papel de um mini "Extract + Load". Um warehouse de produção não faz isso: ele só enxerga o que já foi carregado dentro dele (ou o que está em object storage, num formato que ele sabe ler como tabela externa). Tirando o DuckDB da equação, cada formato precisa de um caminho próprio até chegar lá.
🧸 Explicando fácil

O DuckDB no seu laptop é como uma pessoa poliglota que lê qualquer carta, em qualquer idioma, na hora que ela chega. O warehouse de produção é mais como uma biblioteca gigante e rapidíssima — mas que só aceita livros que já foram traduzidos, catalogados e colocados na prateleira certa antes. Alguém (uma ferramenta de EL) precisa ter feito esse trabalho de tradução com antecedência; o bibliotecário (o warehouse) nunca faz isso sozinho.

💡 Um padrão comum

Usar o próprio DuckDB (ou uma lib como Python + pandas) como o motor da etapa de Extract + Load: um job pequeno lê Parquet/CSV/JSON/Excel/SQLite localmente e escreve tudo já padronizado em Parquet dentro do object storage do warehouse. Isso combina a flexibilidade do DuckDB para ler formatos heterogêneos com a escala de um warehouse gerenciado para consulta — sem precisar de um conector dedicado para cada formato de origem.

⚠️ Isso reforça o limite do dbt visto lá no início da aula: mesmo em dev, quando parece que "o dbt está lendo o Excel", quem faz esse trabalho é o DuckDB, por baixo do source(). Em produção essa responsabilidade não desaparece — ela só se move para fora do dbt, para uma ferramenta de EL dedicada (Fivetran, Airbyte, Meltano, ou um script próprio).

🐘 DuckDB na Transformação: a Parte Mais Cara, pelo Preço Mais Barato

A decisão mais importante não é "minha produção usa DuckDB ou um warehouse" — é onde a transformação roda. As camadas staging → intermediate → marts são, disparado, a parte do pipeline que mais escaneia e junta dados repetidamente, sempre recalculando o mesmo JOIN/GROUP BY — exatamente o tipo de carga que um warehouse cobra mais caro, por segundo de computação ou por byte escaneado. Rodar esse dbt build com DuckDB — numa VM pequena, um runner de CI, uma função serverless — custa uma fração disso. Só depois de já ter os dados limpos, testados e agregados é que entra a pergunta de onde servi-los.

💰 Por que transformar com DuckDB é mais barato
Cada model de staging/intermediate recalcula um JOIN/GROUP BY pesado — se isso roda dentro do warehouse, cada execução consome crédito dele, mesmo sendo um passo intermediário que ninguém consulta diretamente. Em DuckDB, você paga só o compute genérico da máquina que roda o dbt build (geralmente centavos), e guarda o warehouse — se ele existir no seu stack — só para as consultas finais.
🧭 A pergunta muda de lugar
Em vez de "dev usa DuckDB, prod usa warehouse", a pergunta certa é: a transformação roda em DuckDB (quase sempre vale a pena, é mais barato) — e, depois de pronta, o resultado fica em DuckDB ou é carregado em outro lugar só para servir?
Depois que o dbt build termina (sempre em DuckDB), dois caminhos possíveis
🅰️ Continuar servindo direto do DuckDB
O .duckdb gerado pelo build é o produto final — sem exportar nada para lugar nenhum. Faz sentido quando o volume e a concorrência de leitura cabem numa única máquina (ou no MotherDuck).
🅱️ Carregar o resultado já transformado em outro lugar
O dbt build pesado continua rodando em DuckDB — barato. No fim, só os marts (já pequenos, já agregados) são exportados e carregados num warehouse, Postgres etc., onde o consumo final precisa de mais concorrência, governança ou integração com outras ferramentas.
📦 A — Build agendado + artefato imutável
Um job (cron, Airflow, GitHub Actions) roda dbt build periodicamente e publica o .duckdb num bucket ou volume compartilhado. Apps e BI só leem esse artefato — sem concorrência de escrita para coordenar.
🔌 A — Motor embutido na aplicação
Uma API interna ou um dashboard carrega o arquivo .duckdb direto no próprio processo — a mesma filosofia in-process da primeira aula de DuckDB. Sem rede, sem servidor de banco separado.
🦆☁️ A — MotherDuck
Serviço gerenciado (dos criadores do DuckDB) que hospeda DuckDB na nuvem: concorrência multiusuário, execução híbrida e compartilhamento fácil — o caminho "oficial" para crescer além de um laptop sem trocar de motor.
🅱️ Exemplo: exportar o mart pronto e carregar num warehouse só para servir
sql — no fim do dbt buildcopiar-- fct_pedidos já está pronto, pequeno e agregado COPY (select * from fct_pedidos) TO 's3://meu-bucket/marts/fct_pedidos.parquet' (FORMAT parquet);
sql — carga final no warehousecopiar-- Snowflake, só a etapa de "servir" COPY INTO analytics.fct_pedidos FROM @meu_stage/marts/fct_pedidos.parquet FILE_FORMAT = (TYPE = parquet);
O JOIN pesado entre pedidos, clientes, produtos e vendedores já aconteceu em DuckDB — o warehouse só recebe e serve uma tabela pequena e pronta. É o mesmo COPY INTO visto lá em cima para Parquet/CSV/JSON, só que agora o arquivo de origem foi gerado pelo próprio pipeline, não veio de um sistema externo.
Cenário (para o caminho 🅰️, servir direto do DuckDB)DuckDB sozinho resolve?
Alguns GB a algumas centenas de GB, poucos leitores✅ Sim, tranquilamente
Centenas de GB a poucos TB, leitura pesada, um build por vez⚠️ Sim, com cuidado — máquina robusta ou MotherDuck
Muitos usuários escrevendo ao mesmo tempo❌ Não — um arquivo .duckdb aceita só 1 processo em modo escrita. Hora do caminho 🅱️
Múltiplos TB, precisa de cluster distribuído❌ Não — hora do caminho 🅱️, com Snowflake/BigQuery/Databricks/Spark servindo

💡 A calculadora "seu dataset cabe na RAM disponível?" da aula de DuckDB já mostrou que o motor processa mais dado do que cabe em memória via out-of-core processing — mas isso continua limitado pelo disco e pela CPU de uma única máquina. Repare que essa tabela é sobre servir (caminho 🅰️): a transformação em si, caminho 🅱️ ou não, quase sempre compensa rodar em DuckDB primeiro — a pergunta é só o que fazer com o resultado depois.

Checklist
✅ Boas Práticas
📐 Staging 1:1 com a fonte
Cada model de staging deve corresponder a exatamente uma tabela/fonte, sem joins — só renomeação, cast de tipos e limpeza leve.
🚫 Nunca referencie tabelas físicas direto
Use sempre ref()/source(), nunca o nome hardcoded da tabela — é isso que mantém o DAG e o lineage corretos.
🧪 Teste toda chave primária
unique + not_null em toda chave de model deveria ser o mínimo inegociável em qualquer projeto.
💾 DuckDB para dev, warehouse para prod
Use o adapter DuckDB para desenvolvimento e CI rápidos — decida com o time se ele também serve para produção, ou se o volume/concorrência pede um warehouse gerenciado.

⚠️ DuckDB em modo arquivo aceita apenas um processo escrevendo por vez — um pipeline dbt+DuckDB em produção com múltiplos jobs concorrentes escrevendo no mesmo arquivo precisa de coordenação cuidadosa (ou de um motor multiusuário de verdade).
