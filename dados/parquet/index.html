O arquivo que ensinou o Big Data a ler só o que importa

Parquet é um formato de armazenamento colunar, binário e open-source, criado em 2013 por engenheiros do Twitter e da Cloudera e inspirado no paper Dremel, do Google. Hoje é o formato de fato para dados analíticos em data lakes e lakehouses — usado por Spark, Trino, DuckDB, BigQuery, Snowflake, Athena e praticamente todo motor de consulta moderno. Nesta aula, vamos abrir o arquivo por dentro: bytes, metadados, encodings e as técnicas que fazem uma consulta ler megabytes em vez de gigabytes.

Fundamentos
🗂️ Por que armazenamento colunar?

Formatos tradicionais como CSV, JSON e bancos transacionais guardam os dados linha a linha: todos os campos de um registro ficam fisicamente juntos. Isso é ótimo para gravar ou buscar um registro inteiro (OLTP), mas péssimo para perguntas analíticas que tocam poucas colunas em milhões de linhas. O Parquet vira essa lógica de cabeça para baixo: guarda cada coluna separadamente e de forma contígua, para que o motor de consulta leia só as colunas que a query realmente pede. Vamos acompanhar essa mesma tabela de vendas do início ao fim da aula.

Economia vs. row-store—
O toque extra do Parquet: Row Groups

O Parquet não é puramente colunar — ele é híbrido. O arquivo é dividido horizontalmente em row groups (grupos de linhas) e, dentro de cada row group, os dados são armazenados por coluna. Isso combina o melhor dos dois mundos: leitura de coluna dentro de cada grupo, e a possibilidade de pular row groups inteiros usando estatísticas — o assunto da seção de Predicate Pushdown mais abaixo.

Um arquivo Parquet é dividido em duas grandes partes: os dados (organizados em row groups → column chunks → pages) e o rodapé (footer), que guarda todos os metadados. Clique nas caixas abaixo — a mesma lógica do diagrama oficial da Apache — para entender como cada pedaço se conecta.

👆 Clique em qualquer bloco
Cada elemento do arquivo tem um par correspondente no footer. É assim que um leitor sabe, sem escanear o arquivo inteiro, exatamente em que byte cada coluna começa.

💡 Repare que o footer fica no final do arquivo, não no início. Isso permite que o Parquet seja escrito em single pass (o gravador não sabe os tamanhos finais das colunas até terminar de escrever os dados). Um leitor então: (1) lê os últimos 8 bytes do arquivo — 4 bytes de "tamanho do footer" + 4 bytes do magic number "PAR1"; (2) volta esse tamanho a partir do final e decodifica o FileMetaData em Thrift; (3) só então sabe exatamente quais offsets ler para cada coluna que a query pediu.

🔬 Zoom: o que é exatamente o Magic Number "PAR1"?
🔤 Por que bytes ASCII legíveis?
"PAR1" não é uma sequência binária arbitrária — são 4 bytes que correspondem literalmente aos caracteres P (0x50), A (0x41), R (0x52) e 1 (0x31). Usar uma assinatura em texto plano é uma convenção comum entre formatos de arquivo: o PNG começa com \x89PNG, o GIF com GIF89a, o ZIP com PK\x03\x04. Qualquer pessoa consegue enxergar a assinatura só abrindo o arquivo num editor hexadecimal (xxd, hexdump), sem precisar de nenhuma ferramenta especializada.
🎭 Por que ele aparece duas vezes?
No início, funciona como etiqueta de identidade — o mesmo princípio usado por utilitários de detecção de tipo de arquivo (como o comando file do Unix), permitindo reconhecer o formato sem interpretar mais nada. No final, o papel é mais crítico: como o footer só é escrito depois de todos os dados, a presença do "PAR1" final confirma que a gravação terminou por completo — é uma checagem de integridade embutida no próprio formato.
O que acontece se o "PAR1" final estiver faltando?

Se a escrita do arquivo for interrompida no meio — queda de energia, falha de rede, job cancelado — o footer e o magic number final simplesmente não chegam a ser gravados. Um leitor que tenta abrir esse arquivo lê os últimos 4 bytes, percebe que não são "PAR1" e rejeita o arquivo imediatamente como corrompido/incompleto, em vez de tentar interpretar dados parciais e devolver um resultado errado silenciosamente. Todo esse mecanismo de segurança custa apenas 8 bytes (2 × 4) do arquivo inteiro — praticamente de graça.

Algoritmo de leitura, passo a passo
pseudo-código# 1. vai direto para o final do arquivo, sem escanear nada seek(fim_do_arquivo - 8) # 2. lê os últimos 4 bytes e confere a assinatura magic_final = read(4) assert magic_final == b"PAR1" # senão: arquivo corrompido/incompleto # 3. lê os 4 bytes anteriores: tamanho do footer (little-endian) footer_length = read_uint32_le() # 4. recua exatamente até o início do FileMetaData seek(fim_do_arquivo - 8 - footer_length) file_meta_data = thrift_decode(read(footer_length))
Hierarquia Interna
🧱 Row Groups, Column Chunks e Pages

O arquivo tem três níveis de granularidade, do maior para o menor. Entender essa hierarquia é a chave para entender paralelismo, compressão e pruning no Parquet.

1️⃣ Row Group
Uma fatia horizontal do dataset — um conjunto de linhas. Cada row group contém um column chunk para cada coluna do schema. É a unidade de paralelismo: cada task do Spark, por exemplo, normalmente processa um ou mais row groups inteiros. Tamanho típico recomendado: 128 MB a 1 GB.
2️⃣ Column Chunk
Dentro de um row group, é o bloco contíguo de todos os valores de uma única coluna. É a unidade de leitura por coluna — o motor abre exatamente os column chunks das colunas usadas na query, ignorando o resto.
3️⃣ Page
A menor unidade de armazenamento. Cada column chunk é dividido em páginas (tipicamente ~1 MB) — data pages (valores), dictionary pages (tabela de valores únicos) e páginas de índice. Encoding e compressão são aplicados por página.

📄 Data Page
Contém os valores de fato: page header (Thrift) + repetition levels + definition levels + os valores codificados/comprimidos. Existem duas versões — DataPage V1 (tudo comprimido junto) e DataPage V2 (separa levels dos valores, permitindo pular a descompressão dos levels e habilitando os índices de página da próxima seção).
📖 Dictionary Page
Quando a coluna usa Dictionary Encoding, a primeira página do column chunk é especial: guarda a tabela de valores únicos (o dicionário). As data pages seguintes armazenam só os índices inteiros que apontam para essa tabela — é o que vimos na demo da seção de Encodings.
O Cérebro do Arquivo
🗄️ Metadados e o Footer (FileMetaData)

Todo o "conhecimento" sobre o arquivo — schema, quantas linhas, onde cada coluna começa, estatísticas — vive em uma estrutura Thrift chamada FileMetaData, escrita uma única vez no footer. Um leitor sempre lê o footer primeiro, antes de tocar em qualquer dado.

📋 No nível do arquivo
  • version — versão do formato Parquet
  • schema — lista pré-ordenada de SchemaElement (tipos físicos e lógicos)
  • num_rows — total de linhas do arquivo
  • row_groups[] — metadados de cada row group
  • key_value_metadata — pares chave/valor customizados (ex: metadados do Pandas)
  • created_by — ferramenta que escreveu o arquivo
📋 No nível de cada column chunk
  • type / path_in_schema — tipo e caminho da coluna
  • encodings[] — encodings usados (PLAIN, RLE, DICTIONARY...)
  • codec — compressão aplicada (Snappy, Zstd, Gzip...)
  • num_values — quantidade de valores
  • data_page_offset / dictionary_page_offset — onde começar a ler
  • total_compressed_size / total_uncompressed_size
  • statistics — min, max, null_count, distinct_count
Por que isso importa na prática

Como cada column chunk conhece seu offset exato no arquivo, um mecanismo de leitura pode fazer seeks diretos — sem escanear sequencialmente. É o que permite a um motor de consulta ler só 2 de 50 colunas de um arquivo de 10 GB tocando apenas nos bytes daquelas 2 colunas.

🔢 Delta Encoding
Para inteiros ordenados ou quase-ordenados (ex: timestamps, IDs sequenciais), armazena apenas a diferença entre valores consecutivos — números muito menores para compactar. Variantes: DELTA_BINARY_PACKED, DELTA_BYTE_ARRAY.
✂️ Byte Stream Split
Para FLOAT/DOUBLE, separa os bytes de mesma posição de todos os valores em streams distintos antes de comprimir — floats reais têm mais redundância byte a byte do que parece, e essa técnica revela isso ao compressor.
📐 PLAIN
O encoding "sem truque": valores em sequência, tamanho fixo por tipo. É o fallback usado quando nenhum encoding especializado compensa — e a base sobre a qual o codec de compressão genérico ainda atua.

A Mágica da Performance
🎯 Estatísticas e Predicate Pushdown

Cada column chunk guarda min, max e null_count no footer. Antes de ler um único byte de dado, o motor de consulta compara o filtro da query com essas estatísticas — se não houver interseção possível, o row group inteiro é pulado. Isso se chama predicate pushdown (ou row group / page pruning).

💡 Isso funciona em duas granularidades: row group (estatística grosseira, sempre presente) e página (estatística fina, opcional — próxima seção). Quanto mais os dados estiverem ordenados fisicamente pela coluna filtrada, mais eficaz o pruning — daí a prática comum de ordenar (ORDER BY / Z-ORDER) antes de gravar em Parquet.

Recursos Avançados
🔎 Column Index, Offset Index e Bloom Filter

O formato evoluiu para permitir pruning ainda mais fino do que "o row group inteiro". Estes três recursos são opcionais (nem todo arquivo/escritor os inclui), mas quando presentes reduzem drasticamente o I/O.

📇 Column Index
Guarda min/max/null_count por página, não só por row group. Permite pular páginas individuais dentro de um column chunk sem descartar o row group inteiro — pruning de granularidade fina.
📍 Offset Index
Guarda o offset de byte e o tamanho de cada página (a estrutura PageLocation: offset, tamanho comprimido, primeira linha). Combinado com o Column Index, o leitor sabe exatamente quais bytes buscar (seek) para pegar só as páginas relevantes — sem decodificar as demais.
🌸 Bloom Filter
Estrutura probabilística por column chunk que responde "este valor certamente não está aqui" com custo baixíssimo. Essencial para colunas de alta cardinalidade (IDs, UUIDs, e-mails) em filtros de igualdade, onde min/max não ajuda muito.

O Column Index resolve um problema real: um row group inteiro pode ter um intervalo min/max muito amplo (e por isso nunca ser descartado sozinho), mesmo que a maioria das páginas dentro dele não tenha chance nenhuma de conter o valor buscado. Veja com uma coluna preco cujo row group vai de 10 a 980 — bem largo demais para qualquer pruning por row group:

💡 Sozinho, o row group (min=10, max=980) sempre seria marcado como "pode ter match" — ele nunca é descartado por estatística de row group. É só descendo ao nível de página, com o Column Index, que o motor consegue pular parte do trabalho mesmo sem descartar o row group inteiro. O Offset Index é o que torna isso possível na prática: sem ele, o leitor saberia quais páginas pular, mas não onde elas começam no arquivo.

Já min/max não ajuda em nada para uma pergunta como WHERE user_id = 'user_247' — o valor pode estar em qualquer lugar dentro do intervalo. É exatamente aí que entra o Bloom Filter: uma estrutura de bits que testa pertencimento de forma probabilística.

O Truque do Dremel
🪆 Dados aninhados: repetition & definition levels

Como guardar uma coluna que é, na verdade, uma lista (várias ocorrências por registro, algumas nulas) em formato colunar? O Parquet resolve isso com a técnica do paper Dremel: cada valor ganha um repetition level (em qual posição da lista ele reinicia) e um definition level (até que ponto do caminho aninhado o valor está de fato preenchido).

📦 Exemplo: pessoas e telefones
Ana: [11-1111, 11-2222]
Bruno: [] (sem telefone)
Carla: [21-3333]
🧩 Por que isso é poderoso
A coluna telefones é achatada em uma única sequência física de valores + níveis — sem precisar duplicar nome para cada telefone, e sem quebrar o armazenamento colunar mesmo com listas e nulos aninhados.

💡 Você não precisa calcular esses níveis manualmente — bibliotecas como PyArrow, Spark e Pandas fazem isso por você ao gravar struct, list e map. O importante para a aula é entender por que tipos aninhados em Parquet não "quebram" a leitura colunar.

Organização em Disco
🗃️ Particionamento (Hive-style)

O pruning por estatísticas acontece dentro de um arquivo. Antes disso, dá para evitar abrir arquivos inteiros organizando o dataset em pastas por valor de coluna — o padrão que Spark, Hive e a maioria dos data lakes usam.

vendas/
ano=2023/
mes=12/
part-0000.parquet
ano=2024/
mes=01/
part-0000.parquet
mes=02/
part-0000.parquet
Duas camadas de pruning combinadas
Uma query com WHERE ano = 2024 AND mes = 1 primeiro elimina pastas inteiras sem abrir nenhum arquivo (partition pruning no sistema de arquivos) e, dentro dos arquivos restantes, ainda aplica o predicate pushdown por estatísticas de row group. É por isso que pipelines bem desenhados combinam as duas técnicas.

⚠️ Particionar demais (ex: por cliente_id, com milhões de valores únicos) gera o problema dos arquivos pequenos: milhares de arquivos minúsculos, cada um com overhead de metadados desproporcional ao dado real. Particione por colunas de baixa/média cardinalidade e com padrão de filtro real (data, região, categoria).

Checklist
✅ Boas práticas e o Lakehouse
📏 Tamanho de arquivo e row group
Mire em arquivos de algumas centenas de MB a ~1 GB. Arquivos pequenos demais multiplicam overhead de metadados e desperdiçam o benefício do formato colunar; arquivos grandes demais prejudicam paralelismo. Compacte arquivos pequenos periodicamente.
🗜️ Escolha de codec
Snappy é o padrão histórico (rápido, compressão moderada). Zstd tornou-se a escolha moderna recomendada — melhor taxa de compressão com velocidade próxima do Snappy. Gzip comprime mais, mas é mais lento para ler.
📐 Ordene o que você filtra
Ordenar (ou usar Z-ORDER) os dados pela coluna mais filtrada antes de gravar concentra valores parecidos no mesmo row group — o que maximiza a eficácia do predicate pushdown (min/max mais "apertados").
🏛️ Delta Lake, Iceberg e Hudi
Parquet não tem transações, versionamento ou DELETE/UPDATE nativos. Formatos de tabela como Delta Lake, Apache Iceberg e Apache Hudi adicionam um log de transações por cima de arquivos Parquet — trazendo ACID, time travel e schema evolution: a base do conceito de Lakehouse.
