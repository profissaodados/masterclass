O lakehouse que cabe numa frase

DuckLake é uma extensão do DuckDB que transforma qualquer pasta de arquivos Parquet num lakehouse transacional completo — com snapshots, viagem no tempo e múltiplas tabelas — sem precisar de Spark, sem cluster, sem JVM. A ideia central é simples de explicar até pra uma criança: guarde os "arquivos grandes" (os dados) numa caixa gigante — o AWS S3 — e guarde o "índice da biblioteca" (o catálogo, quem sabe onde cada coisa está) num banco de dados normal — o Supabase, que é só um Postgres na nuvem com uma cara bonita. Nesta aula vamos montar essa arquitetura peça por peça, com bastante desenho e exemplo visual.

Por que isso existe
🗃️ O problema dos "mil arquivinhos"

Pense num lakehouse como uma biblioteca gigante. Formatos como Iceberg e Delta Lake guardam o "índice da biblioteca" também dentro da própria estante — como um monte de fichinhas de papel (arquivos JSON, Avro, checkpoints) espalhadas junto com os livros. Cada vez que alguém adiciona ou muda um livro, uma fichinha nova é criada. Depois de milhares de mudanças, você tem milhares de fichinhas pequenas pra organizar — e isso fica lento e complicado de manter. O DuckLake faz diferente: tira todas as fichinhas da estante e guarda tudo organizado dentro de um único fichário — um banco de dados SQL de verdade (aqui, o Supabase). Arraste o controle abaixo e veja a diferença crescer.

✅ Vantagem do DuckLake

Consultar "qual é o estado atual da tabela?" vira uma consulta SQL comum no catálogo — rápida, indexada, com transações ACID de verdade — em vez de precisar ler e somar centenas de arquivos pequenos no object storage.

ℹ️ Não é mágica

Os dados em si (os Parquet) continuam morando no S3, exatamente como no Iceberg. A diferença é só onde mora o índice — e trocar "um monte de arquivos" por "uma tabela SQL" é o que torna o DuckLake tão mais simples de operar.

A Planta Baixa
🏗️ As 3 peças do Lakehouse

Todo lakehouse precisa de três papéis bem separados: alguém que executa a pergunta (o motor), alguém que sabe onde tudo está guardado (o catálogo) e o lugar onde os dados de fato moram (o armazenamento). No DuckLake, cada papel é ocupado por uma ferramenta diferente e substituível. Clique em cada peça para entender o que ela faz.

A jornada de uma consulta
🔎 O que acontece quando você roda um SELECT
A Peça 1
📇 O catálogo mora no Supabase

O Supabase é, no fundo, um PostgreSQL hospedado na nuvem com um painel bonito por cima — você cria um projeto gratuito, ganha um banco Postgres pronto em segundos, sem precisar rodar docker run postgres na sua máquina. É exatamente esse banco que o DuckLake usa como catálogo: nele ficam tabelas internas (ducklake_table, ducklake_snapshot, ducklake_data_file etc.) que guardam o índice — nomes de tabelas, colunas, esquemas e qual arquivo Parquet pertence a qual snapshot. Os dados de verdade (as linhas da sua tabela de vendas) nunca ficam nessas tabelas — só a "ficha catalográfica" delas.

🧸 Explicando pra uma criança
Imagine uma caixa de brinquedos enorme guardada na garagem (o S3). Do lado, na sua mesa, tem um caderninho (o Supabase) que diz: "o carrinho azul está na caixa 3, gaveta 2". Você nunca precisa abrir a caixa inteira pra saber onde está o carrinho — só olha o caderninho.
🔌 Pooler de conexão
O Supabase oferece um endereço de connection pooler (porta 6543) além da conexão direta (porta 5432). Para pipelines com muitas conexões curtas (ETL, funções serverless), prefira o pooler — evita esgotar o limite de conexões do Postgres.
⚠️ A armadilha mais comum: o formato do DSN

É natural copiar a "Connection string" do painel do Supabase, que vem no formato postgresql://user:pass@host:porta/db — e colar direto no ATTACH do DuckLake. Isso falha. O DuckLake espera o formato libpq (pares chave=valor), não uma URL.

A Peça 2
🪣 Os dados moram no AWS S3

Enquanto o catálogo guarda "quem é quem", o AWS S3 guarda os bytes de verdade: os arquivos .parquet com as linhas da sua tabela. Um bucket S3 funciona como aquela caixa gigante na garagem — aceita quantidade praticamente ilimitada de arquivos, é barato por gigabyte, e qualquer motor de consulta (DuckDB, Spark, Athena, Trino) consegue ler os mesmos arquivos por ali, sem precisar "pedir licença" a um servidor de banco de dados.

📦 O bucket
Um bucket é só uma "gaveta" com nome único no mundo todo. Dentro dele, o DuckLake organiza os arquivos Parquet em pastas por tabela e por snapshot — algo como s3://meu-bucket-lakehouse/main/ducklake-data/nome_da_tabela/.
🔑 Credenciais
O DuckDB precisa de uma SECRET do tipo S3 com sua KEY_ID, SECRET e a REGION do bucket — as mesmas credenciais IAM que você usaria com o boto3 ou a AWS CLI.
sqlcopiar-- credencial de acesso ao AWS S3, dentro do próprio DuckDB CREATE OR REPLACE SECRET aws_s3 ( TYPE S3, KEY_ID 'AKIAIOSFODNN7EXAMPLE', SECRET 'wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY', REGION 'sa-east-1' );
✅ Boa prática

Nunca escreva a chave direto no SQL de produção — use variáveis de ambiente (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY) ou uma SECRET do tipo CREDENTIAL_CHAIN, e restrinja a política IAM do bucket só às ações que o pipeline realmente precisa (s3:GetObject, s3:PutObject, s3:ListBucket).

Ligando as Peças
🔌 Um único ATTACH liga tudo

Com o catálogo (Supabase) e o armazenamento (S3) prontos, o DuckLake conecta os dois com um único comando ATTACH. A partir daí, o DuckDB passa a enxergar o lakehouse inteiro como se fosse um banco comum — você cria schemas, tabelas, roda INSERT, SELECT, tudo em SQL puro.

sqlcopiarINSTALL ducklake; INSTALL postgres; LOAD ducklake; -- o catálogo fica no Supabase (Postgres), os dados ficam no bucket S3 ATTACH 'ducklake:postgres:host=aws-0-sa-east-1.pooler.supabase.com port=6543 user=postgres.xxxxxxxxxxxx password=SUASENHA dbname=postgres' AS northwind_lake (DATA_PATH 's3://meu-bucket-lakehouse/'); USE northwind_lake; CREATE SCHEMA IF NOT EXISTS bronze; CREATE SCHEMA IF NOT EXISTS silver; CREATE SCHEMA IF NOT EXISTS gold;
🧩 O que o ATTACH faz nos bastidores
Cria (se não existirem) as tabelas internas do DuckLake dentro do banco Postgres do Supabase — ducklake_metadata, ducklake_table, ducklake_snapshot, ducklake_data_file — e passa a registrar ali toda mudança de esquema e todo commit de dados.
📛 Apelido (alias)
O AS northwind_lake é só um apelido local — você pode ter vários lakehouses (vários ATTACH) na mesma sessão do DuckDB, cada um com seu próprio catálogo Supabase e seu próprio bucket S3.
O Superpoder
🕰️ Snapshots: uma "foto" a cada mudança

Cada INSERT, UPDATE ou DELETE vira uma nova linha na tabela ducklake_snapshot do Supabase — uma "foto" com número de versão e carimbo de data/hora. Como essas fotos nunca são apagadas, você pode voltar no tempo e consultar a tabela exatamente como ela estava em qualquer momento do passado. Organizando o Lago
🥉 Pipeline Bronze → Silver → Gold

Dentro do mesmo lakehouse, é comum organizar as tabelas em três "camadas" cada vez mais refinadas — a chamada arquitetura medalhão. Pense como cozinhar: Bronze é a feira chegando crua na cozinha, Silver é tudo lavado, cortado e padronizado, e Gold é o prato pronto pra servir. Clique em "rodar pipeline" para ver os dados passando por cada etapa.

sqlcopiar-- BRONZE: carga crua, sem transformar nada CREATE TABLE bronze.pedidos AS SELECT * FROM read_csv_auto('pedidos.csv');
sqlcopiar-- SILVER: tipos corretos + colunas calculadas CREATE TABLE silver.pedidos AS SELECT CAST(order_id AS INTEGER) order_id, CAST(preco*qtd*(1-desconto) AS DOUBLE) valor_liquido FROM bronze.pedidos;
sqlcopiar-- GOLD: agregado pronto pro dashboard CREATE TABLE gold.receita_por_mes AS SELECT date_trunc('month', data) mes, sum(valor_liquido) receita FROM silver.pedidos GROUP BY 1;

Passo 1 — conectar Supabase (catálogo) + S3 (dados)
pythoncopiarimport duckdb, os con = duckdb.connect() con.execute("INSTALL ducklake; INSTALL postgres; LOAD ducklake;") # credenciais via variáveis de ambiente, nunca hardcoded con.execute(f""" CREATE OR REPLACE SECRET aws_s3 ( TYPE S3, REGION '{os.environ["AWS_REGION"]}', KEY_ID '{os.environ["AWS_ACCESS_KEY_ID"]}', SECRET '{os.environ["AWS_SECRET_ACCESS_KEY"]}' ); """) dsn = (f"postgres:host={os.environ['SUPABASE_HOST']} " f"port=6543 user={os.environ['SUPABASE_USER']} " f"password={os.environ['SUPABASE_PASSWORD']} dbname=postgres") con.execute(f"ATTACH 'ducklake:{dsn}' AS lake (DATA_PATH 's3://meu-bucket-lakehouse/')") con.execute("USE lake;") for schema in ("bronze", "silver", "gold"): con.execute(f"CREATE SCHEMA IF NOT EXISTS {schema}")
Passo 2 — Bronze: carregar os CSVs do Northwind, sem transformar nada
pythoncopiar# cada CSV do Northwind vira uma tabela bronze, tal como chegou FILES = { "customers": "customers.csv", "orders": "orders.csv", "order_details": "order_details.csv", "products": "products.csv", "categories": "categories.csv", } for table, filename in FILES.items(): con.execute(f""" CREATE OR REPLACE TABLE bronze.{table} AS SELECT * FROM read_csv_auto('dados/northwind/{filename}', HEADER=TRUE, SAMPLE_SIZE=-1); """)
Passo 3 — Silver: tipos corretos + valor líquido calculado por item vendido
sqlcopiar-- valor líquido de cada linha de pedido, já descontado o desconto CREATE OR REPLACE TABLE silver.order_details AS SELECT CAST(od.OrderID AS INTEGER) AS order_id, CAST(od.ProductID AS INTEGER) AS product_id, CAST(od.Quantity AS INTEGER) AS quantity, CAST(od.UnitPrice * od.Quantity * (1 - od.Discount) AS DOUBLE) AS net_amount FROM bronze.order_details od; -- pedidos com datas e país de entrega já tipados CREATE OR REPLACE TABLE silver.orders AS SELECT CAST(OrderID AS INTEGER) AS order_id, CAST(CustomerID AS VARCHAR) AS customer_id, CAST(EmployeeID AS INTEGER) AS employee_id, CAST(OrderDate AS DATE) AS order_date, CAST(ShipCountry AS VARCHAR) AS ship_country FROM bronze.orders;
Passo 4 — Gold: modelo estrela (fact_sales + dimensões) e uma tabela flat pronta pra dashboard
sqlcopiarCREATE OR REPLACE TABLE gold.dim_products AS SELECT p.ProductID AS product_id, p.ProductName AS product_name, c.CategoryName AS category_name FROM bronze.products p JOIN bronze.categories c ON c.CategoryID = p.CategoryID; CREATE OR REPLACE TABLE gold.fact_sales AS SELECT o.order_id, o.order_date, o.ship_country, od.product_id, od.quantity, od.net_amount FROM silver.order_details od JOIN silver.orders o ON o.order_id = od.order_id; -- tabela desnormalizada: uma linha por venda, pronta pro dashboard/API CREATE OR REPLACE TABLE gold.sales_flat AS SELECT f.order_date, f.ship_country, d.product_name, d.category_name, f.quantity, f.net_amount FROM gold.fact_sales f JOIN gold.dim_products d ON d.product_id = f.product_id;
Passo 5 — consultas analíticas prontas
sqlcopiar-- top 5 produtos por receita líquida SELECT product_name, round(sum(net_amount), 2) AS receita FROM gold.sales_flat GROUP BY 1 ORDER BY 2 DESC LIMIT 5;
sqlcopiar-- receita líquida por país de entrega SELECT ship_country, round(sum(net_amount), 2) AS receita FROM gold.sales_flat GROUP BY 1 ORDER BY 2 DESC;

Sem Python Nenhum
⌨️ O mesmo pipeline, direto no terminal (CLI do DuckDB)

Nem sempre você quer escrever Python só pra rodar um pipeline. O duckdb também é um shell SQL interativo — os mesmos comandos ATTACH, CREATE TABLE e SELECT funcionam ali dentro, tal e qual no script Python, mais alguns "dot-commands" exclusivos do terminal pra explorar o catálogo e exportar resultados.

Abrindo o CLI e conectando no lakehouse
bashcopiar# instala o CLI (macOS) e abre o shell interativo brew install duckdb duckdb -- a partir daqui, tudo é digitado no prompt "D " INSTALL ducklake; INSTALL postgres; LOAD ducklake; CREATE OR REPLACE SECRET aws_s3 ( TYPE S3, REGION 'sa-east-1', KEY_ID 'AKIAIOSFODNN7EXAMPLE', SECRET 'wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY' ); ATTACH 'ducklake:postgres:host=aws-0-sa-east-1.pooler.supabase.com port=6543 user=postgres.xxxxxxxxxxxx password=SUASENHA dbname=postgres' AS lake (DATA_PATH 's3://meu-bucket-lakehouse/'); USE lake;
Dot-commands úteis pra explorar o catálogo
sqlcopiar-- lista todas as tabelas visíveis (bronze/silver/gold) .tables -- mostra o DDL de uma tabela específica .schema gold.sales_flat -- formata a saída como uma caixa bonitinha no terminal .mode box SELECT * FROM gold.sales_flat LIMIT 5; -- liga o cronômetro, útil pra comparar performance .timer on

sqlcopiar-- redireciona a saída da próxima consulta pra um arquivo .mode csv .output receita_por_pais.csv SELECT ship_country, round(sum(net_amount),2) receita FROM gold.sales_flat GROUP BY 1 ORDER BY 2 DESC; -- volta a imprimir na tela, em formato de tabela .output stdout .mode duckbox
ℹ️ CLI ou Python — quando usar cada um

O CLI brilha em exploração ad-hoc, depuração rápida e scripts de shell/CI. O Python brilha quando o pipeline precisa se integrar com outra coisa — um orquestrador (Airflow, Dagster), uma API (FastAPI) ou testes automatizados. Debaixo do capô, os dois rodam exatamente o mesmo SQL, contra o mesmo catálogo no Supabase e o mesmo bucket no S3 — a escolha é só sobre onde o comando é digitado.

Aprendendo com Cicatrizes
⚠️ Armadilhas e boas práticas

Trocar a infraestrutura por trás de um lakehouse parece trivial no papel — "é só S3 de novo" — mas os detalhes de configuração é que decidem se o pipeline roda uma vez no tutorial ou roda todo dia em produção.

⚠️ DSN no formato errado

Colar a "Connection string" (postgresql://...) do painel do Supabase direto no ATTACH falha silenciosamente ou com erro confuso. Sempre converta para o formato postgres:host=... port=... user=... password=... dbname=... que o DuckLake espera.

⚠️ Esgotar conexões do Supabase

O plano gratuito do Supabase tem um limite baixo de conexões diretas simultâneas. Pipelines que abrem/fecham conexão a cada lote devem usar o connection pooler (porta 6543), não a porta direta 5432.

✅ Teste em escala antes de confiar

Rodar 10 linhas no notebook e declarar vitória não garante nada sobre 10 milhões de linhas em produção. Valide o pipeline com um volume realista antes de trocar o ambiente de testes pelo definitivo — atritos de integração aparecem justamente na escala.

✅ IAM de mínimo privilégio

A credencial AWS usada pelo DuckDB deve poder só o necessário no bucket (GetObject, PutObject, ListBucket num prefixo específico) — nunca uma chave de administrador da conta inteira.
