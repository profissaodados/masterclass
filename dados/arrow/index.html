O formato que ensinou as ferramentas de dados a parar de se traduzir

Apache Arrow é uma especificação de memória colunar, criada em 2016 por um grupo de mantenedores de projetos como Pandas, Spark, Drill e Impala. Ele não guarda arquivo nenhum em disco — ele descreve exatamente como os bytes de uma tabela devem ficar organizados na RAM, de um jeito padronizado o suficiente para que Python, R, Java, C++, Rust e Go leiam os mesmos bytes, sem copiar nem converter nada. Nesta aula vamos abrir essa memória por dentro: bits de nulo, buffers, RecordBatches, o formato de arquivo IPC e a mágica do zero-copy.

O Problema
🗼 A Torre de Babel dos dados

Imagine seis crianças que falam línguas diferentes tentando brincar juntas: cada par precisa de um tradutor só para aquela dupla. É assim que as ferramentas de dados viviam antes do Arrow — Pandas guarda dados de um jeito, Spark de outro, cada driver de banco de outro. Toda vez que os dados passam de uma ferramenta para outra, alguém precisa serializar (empacotar em bytes de um formato) e desserializar (desempacotar para o formato de destino) — um trabalho que não ensina nada sobre os dados, só custa tempo e memória duplicada.

Experimente: quantos "tradutores" cada mundo precisa?
A ideia central do Arrow, em uma frase

Em vez de N ferramentas precisarem de N×(N−1)/2 conversores entre si, todas concordam em ler e escrever o mesmo layout de bytes na memória. Isso transforma um problema que cresce quadraticamente em um problema que cresce linearmente — e, melhor ainda, permite que a "tradução" simplesmente não aconteça: um ponteiro de memória é compartilhado, não copiado.

Fundamentos
🧱 Linhas vs. colunas — agora dentro da RAM

O mesmo raciocínio do Parquet em disco vale, de forma ainda mais crítica, dentro da memória: um objeto Python "linha a linha" (uma lista de dicionários, por exemplo) espalha os campos de cada registro em posições de memória distantes umas das outras. O Arrow guarda cada coluna como um bloco contíguo de bytes — o que não só evita ler campos inúteis, como também deixa o processador usar SIMD (operações vetorizadas que processam vários valores de uma vez) e aproveitar melhor a cache da CPU.

A Peça Fundamental
🔬 Anatomia de um Arrow Array

Tudo no Arrow é construído em cima de um único conceito: o Array. Um Array é sempre a mesma receita — um length (quantos valores), um null_count (quantos são nulos) e uma lista pequena de buffers (blocos de bytes crus). Para um tipo simples de tamanho fixo, como Int32, existem exatamente dois buffers: o bitmap de validade (quem é nulo) e o buffer de valores (os números em si, lado a lado). Repare: mesmo as posições nulas reservam espaço no buffer de valores — o Arrow nunca "pula" bytes, só marca que aquele valor não deve ser lido.

💡 Por que um bitmap e não, por exemplo, um valor sentinela como -1 ou NaN? Porque um bit por valor custa 8× menos memória do que um byte por valor, funciona igual para qualquer tipo (inteiro, texto, data, booleano...) e nunca é confundido com um valor real. É por isso que o Arrow consegue representar nulos de forma universal e barata — cada Array reserva só ceil(length / 8) bytes para o bitmap.

🧩 Os três campos que todo Array tem
length — quantos elementos o array tem, incluindo os nulos.
null_count — quantos desses elementos são nulos (calculado a partir do bitmap, guardado para consulta rápida).
buffers[] — os blocos de memória crua: bitmap de validade sempre em buffers[0], e um ou mais buffers de dados depois, dependendo do tipo.
⚡ Por que isso é rápido de verdade
Como não existe nenhum objeto Python (ou ponteiro solto) por valor — só bytes crus e contíguos — o processador consegue somar, filtrar ou comparar vários valores de uma vez só usando instruções SIMD, e o bitmap de validade pode ser testado com operações binárias extremamente baratas (AND, popcount) em vez de checar nulo valor a valor.
O Truque dos Offsets
📏 Tipos de tamanho variável: o buffer de offsets

Um Int32 sempre ocupa 4 bytes, então é fácil calcular onde cada valor começa. Mas e um texto (Utf8), onde "Ana" tem 3 letras e "Bruno" tem 5? O Arrow resolve isso com um terceiro buffer: o buffer de offsets — uma lista de números inteiros que diz onde, dentro de um único buffer de dados gigante, cada valor começa e termina. É a mesma ideia usada para List (listas dentro de uma coluna): os offsets marcam onde cada "sub-lista" começa.

Como ler o valor 1 ("Bruno") sem escanear nada

O leitor olha só para offsets[1] = 3 e offsets[2] = 8 e recorta o buffer de dados exatamente entre as posições 3 e 8: "AnaBrunoCarla"[3:8] = "Bruno". Nenhum separador, nenhuma varredura — apenas aritmética de ponteiros. É por isso que o mesmo mecanismo de offsets também representa colunas do tipo List<Int32>: os offsets marcam onde cada sub-lista começa dentro de um único array "achatado" de valores filhos.

Um Bit Por Valor
✅ Nulos: por que um bitmap muda tudo

Guardar "isto é nulo" parece trivial, mas a forma como cada sistema faz isso tem consequências enormes de performance e de memória. Compare as três abordagens mais comuns:

🐍 Objeto None (Python puro)
Cada valor é um ponteiro para um objeto na heap — um None é só mais um ponteiro, mas cada valor "normal" já custa muito mais que os bytes do número em si, e o processador não consegue vetorizar nada.
🔢 Valor sentinela (ex: NaN, -1)
Barato, mas ambíguo: só funciona para tipos que têm um valor "livre" sobrando (float tem NaN; inteiro não tem nada equivalente) e pode confundir um nulo de verdade com um dado real.
🏹 Bitmap de validade (Arrow)
1 bit por valor, separado dos dados, funciona igual para qualquer tipo (inteiro, texto, data, struct...) e permite testar milhões de nulos com poucas instruções de CPU usando operações bit a bit.

💡 Um detalhe curioso: se uma coluna não tem nenhum valor nulo, o Arrow nem se dá ao trabalho de alocar o buffer de validade — ele fica marcado como null_count = 0 e o buffer 0 vira um ponteiro nulo. Isso economiza memória exatamente nos casos (a maioria!) em que a coluna é totalmente preenchida.

🧬 Struct — "endereço" com rua e cidade
Um Struct<rua: Utf8, cidade: Utf8> não é um array de objetos — é dois Arrays Utf8 lado a lado (um para rua, um para cidade), com o mesmo length, mais um bitmap de validade só do Struct em si (para o caso raro de o endereço inteiro ser nulo). Ler só a cidade de todo mundo continua sendo uma leitura colunar pura, mesmo dentro de um tipo aninhado.
Organizando Vários Arrays
📦 Schema, RecordBatch e Table

Um Array sozinho é uma coluna. Para representar uma tabela de verdade, o Arrow empilha três conceitos: o Schema (nomes e tipos das colunas — o "contrato"), o RecordBatch (um Schema + um Array por coluna, todos com o mesmo length — um "pedaço" horizontal da tabela) e a Table (uma coleção de RecordBatches empilhados, todos com o mesmo Schema). Isso permite processar datasets enormes em pedaços (chunks), sem nunca precisar ter tudo na RAM de uma vez.

Do Papel Para o Byte
🔌 O formato IPC: Streaming e File

Até aqui, tudo vivia só na RAM. Mas às vezes você precisa persistir Arrow em disco ou mandar pela rede — sem perder a promessa de zero-copy. É para isso que existe o formato IPC (Inter-Process Communication), com duas variantes: Streaming (uma sequência de mensagens, sem volta ao início — ótimo para redes) e File (o mesmo conteúdo, mais um rodapé no final que permite pular direto para qualquer RecordBatch — o formato por trás do arquivo .arrow / Feather V2). O File Format é o Streaming Format com uma capa a mais: magic number no início e no fim, e um footer que permite seek direto para qualquer RecordBatch sem ler os anteriores.
🔬 Zoom: o Magic Number "ARROW1"

⚠️ Repare que o Streaming Format não tem footer nem magic number — de propósito. Ele é pensado para ser lido uma vez, na ordem, direto de um socket de rede (por exemplo, dentro do Arrow Flight, na próxima seção), onde "voltar ao início" não existe. Já o File Format assume um arquivo real em disco, onde vale a pena pagar o custo extra do footer para ganhar acesso aleatório.

A Mágica de Verdade
⚡ Zero-copy: por que isso é rápido de um jeito absurdo

Quando duas ferramentas diferentes (Pandas e DuckDB, por exemplo) já entendem o mesmo layout de bytes do Arrow, passar dados de uma para outra não exige nenhuma tradução — apenas compartilhar o endereço de memória onde os buffers já estão. É a diferença entre fotocopiar um livro inteiro para emprestar, e simplesmente apontar para a estante e dizer "pode ler esse aqui".

🧠 Dentro do mesmo processo/linguagem
Um pandas.DataFrame apoiado em Arrow (pandas 2.x com dtype_backend="pyarrow") pode entregar seus buffers para o DuckDB, que consulta os mesmos bytes na RAM — sem criar uma cópia da tabela inteira.
🌐 Entre linguagens diferentes
A Arrow C Data Interface define uma estrutura C minúscula e estável (ponteiros + metadados) que permite Python, R e Rust compartilharem o mesmo bloco de memória sem nenhuma das linguagens precisar entender a linguagem da outra — só o layout Arrow.
Zero-Copy Também Pela Rede
✈️ Arrow Flight: o protocolo de rede nativo do Arrow

Zero-copy dentro de uma máquina é ótimo, mas dados também precisam viajar entre máquinas. Bancos tradicionais respondem consultas via ODBC/JDBC, que serializam linha a linha — lento para grandes volumes analíticos. O Arrow Flight é um protocolo sobre gRPC que transmite dados já em RecordBatches Arrow, em paralelo, direto para dentro da memória do cliente.

1
Cliente chama GetFlightInfo perguntando "quero os dados de tal consulta/tabela" e recebe de volta um ou mais tickets (um por partição dos dados, permitindo paralelismo).
2
Cliente chama DoGet com um ticket e recebe de volta um stream IPC — a mesma sequência de mensagens Schema + RecordBatches que vimos na seção anterior, agora trafegando dentro de chamadas gRPC.
3
Os RecordBatches chegam já prontos para uso — sem parsing de texto, sem conversão de tipos — e podem ser processados em paralelo por múltiplas threads, cada uma consumindo um stream.
4
DoPut faz o caminho inverso: o cliente empurra RecordBatches para o servidor, útil para ingestão em massa de dados analíticos.

💡 Flight SQL é uma camada por cima do Flight que padroniza como pedir metadados de bancos (tabelas, catálogos, tipos de coluna) — a ideia é virar um substituto moderno do ODBC/JDBC para cargas analíticas, já nativamente colunar e paralelo.

Categorias Como Tipo de Primeira Classe
🔠 DictionaryArray: categorias com poucos valores únicos

Quando uma coluna de texto repete os mesmos valores várias vezes (categoria, status, país...), o Arrow pode representá-la como um DictionaryArray: um array de índices inteiros pequenos + um array separado de valores únicos (o "dicionário"). Diferente do Parquet, aqui isso não é um truque escondido de compressão — é um tipo de dado real no sistema de tipos do Arrow, o mesmo que aparece como category no pandas e factor no R.

Não São Concorrentes
⚖️ Arrow vs. Parquet — memória vs. disco

Confusão comum: Arrow e Parquet não competem entre si — eles resolvem problemas em pontos diferentes do mesmo pipeline, e na prática quase sempre aparecem juntos.

AspectoApache ArrowApache Parquet
Onde viveNa RAM, enquanto o programa rodaNo disco (ou object storage como S3), persistido

Como colaboramUm motor lê um arquivo .parquet do disco e descomprime direto para Arrays Arrow na RAM — a "moeda comum" que todas as ferramentas seguintes (pandas, DuckDB, Spark) já entendem sem conversão.

✅ Regra prática: use Parquet para guardar dados no disco por muito tempo; use Arrow para representar esses dados enquanto eles estão sendo processados, movidos entre bibliotecas, ou trafegando pela rede.

Quem Já Fala Arrow
🌐 O ecossistema construído em cima do Arrow

O Arrow virou a "língua franca" silenciosa por trás de boa parte do ecossistema moderno de dados.

🐼 pandas 2.x+
Suporte a dtype_backend="pyarrow": colunas apoiadas diretamente em Arrays Arrow, com nulos e strings muito mais eficientes que o NumPy clássico.
🦀 Polars
DataFrame construído desde o início sobre o Arrow (via Rust), aproveitando o layout colunar para paralelismo e vetorização nativos.
🦆 DuckDB
Lê e escreve Arrow nativamente — pode escanear uma Arrow Table em memória como se fosse uma tabela SQL, sem cópia.
⚡ Apache Spark
Usa Arrow internamente para acelerar toPandas() e Pandas UDFs, evitando serialização linha a linha entre JVM e Python.
📊 R {arrow}
Traz o mesmo formato de memória para dentro do R, permitindo trocar dados com Python/Pandas sem conversão.
🔌 ADBC
Arrow Database Connectivity — uma alternativa moderna ao ODBC/JDBC onde os drivers já devolvem os resultados como Arrow.
✈️ Flight SQL
Protocolo de rede para bancos analíticos trocarem consultas e resultados já em RecordBatches Arrow.
🔄 Interchange Protocol
O método __arrow_c_array__/__arrow_c_stream__ permite qualquer biblioteca Python compartilhar dados via Arrow sem depender do PyArrow como dependência obrigatória.
