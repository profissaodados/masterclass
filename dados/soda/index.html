Soda é uma plataforma de qualidade de dados que fica de olho nas suas tabelas o tempo todo — não só uma vez. Você escreve regras simples, em YAML (a linguagem SodaCL), sobre como os dados deveriam se comportar — "essa coluna não pode ter nulo", "esse país tem que estar numa lista", "essa tabela não pode ficar mais de 24h sem atualizar" — e o Soda roda essas regras em scans repetidos, sobe o resultado para o Soda Cloud, monta histórico e dispara alerta assim que algo foge do combinado. Não é um inspetor que passa uma vez; é um alarme que fica ligado.

Fundamentos
🧸 Por que qualidade de dados importa (explicado como para uma criança)

Pense numa fábrica de refrigerantes de verdade — sim, daquele tipo de "soda" mesmo. Antes de uma garrafa sair pra loja, alguém garante que o gás está certo, o rótulo não está torto, a validade não venceu. E essa checagem não acontece uma vez só quando a fábrica abre: ela roda em toda garrafa, todo santo dia, porque uma máquina pode desregular do nada na terça-feira, mesmo tendo passado perfeita na segunda. A ferramenta Soda brinca exatamente com essa ideia — só que em vez de garrafas, ela fiscaliza linhas de uma tabela, sem parar, dia após dia.

🕵️ Checagem pontual
Alguém roda uma consulta manual "de vez em quando" pra conferir se está tudo bem. Funciona até o dia em que ninguém lembra de rodar de novo.
🐌 Piora aos poucos
Nem todo problema de dado é um erro gritante — às vezes é uma taxa de nulos subindo 1% por semana, silenciosa demais pra alguém perceber olhando só uma vez.
🔥 Descoberto tarde demais
Sem monitoramento contínuo, o problema só aparece quando um número no painel do diretor já parece estranho — dias ou semanas depois de ter começado.
🚨
Pensando como criança

Imagine o detector de fumaça lá em casa. Ele não é um bombeiro que visita sua casa uma vez por ano pra cheirar o ar — ele fica ligado o tempo todo, e apita na hora que sente cheiro de queimado, mesmo que ninguém esteja olhando. O Soda quer ser esse detector de fumaça para os seus dados: sempre ligado, sempre checando, avisando o time assim que algo sai do esperado — não um mês depois.

Fundamentos
🔍 O que é o Soda?

Soda nasceu como um projeto open source — o Soda SQL, lançado em 2020 — que evoluiu para o Soda Core e a linguagem declarativa SodaCL (Soda Checks Language), além de uma camada paga de visualização e colaboração, o Soda Cloud. Nos últimos anos a plataforma vem se consolidando em torno dos Data Contracts: um único arquivo que combina o schema esperado de uma tabela com as regras de qualidade que ela precisa cumprir, tratado como um acordo formal entre quem produz e quem consome o dado. Em qualquer uma dessas versões, a ideia central não muda: você declara o que espera dos dados, e o Soda cuida de checar isso de verdade, repetidamente.

📜 Declarativo (YAML)
Você escreve o que espera — missing_count(email) = 0 — não um script inteiro de validação linha a linha. O Soda cuida do "como".
🔌 Motor plugável
O mesmo check roda sobre Postgres, Snowflake, BigQuery, Databricks, Spark ou dezenas de outras fontes — você troca o banco sem reescrever as regras.
☁️ Cloud opcional
O CLI (Soda Core) roda 100% sozinho, sem depender de nada além do terminal. O Soda Cloud entra por cima quando você quer histórico, gráfico e alerta automático.
🛒
Pensando como criança

Um arquivo de checks do Soda é que nem uma lista de compras que você entrega pra alguém no mercado: "compra 6 ovos, sem casca rachada; leite dentro da validade; pão fresquinho, feito hoje". A pessoa não precisa que você explique como checar cada item — a lista já diz exatamente o que precisa ser verdade. O Soda faz esse papel dentro do banco de dados.

A Menor Peça
🔬 Anatomia de um Check (SodaCL)

Um Check é a unidade mais básica do Soda: uma única linha, em YAML, que descreve uma expectativa sobre uma métrica de uma tabela. A sintaxe segue o padrão <métrica>(<coluna>) <operador> <valor> — dá quase pra "ler" a regra em voz alta, mesmo sem nunca ter visto Soda antes.

yaml — checks.ymlcopiarchecks for pedidos: - row_count > 0 - missing_count(email) = 0 - duplicate_count(id) = 0 - invalid_count(pais) = 0: valid values: [BR, US, PT, AR] - freshness(data_pedido) < 24h
📏 Métrica
row_count, missing_count, duplicate_count, freshness — o que está sendo medido na tabela ou coluna.
⚖️ Operador
>, =, <, between — o limite que a métrica precisa respeitar para o check passar.
🎯 Configuração extra
valid values, valid min, valid max — parâmetros opcionais que refinam o que conta como um valor válido.
⚽
Pensando como criança

Um check é igualzinho a uma regra de um jogo: "a bola não pode sair da linha". O juiz (o Soda) não fica inventando novas regras no meio do jogo — ele só apita quando a regra escrita é quebrada, nem mais nem menos. Se ninguém escreveu a regra "a bola não pode ser azul", uma bola azul passa reto, mesmo estranha.

💡 Cada check é ao mesmo tempo um teste (roda e retorna passou/falhou) e uma documentação (o YAML já explica a regra em texto quase legível). Não é preciso escrever SQL manualmente — embora dê, para regras que nenhuma métrica pronta cobre (veja a seção de Tipos de Checks).

Onde a Checagem Roda de Verdade
🔎 O Scan: não uma vez, sempre de novo

Um checks.yml sozinho é só uma lista de regras — ele não faz nada até um scan rodar. O scan é a execução de fato: o Soda conecta na fonte de dados, calcula cada métrica, compara com o limite definido e decide, check por check, se passou ou falhou. A diferença que mais importa na prática: o scan normalmente é agendado — via cron, Airflow, dbt Cloud, GitHub Actions — rodando de hora em hora ou uma vez por dia, e não só quando alguém lembra de rodar manualmente.

bashcopiar# roda todos os checks de checks.yml contra a fonte "pedidos_datasource" soda scan -d pedidos_datasource -c configuration.yml checks.yml # o scan termina com exit code != 0 se algum check falhar — # o suficiente pra travar um pipeline de propósito echo $?
🪥
Pensando como criança

Um scan agendado é que nem escovar os dentes todo dia, não só quando começa a doer. Checar os dados de vez em quando resolve o problema de hoje; checar toda vez evita que o problema apareça no meio da noite, sem ninguém olhando.

⏱️ Scan agendado
Roda sozinho, em intervalo fixo (ex: a cada hora), sem depender de alguém lembrar.
🔗 Scan no pipeline
Chamado como mais um passo de um DAG do Airflow ou de um job dbt — se falhar, o pipeline para antes de propagar dado ruim.
🖱️ Scan sob demanda
Rodado manualmente no terminal, útil para testar um checks.yml novo antes de agendá-lo de verdade.

A Nova Geração
📜 Data Contracts: schema + qualidade, num acordo só

A plataforma Soda vem migrando o centro de gravidade: em vez de só um checks.yml solto num repositório, a peça central passa a ser um Data Contract — um arquivo versionado no Git que combina, num só lugar, o schema esperado de uma tabela e as regras de qualidade que ela precisa cumprir. A ideia é que esse arquivo funcione como uma promessa formal entre quem produz o dado (engenharia) e quem consome (BI, outro time de dados, o negócio) — engenheiros trabalham direto no Git, enquanto usuários de negócio conseguem revisar e ajustar o mesmo contrato pela interface visual, sem escrever YAML.

yaml — contrato ilustrativocopiardataset: pedidos schema: - column: id type: integer - column: email type: varchar - column: valor_pedido type: double checks: - missing_count(email) = 0 - duplicate_count(id) = 0 - invalid_count(valor_pedido) = 0: valid min: 0.01
🧑‍💻 Engenharia no Git
O contrato é código: versionado, revisado em Pull Request, com histórico de quem mudou o quê e por quê — igual qualquer outro arquivo do repositório.
🧑‍💼 Negócio na interface
O mesmo contrato pode ser lido e ajustado por quem não programa, direto na UI do Soda Cloud — sem depender de abrir um Pull Request para uma mudança simples.
🤝
Pensando como criança

Um contrato de dados é igual a uma promessa escrita entre dois amigos: "eu te entrego a boneca do jeitinho combinado, sem faltar peça". Se um dos dois quebra a promessa, não precisa ninguém desconfiar ou brigar — está escrito, e todo mundo fica sabendo na hora que algo saiu do combinado.

💡 A sintaxe exata evolui conforme a plataforma é atualizada — o conceito que fica é o que importa: schema e regras de qualidade vivendo juntos, num único contrato versionado, em vez de testes soltos e desconectados da definição da tabela.

💡 Duas lições do caminho

1) Python 3.12 removeu o módulo distutils, mas o Soda Core 3.5.x ainda importa distutils.util por baixo dos panos — o projeto inclui um shim mínimo em _compat/ pra contornar isso, sem mexer no venv. 2) missing_count por padrão só conta valores NULL, não string vazia '' — foi preciso declarar missing values: [''] explicitamente para o check de e-mail pegar as duas linhas vazias de propósito.

Checklist
✅ Boas Práticas
🎯 Comece pelos checks que mais doem
Não tente cobrir 100% das colunas no primeiro dia. Comece pelas 3-4 regras que, se quebrarem, causam o maior estrago — nulidade de chaves, unicidade e freshness das tabelas críticas.
🎚️ Use valid values/min/max com intenção
Dados reais raramente são 100% perfeitos. Definir limites conscientemente é melhor do que uma regra rígida demais que quebra o pipeline toda semana à toa.
🔔 Conecte a um canal de alerta de verdade
Um check que falha silenciosamente, sem notificar ninguém, tem o mesmo efeito de não ter check nenhum.
📜 Trate o checks.yml/contrato como código
Versionado no Git, revisado em Pull Request — mudanças em regras de qualidade merecem o mesmo cuidado que mudanças no pipeline.

⚠️ Soda valida a forma dos dados (volume, nulos, unicidade, faixas, frescor) e ajuda a flagar desvios estatísticos — ele não substitui a validação de regra de negócio profunda, que geralmente exige contexto humano. Use-o como a primeira linha de defesa, não como a única.
