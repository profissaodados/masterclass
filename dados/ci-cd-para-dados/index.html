Seus dados também merecem uma esteira de fábrica, não uma corrida de obstáculos.

CI/CD significa Integração Contínua (Continuous Integration) e Entrega/Implantação Contínua (Continuous Delivery/Deployment). No mundo de software, é a prática de testar e publicar código automaticamente, em vez de um humano copiar arquivos manualmente para produção. No mundo de dados, a ideia é a mesma — só que em vez de testar um botão de app, testamos se uma tabela, uma métrica ou um modelo dbt continuam corretos antes de deixá-los chegar ao dashboard que o diretor olha toda manhã. Hoje vamos destrinchar isso com muita analogia simples, diagrama visual e um simulador de pipeline que você mesmo vai "quebrar" e "consertar".

Fundamentos
🎒 Primeiro, o básico: o que são CI e CD?

Imagine uma fábrica de brinquedos com uma esteira: cada brinquedo passa por várias estações — uma verifica se a pintura está certa, outra testa se as peças não soltam, outra empacota. Só se passar por todas as estações o brinquedo chega até a loja. Ninguém carrega o brinquedo na mão, estação por estação, torcendo para não esquecer nenhuma etapa. É exatamente isso que CI/CD faz com o seu código e com os seus dados: transforma um processo manual, arriscado e cheio de "esqueci de testar isso" numa esteira automática, sempre igual, sempre completa.

🔍 CI — Integração Contínua
Toda vez que alguém termina um pedacinho do trabalho (uma nova métrica, uma correção), o código é testado automaticamente assim que chega — não só "quando der". É como um professor que corrige cada exercício assim que o aluno entrega, em vez de corrigir tudo de uma vez só no fim do bimestre.
🚀 CD — Entrega/Implantação Contínua
Depois que o trabalho passa em todos os testes, ele é publicado automaticamente — sem alguém ter que copiar arquivo, rodar script na mão ou lembrar dos passos. É o dever de casa aprovado indo direto pro mural da escola sozinho.
🏭
Pensando como criança

Pensa numa linha de montagem de brinquedos numa fábrica: cada estação da esteira faz UMA verificação (a pintura está boa? as peças não soltam?) e só deixa passar pra frente o que está certinho. Se alguma estação encontra um problema, ela para a esteira ali mesmo — o brinquedo quebrado nunca chega até a caixa que vai pra loja. CI é a esteira cheia de estações de verificação. CD é a parte da esteira que empacota e manda pra loja sozinha, sem ninguém precisar empurrar a caixa à mão.

Esse é o "espinhaço" da aula de hoje — o pipeline completo, do código até o dado publicado. Vamos abrir cada uma dessas estações, uma por uma, nas próximas seções:

O Gatilho de Tudo
❓ O problema: publicar dados "na mão" é uma aposta

Sem CI/CD, o fluxo comum é: alguém edita uma query ou um modelo no notebook, testa "no olho" na própria máquina, e depois copia o código para produção manualmente — muitas vezes rodando um script direto no banco de produção, sexta à tarde, torcendo para nada quebrar. Não existe uma estação de verificação entre "terminei de editar" e "todo mundo da empresa está vendo esse número no dashboard".

🎲 Sem CI/CD — publicação manual
Uma pessoa roda o script direto na produção. Se ela esquecer um WHERE, duplicar uma linha ou digitar a coluna errada, ninguém percebe até o dashboard mostrar um número absurdo — e aí já é tarde, o diretor já viu.
✅ Com CI/CD — esteira automática
O mesmo script passa primeiro por testes automáticos (schema, duplicidade, nulos). Se algo está errado, o pipeline para sozinho antes de chegar em produção — o erro fica só no computador de quem editou, nunca no dashboard de ninguém.

⚠️ O nome popular para isso é "funciona na minha máquina": o código roda liso no notebook de quem escreveu, mas quebra em produção porque lá os dados são maiores, mais sujos ou vêm de uma fonte diferente. CI/CD existe justamente para pegar esse tipo de problema numa estação de teste, e não no colo do usuário final.

Compare o efeito de um mesmo erro de digitação — um JOIN duplicando linhas — nos dois cenários:

A Metade "CI"
🔍 Integração Contínua: testar antes de juntar

"Integração" quer dizer juntar o trabalho de uma pessoa ao trabalho de todo mundo. "Contínua" quer dizer que isso acontece toda vez que alguém termina um pedaço — não uma vez por semana. Na prática: cada vez que alguém sobe uma mudança (um commit) e abre um Pull Request, uma esteira automática roda uma bateria de verificações antes de deixar essa mudança se juntar ao código principal.

🧹 Lint / Estilo
Verifica se o código (SQL, Python, YAML) segue o padrão combinado pelo time — nomes de coluna, indentação, formatação. Rápido e barato de rodar.
🧪 Testes Automáticos
Roda os testes de transformação e de qualidade de dados (próxima seção) — a parte que realmente garante que o resultado está correto, não só bonito.
📦 Build
Compila/monta o pacote final — no mundo de dados, costuma ser "materializar" os modelos (rodar as queries de verdade contra um banco de teste) para confirmar que tudo executa sem erro.
📝
Analogia

É como entregar o dever de casa aos poucos, capítulo por capítulo, e o professor corrigir cada capítulo assim que chega — em vez de entregar o caderno inteiro só no último dia do ano e descobrir, tarde demais, que errou tudo desde o capítulo 2.

Um exemplo simples de teste automático de transformação, verificando se uma função de limpeza de CPF continua funcionando como esperado:

python · pytestcopiardef test_limpa_cpf_remove_pontuacao(): assert limpa_cpf("123.456.789-00") == "12345678900" def test_limpa_cpf_com_valor_nulo_retorna_none(): assert limpa_cpf(None) is None # roda automaticamente a cada push — ninguém precisa lembrar de testar na mão
O Coração do CI para Dados
🧪 Testando dados (não só código)

Aqui está a maior diferença entre CI/CD de software comum e CI/CD de dados: além de testar se o código funciona, é preciso testar se o resultado — a tabela, a métrica — continua fazendo sentido. Um código pode rodar sem erro nenhum e ainda assim produzir uma tabela com CPFs duplicados ou vendas negativas. Por isso, testes de dados olham para o dado em si, não só para a lógica que o gerou.

🗂️ Schema
A tabela tem as colunas certas, com os tipos certos? Uma coluna valor virou texto sem querer?
🕳️ Nulos
id_cliente nunca deveria estar vazio — se estiver, algo quebrou lá na origem.
👯 Duplicidade
Cada id_pedido deveria aparecer só uma vez. Um JOIN mal feito costuma duplicar linhas.
📏 Faixa de Valores
idade entre 0 e 120, valor_venda nunca negativo — limites de bom senso do negócio.

Exemplo de teste de qualidade rodando contra uma tabela recém-gerada — repare como cada linha do resultado vira um ✅ ou ❌ dentro do pipeline:

TesteRegraResultado
not_nullid_cliente nunca é nulopassou
uniqueid_pedido é único na tabelapassou
accepted_rangevalor_venda entre 0 e 100.000falhou — 3 linhas negativas

⚠️ Com esse resultado, o pipeline para na estação de testes — a tabela nova nem chega a substituir a de produção. O time recebe um alerta apontando exatamente qual teste falhou e em quais linhas.

Esse mesmo teste, escrito como código (padrão dbt, um dos jeitos mais comuns de declarar testes de dados hoje em dia):

yaml · dbt schema.ymlcopiarmodels: - name: fato_venda columns: - name: id_pedido tests: - unique - not_null - name: valor_venda tests: - dbt_utils.accepted_range: min_value: 0 max_value: 100000 - name: id_produto tests: - relationships: to: ref('dim_produto') field: id_produto
A Metade "CD"
🚀 Entrega/Implantação Contínua: publicar sem medo

Depois que tudo passou pela esteira de testes, o CD entra em ação: publicar a mudança onde as pessoas realmente vão usá-la — o banco de produção, o painel do BI, a API que outros times consomem. Existem dois níveis, com uma diferença sutil mas importante:

📮 Continuous Delivery (Entrega Contínua)
Toda mudança aprovada fica pronta para publicar a qualquer momento — mas alguém ainda aperta um botão para confirmar o "vai" para produção. Bom para dados sensíveis, onde um humano quer dar o aval final.
🤖 Continuous Deployment (Implantação Contínua)
Toda mudança aprovada vai para produção automaticamente, sem clique nenhum de humano. Exige muita confiança na esteira de testes — se os testes são bons o bastante, não precisa de gente no meio do caminho.
📬
Analogia

Delivery é a carta pronta, selada, em cima da mesa do carteiro — mas o carteiro só sai pra entregar quando alguém disser "pode ir". Deployment é a mesma carta, só que ela entra sozinha na caixa de correio assim que fica pronta, sem ninguém precisar avisar o carteiro.

Como publicar sem quebrar nada
🎯 Estratégias de Deploy para dados

Passar nos testes não é garantia de 100% — dados de produção às vezes surpreendem. Por isso existem estratégias para publicar mudanças gradualmente, reduzindo o risco de um erro afetar todo mundo de uma vez.

💥 Direto (Big Bang)
A tabela/modelo antigo é substituído de uma vez só, para todo mundo, no mesmo instante. Simples, mas se algo passou despercebido pelos testes, todo mundo sente o erro ao mesmo tempo.
🔵🟢 Azul-Verde (Blue-Green)
A versão nova é construída do lado, sem afetar ninguém, e só depois de validada, um "interruptor" troca quem está em produção — instantâneo e fácil de reverter.
🐤 Canário (Canary)
A versão nova recebe só uma fatia pequena do tráfego/uso primeiro. Se passar bem, a fatia cresce aos poucos até virar 100%.
🔵🟢 Blue-Green na prática (ex: dbt)
A tabela nova é criada com outro nome (fato_venda__novo), totalmente testada, e só então uma view ou um RENAME atômico faz o público passar a enxergar a versão nova — a antiga continua existindo, pronta para um retorno instantâneo se algo der errado.
🔵 Azul (atual)
fato_venda

🟢 Verde (nova)
fato_venda__novo

🐤 Canário na prática (ex: novo modelo de recomendação)
O novo pipeline roda em paralelo ao antigo, alimentando só 10% dos usuários. As métricas dos dois grupos são comparadas — só depois de confirmar que o novo está tão bom (ou melhor) é que a fatia aumenta.

💡 Nenhuma estratégia substitui os testes automáticos — elas são a segunda camada de proteção, para quando algo passa despercebido pelos testes mas só aparece com dado real de produção.

Onde cada coisa roda
🏗️ Ambientes: Dev, Staging e Produção

O pipeline não roda tudo no mesmo lugar. Cada mudança viaja por "salas" cada vez mais parecidas com o mundo real, e só a última sala é vista pelo público.

🧪 Dev (Desenvolvimento)
A "bancada de testes" de cada pessoa. Dados de amostra, pequenos e às vezes fictícios. Erros aqui não afetam ninguém além de quem está editando.
🎭 Staging (Homologação)
Uma cópia o mais parecida possível com produção — mesmo volume de dados (ou uma amostra representativa), mesma estrutura. É o "ensaio geral" antes da estreia.
🏛️ Produção
O ambiente real, que alimenta os dashboards e decisões de verdade. Só chega aqui o que já passou por CI e, geralmente, por staging.

Onde tudo começa
🌳 Git e branches: o ponto de partida do pipeline

Todo pipeline de CI/CD começa com uma mudança de código salva no Git. Em vez de editar direto a versão principal (main), cada mudança nasce numa branch separada — uma cópia paralela da história — que só se junta ("merge") à principal depois de revisada e aprovada.

🎨
Analogia

É como pedir uma folha de rascunho antes de escrever na prova de verdade. Você rabisca, erra, refaz à vontade no rascunho (a branch) — e só passa a limpo na prova (a main) quando o professor (o revisor do Pull Request) confere e aprova.

Linha do tempo: uma nova métrica sendo desenvolvida em paralelo

🔀 Pull Request (PR)
O pedido formal de "posso juntar meu rascunho na versão principal?". É nesse momento que o CI dispara os testes automaticamente, e colegas revisam o código antes de aprovar.
✅ Merge
A junção de fato: o rascunho vira parte oficial da main. É esse evento que costuma disparar o CD — a publicação automática em staging e, depois, em produção.
Mão na Massa
💻 Um pipeline real, com GitHub Actions + dbt

Vendo tudo isso escrito como configuração de verdade fica mais fácil enxergar que não tem mágica nenhuma — é um arquivo YAML dizendo "quando X acontecer, rode Y, e se Y passar, rode Z".

1Gatilho: disparar sempre que um Pull Request é aberto contra a main
yaml · .github/workflows/ci.ymlcopiarname: CI de Dados on: pull_request: branches: [main]
2Preparar o ambiente e instalar as dependências
yamlcopiarjobs: testar-dados: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - name: Instalar dbt run: pip install dbt-duckdb
3Rodar lint, depois os modelos, depois os testes de dados — nessa ordem
yamlcopiar - name: 🧹 Lint do SQL run: sqlfluff lint models/ - name: 📦 Build (materializar modelos em ambiente de teste) run: dbt run --target ci - name: 🧪 Testes de dados run: dbt test --target ci
4Só depois do merge: outro workflow publica em produção (CD)
yaml · .github/workflows/cd.ymlcopiarname: CD de Dados on: push: branches: [main] # só dispara depois do merge aprovado jobs: publicar-producao: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - name: 🚀 Publicar modelos em produção run: dbt run --target prod - name: 🧪 Confirmar qualidade em produção run: dbt test --target prod

✅ Repare: o mesmo comando dbt test roda duas vezes — uma vez no CI (ambiente de teste, antes do merge) e outra no CD (produção, depois do merge). Testar de novo em produção pega qualquer coisa que só aparece com o volume real de dados.

Quando, mesmo assim, algo dá errado
⏪ Rollback: o botão de desfazer

Nenhuma esteira de testes pega 100% dos problemas — às vezes o erro só aparece com o volume e a variedade real dos dados de produção. Por isso, todo pipeline maduro tem um plano B: voltar rapidamente para a última versão que funcionava.

↩️
Analogia

É o Ctrl+Z de um editor de texto: se a última mudança bagunçou tudo, você não reescreve o documento do zero — só desfaz o último passo e volta pro estado que funcionava.

Linha do tempo de um incidente e sua recuperação
↩️ Reverter o commit
Um novo commit desfaz exatamente a mudança problemática — o CD publica essa reversão como qualquer outra mudança, pela mesma esteira.
🔵🟢 Trocar o interruptor de volta
Se o deploy foi Azul-Verde, basta apontar de volta para a versão "azul" antiga — instantâneo, porque ela nunca foi apagada.
🚩 Feature flag desligada
Se a nova lógica está atrás de uma "chave liga/desliga", desligar a chave já resolve, sem precisar publicar nada de novo.
Checklist
✅ Boas Práticas
🔒 Nunca escreva direto na produção
Toda mudança passa por Pull Request + esteira de testes, mesmo para "uma correção rapidinha" — é justo a correção rápida que mais costuma quebrar coisa.
🧪 Teste o dado, não só o código
Um SQL sem erro de sintaxe ainda pode gerar duplicidade, nulos ou valores fora da faixa — testes de qualidade de dados são tão importantes quanto testes de código.
🎭 Use um ambiente de staging parecido com produção
Testar só com uma amostra de 10 linhas esconde problemas que só aparecem com volume real — staging deve se parecer o máximo possível com produção.
⏱️ Pipelines rápidos são pipelines usados
Se a esteira de testes demora 40 minutos, as pessoas vão procurar atalho. Priorize testes rápidos primeiro (lint), e só depois os mais pesados.
🔵🟢 Tenha sempre um caminho de volta
Antes de publicar, pergunte: "se isso der errado, como eu volto atrás em segundos, não em horas?"
📣 Alerte quem precisa saber, na hora
Um teste que falha silenciosamente, sem notificar ninguém, é quase tão ruim quanto não ter teste nenhum.
