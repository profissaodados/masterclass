🏭 List Comprehension — a Fábrica de Transformar Listas

Imagine uma fábrica de suco: maçãs entram de um lado, uma máquina espreme cada uma, e copos de suco saem do outro lado. Uma list comprehension é exatamente essa fábrica, só que para listas Python: você diz "para cada item de uma lista, faça essa transformação, e me devolva uma lista nova" — tudo em uma linha só.

🧩 A anatomia da fábrica
[expressão for item in lista] — a expressão é a máquina (o que fazer com cada item), o item é a peça passando pela esteira, e a lista é de onde as peças vêm. O colchete [ ] avisa: "quero uma lista pronta no final".
✅ Quando vale a pena usar
Quando a transformação cabe numa linha e é fácil de ler. Se a lógica precisa de vários if, várias linhas ou comentários explicando — volte para o for tradicional. Comprehension é sobre clareza, não sobre parecer esperto.

Adicionar um if no final vira uma peneira: só os itens que passam no teste chegam à máquina. Os que não passam são descartados, sem erro, sem drama.

⚠️ Onde a fábrica vira bagunça

Comprehension aninhada (uma dentro da outra) resolve casos reais — como "achatar" uma lista de lotes em uma lista única — mas depois de 2 níveis vira ilegível. Se você precisar de um terceiro for ou de comentário para explicar, é hora de voltar para um for tradicional com nomes de variável claros.

✓ Achatar uma lista de listas — ok, 1 nível
[linha for lote in lotes for linha in lote] — lê-se "para cada lote, para cada linha do lote". Comum ao juntar páginas de uma API paginada.
✗ 3 níveis com if no meio — pare aqui
[f(x) for a in A for b in a if g(b) for x in b if h(x)] — tecnicamente válido, impossível de revisar em um PR. Vire um for com nomes de variável decentes.
A ponte para o próximo pilar

Troque os colchetes [ ] por parênteses ( ) — (n * 10 for n in precos) — e a fábrica para de empacotar tudo numa lista pronta. Isso é uma generator expression, o assunto da próxima seção: em vez de uma lista inteira na memória, você ganha uma promessa de valores, um de cada vez.

🗺️ map / filter — os "avós" da comprehension

Antes da comprehension existir, Python já resolvia "transformar cada item" e "manter só alguns itens" com map() e filter(). Eles ainda aparecem em código mais antigo (ou funcional) — vale reconhecer, mesmo preferindo comprehension no dia a dia.

map() + filter() — estilo funcional
list(map(lambda n: n * 10, precos))
transforma cada item.

list(filter(lambda n: n > 0, precos))
mantém só quem passa no teste.
Comprehension — o mesmo resultado
[n * 10 for n in precos]
mesma transformação.

[n for n in precos if n > 0]
mesmo filtro, mais fácil de ler com os dois juntos.

💡 A comunidade Python hoje prefere comprehension na maioria dos casos, por ler quase como português. Uma exceção comum: map(str.upper, nomes) — passar uma função já pronta (sem lambda) para map() pode ficar mais limpo que [nome.upper() for nome in nomes], especialmente em pipelines funcionais encadeados.

⏸️ Generators e yield — uma Função que Pausa em Vez de Terminar

Uma função comum, com return, calcula tudo de uma vez e entrega o resultado pronto — depois disso, ela terminou. Uma função com yield vira um generator: a cada yield, ela pausa exatamente ali, entrega um valor, e — na próxima vez que alguém pedir mais — continua exatamente de onde parou, em vez de recomeçar do zero.

🧃
Para uma criança entender

Uma função com return é como uma jarra de suco: alguém espreme todas as laranjas de uma vez e enche a jarra antes de te entregar qualquer coisa. Uma função com yield é a máquina de suco automática de padaria: ela só espreme a próxima laranja quando você aperta o botão de novo — nunca deixa suco pronto esperando, e nunca espreme laranja que ninguém vai beber.

🔄 Antes do yield: o que o for faz por baixo dos panos

Todo for item in alguma_coisa: esconde duas chamadas: primeiro iter(alguma_coisa) pede um iterador — um objeto com um botão "próximo" — e depois o for aperta esse botão chamando next(iterador) repetidamente, até ouvir um "acabou" (StopIteration).

iter([1, 2, 3])pede um iterador à lista
→
next() → 1
→
next() → 2
→
next() → 3
→
next() → StopIterationo for entende isso como "pode parar"
🎫
Para uma criança entender

É como pegar senha numa fila: você não recebe todos os atendimentos de uma vez — a cada vez que seu número é chamado (next()), você recebe um atendimento. Quando o painel mostra "fila encerrada" (StopIteration), você sabe que não tem mais ninguém atrás.

É possível construir esse "botão de próximo" manualmente com uma classe — implementando os métodos especiais __iter__ e __next__. Compare com a mesma coisa escrita como generator:

😓 Iterador escrito à mão — classe inteira
class ContaAte:
  def __init__(self, n):
    self.n, self.atual = n, 1
  def __iter__(self):
    return self
  def __next__(self):
    if self.atual > self.n:
      raise StopIteration
    valor = self.atual
    self.atual += 1
    return valor — funciona, mas dá trabalho para algo simples.
✓ Generator — o Python escreve a classe por você
def conta_ate(n):
  atual = 1
  while atual <= n:
    yield atual
    atual += 1

Mesmo resultado, 5 linhas. O yield é açúcar sintático: por baixo, o Python monta um objeto com __iter__/__next__ automaticamente.

💡 É por isso que todo generator é um iterador, mas nem todo iterador precisa ser um generator — generator é só o jeito mais curto de criar um. Entender essa base explica também por que dá para chamar next() diretamente num generator, como no exemplo a seguir.

Pythondef conta_ate(n):
    atual = 1
    while atual <= n:
        yield atual
        atual += 1

contador = conta_ate(3)
print(next(contador))  # 1 — roda até o primeiro yield e pausa
print(next(contador))  # 2 — retoma dali, roda até o próximo yield
print(next(contador))  # 3

# Na prática, quase sempre percorremos com um for — que já chama
# next() por baixo dos panos até a função acabar:
for numero in conta_ate(3):
    print(numero)

O ponto que mais confunde: conta_ate(3) não roda três vezes — ela roda uma única vez, do início ao fim, só que pausada em cada yield. O trace abaixo é essa única execução completa, com as três pausas marcadas:

💡 É por isso que um generator só pode ser percorrido uma vez. Depois do StopIteration não existe "reiniciar" — é a mesma função, pausada e retomada, que já chegou ao fim. Para percorrer de novo, chame conta_ate(3) outra vez: isso cria um generator novo, do zero.

🔗 yield from — encadeando generators

Um pipeline de dados real é uma fila de etapas: extrair → transformar → carregar. Cada etapa pode ser um generator que consome o generator anterior — os dados fluem linha por linha por toda a fila, sem nunca virar uma lista gigante no meio do caminho.

Pythondef extrai(caminho):
    with open(caminho) as f:
        yield from f   # repassa cada linha de f, uma a uma

def transforma(linhas):
    for linha in linhas:
        yield linha.strip().upper()

def carrega(linhas):
    for linha in linhas:
        print("gravando:", linha)

# nada roda ainda — só quando carrega() começa a "puxar" é que os dados fluem
carrega(transforma(extrai("vendas.csv")))
É por isso que ferramentas de ingestão pedem yield

Em bibliotecas como dlt, cada yield linha dentro de uma função de extração entrega uma linha (ou um lote) imediatamente para ser processado e enviado ao destino — sem esperar a tabela inteira ser lida. Trocar yield por return ainda funcionaria para tabelas pequenas, mas quebraria a promessa de streaming que faz esse tipo de pipeline escalar para milhões de linhas.

🔐 Context Managers — o with que Garante a Devolução

Abrir uma conexão de banco (ou um arquivo) exige fechá-la depois — sempre, mesmo que algo dê errado no meio do caminho. Escrever esse cuidado à mão, toda vez, é repetitivo e fácil de esquecer. Um context manager empacota "abrir" + "fechar garantido" atrás da palavra-chave with.

📚
Para uma criança entender

É como pegar um livro emprestado na biblioteca com um bibliotecário atencioso: ele te entrega o livro (as f), e não importa o que aconteça enquanto você lê — se você adorar, se derrubar café, se a luz apagar — no fim ele sempre pega o livro de volta e guarda na prateleira. Você nunca precisa lembrar de devolver: o with devolve por você.

🛠️ Criando seu próprio context manager

Existem dois jeitos de criar um context manager próprio. O primeiro, com uma classe, expõe os dois momentos-chave explicitamente: __enter__ (o que roda ao abrir o with) e __exit__ (o que roda ao sair — sempre, com ou sem erro).

Pythonimport time

class Cronometro:
    def __enter__(self):
        self.inicio = time.time()
        return self  # isso vira o "as x" do with

    def __exit__(self, tipo_erro, erro, traceback):
        duracao = time.time() - self.inicio
        print(f"etapa levou {duracao:.2f}s")
        # mesmo se 'erro' não for None (deu exceção), esta linha roda

with Cronometro():
    extrai_dados_da_api()   # mede o tempo dessa etapa do pipeline

O segundo jeito, mais curto, usa o decorator @contextmanager — repare que ele mistura os três pilares desta aula numa função só: é um decorator, usa yield, e vira um with.

Pythonfrom contextlib import contextmanager

@contextmanager
def conexao(nome):
    print(f"abrindo conexão com {nome}")
    try:
        yield f"conexao-{nome}"   # tudo ANTES do yield = __enter__
    finally:
        print(f"fechando conexão com {nome}")  # tudo DEPOIS = __exit__

with conexao("postgres") as conn:
    print(f"usando {conn}")

# abrindo conexão com postgres
# usando conexao-postgres
# fechando conexão com postgres  <- roda mesmo se der erro no bloco with

💡 O yield aqui tem um papel diferente do generator da seção anterior: ele marca o único ponto de entrega (o que vira o conn do as conn), dividindo a função em "antes" (abrir) e "depois" (fechar, dentro do finally).

🧵 Múltiplos recursos em um único with

É possível abrir mais de um recurso na mesma linha, separando por vírgula — útil ao ler de um arquivo e gravar em outro ao mesmo tempo, por exemplo.

Pythonwith open("entrada.csv") as origem, open("saida.csv", "w") as destino:
    for linha in origem:
        destino.write(linha.upper())
# os DOIS arquivos fecham sozinhos ao sair do bloco, na ordem inversa
Onde isso aparece em pipelines de verdade

Toda vez que um pipeline abre uma conexão JDBC, um cliente de API, um arquivo temporário, um lock ou uma sessão de banco — a resposta correta é sempre "isso merece um with". É o jeito Python de dizer: "eu prometo devolver isso, e o interpretador garante".

🎁 Decorators — uma Função que Embrulha Outra

Um decorator é uma função que recebe outra função, adiciona algum comportamento antes/depois dela, e devolve essa versão "embrulhada". A sintaxe @nome_do_decorator escrita em cima de uma função é só um atalho para essa troca.

🎀
Para uma criança entender

É como embrulhar um presente: o presente (a função original) continua exatamente o mesmo por dentro. O papel de embrulho e o laço (o decorator) só adicionam algo por fora — um cronômetro, um log, uma nova tentativa em caso de erro — sem abrir a caixa e mexer no presente.

🎒 Antes do wrapper: o que são *args e **kwargs

Repare, no exemplo logo abaixo, que a função interna é def wrapper(*args, **kwargs):. Isso é o que permite ao decorator embrulhar qualquer função — sem saber de antemão quantos argumentos ela recebe, nem quais nomes.

🎒
Para uma criança entender

Pense em duas mochilas universais penduradas na entrada de uma função: *args é a mochila onde caem todos os argumentos que chegaram sem nome, na ordem — vira uma tupla. **kwargs é a mochila dos argumentos que chegaram com nome (tabela="vendas") — vira um dicionário. Não importa quantos itens cheguem: sempre cabem numa das duas mochilas.

Pythondef resume_carga(*args, **kwargs):
    print("posicionais:", args)
    print("nomeados:", kwargs)

resume_carga("vendas.csv", linhas=1000, formato="csv")
# posicionais: ('vendas.csv',)
# nomeados: {'linhas': 1000, 'formato': 'csv'}

Pythonimport time

def cronometro(func):
    def wrapper(*args, **kwargs):
        inicio = time.time()
        resultado = func(*args, **kwargs)
        print(f"{func.__name__} levou {time.time() - inicio:.4f}s")
        return resultado
    return wrapper

@cronometro
def extrai_dados_lentos():
    time.sleep(1)
    return "dados extraídos"

extrai_dados_lentos()
# extrai_dados_lentos levou 1.0002s
O que o @ realmente faz
@cronometro em cima de def extrai_dados_lentos() equivale a escrever extrai_dados_lentos = cronometro(extrai_dados_lentos) logo abaixo. O @ é só açúcar sintático para essa reatribuição.
Por que "wrapper" existe
A função interna wrapper é o que roda de fato no lugar da original — ela chama func(*args, **kwargs) no meio, então quem usa extrai_dados_lentos() nem percebe a camada extra por baixo.

2º@retry(tentativas=3) — tenta de novo se falhar

Leia de baixo para cima na hora de aplicar, e de cima para baixo na hora de executar — como uma boneca russa (matryoshka).

🏷️ Decorators com argumento

Reparou no @retry(tentativas=3) acima? Um decorator "configurável" precisa de uma função a mais por fora — a que recebe os argumentos e devolve o decorator de verdade.

Pythondef retry(tentativas=3):
    def decorator(func):
        def wrapper(*args, **kwargs):
            for tentativa in range(1, tentativas + 1):
                try:
                    return func(*args, **kwargs)
                except Exception as erro:
                    print(f"tentativa {tentativa} falhou: {erro}")
            raise RuntimeError("todas as tentativas falharam")
        return wrapper
    return decorator

@retry(tentativas=3)
def chama_api_instavel():
    ...
⚠️ O gotcha do functools.wraps

Sem cuidado extra, a função "embrulhada" perde sua identidade: extrai_dados_lentos.__name__ vira "wrapper", e ferramentas de debug/documentação se confundem. A correção é uma linha: adicione @functools.wraps(func) em cima do def wrapper(...).

Pythonimport functools

def cronometro(func):
    @functools.wraps(func)  # preserva __name__, __doc__ da função original
    def wrapper(*args, **kwargs):
        ...
        return func(*args, **kwargs)
    return wrapper
Decorators do dia a dia em engenharia de dados

@functools.lru_cache guarda o resultado de uma função cara e devolve na hora se for chamada de novo com os mesmos argumentos (ótimo para lookups repetidos). @retry(...) reexecuta uma chamada de API instável. @dlt.resource (em bibliotecas de ingestão) embrulha uma função geradora com toda a maquinaria de schema e carga. Todos seguem exatamente o mecanismo desta seção.

🧩 Juntando os 4 Pilares em uma Função Só

Este é o tipo de função que aparece em qualquer pipeline real de ingestão — e agora cada peça dela conta uma história que você já conhece:

Python@retry(tentativas=3)                        # decorator: reexecuta se a extração falhar
@dlt.resource(name="orders")             # decorator: embrulha com a maquinaria de ingestão
def extrai_orders():
    engine = create_engine(dlt.secrets.get("credentials"))
    with engine.connect() as conn:                 # context manager: fecha a conexão sempre
        resultado = conn.execute(text("SELECT * FROM orders"))
        colunas_uteis = ["id", "cliente", "valor"]   # list comprehension mais abaixo
        for linha in resultado:
            registro = {c: linha._mapping[c] for c in colunas_uteis}  # dict comprehension: filtra colunas
            yield registro                        # generator: entrega 1 linha por vez, sem RAM extra
✓ @retry(...) e @dlt.resource(...) — decorators: cada um adiciona uma camada de comportamento sem tocar na lógica de extração
✓ with engine.connect() as conn: — context manager: a conexão fecha sozinha, mesmo se a query falhar
✓ {c: linha._mapping[c] for c in colunas_uteis} — dict comprehension: monta o registro só com as colunas que interessam
✓ yield registro — generator: entrega linha por linha, permitindo streaming de tabelas gigantes
