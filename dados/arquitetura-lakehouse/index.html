Por muito tempo, times de dados tiveram que escolher entre dois mundos: o Data Warehouse — organizado, confiável, mas caro e rígido — ou o Data Lake — barato, flexível, mas bagunçado e sem garantias. O Lakehouse é uma arquitetura que junta os dois: dados brutos guardados em armazenamento barato (como um data lake), com uma camada de metadados por cima que adiciona transações ACID, schema, versionamento e governança (como um data warehouse) — tudo sobre o mesmo arquivo, sem duplicar dado nenhum.

Fundamentos
🏛️ O que é um Lakehouse?

O termo "Lakehouse" foi formalizado em 2020 pela Databricks, num artigo acadêmico que descrevia um novo tipo de plataforma de dados: um data lake (armazenamento de arquivos barato e aberto, geralmente Parquet — já vimos essa base na aula de Parquet) que ganha, por cima, uma camada de metadados que oferece as garantias que só existiam em data warehouses: transações confiáveis, schema, indexação e governança. Na prática, é a mesma ideia de "uma tabela de banco de dados", só que os arquivos continuam sendo arquivos comuns num object storage — qualquer motor (Spark, DuckDB, Trino) pode lê-los diretamente.

🏞️ Data Lake
Armazenamento barato e flexível para qualquer tipo de arquivo — mas sem transações, sem schema garantido. Fácil de sujar.
🏢 Data Warehouse
Estruturado, confiável, ótimo para BI — mas caro, fechado e lento para incorporar dados novos ou não estruturados.
🏛️ Lakehouse
Storage do lake + confiabilidade do warehouse, na mesma cópia dos dados. O "melhor dos dois mundos" — sem duplicar nada.
Origem

O paper "Lakehouse: A New Generation of Open Platforms that Unify Data Warehousing and Advanced Analytics" (CIDR 2021) formalizou o termo, mas as ideias já vinham amadurecendo: Databricks abriu o código do Delta Lake em 2019, a Netflix já usava o Apache Iceberg desde 2018, e a Uber criou o Apache Hudi em 2016 — todos resolvendo o mesmo problema por caminhos parecidos.

💡 Conecte com o que você já viu: o Parquet é o formato de arquivo (como os bytes são organizados no disco); o DuckDB é um motor de consulta que pode ler tabelas Lakehouse direto; o Lakehouse é a camada de organização que fica entre os dois — arquivos Parquet + metadados que os transformam numa "tabela" de verdade.

Como Chegamos Aqui
🕰️ A Evolução: Warehouse → Lake → Lakehouse

A arquitetura Lakehouse não surgiu do nada — ela é resposta a limitações que foram aparecendo em cada geração anterior de plataformas de dados.

anos 1980–90
🏢 Data Warehouse
Inmon e Kimball formalizam o modelo dimensional. Ótimo para BI, mas caro e rígido — schema definido antes de qualquer dado entrar.
2006–2010
🐘 Hadoop / Data Lake
HDFS populariza guardar qualquer arquivo, barato, em massa. Nasce o "schema-on-read" — mas sem transações nem organização por padrão.
2015–2018
🌊 Data Swamp
Data lakes viram "pântanos": ninguém confia nos dados, updates/deletes são quase impossíveis, cada leitura pode ver um estado inconsistente.
2016–2019
📜 Table Formats
Hudi (Uber, 2016), Iceberg (Netflix, 2018) e Delta Lake (Databricks, 2019) nascem para trazer ACID e schema para cima dos arquivos do lake.
2020–21
🏛️ "Lakehouse"
Databricks publica o paper que dá nome à arquitetura: um lake com garantias de warehouse, na mesma cópia dos dados.
hoje
🌐 Padrão da Indústria
Snowflake, BigQuery, Databricks e motores open-source convergem: ler/escrever tabelas Iceberg/Delta é hoje suporte de primeira classe.
O Primeiro Mundo
🏢 Data Warehouse — a biblioteca super organizada

Imagine uma biblioteca onde, antes de qualquer livro entrar na estante, um bibliotecário exige que ele já esteja catalogado: título, autor, assunto, número certinho na prateleira. É assim que um data warehouse trata os dados: schema-on-write — o formato é definido antes do dado ser carregado, e um processo de ETL organiza tudo antes de guardar.

✅ Pontos fortes
Consultas SQL rapidíssimas para BI, dados sempre consistentes e bem tipados, forte governança e segurança, décadas de ferramentas maduras (dashboards, relatórios).
⚠️ Limitações
Armazenamento e processamento vendidos juntos (caro escalar um sem o outro), formatos proprietários, difícil guardar dados semiestruturados/não estruturados (JSON solto, imagens, logs, vídeo), ETL lento para incorporar fontes novas.

💡 Na "biblioteca", adicionar um tipo de mídia novo (um DVD, uma revista) exige repensar todo o sistema de catalogação. Da mesma forma, um warehouse tradicional sofre para incorporar dados de sensores IoT, cliques de app ou imagens — tudo tem que virar linha e coluna antes de entrar.

O Segundo Mundo
🏞️ Data Lake — a garagem gigante e barata

Agora imagine uma garagem enorme: você pode jogar qualquer caixa lá dentro — não importa o tamanho, o formato, se está rotulada ou não. É barato guardar, e nada te impede de guardar. Esse é o data lake: armazenamento de objetos (S3, ADLS, GCS) barato, aceita qualquer arquivo (CSV, JSON, Parquet, imagem, vídeo, log), com schema-on-read — você só decide a estrutura quando for ler o dado, não quando ele chega.

✅ Pontos fortes
Armazenamento muito barato, aceita qualquer formato/tipo de dado, storage e processamento desacoplados (escale cada um separado), ótimo para ciência de dados e ML explorando dado bruto.
⚠️ Limitações clássicas
Sem transações ACID (uma escrita que falha no meio pode deixar arquivos parciais), sem garantia de schema, updates/deletes de linhas individuais são difíceis (os arquivos são, em geral, apenas escritos uma vez), performance ruim para BI sem um motor por cima.

Sem rótulos e sem regras, a garagem vira bagunça — o que o mercado apelidou de "data swamp" (pântano de dados). Clique para organizar as caixas e veja a diferença:

Uma garagem sem etiquetas — clique para organizar

⚠️ Um data lake puro, sem uma camada de organização, tende a virar um "pântano de dados": ninguém sabe qual arquivo é a versão certa, schemas conflitam entre times, e consultas simples exigem varrer terabytes de arquivo por arquivo. É exatamente esse problema que o Lakehouse resolve.

Os Ingredientes
🧱 Os Pilares do Lakehouse

O que exatamente uma camada de "table format" adiciona sobre arquivos Parquet soltos num bucket? Estes sete pilares são o que separa um data lake comum de um Lakehouse de verdade.

🔒 Transações ACID
Uma escrita concorrente nunca deixa a tabela num estado quebrado — ou ela acontece inteira, ou não acontece.
📐 Schema Enforcement
A tabela recusa escritas que não batem com o schema esperado — evita que um tipo errado corrompa a tabela.
🧬 Schema Evolution
Adicionar/renomear uma coluna é uma operação controlada, sem quebrar leituras antigas.
🕰️ Time Travel
Cada escrita gera uma nova versão da tabela — dá para consultar (ou reverter) exatamente como ela estava ontem.
📦 Formatos Abertos
Os dados continuam em Parquet/ORC comuns — nenhum motor fica "preso" a um formato proprietário.
🔓 Storage/Compute Desacoplados
Escale armazenamento e poder de processamento de forma independente — e troque de motor sem migrar dado.
🌊 Batch + Streaming Unificados
A mesma tabela recebe tanto cargas em lote quanto streams contínuos, sem duas arquiteturas paralelas.

O Coração do Lakehouse
📜 Table Formats: Delta Lake, Iceberg e Hudi

Um table format não é um formato de arquivo (isso é o Parquet) — é uma especificação de metadados que fica ao lado dos arquivos Parquet e registra: quais arquivos pertencem à tabela agora, qual é o schema, e o histórico completo de mudanças. É essa camada extra que transforma "uma pasta cheia de arquivos Parquet" em "uma tabela com transações ACID".

✅ Na prática, os três resolvem o mesmo conjunto de problemas (ACID, schema, time travel) de formas parecidas — a escolha costuma depender de qual motor de processamento e catálogo sua empresa já usa, não de uma diferença técnica radical.

A Mágica por Trás do ACID
📝 Metadados & Transaction Log

Todo table format guarda, ao lado dos arquivos Parquet de dados, um log de transações: uma sequência numerada de "commits" que dizem exatamente quais arquivos fazem parte da tabela em cada versão. Ler a tabela não é "abrir a pasta e ver o que tem lá" — é reproduzir o log até a versão desejada.

vendas/ (tabela Delta)
_delta_log/
00000000000000000000.json ← commit 0: cria a tabela, adiciona 2 arquivos
00000000000000000001.json ← commit 1: adiciona 1 arquivo novo
00000000000000000002.json ← commit 2: remove 1 arquivo, adiciona 2 (UPDATE)
part-0001-....parquet
part-0002-....parquet
part-0003-....parquet
part-0004-....parquet
json (trecho de um commit){ "add": {"path": "part-0003-....parquet", "size": 204800, "dataChange": true}, "remove": {"path": "part-0001-....parquet", "dataChange": true}, "commitInfo": {"timestamp": 1719500000000, "operation": "UPDATE"} }

💡 Note que "remover" um arquivo aqui não apaga o Parquet do disco imediatamente — só marca, no log, que ele não faz mais parte da versão atual. É exatamente essa marcação (em vez de deleção física) que torna o time travel possível.

A Garantia Fundamental
🔐 Transações ACID

Pense num pote de biscoitos com um cartaz: "o último biscoito não pode ser pego por duas pessoas ao mesmo tempo". ACID é o conjunto de garantias que faz isso valer também para tabelas de dados, mesmo quando várias escritas acontecem ao mesmo tempo.

A · Atomicidade
Uma escrita acontece inteira ou nada — nunca fica "meio feita" se algo falhar no meio do caminho.
C · Consistência
A tabela sai de um estado válido para outro estado válido — nunca viola as regras de schema.
I · Isolamento
Duas escritas concorrentes não se enxergam pela metade — cada uma vê a tabela antes ou depois da outra, nunca no meio.
D · Durabilidade
Depois que o commit é confirmado, ele sobrevive a quedas de energia ou falhas — está gravado no log, para sempre.
Simule: dois processos escrevendo na mesma tabela ao mesmo tempo
Uma Máquina do Tempo
🕰️ Time Travel & Versionamento

Como cada escrita vira um novo "commit" numerado no log, o table format guarda — na prática — um álbum de fotos da tabela: uma foto por versão. Você pode consultar (ou restaurar) qualquer foto antiga, sem precisar de backup separado.

Mudança Sem Quebrar Nada
🧬 Schema Enforcement & Evolution

Schema enforcement é o "segurança na porta": uma escrita com um tipo errado (texto onde se espera número) é recusada antes de sujar a tabela. Schema evolution é o processo controlado de mudar essa estrutura — como adicionar uma coluna nova num formulário sem invalidar os formulários já preenchidos.

✅ Arquivos antigos continuam válidos: as linhas gravadas antes da coluna telefone existir simplesmente retornam NULL nela — ninguém precisa reescrever o histórico inteiro.

⚠️ Mudanças "destrutivas" (mudar o tipo de uma coluna existente, renomear) exigem mais cuidado — a maioria dos table formats trata isso como uma operação explícita, não automática.

Quem Escreve as Transformações
🔧 dbt: automatizando Bronze → Silver → Gold

dbt (data build tool) virou o padrão de mercado para implementar, na prática, as transformações entre as camadas do medalhão — só com SQL. Ele não extrai nem carrega dado nenhum (isso já aconteceu quando o dado chegou na Bronze, via Auto Loader, Fivetran, Kafka Connect...); dbt cuida exclusivamente do "T" de um pipeline ELT: transforma tabelas que já existem no Lakehouse em outras tabelas, com controle de versão (Git), testes automatizados e documentação gerada a partir do próprio código.

📁 staging ≈ Bronze → Silver
Um modelo por tabela de origem: renomeia colunas, corrige tipos, faz limpeza superficial. Ainda é "1 para 1" com a fonte — nenhuma regra de negócio ainda.
🔗 intermediate ≈ Silver
Junta modelos de staging entre si, aplica regras de negócio e deduplicação. Normalmente não é exposto diretamente para quem consome BI.
🏆 marts ≈ Gold
Tabelas finais, modeladas como fatos e dimensões, otimizadas para a pergunta de negócio que um time específico faz o tempo todo.

A estrutura de pastas de um projeto dbt normalmente espelha essas mesmas três camadas:

✅ Testes declarativos (schema enforcement na prática)
Testes como not_null, unique, relationships e accepted_values rodam antes de qualquer modelo consumir dado errado — o equivalente prático do "schema enforcement" do table format, mas em nível de regra de negócio.
yamlcopiarmodels: - name: stg_pedidos columns: - name: pedido_id tests: [unique, not_null] - name: valor tests: - dbt_utils.accepted_range: min_value: 0
🏗️ Materializações — como cada camada vira objeto no banco
view — não persiste, recalculada a cada consulta; boa para staging.
ephemeral — nem vira objeto, só um CTE embutido; boa para intermediate.
table — persiste, recalcula tudo do zero; boa para marts menores.
incremental — só processa linhas novas/alteradas; essencial para tabelas Gold grandes.
📖 Documentação & Lineage
dbt docs generate cria um site navegável com o DAG completo, descrição de cada tabela e cada coluna — gerado a partir de comentários que já vivem no próprio projeto, nunca desatualizado.
▶️ Um comando roda tudo na ordem certa
dbt build executa modelos e testes na ordem definida pelo DAG (staging antes de intermediate, antes de marts), parando cedo se um teste crítico falhar.

💡 dbt normalmente não toca na camada Bronze — a ingestão bruta é feita por outra ferramenta antes dele. dbt entra a partir daí: staging ≈ limpeza inicial a caminho da Silver, intermediate ≈ Silver, marts ≈ Gold. Repare também que o GROUP BY ALL do exemplo de marts é a mesma sintaxe "SQL amigável" vista na aula de DuckDB.

Um Dado, Muitos Motores
⚙️ Motores de Consulta

Porque a tabela vive como arquivos abertos + metadados, qualquer motor com um "conector" para o table format pode ler (e muitos, escrever) a mesma tabela — sem cópias paralelas apodrecendo em sincronia.

⚡ Apache Spark
O motor "nativo" de Delta Lake e um dos mais usados com Iceberg/Hudi — processamento distribuído em lote e streaming.
🔍 Trino / Presto
SQL federado e rápido para consultas ad hoc e BI direto sobre as tabelas do lakehouse, sem mover dado.
🦆 DuckDB
Da nossa aula anterior: consegue ler tabelas Delta/Iceberg diretamente via extensão, ótimo para exploração local sem cluster.
🌊 Apache Flink
Processamento de streaming que escreve incrementalmente nas mesmas tabelas — batch e streaming, uma única fonte de verdade.
❄️ Snowflake / BigQuery
Motores de data warehouse na nuvem que também sabem ler tabelas Iceberg como "tabelas externas", sem importar o dado para dentro.
🐍 Pandas / Polars
Via conectores Python, cientistas de dados leem snapshots de tabelas Lakehouse direto em DataFrames para exploração e ML.
O diferencial real

Antes do Lakehouse, cada ferramenta exigia sua própria cópia dos dados (um extract para o BI, outro para o ML, outro para o warehouse). Com uma única tabela aberta, todos os motores leem a mesma fonte de verdade — menos cópias, menos divergência, menos custo de storage duplicado.

Onde ele Brilha
🎯 Casos de Uso
📊 Unificar BI e ML
Dashboards e modelos de machine learning consultando a mesma tabela Gold, sem pipelines de extração paralelos.
🌊 Streaming + batch juntos
Uma tabela Silver recebendo tanto eventos em tempo real quanto cargas noturnas em lote, com as mesmas garantias ACID.
💸 Substituir warehouse caro
Migrar workloads analíticas de um warehouse proprietário para tabelas abertas sobre object storage, reduzindo custo de armazenamento.
🔍 Auditoria e compliance
Time travel permite provar exatamente como um dado estava em uma data específica, sem manter backups paralelos.
🧩 Multi-engine sem duplicar
Times diferentes usando Spark, Trino e DuckDB sobre a mesma cópia dos dados, cada um com a ferramenta certa para o trabalho.
🕰️ Slowly Changing Dimensions
MERGE/upserts nativos do table format viabilizam padrões de SCD Tipo 2 direto na camada Silver/Gold — sem reprocessar a tabela inteira.
Checklist
✅ Boas Práticas
📐 Particione com propósito
Escolha colunas de partição pelas consultas mais comuns (data, região) — partições demais criam arquivos pequenos demais.
🗜️ Rode compaction (OPTIMIZE) regularmente
Streaming e micro-batches geram muitos arquivos pequenos — compactá-los periodicamente evita o "small file problem" na leitura.
🗂️ Centralize um catálogo
Um catálogo único (Unity Catalog, Glue, Hive Metastore, Nessie) evita que times criem tabelas "invisíveis" para o resto da empresa.
🧹 Cuidado com VACUUM/expiração
Remover arquivos antigos libera espaço, mas também encurta quanto tempo de time travel fica disponível — ajuste a retenção com intenção.

⚠️ O problema dos arquivos pequenos: cada arquivo Parquet extra é mais uma abertura de arquivo, mais metadado para o motor ler antes mesmo de tocar num dado. Uma tabela com milhões de arquivinhos de poucos KB fica lenta para qualquer motor — compaction periódica (bronze→silver, por exemplo) é essencial.
