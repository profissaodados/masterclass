Seus dados têm uma rotina. Quem garante que ela acontece, na ordem certa, todo santo dia?

Apache Airflow é uma ferramenta para programar, agendar e monitorar fluxos de trabalho — sequências de tarefas com dependências entre si, como "primeiro extrai os dados, depois valida, depois transforma, só então carrega no banco". Ele não processa dados pesados como o Spark, e não guarda dados como um banco: ele é o regente da orquestra — decide quem toca, quando toca, o que fazer se alguém errar a nota, e mostra pra todo mundo, num painel visual, como o concerto está indo. Criado no Airbnb em 2014 e hoje mantido pela Apache Software Foundation, virou o orquestrador mais usado do mundo dos dados. Hoje vamos destrinchar cada peça dele, com muita analogia simples e exemplo visual.

Um DAG é só um arquivo Python — mas vira esse "roteiro" que o Airflow executa sozinho
Fundamentos
🎻 Primeiro, pensando como criança: o que é um "orquestrador"?

Imagine uma orquestra. O violinista sabe tocar violino, o baterista sabe tocar bateria — cada um é ótimo no seu instrumento. Mas ninguém sabe, sozinho, quando deve entrar, depois de quem, e o que fazer se alguém errar. É pra isso que existe o regente: ele não toca nenhum instrumento, mas garante que a música saia na ordem certa. O Airflow é o regente da sua "orquestra de dados" — os "músicos" são scripts Python, comandos SQL, chamadas de API — e o Airflow garante que cada um entre na hora certa, na ordem certa, todo santo dia, sem ninguém precisar clicar em "rodar" manualmente.

🎼
Pensando como criança

É como a rotina de uma casa de manhã: primeiro o despertador toca, depois alguém faz o café, depois as crianças tomam café, só então o ônibus escolar é chamado. Se você chamar o ônibus antes do café ficar pronto, a rotina quebra. O Airflow é a "lista de regras da casa" escrita em código: o que vem primeiro, o que espera o quê, e o que fazer se alguém dormiu demais (falhou).

🚫 O que o Airflow NÃO é
Não processa dados pesados (isso é trabalho do Spark, DuckDB, etc.) e não guarda dados (isso é trabalho de um banco/Data Warehouse). Ele não "faz" o trabalho pesado — ele manda outras ferramentas fazerem, na hora certa.
✅ O que o Airflow É
Um orquestrador de workflows: agenda quando cada tarefa roda, garante a ordem entre elas, tenta de novo se algo falha, e mostra visualmente o que aconteceu — tudo definido como código Python, não cliques numa interface.
🧠 Por que "código", não clique-clique?
Código pode ser versionado no Git, revisado por colegas, testado e reutilizado. É a ideia de "Workflows as Code" — a mesma disciplina de engenharia de software aplicada à rotina dos seus dados.

💡 Um jeito rápido de lembrar a diferença: se a pergunta é "o que fazer e quando fazer", é problema do Airflow. Se a pergunta é "como processar 500 milhões de linhas rápido", é problema de outra ferramenta (Spark, DuckDB, um banco...) — que o Airflow apenas aciona no momento certo.

A peça central
🧩 Anatomia de um DAG

DAG é a sigla de Directed Acyclic Graph — "Grafo Acíclico Dirigido", em português. Parece complicado, mas quebrando a sigla em três pedaços fica simples: é um Grafo (um desenho de caixinhas ligadas por setas), Dirigido (as setas têm sentido — "A vem antes de B", não o contrário) e Acíclico (as setas nunca voltam pro começo, formando um círculo infinito). No Airflow, cada caixinha é uma task (tarefa), e as setas são as dependências entre elas.

🍰
Analogia

É como uma receita de bolo: você não pode assar antes de misturar, e não pode misturar antes de separar os ingredientes. Cada passo da receita é uma "task", e a ordem entre os passos é o "DAG". "Acíclico" só quer dizer que a receita nunca te manda voltar pro passo 1 depois de já ter chegado no passo 5 — senão o bolo nunca fica pronto!

Veja o DAG do nosso exemplo (dag_vendas_diarias) desenhado como o Airflow mostra na tela — repare que três tasks de transformação rodam em paralelo, porque nenhuma depende da outra, só todas dependem de validar_dados ter terminado antes:

E é assim que esse desenho vira código — a versão moderna do Airflow (TaskFlow API, a partir da versão 2.0) deixa isso bem próximo de Python "normal", com decorators marcando o que é um DAG e o que é uma task:

pythoncopiarfrom airflow.decorators import dag, task from airflow.operators.empty import EmptyOperator from pendulum import datetime @dag( dag_id="dag_vendas_diarias", schedule="0 6 * * *", # todo dia às 06:00 start_date=datetime(2026, 1, 1), catchup=False, tags=["vendas", "producao"], ) def vendas_diarias(): inicio = EmptyOperator(task_id="inicio") @task def extrair_vendas(): return buscar_vendas_da_api() @task def validar_dados(dados): return checar_qualidade(dados) @task def transformar(regiao: str, dados): return agregar_por_regiao(regiao, dados) @task def carregar_dw(partes: list): escrever_no_data_warehouse(partes) dados = extrair_vendas() validados = validar_dados(dados) partes = [transformar(r, validados) for r in ["sul", "sudeste", "nordeste"]] inicio >> dados carregar_dw(partes) vendas_diarias()

✅ Repare: não existe nenhum loop while True nem "rodar agora" no código. O DAG só descreve o que precisa acontecer e quando — quem decide quando de fato disparar é uma peça separada chamada Scheduler, que vamos conhecer daqui a pouco.

As caixinhas do grafo
⚙️ Tasks & Operators — os "funcionários" especializados

Uma task é uma caixinha do DAG — um passo do trabalho. Todo task é criado a partir de um Operator: um "molde" pronto que sabe fazer um tipo de trabalho específico. O Airflow já vem com dezenas deles, e a comunidade mantém centenas a mais via providers (pacotes extras para conectar com AWS, GCP, Slack, Postgres, e praticamente qualquer sistema famoso).

🧑‍🔧
Analogia

Pense numa equipe de reforma: o pedreiro sabe assentar tijolo, o eletricista sabe mexer com fiação, o pintor sabe pintar parede. Cada "Operator" é uma especialidade contratada pronta — você só diz o quê fazer (qual parede, qual comando, qual script), e o Operator já sabe como fazer.

🐍 PythonOperator
Roda uma função Python qualquer. O "curinga" — se não existe um Operator pronto pra algo, dá pra fazer com Python puro aqui dentro.
💻 BashOperator
Roda um comando de shell/terminal. Útil para scripts existentes, CLIs de outras ferramentas, ou comandos rápidos.
🗄️ SQLExecuteQueryOperator
Roda uma query SQL num banco (Postgres, MySQL, Snowflake...) usando uma connection configurada. Não precisa reescrever a lógica de conexão.
🏁 EmptyOperator
Não faz nada sozinho — serve só como um "marco" visual no grafo, tipo um ponto de encontro onde vários caminhos se juntam antes de continuar.
📡 HttpOperator / SimpleHttpOperator
Faz uma chamada HTTP a uma API externa — GET, POST, o que precisar.
📨 EmailOperator / SlackWebhookOperator
Envia notificações — muito usado no final de um DAG, ou em callbacks de falha.
☁️ S3, BigQuery, Snowflake...
Centenas de Operators específicos vêm em providers — pacotes extras instalados à parte (ex: apache-airflow-providers-amazon).
🧩 Operator customizado
Se nada pronto serve, você cria o seu: uma classe Python que herda de BaseOperator e implementa o método execute().

O mesmo DAG de vendas, agora escrito no estilo clássico (pré-TaskFlow), que você vai encontrar em muitos projetos por aí — instanciando Operators diretamente dentro de um bloco with DAG(...):

pythoncopiarfrom airflow import DAG from airflow.operators.python import PythonOperator from airflow.providers.common.sql.operators.sql import SQLExecuteQueryOperator from pendulum import datetime with DAG( dag_id="dag_vendas_diarias_classico", schedule="0 6 * * *", start_date=datetime(2026, 1, 1), catchup=False, ) as dag: extrair = PythonOperator( task_id="extrair_vendas", python_callable=extrair_vendas_da_api, ) carregar = SQLExecuteQueryOperator( task_id="carregar_dw", conn_id="dw_vendas", sql="sql/carrega_fato_vendas.sql", ) extrair >> carregar

💡 Hoje a comunidade recomenda a TaskFlow API (com @dag/@task) para código Python puro, e reserva Operators tradicionais para tarefas que já têm um "molde" pronto de um provider (SQL, S3, Kubernetes, etc.). Os dois estilos convivem tranquilamente no mesmo DAG.

A cola entre as caixinhas
🔗 Dependências — quem espera quem

Declarar dependências no Airflow é surpreendentemente visual: os operadores >> ("bitshift direita") e << ("bitshift esquerda") literalmente desenham a seta no código, na mesma direção que ela aparece no grafo. a >> b significa "a task a precisa terminar antes de b começar" — ou seja, a aponta para b.

🚶
Analogia

É como uma fila do banco: você só é chamado depois que a pessoa da sua frente terminou. pessoa_1 >> pessoa_2 >> pessoa_3 é a fila inteira, na ordem. Se três pessoas podem ser atendidas ao mesmo tempo em guichês diferentes (sem depender uma da outra), elas formam uma "lista" — [pessoa_2a, pessoa_2b, pessoa_2c] — todas esperando a mesma pessoa 1, mas sem esperar umas pelas outras.

➡️ Sequencial
pythonextrair >> validar >> carregar
Uma depois da outra. validar só começa quando extrair tiver sucesso.
🌿 Fan-out (uma vira várias)
pythonvalidar >> [transf_sul, transf_sudeste, transf_ne]
As três tasks de transformação só esperam validar — e depois rodam ao mesmo tempo, sem se esperar.
🌾 Fan-in (várias viram uma)
python[transf_sul, transf_sudeste, transf_ne] >> carregar
carregar só começa quando todas as três transformações tiverem terminado.
🔧 set_upstream / set_downstream
pythoncarregar.set_upstream(validar)
A forma "por extenso" de >> / << — faz exatamente a mesma coisa, mas menos usada no dia a dia.

Quando o TaskFlow API está em uso, a dependência muitas vezes nem precisa ser escrita explicitamente: passar o retorno de uma task como argumento de outra já cria a seta automaticamente, porque o Airflow entende que uma depende do resultado da outra:

pythoncopiar# o simples fato de usar "dados" aqui já cria a dependência # extrair_vendas() >> validar_dados(dados) — sem precisar escrever >> dados = extrair_vendas() validados = validar_dados(dados)
Quando disparar
⏰ Agendamento — o despertador do DAG

Três parâmetros do DAG controlam quando ele roda: schedule (com que frequência), start_date (a partir de quando ele existe) e catchup (se runs "perdidos" no passado devem ser recuperados — assunto da seção de Backfill, mais à frente).

⏰
Analogia

schedule é o despertador ("toca todo dia às 6h"). start_date é "a partir de que dia o despertador existe" — um despertador comprado hoje não toca em datas do ano passado. E se você desligou o despertador por 3 dias e religou, catchup decide se ele toca 3 vezes seguidas "recuperando o atraso" ou só uma vez, pra frente.

📅 schedule (cron)
"0 6 * * *" = todo dia às 06:00. "*/15 * * * *" = a cada 15 minutos. "0 0 1 * *" = todo dia 1º do mês.
🏷️ schedule (presets)
"@daily", "@hourly", "@weekly", "@monthly" — atalhos legíveis para os crons mais comuns.
🖱️ schedule=None
O DAG nunca dispara sozinho — só roda quando alguém aciona manualmente (UI, CLI ou API) ou quando outro DAG o aciona.
Expressão cronSignificadoPreset equivalente
0 6 * * *Todo dia, às 06:00—
0 0 * * *Todo dia, à meia-noite@daily
0 * * * *A cada hora, no minuto 0@hourly
0 0 * * 1Toda segunda-feira, à meia-noite@weekly
0 9 * * 1-5Dias úteis, às 09:00—
*/10 * * * *A cada 10 minutos—

⚠️ start_date deve ser uma data fixa no passado, nunca algo dinâmico como datetime.now(). Se ela mudar toda vez que o Airflow reler o arquivo (o que acontece o tempo todo), o Scheduler fica confuso sobre quais runs já existem — é um dos erros mais clássicos de quem está começando.

O conceito que mais confunde iniciantes
📅 Execution Date & Data Interval — o "boletim escolar"

Aqui está a pegadinha mais famosa do Airflow: um DAG agendado para rodar todo dia às 00:00 não roda "para processar o dia de hoje" — ele roda depois que o dia terminou, para processar o dia que acabou de passar. O período de dados que uma execução representa se chama data interval (data_interval_start até data_interval_end), e o disparo de fato só acontece no fim desse intervalo.

📋
Pensando como criança

É como um boletim escolar: o boletim do 1º bimestre só sai depois que o bimestre termina — ele não sai no primeiro dia de aula, e mesmo saindo depois, ele descreve o que aconteceu durante aquele bimestre, não o dia em que foi entregue. Um DAG diário funciona igual: a execução que "sai" na quinta-feira de manhã carrega no nome dela a quarta-feira — o dia que ela está reportando, não o dia em que rodou.

Veja isso com datas reais, para um DAG com schedule="@daily":

data_interval_startdata_interval_endQuando o Scheduler disparaO que a task deve processar
03/08/2026 00:0004/08/2026 00:0004/08/2026 00:00"os dados de 03/08"
04/08/2026 00:0005/08/2026 00:0005/08/2026 00:00"os dados de 04/08"
05/08/2026 00:0006/08/2026 00:0006/08/2026 00:00"os dados de 05/08"
🕰️ logical_date (antigo execution_date)
É o data_interval_start — a data que identifica a execução e aparece nos logs/URL da UI. Em versões antigas do Airflow (pré-2.2), esse era o único nome usado, e muita documentação por aí ainda fala em execution_date.
🧩 {{ ds }} — o template mais usado
Dentro de um template Jinja (ex: num BashOperator), {{ ds }} vira a string "2026-08-03" — a data do intervalo que essa execução representa, pronta para usar num nome de arquivo ou filtro de query.
pythoncopiar@task def extrair_vendas(data_interval_start=None, data_interval_end=None): # na execução que dispara em 04/08, esses valores chegam como: # data_interval_start = 2026-08-03 00:00 # data_interval_end = 2026-08-04 00:00 return buscar_vendas_do_periodo(data_interval_start, data_interval_end)

⚠️ Essa é a razão pela qual, ao ligar um DAG novo com start_date no passado, a primeira execução que dispara processa o primeiro intervalo completo — não "agora". Entender isso evita muita confusão do tipo "liguei o DAG e ele não rodou pra hoje!" (ele vai rodar amanhã, processando hoje).

A sala de máquinas
🏗️ Arquitetura por dentro — quem faz o quê

O Airflow não é um programa único — é um conjunto de peças que conversam entre si através de um banco de dados compartilhado. Clique em cada bloco abaixo para entender seu papel.

Analogia

Pense numa escola: a secretaria (Scheduler) decide o horário de cada aula e avisa quando é hora de começar. O mural de avisos (Webserver) é onde todo mundo vê o calendário. O livro de registros (Metadata Database) guarda quem fez o quê e quando. E os professores (Workers) são quem de fato "dá a aula" — executam o conteúdo da task. O Executor é o coordenador que decide quantos professores estão disponíveis e como distribuir as aulas entre eles.

💡 Repare que o Scheduler nunca executa o código da sua task diretamente — ele só decide "está na hora, dispare!" e delega a execução de fato ao Executor. Essa separação é o que permite escalar o Airflow: trocar o Executor muda onde e como as tasks rodam, sem mudar nada no código dos DAGs.

Quantos "trabalhadores" ao mesmo tempo?
🏎️ Executors — a diferença entre 1 fila e várias

O Executor decide onde e quantas tasks ao mesmo tempo rodam. Trocar de Executor não muda uma linha do seu DAG — só muda o quanto ele escala. Escolha um executor abaixo e veja o impacto no tempo total do nosso DAG de vendas (extrair → 3 transformações em paralelo → carregar).

Simule o tempo total do DAG em cada Executor
1️⃣ SequentialExecutor
Uma task de cada vez, sempre — mesmo tasks independentes esperam na fila. Usa SQLite. Só serve para testar o Airflow localmente, nunca para produção.
💻 LocalExecutor
Roda várias tasks em paralelo como processos na mesma máquina do Scheduler, até um limite de parallelism. Simples de operar, ótimo para times pequenos/médios.
🐝 CeleryExecutor
Distribui tasks para várias máquinas worker através de uma fila de mensagens (Redis/RabbitMQ). Escala horizontalmente — adicione mais workers, processe mais tasks ao mesmo tempo.
☸️ KubernetesExecutor
Cada task roda no seu próprio pod efêmero do Kubernetes, criado sob demanda e destruído ao terminar. Isolamento máximo e autoscaling nativo, ao custo de um tempo de "cold start" por task.
A vida de uma task
🚦 Ciclo de vida de uma Task Instance

Cada vez que uma task roda dentro de um DAG Run específico, ela vira uma Task Instance — e essa instância percorre uma série de estados, visíveis na UI através de cores. Entender essa "semáforo" é essencial para debugar qualquer DAG.

Mas nem sempre o caminho é feliz — abaixo, os estados "de desvio" mais importantes:

❌ failed
A task rodou e deu erro. Sem retries restantes.
🔁 up_for_retry
Falhou, mas ainda tem tentativas — vai rodar de novo em breve.
⏭️ skipped
Foi deliberadamente pulada (ex: um branch que não foi escolhido).
⛔ upstream_failed
Nem chegou a rodar, porque uma task da qual ela depende falhou antes.
🚦
Analogia

É exatamente como um semáforo de trânsito com mais de três cores: cinza é "ainda nem chegou nessa rua", amarelo é "esperando abrir passagem", azul piscando é "atravessando agora", verde é "passou tranquilo", e vermelho é "bateu, precisa de atenção". A tela do Airflow (o "Grid" e o "Graph") é basicamente esse semáforo aplicado a cada task, em cada dia.

Comunicação entre tasks
📬 XComs — bilhetinhos de recado entre tasks

Cada task do Airflow roda isolada — possivelmente em máquinas diferentes. Então como uma task "conta" um resultado pequeno para a próxima? Através de XCom (abreviação de cross-communication): um mecanismo simples de chave-valor, guardado no banco de metadados, que qualquer task pode "empurrar" (push) e a próxima pode "puxar" (pull).

📝
Analogia

É como deixar um bilhete colado na geladeira para quem chegar depois: "comprei 3 caixas de leite". Funciona ótimo para um recado curto — mas ninguém cola um armário inteiro na porta da geladeira. XCom é exatamente assim: perfeito para IDs, contagens, nomes de arquivo, pequenos JSONs — péssimo para DataFrames gigantes ou arquivos pesados.

pythoncopiar@task def extrair_vendas(): total = buscar_total_de_vendas() return total # TaskFlow empurra (push) isso pro XCom automaticamente @task def avisar_se_vendas_caiu(total_vendas): # e puxa (pull) aqui, como argumento if total_vendas < 1000: enviar_alerta_slack("Vendas abaixo do esperado!") total = extrair_vendas() avisar_se_vendas_caiu(total)

No estilo clássico (sem TaskFlow), o mesmo recado é passado explicitamente com xcom_push / xcom_pull, usando o objeto de contexto ti (task instance):

pythoncopiardef extrair(**context): context["ti"].xcom_push(key="total_vendas", value=4521) def avisar(**context): total = context["ti"].xcom_pull(task_ids="extrair", key="total_vendas")

⚠️ Por padrão, XComs ficam no banco de metadados relacional — um valor gigante lá deixa o banco lento para todo mundo, não só para o seu DAG. Para dados grandes, passe apenas uma referência (ex: o caminho de um arquivo no S3) via XCom, e deixe o dado de verdade no armazenamento apropriado.

Esperando o mundo externo
👀 Sensors — o vigia que espera algo acontecer

Um Sensor é um tipo especial de task que fica checando repetidamente se uma condição externa ficou verdadeira — "esse arquivo já chegou no S3?", "essa outra DAG já terminou?" — e só deixa o DAG seguir adiante quando a resposta for sim.

📮
Analogia

É a criança sentada no muro de casa esperando o carro do correio chegar. Ela pode ficar de olho o tempo todo, sem piscar (gastando a atenção dela inteira nisso), pode dar uma espiada a cada 5 minutos e voltar a brincar entre uma espiada e outra (mais eficiente!), ou — melhor ainda — pode pedir pro cachorro latir quando o carro aparecer e ir brincar tranquila, sem gastar atenção nenhuma até o aviso chegar.

👁️ mode="poke" (padrão)
Ocupa um worker inteiro do início ao fim, checando em intervalos (poke_interval). Simples, mas desperdiça um "slot" de execução enquanto só espera.
😴 mode="reschedule"
Libera o worker entre uma checagem e outra, virando up_for_reschedule — muito mais eficiente para esperas longas (minutos/horas).
⚡ Deferrable / Triggerer
A opção mais moderna: a espera vira assíncrona e roda no Triggerer (não num worker), liberando recursos quase por completo enquanto aguarda.
pythoncopiarfrom airflow.providers.amazon.aws.sensors.s3 import S3KeySensor esperar_arquivo = S3KeySensor( task_id="esperar_arquivo_vendas", bucket_name="meu-bucket", bucket_key="vendas/{{ ds }}/dados.csv", poke_interval=60, # checa a cada 60s timeout=60 * 60 * 3, # desiste depois de 3h mode="reschedule", )
Bifurcações no caminho
🔀 Branching — escolhendo qual caminho seguir

Às vezes o DAG precisa decidir, em tempo de execução, qual caminho seguir — "se hoje é dia útil, roda o pipeline completo; se é fim de semana, só manda um resumo". Isso é @task.branch (ou o clássico BranchPythonOperator): uma task que, em vez de fazer um trabalho, retorna o task_id do próximo passo a seguir — e todos os outros caminhos possíveis viram skipped automaticamente.

🛤️
Analogia

É o garfo na estrada de uma história "escolha sua aventura": você lê a pergunta ("está chovendo?"), escolhe um caminho ("sim" ou "não"), e as páginas do outro caminho simplesmente não são lidas — elas não "falharam", só nunca foram visitadas. É exatamente esse o estado skipped que vimos na seção de estados.

Por padrão (all_success), o Airflow exige que todos os pais tenham sucesso — mas um deles vai estar skipped de propósito! Por isso se usa trigger_rule="none_failed": "segue em frente desde que ninguém tenha falhado de verdade".

Organizando e multiplicando tasks
📦 TaskGroups & Dynamic Task Mapping

Duas ferramentas para DAGs que crescem: TaskGroups agrupam tasks visualmente na UI (uma "pastinha" que dobra e desdobra, sem mudar a execução), e Dynamic Task Mapping cria automaticamente uma task para cada item de uma lista descoberta em tempo de execução — sem você precisar saber, ao escrever o código, quantas vão existir.

🗂️ TaskGroup — organização visual
As três tasks de transformação, escondidas dentro de uma "pasta" chamada transformacoes no Graph View — puramente cosmético, o comportamento de execução não muda em nada.

Falando com o mundo lá fora
🔌 Hooks & Connections

Uma Connection guarda, de forma centralizada e criptografada, o "endereço e a chave" de um sistema externo — host, porta, usuário, senha de um banco, um bucket S3, um workspace do Slack. Um Hook é o cliente Python que sabe usar essa connection para de fato conversar com o sistema — é o que os Operators usam por baixo dos panos.

🔑
Analogia

Connection é a chave e o endereço da casa, guardados num chaveiro central e trancado. Hook é o carteiro que sabe exatamente como usar aquela chave para entrar, deixar a encomenda no lugar certo e sair — sem que você precise explicar pra ele, toda vez, como a fechadura funciona.

🔐 Onde ficam as Connections
Cadastradas na UI (Admin → Connections), via variável de ambiente, ou — em produção — num Secrets Backend externo (Vault, AWS Secrets Manager, GCP Secret Manager). Nunca hardcoded no código do DAG.
🧰 Hook em ação
Um PostgresHook(postgres_conn_id="dw_vendas") sabe abrir a conexão, rodar a query e devolver o resultado — toda a complexidade de driver/conexão fica escondida atrás de poucas linhas.
pythoncopiarfrom airflow.providers.postgres.hooks.postgres import PostgresHook @task def contar_vendas_do_dia(): hook = PostgresHook(postgres_conn_id="dw_vendas") return hook.get_first("SELECT COUNT(*) FROM fato_vendas WHERE data = CURRENT_DATE")
Quando algo dá errado
🔁 Retries, SLA & Alertas

Sistemas externos falham por motivos temporários o tempo todo — uma API que engasgou por 5 segundos, uma rede instável. O Airflow trata isso como algo esperado, não excepcional: cada task pode ter uma política própria de tentar de novo, esperar antes de tentar, desistir depois de um tempo, e avisar alguém quando algo realmente quebra.

🚪
Analogia

Se você bate numa porta e ninguém atende, faz sentido bater de novo — mas não imediatamente, e não para sempre. Você espera um pouquinho (retry_delay), tenta de novo algumas vezes (retries), e se ainda assim ninguém atender, você desiste e liga pra alguém avisando (on_failure_callback).

pythoncopiarfrom datetime import timedelta @task( retries=3, retry_delay=timedelta(minutes=2), retry_exponential_backoff=True, # 2min, 4min, 8min... execution_timeout=timedelta(minutes=30), on_failure_callback=avisar_time_no_slack, ) def extrair_vendas(): return chamar_api_instavel()
🔁 retries + retry_delay
Quantas vezes tentar de novo, e quanto esperar entre uma tentativa e outra antes de virar failed de vez.
⏱️ execution_timeout
Tempo máximo que uma task pode rodar antes de ser cancelada à força — evita uma task "travada" segurando um worker para sempre.
📢 callbacks
on_failure_callback, on_success_callback, on_retry_callback — funções chamadas automaticamente nesses eventos, ótimo para integrar com Slack, PagerDuty, e-mail.
Voltando no tempo
⏮️ Backfill & Catchup — recuperando o passado

Como o Airflow sabe processar qualquer intervalo de datas (não só "agora"), ele consegue fazer algo raro entre orquestradores: reprocessar o passado como se fosse a coisa mais normal do mundo. Dois mecanismos cuidam disso — catchup, automático, e backfill, manual.

1
catchup=True (o padrão) — recupera runs perdidos sozinho
Se um DAG tem start_date=2026-01-01 e é ligado só em 15/01, o Scheduler cria e dispara, em sequência, uma execução para cada dia perdido entre 01/01 e 15/01 — não só a mais recente. É ótimo para nunca deixar um "buraco" no histórico, mas perigoso se ninguém esperava 15 execuções simultâneas martelando uma API externa de uma vez.
2
catchup=False — só olha para frente
O DAG ignora todo o passado entre start_date e agora, e só começa a criar execuções a partir da próxima vez que o schedule mandar. É o valor recomendado para a maioria dos DAGs novos, justamente para evitar a avalanche de runs do item acima.
3
Backfill manual — reprocessar de propósito
Mesmo com catchup=False, você pode pedir explicitamente para reprocessar um intervalo — por exemplo, depois de corrigir um bug que afetou os cálculos da semana passada. Isso é feito via CLI (ou UI, a partir do Airflow 2.x mais recente), sem alterar o DAG:
bashcopiar# reprocessa de 01/01 até 10/01, ignorando o que já rodou airflow dags backfill \ --start-date 2026-01-01 \ --end-date 2026-01-10 \ dag_vendas_diarias
🗓️
Analogia

É como voltar num caderno de anotações diárias que ficou esquecido por duas semanas: catchup=True é preencher toda página em branco, uma por dia, até chegar em hoje. catchup=False é virar direto pra página de hoje e seguir em frente. E "backfill manual" é pegar uma caneta e corrigir de propósito uma página específica de duas semanas atrás, porque você percebeu um erro nela.

Antes de ir para produção
✅ Boas Práticas
♻️ Idempotência
Rodar a mesma task duas vezes para o mesmo data_interval deve dar o mesmo resultado, sem duplicar dados. Prefira DELETE + INSERT ou MERGE a um INSERT simples.
🧱 Tasks atômicas
Uma task, uma responsabilidade. "Extrai e transforma e carrega" numa task só dificulta retry seletivo e observabilidade — se falhar no meio, tem que refazer tudo.
🚫 Nada pesado no topo do arquivo
Código fora de funções/tasks roda toda vez que o Scheduler relê o arquivo (a cada poucos segundos!) — nunca faça uma chamada de API ou query pesada fora de uma task.
🔑 Connections nunca hardcoded
Sempre via Connections/Variables da UI ou um Secrets Backend — nunca senha ou token escritos direto no código do DAG.
⏱️ Sempre defina retries + timeout
Um default_args no nível do DAG com retries e execution_timeout razoáveis evita tanto falhas por instabilidade momentânea quanto tasks travadas para sempre.
🧪 Teste seus DAGs
Rode python meu_dag.py para pegar erros de import cedo, use dag.test() para simular um run completo localmente, e escreva testes unitários para a lógica de dentro das tasks.

💡 Regra de ouro: pense no seu DAG como código de produção de verdade — versionado no Git, revisado em PR, com testes — porque é exatamente isso que ele é. A diferença para qualquer outro sistema é que ele roda sozinho, todo dia, sem ninguém olhando.

Onde o Airflow se encaixa
📊 Airflow vs. Outras Ferramentas

Airflow não compete com tudo — ele resolve um problema específico (orquestração), e frequentemente trabalha ao lado de outras ferramentas, não no lugar delas.

FerramentaO que fazRelação com o Airflow
CronSó dispara um comando num horário fixo.Sem dependências entre tarefas, sem retry, sem histórico visual, sem backfill. O Airflow "é um cron com cérebro".
dbtTransforma dados dentro do Data Warehouse, em SQL declarativo.Complementares, não concorrentes: o Airflow costuma disparar um dbt run como uma task do pipeline.
Spark / DuckDBMotores de processamento — de fato transformam grandes volumes de dados.O Airflow aciona um job Spark ou uma query DuckDB na hora certa — não substitui o motor de processamento.
LuigiOrquestrador mais antigo (Spotify), foco em dependências de arquivo.Precursor conceitual do Airflow — hoje bem menos ativo/adotado em novos projetos.
Prefect / DagsterOrquestradores mais recentes, com foco em DX (developer experience) e tipagem de dados.Concorrentes diretos do Airflow — resolvem o mesmo problema com filosofias diferentes de configuração e observabilidade.
