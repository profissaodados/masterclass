Antes de um dado chegar no seu painel, alguém devia checar se ele está certo

Great Expectations (hoje chamado apenas de GX) é um framework open source em Python que faz exatamente isso: você escreve expectativas sobre como seus dados deveriam ser — "esta coluna nunca pode ser nula", "esta idade tem que estar entre 0 e 120", "este valor tem que ser positivo" — e o GX testa essas regras contra os dados de verdade, toda vez que uma nova leva chega. Se algo quebra a regra, ele avisa antes que o erro vire um relatório errado, uma decisão ruim ou um cliente irritado.

Fundamentos
🧸 Por que qualidade de dados importa (explicado como para uma criança)

Imagine uma fábrica de brinquedos. Antes de qualquer boneco sair da fábrica, um inspetor confere: "tem os dois olhos?", "a pintura não está borrada?", "não tem peça solta que uma criança possa engolir?". Se o brinquedo passa, ele vai pra loja. Se não passa, ele é separado ali mesmo, antes de chegar em qualquer criança. Dados funcionam do mesmo jeito: eles saem de sistemas, passam por pipelines e chegam em painéis, modelos de machine learning e decisões de negócio. Sem um inspetor no meio do caminho, um "brinquedo quebrado" — uma linha com idade "-5" ou um e-mail vazio — segue viagem até o fim, sem ninguém perceber.

🏭 Sem inspetor
O dado ruim entra pela ponta ("idade = -5", "país = XX") e sai do outro lado direto no painel do diretor, sem ninguém barrar no meio do caminho.
📉 Decisão errada
Um painel de vendas "bonito" mas alimentado com dados sujos gera conclusões erradas — e decisões de negócio tomadas em cima de números que não existem de verdade.
🔥 Descoberto tarde demais
Sem validação automática, o erro só é percebido quando alguém desconfia de um número estranho — dias ou semanas depois do problema ter começado.
Garbage in, garbage out

É o ditado mais velho da computação: se o que entra é lixo, o que sai também é lixo — não importa o quão sofisticado seja o pipeline, o dashboard ou o modelo de IA no fim da linha. Great Expectations existe para colocar um inspetor automático logo na entrada, testando cada nova leva de dados contra um checklist antes de deixá-la seguir.

Fundamentos
🔍 O que é o Great Expectations?

Great Expectations é uma biblioteca Python open source (licença Apache 2.0) criada em 2017 por Abe Gong e James Campbell, sob a empresa Superconductive — hoje simplesmente chamada GX. A ideia central: em vez de escrever if/assert soltos espalhados pelo código do pipeline, você declara suas regras de qualidade de forma estruturada e reutilizável, chamadas Expectations. O GX roda essas regras contra os dados de verdade, guarda o resultado, e ainda publica um relatório HTML navegável — os Data Docs — para qualquer pessoa do time conferir sem precisar ler código.

📜 Declarativo
Você descreve o que espera dos dados (expect_column_values_to_not_be_null), não como checar isso linha a linha — o GX cuida da execução.
🧠 Motor plugável
A mesma Expectation roda sobre Pandas, Spark ou um banco SQL — você troca a fonte dos dados sem reescrever as regras.
📑 Documentação viva
Cada suite de regras já é a documentação do que o dataset deveria ser — e vira automaticamente um relatório em HTML.

💡 O nome não é acaso: você declara suas "grandes expectativas" sobre os dados — e o framework verifica, a cada execução, se a realidade bate com o que você esperava. Hoje a versão atual (chamada GX Core) simplificou bastante a API de versões antigas, e existe também uma versão hospedada, a GX Cloud.

A Menor Peça
🔬 Anatomia de uma Expectation

Uma Expectation é a unidade mais básica do GX: uma única afirmação, verificável, sobre uma coluna ou tabela. O nome do método sempre segue o mesmo padrão em inglês — expect_<sujeito>_to_<condição> — o que faz até quem nunca usou o GX conseguir "ler" a regra em voz alta.

pythoncopiarvalidator.expect_column_values_to_not_be_null("email") validator.expect_column_values_to_be_between("idade", min_value=0, max_value=120) validator.expect_column_values_to_be_in_set("pais", ["BR", "US", "PT", "AR"]) validator.expect_column_values_to_be_between("valor_pedido", min_value=0.01)
🧍 Sujeito
column, column_pair, multicolumn ou table — o que está sendo testado: uma coluna, duas colunas relacionadas, várias colunas juntas ou a tabela inteira.
⚖️ Condição
to_not_be_null, to_be_between, to_be_in_set, to_match_regex — a regra em si, em inglês quase natural.
🎚️ mostly
Parâmetro opcional que tolera uma % de exceções — ex: mostly=0.95 aceita até 5% de linhas fora da regra sem marcar falha total. Ideal para dados do mundo real, que raramente são 100% perfeitos.

💡 Cada Expectation é ao mesmo tempo um teste (roda e retorna passou/falhou) e uma documentação (o nome já explica a regra em português claro). Existem mais de 300 Expectations prontas na "Expectation Gallery" da comunidade — e dá pra criar as suas próprias quando nenhuma pronta serve.

📋 Tipos de Expectations

As Expectations prontas se agrupam em algumas famílias. Você raramente precisa de todas — a maioria das suites reais combina só 4 ou 5 tipos diferentes, aplicados às colunas certas.

Onde a Validação Roda de Verdade
🚦 Checkpoints: o portão de entrada

Uma Expectation Suite sozinha é só uma lista de regras — ela não faz nada até alguém rodá-la contra dados reais. É isso que o Checkpoint faz: ele empacota quais dados validar, qual suite aplicar, e o que fazer com o resultado (as chamadas Actions). Pense nele como a cancela do estacionamento: todo carro (batch de dados) passa por ali, é conferido, e só então o portão abre — ou não.

pythoncopiarcheckpoint = context.add_or_update_checkpoint( name="pedidos_diarios_checkpoint", validation_definitions=[validation_definition], ) resultado = checkpoint.run() if not resultado.success: avisar_time_no_slack("🚨 Dados de pedidos falharam na validação!") raise Exception("Pipeline interrompido — dado não confiável")
Action (o que acontece após rodar)Para que serve
Store Validation ResultSalva o resultado (JSON) num Store — arquivo local, S3, banco — para histórico e auditoria.
Update Data DocsRegenera o relatório HTML público com o resultado mais recente.
Slack / E-mail NotificationAvisa o time automaticamente quando algo falha — sem ninguém precisar ficar checando manualmente.
Custom ActionQualquer código Python seu — como interromper um DAG do Airflow, abrir um ticket, ou bloquear um deploy.

Em Produção
☁️ Great Expectations em escala: Spark + Airflow no EMR

Em produção, o GX raramente roda sozinho — ele entra como mais um passo dentro do pipeline. Um padrão comum: o Airflow orquestra um cluster EMR que sobe um job Spark; o Spark lê os dados brutos do S3 e, antes de gravar na camada curada, o GX valida o DataFrame Spark diretamente (usando o motor de execução Spark do GX, sem precisar converter para Pandas). Compare o pipeline sem e com essa inspeção — clique nos blocos.

Grava direto na camada curada
Dashboard / modelo usa o dado — já contaminado
✅ Pipeline com Great Expectations

🎯 Casos de Uso
🚪 Portão de entrada do Data Lake
Validar arquivos brutos assim que chegam (S3, landing zone) antes de qualquer transformação consumir esse dado.
🔁 Entre etapas de um pipeline ETL/ELT
Checar a saída de cada etapa (bronze → silver → gold) para não deixar um erro se propagar e se multiplicar pipeline abaixo.
🤖 Antes de treinar um modelo de ML
Garantir que o dataset de treino não tem nulos inesperados, outliers absurdos ou drift de schema, antes de gastar horas de treino.
📊 Antes de publicar um relatório de BI
Bloquear a atualização de um dashboard executivo se os números da base mudaram de forma anômala.
🤝 Contrato entre times
Um time de dados publica uma Expectation Suite como "contrato" — outro time consumidor sabe exatamente o que pode esperar daquela tabela.
📜 Auditoria e compliance
Data Docs funcionam como evidência histórica de que os dados foram checados — útil em setores regulados (financeiro, saúde).
Checklist
✅ Boas Práticas
🎯 Comece pequeno, com o que mais dói
Não tente cobrir 100% das colunas no primeiro dia. Comece pelas 3-4 regras que, se quebrarem, causam o maior estrago — nulidade de chaves, tipos e ranges óbvios.
🎚️ Use mostly com intenção
Dados reais raramente são 100% perfeitos. Definir mostly=0.98 conscientemente é melhor do que uma regra rígida demais que quebra o pipeline toda semana à toa.
🔔 Conecte a um canal de alerta de verdade
Uma validação que falha silenciosamente, sem notificar ninguém, tem o mesmo efeito de não ter validação nenhuma.
📑 Publique os Data Docs em local acessível
Hospede o relatório num bucket S3 estático ou site interno — quanto mais fácil for pra outras pessoas do time conferir, mais confiança o processo gera.

⚠️ Great Expectations valida a forma dos dados (nulos, tipos, ranges, padrões) — ele não substitui a validação de regra de negócio profunda, que geralmente exige contexto humano. Use-o como a primeira linha de defesa, não como a única.
