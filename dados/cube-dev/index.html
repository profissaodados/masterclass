Toda ferramenta de BI já sabe falar Postgres. E se a sua camada de métricas também falasse?

O Cube.dev é uma semantic layer (camada de métricas) open source — a mesma ideia do dbt Semantic Layer: definir "receita" e "ticket médio" uma única vez, num lugar central, para qualquer ferramenta consultar. A diferença está em como essa definição chega até você. Em vez de inventar uma API nova que cada ferramenta de BI precisaria aprender a falar, o Cube decidiu fingir ser um banco de dados Postgres comum. Qualquer ferramenta que já sabe se conectar a um Postgres — Power BI, Metabase, Tableau, DBeaver, Excel — conecta direto na camada de métricas do Cube, sem esperar um conector dedicado. Além da SQL API, o Cube também expõe REST API e GraphQL API, para quando você está construindo sua própria aplicação.

O Gatilho de Tudo
❓ O problema: métricas centralizadas, mas só um punhado de ferramentas sabe "conversar" com elas

O dbt Semantic Layer resolveu o problema de números divergentes: uma métrica, uma definição. Mas ele criou um problema novo — expôs essa definição através de uma API própria (GraphQL + um driver JDBC chamado Arrow Flight SQL). Toda ferramenta de BI que quiser consultar essa API precisa construir, do zero, um conector dedicado para falar essa língua nova. Hoje, só um punhado de ferramentas fez esse trabalho: Tableau, Google Sheets, Excel, Hex, Mode, Sigma. Power BI e Metabase — duas das ferramentas mais usadas no mercado — não têm conector nativo. Power BI só funciona via script Python (importação, não consulta ao vivo); Metabase exigiria um driver JDBC customizado que simplesmente não existe pronto.

🗺️
Pensando como criança

Imagine que você inventou um idioma novo, todo certinho, com gramática perfeita — mas só seis dos seus amigos aprenderam a falar com você. Os outros amigos, que já falam um idioma muito mais comum (tipo o "português" das ferramentas de banco de dados: o Postgres), ficam de fora, mesmo que a mensagem que você quer passar seja exatamente a mesma. O Cube.dev resolveu isso ao decidir aprender a falar o idioma que todo mundo já sabia, em vez de esperar todo mundo aprender o idioma novo.

Fundamentos
🧠 Então, o que é exatamente o Cube.dev?

O Cube.dev é uma camada que fica entre o seu banco de dados (Postgres, Snowflake, BigQuery, DuckDB, e mais de 20 outros) e as ferramentas que consomem números. Você descreve suas tabelas em termos de negócio — um Cube Schema — e o Cube.dev traduz perguntas ("qual foi a receita por status, em março?") em SQL otimizado para o seu banco. Até aqui, é exatamente a mesma ideia do dbt Semantic Layer. A diferença é o "sotaque": o Cube expõe tudo isso através de um servidor que finge ser um Postgres de verdade — a chamada SQL API — além de uma REST API e uma GraphQL API próprias.

🗣️ API nova (dbt Semantic Layer)
Expõe GraphQL + Arrow Flight SQL (JDBC). Poderosa, mas exige que cada ferramenta construa um conector dedicado para entender essa API.
🐘 Protocolo universal (Cube.dev)
Expõe Postgres wire protocol — o mesmo "idioma" que qualquer driver, ODBC, ou ferramenta de BI já sabe falar há décadas.
⚙️ Cube API Server
O "tradutor" de verdade: lê o Cube Schema e compila SQL válido, na hora, para o seu banco — igual o MetricFlow faz no mundo dbt.

💡 O Cube.dev não é exclusivo do ecossistema dbt — ele é agnóstico de ferramenta de transformação. Funciona em cima de qualquer banco ou warehouse, tenha você usado dbt para transformar os dados ou não.

A peça central
🧊 Cube Schema — dimensions, measures e joins, tudo num único arquivo

Um cube é a unidade básica do Cube.dev: um arquivo que descreve uma tabela (ou uma consulta) em termos que qualquer pessoa de negócio entende. Diferente do dbt Semantic Layer — que separa a "ficha técnica" (semantic model) da "receita" (metric) em dois conceitos — o Cube junta tudo num único lugar: dimensions (o que agrupa e filtra), measures (o que já é a métrica de negócio, pronta para consumo) e joins (como esse cube se conecta com outros). O Cube Schema pode ser escrito em YAML ou em JavaScript — em JS, você ganha a possibilidade de gerar cubos dinamicamente com código.

🧊
Analogia

Se no dbt Semantic Layer a "ficha técnica do brinquedo" (semantic model) e a "receita de como brincar" (metric) são duas folhas separadas, no Cube.dev elas viram um cubo mágico único: cada lado do cubo já mostra tanto o encaixe (join) quanto a etiqueta (dimension) quanto a contagem pronta (measure). Você olha para um cubo só e já sabe tudo sobre aquele pedaço do seu negócio.

Conectando cubos
🔗 Joins — o encaixe declarado explicitamente, com SQL de verdade

Uma métrica raramente vive sozinha num cubo só. Para agrupar "receita" (que mora no cubo orders) por "região" (que mora no cubo users), o Cube precisa saber como ligar os dois. No dbt Semantic Layer, essa ligação é inferida a partir de entities com nomes compatíveis. No Cube.dev, você declara o join explicitamente, com uma condição SQL e um tipo de relacionamento (one_to_one, one_to_many, many_to_one) — menos "mágica automática", mais controle sobre exatamente como o encaixe acontece.

1️⃣ one_to_one
Cada linha de um cubo corresponde a exatamente 1 linha do outro. Raro — ex: orders e order_details 1 pra 1.
🔁 one_to_many
1 linha aqui pode casar com várias linhas do outro cubo. Ex: users → vários orders.
↩️ many_to_one
Várias linhas aqui apontam pra 1 linha do outro. Ex: orders → 1 users. O mais comum em fatos apontando pra dimensões.

💡 Na SQL API, você não aciona esse join com um ON orders.user_id = users.id — a coluna física não fica exposta como campo, a menos que você a declare como dimension. O jeito certo é ON orders.__cubeJoinField = users.__cubeJoinField, um campo especial que aciona o join já descrito no joins: do schema. Confirmado rodando o projeto prático desta aula.

O diferencial
⚡ Pre-aggregations — o cache que o dbt Semantic Layer não tem de forma explícita

Toda vez que alguém pede uma métrica ao MetricFlow, ele recalcula do zero, direto no warehouse — não existe uma camada de cache própria; a velocidade depende inteiramente do seu banco. O Cube.dev resolve isso com pre-aggregations: você declara, dentro do próprio cubo, um resumo (rollup) que deve ser materializado e mantido atualizado num armazenamento rápido chamado Cube Store. Quando uma consulta bate com esse resumo, o Cube responde a partir do cache — não do banco de origem.

🍱
Analogia

É a diferença entre cozinhar o jantar do zero toda vez que alguém tem fome, e ter uma marmita pronta na geladeira para as perguntas mais comuns. Se todo dia 200 pessoas perguntam "quanto vendemos por status, hoje?", não faz sentido escanear a tabela inteira 200 vezes — você prepara essa marmita (a pre-aggregation) uma vez, atualiza de tempos em tempos, e serve na hora pra quem perguntar.

yamlcopiarcubes: - name: orders # ...dimensions e measures já definidas acima... pre_aggregations: - name: orders_by_status_daily measures: - orders.count - orders.total_amount dimensions: - orders.status time_dimension: orders.created_at granularity: day refresh_key: every: 1 hour # de quanto em quanto tempo o Cube Store se atualiza
❌ Sem pre-aggregation
Cada consulta escaneia a tabela inteira no warehouse. Dashboards pesados ficam lentos e o custo de computação escala junto com o número de acessos.
✅ Com pre-aggregation
O resumo já está pronto no Cube Store. A consulta responde em dezenas de milissegundos, e o warehouse só é acionado quando o cache precisa ser atualizado.

💡 O Cube decide sozinho quando uma consulta "bate" com uma pre-aggregation existente (match automático) — você não precisa reescrever a pergunta de negócio para aproveitar o cache, só declarar o rollup uma vez no schema.

🐳 Rodando de verdade: Cube.dev + Postgres num Docker Compose

Existe um projeto completo, testado do início ao fim, na pasta cube_project/ ao lado desta aula. Ele sobe um Postgres real (a fonte dos dados) e o Cube.dev (self-hosted, via Docker) na frente dele — com um Cube Schema que reproduz exatamente os exemplos vistos até aqui. Os dados são os mesmos clientes e pedidos do projeto irmão loja_metrics (dbt Semantic Layer), de propósito: dá pra comparar as duas camadas de métricas sobre a base idêntica.

🏬 db-init/01_init.sql
Cria e popula customers (10 linhas) e orders (73 linhas) — os mesmos CSVs do loja_metrics.
🧊 model/cubes/*.yml
O Cube Schema de verdade: customers.yml e orders.yml, com joins, measures e 1 pre-aggregation.
🐳 docker-compose.yml
Sobe source-db (Postgres 16) e cube (Cube.dev) — 2 containers, nenhuma instalação local além do Docker.

1. Subir o ambiente e esperar a API ficar pronta:

bashcopiarcd cube_project docker compose up -d # espera a API responder 200 curl http://localhost:4000/readyz

⚠️ Se o projeto estiver num disco exFAT (comum em SSDs portáteis usados em Mac e Windows), o macOS cria arquivos ocultos ._nome.yml toda vez que o schema é salvo — o Cube tenta compilar esses arquivos e quebra com EPERM: operation not permitted. Se isso acontecer: find model -name '._*' -delete. O schema recarrega sozinho, sem precisar reiniciar o container.

2. Consultar pela SQL API — o coração da aula. Usando o psql que já vem dentro do container do Postgres, só pra não depender de instalar nada localmente:

bashcopiardocker exec -it cube_source_db bash -c "PGPASSWORD=cube psql -h cube -p 15432 -U cube -d cube_db"
sqlcopiar-- join entre cubos: measure de "orders" agrupada por dimension de "customers". -- __cubeJoinField é o campo especial que aciona o join já declarado no schema -- (ver aviso na seção Joins) — não é a coluna física customer_id. SELECT customers.region, MEASURE(orders.revenue) AS revenue FROM orders LEFT JOIN customers ON orders.__cubeJoinField = customers.__cubeJoinField GROUP BY 1 ORDER BY revenue DESC; -- region | revenue -- --------------+--------- -- Sudeste | 5102.3 -- Sul | 4651.63 -- Norte | 2115.95 -- Nordeste | 1382 -- Centro-Oeste | 1071.16

Repare que você não escreveu SUM, CASE WHEN nem o JOIN de verdade — só pediu MEASURE(orders.revenue) agrupado por customers.region. Por trás dessa pergunta simples, o Cube percorre 4 etapas antes de tocar no Postgres:

🐘1. Chega como SQLo psql manda a query como se falasse com um Postgres comum
→
🧠2. SQL API faz o parseum motor (Apache DataFusion) entende SELECT / MEASURE / JOIN
→
🧊3. Compilador do Schematroca orders.revenue e customers.region pelas colunas reais, com o filtro e o JOIN do schema
→
🏬4. SQL final no PostgresSELECT/SUM/CASE WHEN/JOIN de verdade, executado na fonte

O Cube tem um endpoint que mostra exatamente esse SQL final, sem executar nada — ótimo pra depurar uma measure ou conferir se o filtro saiu como esperado. Rodando ele para a mesma pergunta acima (revenue por region), o SQL gerado de verdade contra o Postgres foi este:

bashcopiar# pede o SQL compilado, sem executar — troque a query por qualquer outra pra depurar curl -H "Authorization: <TOKEN>" \ -G --data-urlencode 'query={"measures":["orders.revenue"],"dimensions":["customers.region"]}' \ http://localhost:4000/cubejs-api/v1/sql
sqlcopiar-- SQL real, devolvido pelo endpoint acima — é isto que rodou no source-db SELECT "customers".region AS "customers__region", sum(CASE WHEN ("orders".status NOT IN ('cancelled', 'refunded')) THEN "orders".order_total END) AS "orders__revenue" FROM public.orders AS "orders" LEFT JOIN public.customers AS "customers" ON "orders".customer_id = "customers".customer_id GROUP BY 1 ORDER BY 2 DESC LIMIT 10000

✅ O CASE WHEN status NOT IN ('cancelled', 'refunded') veio direto do filters: declarado na measure revenue (seção Cube Schema), e o LEFT JOIN ... ON orders.customer_id = customers.customer_id veio direto do joins: declarado no cubo orders (seção Joins) — nada disso foi escrito à mão na consulta.

Isso vale pras 3 APIs: SQL API, REST API e GraphQL API não são 3 motores diferentes — são 3 portas de entrada que convergem no mesmo compilador de schema, que sempre gera o mesmo SQL final para a mesma pergunta.

3. Consultar pela REST API e pela GraphQL API:

bashcopiar# REST API curl -H "Authorization: <TOKEN>" \ -G --data-urlencode 'query={"measures":["orders.revenue","orders.count","orders.average_order_value"]}' \ http://localhost:4000/cubejs-api/v1/load # {"data":[{"orders.revenue":"14323.04","orders.count":"73","orders.average_order_value":"255.7685714285714286"}]} # GraphQL API curl -X POST http://localhost:4000/cubejs-api/graphql \ -H "Authorization: <TOKEN>" \ -H "Content-Type: application/json" \ -d '{"query":"{ cube { orders { status, revenue } } }"}'

4. Confirmar que a pre-aggregation está sendo usada de verdade — o campo usedPreAggregations na resposta mostra a tabela materializada no Cube Store, em vez de recalcular no Postgres:

bashcopiarcurl -H "Authorization: <TOKEN>" \ -G --data-urlencode 'query={"measures":["orders.revenue"],"dimensions":["orders.status"],"timeDimensions":[{"dimension":"orders.created_at","granularity":"day"}]}' \ http://localhost:4000/cubejs-api/v1/load // resposta inclui: // "usedPreAggregations": { // "dev_pre_aggregations.orders_revenue_by_status_daily": { ... } // }

Checklist
✅ Boas Práticas
🧊 Um cube por tabela fato ou dimensão
Não misture grãos diferentes num mesmo cubo — se a granularidade muda, provavelmente é hora de um cubo novo.
🔗 Declare o relationship certo em cada join
one_to_many, many_to_one ou one_to_one errado gera fan-out silencioso — métricas somadas em duplicidade sem nenhum erro visível.
⚡ Comece sem pre-aggregation, meça, depois adicione
Adicione rollups nas consultas que o time realmente repete — pre-aggregation em tudo só aumenta custo de manutenção sem ganho real.
🕰️ Defina sempre um refresh_key nas pre-aggregations
Sem ele, o cache pode ficar desatualizado sem nenhum aviso — decida explicitamente de quanto em quanto tempo os dados devem virar.
🏷️ Nomeie dimensions e measures como o negócio fala
Prefira revenue a sum_order_total_v2 — o nome da measure é o contrato com quem vai consumi-la.
🔐 Use security context para dado sensível
A SQL API expõe seus cubos como se fossem tabelas — sem row-level security no schema, qualquer usuário conectado enxerga tudo.
📦 Versione o Cube Schema num repositório git
Trate como qualquer outro código de produção, com revisão de PR — mudanças aqui afetam o número que todo mundo vê.
🧪 Compare os números durante uma migração
Se está migrando de outra camada de métricas, rode a mesma pergunta nas duas e confirme que os resultados batem antes de desligar a antiga.
