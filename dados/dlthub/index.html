Uma esteira mágica que arruma a bagunça dos dados sozinha

dlt (data load tool) é uma biblioteca Python open source criada para resolver a parte mais chata e repetitiva de qualquer pipeline de dados: pegar dado de uma fonte (API, banco, arquivo), entender sua estrutura sozinho, organizar tudo em tabelas relacionais — mesmo quando o dado vem cheio de listas e objetos aninhados — e carregar num destino (DuckDB, BigQuery, Snowflake, Postgres...), sem que você precise desenhar o schema na mão. Lançado em 2022 pela dltHub, ele roda como uma simples biblioteca dentro do seu script Python: sem servidor, sem interface para configurar, sem cluster para gerenciar.

Fundamentos
🎁 O que é o dlt?

Imagine que toda semana chegam caixas de brinquedos bagunçadas na sua casa: uma caixa de uma loja tem carrinhos soltos, outra caixa de outra loja tem bonecos dentro de saquinhos dentro de outros saquinhos. Você quer guardar tudo organizado, em prateleiras com etiquetas — uma prateleira para carrinhos, outra para bonecos — sem ter que abrir caixa por caixa e decidir isso na mão toda vez. É exatamente esse o trabalho que o dlt faz com dados: ele pega o que vem de uma fonte (API, banco de dados, arquivo, planilha), olha a forma de cada pedacinho e decide sozinho em qual "prateleira" (tabela) e "gaveta" (coluna) cada coisa cabe — inclusive quando um brinquedo tem outros brinquedos menores dentro dele (dado aninhado).

🧒 Explicando para uma criança

Pense no dlt como um robô arrumador muito esperto. Você despeja a caixa bagunçada na mesa dele. Ele olha cada peça, uma por uma: "isso é um número, vai na gaveta de números", "isso é um texto, vai na gaveta de textos", "ah, esse brinquedo tem peças penduradas nele, vou criar uma caixinha extra só pra essas peças e colar uma etiqueta ligando as duas". No fim, tudo vira gavetas certinhas, com etiqueta, prontas pra você achar qualquer coisa rapidinho.

🧠 Descobre o schema sozinho
Você não escreve CREATE TABLE. O dlt olha os dados recebidos, infere o tipo de cada campo (texto, número, data, booleano...) e cria as tabelas automaticamente.
🪆 Desaninha estruturas complexas
JSON com listas dentro de listas dentro de objetos? O dlt separa isso em tabelas relacionais ligadas por chaves — sem você escrever nenhum "achatador" manual.
🔁 Sabe o que já carregou
Guarda um "estado" entre execuções — então uma carga incremental só busca o que é novo, e reprocessar não duplica linha.
Origem

Criado em 2022 pela dltHub (empresa fundada por Matthaus Krzykowski e Adrian Brudaru, com base na experiência do time em engenharia de dados na Scale Vector e na comunidade de "verified sources" do Airbyte). Distribuído como biblioteca Python sob licença Apache 2.0 — 100% open source, instalável com um simples pip install dlt, sem "camada paga escondida" para usar o motor central.

Como Funciona por Dentro
🏗️ Anatomia de um Pipeline

Todo pipeline dlt segue a mesma esteira de 5 peças. Uma source agrupa um ou mais resources (cada resource é "um tipo de brinquedo" — um endpoint, uma tabela, um stream). O pipeline é a esteira que liga tudo a um destination (o banco onde os dados vão morar). Clique em cada peça para ver o que ela faz — em português técnico e em "modo criança".

👆 Clique em qualquer peça da esteira
Veja o papel de cada bloco, do dado bruto até a tabela pronta.
pythoncopiarimport dlt # 1) resource: "um tipo de brinquedo" — aqui, uma lista de clientes @dlt.resource(name="customers") def customers(): yield [{"id": 1, "name": "Ana"}, {"id": 2, "name": "Bruno"}] # 2) pipeline: a esteira, ligando fonte a destino pipeline = dlt.pipeline( pipeline_name="loja", destination="duckdb", dataset_name="loja_dados" ) # 3) run: dispara a esteira — extrai, normaliza, carrega info = pipeline.run(customers()) print(info)

💡 Uma source nada mais é do que uma função decorada com @dlt.source que agrupa vários @dlt.resource relacionados (ex: "clientes", "pedidos", "produtos" da mesma API). Você pode rodar um pipeline com uma única resource solta (como no exemplo acima) ou com uma source inteira — o dlt trata os dois casos da mesma forma.

O Motor por Dentro
⚙️ As 3 Etapas Escondidas: Extract → Normalize → Load

Quando você chama pipeline.run(...), o dlt executa três fases em sequência — como três estações de uma linha de produção de brinquedos. Clique em cada estação para ver o que ela entrega para a próxima.

📥 Extract
Chama sua função Python (o generator), pagina/percorre a API, e grava os dados brutos em arquivos temporários locais — sem ainda decidir tabelas ou tipos.
🧩 Normalize
Olha cada registro, infere tipos, desaninha listas e objetos em tabelas filhas, e gera/atualiza o schema — comparando com o schema salvo da execução anterior.
🚚 Load
Aplica o schema no destino (cria/altera tabelas se preciso) e insere os dados normalizados, respeitando o write disposition escolhido (append, replace ou merge).

Os Blocos de Construção
🧺 Sources & Resources

Uma resource é uma função Python "geradora" (yield) decorada com @dlt.resource — cada yield pode devolver um item ou uma lista de itens, e o dlt processa em streaming, sem precisar carregar tudo na memória de uma vez. Uma source agrupa várias resources relacionadas, geralmente da mesma API.

Resource simples
pythoncopiar@dlt.resource(name="produtos", write_disposition="append") def produtos(): yield {"id": 1, "nome": "Bola"} yield {"id": 2, "nome": "Pipa"}
Source agrupando resources
pythoncopiar@dlt.source def loja_de_brinquedos(): return [produtos(), clientes(), pedidos()] pipeline.run(loja_de_brinquedos())
🌐 REST API genérica
Com rest_api_source(...), você descreve endpoints, paginação e autenticação em um dicionário de configuração — sem escrever loop de paginação na mão.
🗄️ Banco de dados (sql_database)
Aponta para um banco existente (Postgres, MySQL...) e replica tabelas inteiras — ou só as linhas novas — para outro destino.
📄 Arquivos (filesystem)
Lê CSV, JSON, Parquet de uma pasta local, S3, GCS ou Azure como se fosse uma resource comum.
pythoncopiarfrom dlt.sources.rest_api import rest_api_source fonte = rest_api_source({ "client": {"base_url": "https://api.loja.com/"}, "resources": [ {"name": "produtos", "endpoint": {"path": "produtos", "paginator": "json_link"}}, ], }) pipeline.run(fonte)
O Truque Mais Visual
🪆 Desaninhando Dados: de um "brinquedo boneca-russa" a Tabelas Relacionais

APIs adoram devolver JSON aninhado: um cliente que tem uma lista de pedidos dentro dele, cada pedido com seus próprios campos. Bancos relacionais não têm "coluna com lista dentro" — então o dlt desaninha automaticamente: cada lista vira uma tabela filha, ligada à tabela pai por uma chave gerada automaticamente. É como abrir a boneca russa e colocar cada bonequinha na sua própria caixinha, com um fio colorido ligando cada uma à caixa-mãe.

📥 O JSON que chega da API (aninhado)
{ "id": 1, "name": "Ana", "orders": [ { "order_id": 100, "item": "Bola" }, { "order_id": 101, "item": "Pipa" } ] }
🧒 Modo criança

Chegou a "boneca Ana". Dentro dela tem duas bonequinhas menores: o pedido 100 e o pedido 101. O robô arrumador não consegue colar duas bonecas dentro da mesma gaveta — então ele separa a Ana numa prateleira e os pedidos dela em outra prateleira, colando um adesivo com o mesmo código em ambas para lembrar "esses pedidos são da Ana".

🏷️ _dlt_id
Identificador único gerado para cada linha (hash de conteúdo ou aleatório), usado como "adesivo" para linkar pai e filho.
🔗 _dlt_parent_id
Nas tabelas filhas, aponta de volta para o _dlt_id da linha pai — é o "fio colorido" da boneca russa.
🔢 _dlt_list_idx
Guarda a posição original do item dentro da lista — preserva a ordem, caso ela importe.

💡 O nome da tabela filha é tabela_pai__campo_da_lista (dois underscores) — e se houver listas dentro de listas, o dlt continua descendo níveis, criando pai__filho__neto, sempre linkando por _dlt_parent_id. Você raramente precisa pensar nisso: basta fazer JOIN pelas colunas _dlt_id / _dlt_parent_id quando quiser reconectar os dados.

O Robô Medidor
🧬 Schema Automático & Evolução

Na primeira carga, o dlt olha os dados e cria o schema (tabelas, colunas, tipos) sozinho. Da segunda carga em diante, ele compara o novo lote com o schema salvo: se aparecer um campo novo, ele adiciona a coluna automaticamente — sem quebrar o pipeline. 📐 Inferência de tipos
Números viram bigint/double, texto vira varchar, datas em formato ISO viram timestamp, true/false vira boolean — tudo detectado olhando os valores reais.
🧾 Contrato de schema (schema contract)
Você pode travar esse comportamento: permitir evolução livre, exigir aprovação, ou rejeitar dados com campos não esperados — útil quando uma coluna nova pode ser sinal de um bug na fonte.
Não Repetir o Que Já Foi Feito
⏱️ Carga Incremental

Buscar tudo de novo a cada execução é lento e caro. O dlt guarda um estado (o "caderninho de anotações" — até onde ele já chegou, ex: a última data processada) e, na próxima execução, só busca o que é novo a partir dali. Mova o cursor abaixo para simular "até onde já carreguei" e veja quais dias seriam buscados na próxima rodada.

3 Formas de Reabastecer a Prateleira
📝 Write Dispositions: append, replace, merge

Depois que os dados chegam normalizados, o dlt precisa decidir como escrever na tabela de destino. Essa escolha se chama write disposition. Pense em 3 jeitos de reabastecer a prateleira de brinquedos quando chega uma caixa nova.

Não Reinvente a Roda
🔌 Fontes Prontas (Verified Sources)

Além de escrever sua própria resource, o dlt mantém um catálogo de verified sources — conectores testados para as fontes mais comuns, prontos para usar com dlt init.

🌐 REST APIs genéricas
rest_api_source lida com paginação (offset, cursor, link header), autenticação (API key, OAuth, bearer) e retries, a partir de um dicionário declarativo.
🗄️ Bancos relacionais
sql_database replica tabelas de Postgres, MySQL, SQL Server e outros — com detecção automática de coluna incremental.
📁 Sistemas de arquivo & cloud storage
filesystem lê CSV/JSON/Parquet local, S3, GCS ou Azure Blob como uma resource comum, com glob patterns.
📊 SaaS populares
Conectores prontos para Google Sheets, Salesforce, HubSpot, Stripe, Zendesk, Notion e dezenas de outros no repositório de verified sources.
🤖 dlt init + LLM
O comando dlt init gera um projeto inicial com boilerplate pronto; a dltHub também oferece um assistente que gera uma resource nova a partir da doc de uma API.
🧵 Streaming & filas
Kafka, Google Pub/Sub e outras filas também têm sources prontas, tratando cada mensagem como um item da resource.

Checklist
✅ Boas Práticas
🔑 Sempre defina primary_key em merge
Sem primary_key, o dlt não sabe qual linha "atualizar" — merge sem chave primária não funciona como upsert.
⏱️ Prefira incremental a full load quando possível
Reduz custo de API, tempo de execução e carga no destino — full load só quando o volume é pequeno ou não há coluna de corte confiável.
🧾 Trave o schema contract em produção
Um campo novo inesperado pode ser dado ótimo — ou sinal de bug na origem. Decida conscientemente se ele evolui sozinho ou exige revisão.
🔐 Nunca hardcode credenciais
Use secrets.toml ou variáveis de ambiente — o dlt já tem convenção nativa de configuração/segredos por ambiente.

⚠️ dlt não é um orquestrador (Airflow, Dagster) nem uma ferramenta de transformação (dbt) — ele resolve extração + carga. É comum combiná-lo: dlt para trazer o dado bruto até o warehouse, um orquestrador para agendar, e dbt para as transformações analíticas por cima.
