Um lakehouse com os metadados dentro de um banco SQL

DuckLake é um formato aberto de lakehouse, criado pela DuckDB Labs e anunciado em 2025. A ideia central é simples de contar, mas poderosa na prática: os dados continuam sendo arquivos Parquet comuns, guardados baratinho em qualquer armazenamento de objetos (S3, GCS, disco local) — mas os metadados (schema, versões, lista de arquivos, estatísticas) deixam de ser uma pilha de arquivinhos JSON/Avro espalhados pelo lake e passam a morar dentro de um banco de dados relacional de verdade (o próprio DuckDB, PostgreSQL, MySQL ou SQLite). Isso resolve, de um jeito direto, um problema que Iceberg e Delta Lake carregam desde o início: coordenar transações usando um sistema de arquivos que nunca foi feito para ser transacional.

Fundamentos
🏛️ O que é o DuckLake?

Um lakehouse tenta juntar o melhor de dois mundos: o preço baixo e a flexibilidade de um data lake (arquivos Parquet soltos num armazenamento de objetos) com as garantias de um banco de dados de verdade (transações ACID, schema, time travel). Formatos como Apache Iceberg e Delta Lake já resolveram grande parte disso guardando os metadados também como arquivos — só que arquivos de metadado dentro do próprio lake. O DuckLake muda essa peça: tira os metadados do lake e coloca dentro de um banco de dados relacional, que já nasceu pronto pra lidar com transações, índices e concorrência.

🏛️ Pense numa biblioteca

Uma biblioteca tem dois sistemas bem diferentes trabalhando juntos: as prateleiras com os livros (o acervo físico) e o fichário do bibliotecário (o registro de onde está cada livro, quem pegou emprestado, quantas cópias existem). Ninguém tenta descobrir "quantos livros de matemática existem" andando prateleira por prateleira — você consulta o fichário. No DuckLake, os arquivos Parquet são os livros nas prateleiras (o armazenamento barato e simples), e o catálogo SQL é o fichário do bibliotecário (o lugar rápido, indexado e confiável para perguntar "o que existe e onde"). Vamos voltar nessa analogia a aula inteira.

📦 Dados = Parquet, sem novidade
As linhas da sua tabela continuam sendo arquivos .parquet colunares comuns — o mesmo formato que Iceberg, Delta e o próprio DuckDB já usam. O DuckLake não reinventa como o dado é guardado.
📖 Metadados = linhas num banco SQL
Schema, snapshots, qual arquivo pertence a qual versão da tabela, estatísticas de coluna — tudo isso vira linhas em tabelas dentro de um banco relacional (DuckDB, Postgres, MySQL ou SQLite), não arquivos soltos no lake.
🔒 Ganho: transações de banco de verdade
Como o catálogo é um banco relacional, ele já sabe fazer BEGIN/COMMIT/ROLLBACK com garantias ACID — inclusive envolvendo várias tabelas ao mesmo tempo, algo que Iceberg e Delta não fazem nativamente.
Origem

Anunciado em maio de 2025 pela DuckDB Labs (a empresa por trás do DuckDB), o DuckLake nasceu da observação de que Iceberg e Delta Lake já andam "quase reinventando um banco de dados" dentro dos seus próprios arquivos de metadado — manifestos, listas de snapshot, logs de transação. A pergunta que motivou o projeto foi direta: por que não usar logo um banco de dados de verdade para essa parte, já que ele resolve esse problema há décadas? É um formato aberto, com especificação publicada, pensado para ser implementado por qualquer engine — hoje o suporte mais maduro é no próprio DuckDB.

Motivação
📎 O Problema que ele Resolve

Iceberg e Delta Lake guardam seus metadados como arquivos dentro do próprio armazenamento de objetos: um log de transações (Delta) ou uma cadeia de manifestos + lista de manifestos (Iceberg), tudo em JSON/Avro/Parquet. Funciona muito bem — mas um armazenamento de objetos como o S3 foi feito pra guardar blobs, não para ser um banco transacional: não existe um "UPDATE" de verdade, cada commit vira arquivo(s) novo(s), e sem um trabalho de compactação recorrente, esses arquivinhos de metadado se acumulam.

🧊 Iceberg / Delta — metadado é arquivo
Cada COMMIT gera novos arquivos de metadado (manifesto, lista de manifesto, entrada de log). Para planejar uma consulta, o motor precisa listar e baixar esses arquivos do object storage — e, sem compactação, essa lista só cresce.
🦆 DuckLake — metadado é linha de banco
Cada COMMIT vira uma transação SQL dentro do catálogo — inserir/atualizar linhas em tabelas já indexadas. Planejar uma consulta é uma SELECT no catálogo, não uma varredura de arquivos no lake.
Simule: quantas chamadas ao armazenamento são necessárias só para planejar UMA consulta?

Modelo ilustrativo: em Iceberg/Delta sem compactação, planejar a consulta cresce junto com o nº de commits (1 leitura por manifesto/entrada de log novo). No DuckLake, o catálogo já está indexado — uma consulta SQL responde em tempo praticamente constante, não importa há quantos commits o histórico tem.

Essa diferença também aparece dentro do próprio armazenamento de objetos: no Iceberg/Delta, dados e metadados vivem misturados nas mesmas pastas. No DuckLake, o object storage guarda só dados — o metadado nem chega lá.

🧊 Object storage — Iceberg / Delta (dado + metadado misturados)

🦆 Object storage — DuckLake (só dado)
Metadado não mora aqui — está no catálogo SQL, em outro lugar, indexado e transacional.

O Fichário do Bibliotecário
🗂️ O que exatamente mora dentro do Catálogo

O catálogo do DuckLake é, na prática, um punhado de tabelas SQL "de sistema" — parecidas com as tabelas internas que qualquer banco de dados usa para saber quais tabelas de usuário existem. Aqui está uma versão simplificada do que cada uma guarda.

Tabela do catálogo (conceitual)GuardaEquivalente na biblioteca
ducklake_tableQuais tabelas existem, nome, schema atualÍndice geral de seções da biblioteca
ducklake_snapshotCada versão da tabela ao longo do tempo, com timestampAs "fotografias" da estante em cada dia
ducklake_data_fileCaminho de cada arquivo .parquet e a quais snapshots ele pertenceFicha de cada livro: prateleira, posição
ducklake_column_statsMin/max/contagem de nulos por coluna e arquivo, para pular leitura desnecessáriaResumo na capa do livro: "sobre o que trata"
Tudo isso junto—✅ Consultável com SQL comum, transacional, indexado
✅ Por que isso importa na prática

Perguntas como "quais arquivos preciso ler para esta consulta com este filtro de data?" ou "quantas linhas tem essa tabela na versão 12?" deixam de exigir abrir e interpretar dezenas de arquivos de metadado — viram uma SELECT comum, com índice, num banco relacional. É a mesma vantagem de ter um fichário organizado em vez de recados de post-it colados nas prateleiras.

A Grande Vantagem
🔒 Transações ACID Multi-Tabela

Como o catálogo é um banco relacional de verdade, o DuckLake consegue algo que Iceberg e Delta Lake não fazem nativamente: uma transação que envolve várias tabelas ao mesmo tempo, com tudo-ou-nada garantido. Imagine um pedido que precisa gravar em três tabelas — pedidos, estoque e pagamentos. Se qualquer uma falhar, as outras duas não podem ficar gravadas sozinhas, ou o seu lake fica com dados inconsistentes entre si.

Simule uma transação que grava em 3 tabelas ao mesmo tempo
🦆 DuckLake — catálogo transacional (BEGIN ... COMMIT em um único banco)
🧊 Iceberg / Delta — cada tabela faz seu próprio commit, sem coordenação entre elas
sql — ducklakecopiarBEGIN; INSERT INTO pedidos VALUES (501, 'novo'); UPDATE estoque SET qtd = qtd - 1 WHERE produto_id = 42; INSERT INTO pagamentos VALUES (501, 199.90); COMMIT; -- as 3 tabelas viram uma versão nova juntas, ou nenhuma vira

⚠️ Em Iceberg e Delta Lake, cada tabela é a unidade de transação. É perfeitamente possível o COMMIT de pedidos ter sucesso e o de estoque falhar por uma disputa de concorrência — deixando o lake, como um todo, num estado que nenhuma consulta isolada vê como "errado", mas que é inconsistente entre tabelas. Resolver isso exige orquestração na aplicação (retries, sagas) por fora do formato.

A Máquina do Tempo
📸 Snapshots & Time Travel

Toda escrita no DuckLake — um INSERT, UPDATE, DELETE ou até uma mudança de schema — cria um novo snapshot: uma "fotografia" completa e consistente da tabela naquele instante, registrada como uma linha no catálogo. Nenhum arquivo antigo é apagado na hora — por isso dá pra "voltar no tempo" e consultar qualquer versão anterior.

Clique num snapshot da linha do tempo para ver o estado da tabela "pedidos" naquele momento
sqlcopiar-- consultar uma versão específica SELECT * FROM pedidos AT (VERSION => 3); -- ou por instante no tempo SELECT * FROM pedidos AT (TIMESTAMP => '2026-06-01 10:00:00');
sqlcopiar-- listar todos os snapshots existentes SELECT * FROM ducklake_snapshots('my_ducklake'); -- desfazer: voltar a tabela para uma versão antiga CALL ducklake_restore('my_ducklake', VERSION => 3);
Sintaxe ilustrativa baseada na documentação pública do projeto — como o DuckLake é novo (2025) e ainda evolui rápido, confira sempre a versão mais recente em ducklake.select.
Sua Tabela Cresce com Você
🧬 Evolução de Esquema

Adicionar, remover ou renomear uma coluna não exige reescrever nenhum arquivo Parquet existente — é só uma mudança de metadado, registrada como uma nova versão de schema no catálogo. Arquivos antigos continuam válidos: o motor sabe reconciliar "esse arquivo foi escrito com o schema v1" na hora de ler junto com arquivos mais novos do schema v2.

➕ Adicionar coluna
Arquivos antigos simplesmente "não têm" a coluna nova — o motor preenche com NULL ao ler, sem reescrever nada.
✏️ Renomear coluna
O catálogo rastreia a coluna por um ID interno estável, não pelo nome — renomear é só trocar o rótulo no schema, instantâneo.
🔄 Mudar tipo (compatível)
Ex: INTEGER → BIGINT. Registrado como nova versão de schema; leitura converte os tipos antigos automaticamente.
sqlcopiarALTER TABLE pedidos ADD COLUMN cupom_desconto VARCHAR; -- gera um novo snapshot com o schema atualizado; -- arquivos .parquet já gravados não são tocados
Mão na Massa
📦 Primeiros Passos

O jeito mais simples de começar: usar o próprio DuckDB como catálogo (ele também é um banco SQL, então serve perfeitamente para guardar os metadados dele mesmo) e uma pasta local para os dados.

DuckDB CLI — DuckLake local, tudo em duas linhas
sqlcopiarINSTALL ducklake; ATTACH 'ducklake:metadata.ducklake' AS my_lake; USE my_lake; CREATE TABLE pedidos (id INTEGER, status VARCHAR); INSERT INTO pedidos VALUES (1, 'novo');
Python — mesma coisa, via API do DuckDB
pythoncopiarimport duckdb con = duckdb.connect() con.sql("INSTALL ducklake") con.sql("ATTACH 'ducklake:metadata.ducklake' AS my_lake") con.sql("USE my_lake") con.sql("CREATE TABLE pedidos AS SELECT * FROM read_csv('pedidos.csv')")

💡 Esse comando cria dois artefatos: o arquivo de catálogo metadata.ducklake (um banco DuckDB comum, com as tabelas de sistema descritas na seção anterior) e uma pasta de dados (por padrão, metadata.ducklake.files/) onde os arquivos .parquet de verdade são gravados. Dá pra apontar essa pasta de dados para um bucket S3 com o parâmetro DATA_PATH, mantendo o catálogo local ou em outro banco — separando de fato "onde mora o fichário" de "onde moram os livros".

Cuidando do Lake
🧹 Compactação & Manutenção

Assim como qualquer formato de lakehouse, escrever aos poucos gera muitos arquivos Parquet pequenos — ruim para performance de leitura. A diferença é que, no DuckLake, encontrar o que precisa ser compactado ou descartado é uma consulta SQL ao catálogo, não uma varredura de diretórios.

🧵 Merge de arquivos pequenos
Junta vários arquivos .parquet pequenos de um mesmo snapshot em arquivos maiores, atualizando só as linhas do catálogo que apontam para eles.
🗑️ Expirar snapshots antigos
Remove do catálogo as versões que você não precisa mais manter para time travel, liberando os arquivos de dados que só pertenciam a elas.
🧽 Limpar arquivos órfãos
Depois de expirar snapshots, apaga do object storage os arquivos .parquet que nenhum snapshot ativo referencia mais.
sqlcopiar-- juntar arquivos pequenos em arquivos maiores CALL ducklake_merge_adjacent_files('my_lake'); -- expirar snapshots com mais de 30 dias CALL ducklake_expire_snapshots('my_lake', older_than => INTERVAL '30 days'); -- apagar arquivos que sobraram sem dono CALL ducklake_cleanup_old_files('my_lake');

💡 Como essas operações também são transações no catálogo, elas não correm o risco clássico de "apaguei um arquivo que uma leitura concorrente ainda estava usando" — o banco garante que o arquivo só é elegível para exclusão quando nenhum snapshot vivo mais aponta pra ele.

Onde ele Brilha
🎯 Casos de Uso
🧪 Lakehouse pessoal / de time pequeno
DuckDB como catálogo local e uma pasta de dados — zero infraestrutura extra para ter transações e time travel de verdade.
🏢 Lakehouse de produção
Catálogo em PostgreSQL gerenciado (alta disponibilidade, backup) + dados em S3/GCS — o melhor dos dois mundos em escala.
🔗 Pipelines com múltiplas tabelas relacionadas
Cargas que precisam manter consistência entre tabelas fato e dimensão, ou entre tabelas de um mesmo domínio, num único commit.
🌐 Compartilhar dados entre times/engines
Formato aberto: qualquer engine que implemente a especificação pode ler o mesmo lake, sem depender de um único fornecedor.
🕰️ Auditoria e reprodutibilidade
Time travel nativo para reconstituir "como estavam os dados no dia X" sem manter cópias manuais.
🧊 Migração gradual a partir de Iceberg/Delta
Times que já usam DuckDB no dia a dia podem experimentar o DuckLake em cargas novas, mantendo Iceberg/Delta onde já há integração madura.
Seja Realista
⚠️ Limitações & Maturidade
🌱 Projeto muito novo
Anunciado em 2025 — a especificação, as funções de manutenção e até detalhes de sintaxe ainda podem mudar entre versões.
🔌 Ecossistema de engines ainda pequeno
Iceberg é lido por Spark, Trino, Flink, Snowflake, BigQuery e mais; o suporte a DuckLake hoje é forte no DuckDB e ainda crescendo em outros motores.
🏗️ O catálogo vira infraestrutura crítica
Diferente de Iceberg/Delta (onde o catálogo externo é quase opcional para descoberta), no DuckLake o banco de catálogo é indispensável — precisa de backup, alta disponibilidade e monitoramento como qualquer banco de produção.
📚 Menos material e casos de produção publicados
Formatos mais antigos têm anos de "guerra" documentada (blog posts, talks, war stories) — o DuckLake ainda está construindo esse histórico.

⚠️ Para lakehouses grandes, multi-engine, com anos de operação em produção e exigência de suporte de vários fornecedores de nuvem, Iceberg continua sendo a escolha mais testada hoje. O DuckLake é a escolha certa quando simplicidade operacional e transações multi-tabela pesam mais do que maturidade do ecossistema.

Checklist
✅ Boas Práticas
🏢 Use um banco gerenciado como catálogo em produção
Fora de experimentos locais, prefira Postgres/MySQL gerenciados (com backup e alta disponibilidade) em vez de um arquivo DuckDB solto num disco sem redundância.
🧹 Agende compactação e expiração de snapshots
Sem manutenção periódica, os arquivos pequenos e o histórico de versões crescem sem parar — rode as chamadas de manutenção como um job recorrente.
🔗 Agrupe escritas relacionadas numa transação
Aproveite as transações multi-tabela para manter tabelas relacionadas sempre em sincronia, em vez de confiar em retries manuais na aplicação.
📐 Trate DATA_PATH e catálogo como configurações separadas
Decidir "onde moram os dados" e "onde mora o catálogo" de forma independente dá flexibilidade para trocar um sem migrar o outro.

⚠️ DuckLake não substitui um banco transacional de aplicação (OLTP) com milhares de escritas pequenas por segundo — o catálogo é otimizado para coordenar mudanças em tabelas analíticas, não para ser o banco de back-end da sua aplicação web.
