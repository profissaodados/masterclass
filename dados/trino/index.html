SQL que viaja até os dados, em vez dos dados viajarem até ele

Trino (antigo PrestoSQL) e Dremio são motores de consulta SQL distribuídos: eles não guardam seus próprios dados como um banco tradicional — em vez disso, conectam-se a várias fontes (data lake, bancos relacionais, NoSQL, streaming) e executam uma única consulta SQL espalhada por dezenas ou centenas de máquinas ao mesmo tempo. Nesta aula vamos entender como o Presto nasceu no Facebook em 2012 para substituir consultas lentas do Hive, como ele virou Trino, e como o Dremio ataca o mesmo problema com uma proposta diferente: acelerar consultas automaticamente com Reflections e organizar tudo numa camada semântica de autoatendimento.

Fundamentos
🤔 O que é um Motor de Consulta Distribuído?

Um banco de dados tradicional (PostgreSQL, MySQL) faz duas coisas ao mesmo tempo: guarda os dados em disco e os consulta com SQL. O Trino (e o Dremio) separam essas duas responsabilidades: eles não têm um formato de armazenamento próprio — a "verdade" dos dados continua em outro lugar (um data lake em S3, um MySQL de produção, um MongoDB de eventos). O motor apenas se conecta a essas fontes, entende cada uma através de um conector, e executa a consulta SQL de forma distribuída: divide o trabalho entre várias máquinas (workers/executors) que processam pedaços dos dados em paralelo — esse padrão se chama MPP (Massively Parallel Processing).

🧒 Explicando para uma criança

Imagine uma biblioteca gigante espalhada em vários prédios diferentes (um prédio é o MySQL, outro é o MongoDB, outro é uma pasta cheia de arquivos no S3). O Trino é como um bibliotecário superpoderoso que não guarda nenhum livro consigo — ele sabe exatamente em qual prédio e prateleira cada livro está, manda vários ajudantes buscarem pedaços da resposta ao mesmo tempo, e te entrega tudo já organizado numa única resposta, como se todos os livros estivessem na mesma estante.

🚫 Não é um banco de dados
Trino não tem seu próprio formato de arquivo de armazenamento. Ele lê e escreve nas fontes que você conectar — Parquet no S3, tabelas MySQL, coleções MongoDB, tópicos Kafka.
⚡ É um motor MPP
Uma única consulta é fatiada em dezenas/centenas de pedaços (splits) processados em paralelo por várias máquinas (workers), como várias mãos ajudando a carregar uma mudança.
🔗 SQL federado
A mesma consulta pode juntar (JOIN) uma tabela do MySQL com um arquivo Parquet do data lake e uma coleção do MongoDB — sem copiar nada antes.

De Onde Veio
📜 A História: do Presto ao Trino (e o Dremio no meio do caminho)

O Presto nasceu dentro do Facebook em 2012 porque as consultas analíticas via Hive/MapReduce sobre o data warehouse (na época, com dezenas de petabytes) demoravam minutos ou horas. Um pequeno time — Martin Traverso, Dain Sundstrom, David Phillips e Eric Hwang — construiu um motor novo, pensado para respostas interativas, em segundos. Anos depois, o próprio projeto passou por uma divisão que gerou o nome "Trino" que usamos hoje.

🧒 Explicando para uma criança

É como uma banda de música que toca muito bem junta. Em 2019, parte da banda original decidiu sair da gravadora (Facebook) para tocar por conta própria, com outro nome — só que o nome antigo ("Presto") ficou preso à gravadora. Então a banda trocou de nome para Trino e continuou compondo músicas novas, enquanto a gravadora manteve sua própria versão da banda tocando as músicas antigas com o nome antigo.

💡 Hoje as duas continuam vivas: PrestoDB é mantido pela Presto Foundation (Linux Foundation), com Meta/Facebook como grande usuário e contribuidor; Trino é mantido pela Trino Software Foundation, com a Starburst como principal apoiadora comercial. As bases de código divergiram desde o fork — não são mais binariamente compatíveis — mas o SQL, os conceitos de arquitetura (coordinator/worker) e a filosofia de conectores continuam extremamente parecidos.

Como Funciona por Dentro
🏗️ Arquitetura: Coordinator & Workers

Um cluster Trino tem dois papéis: um Coordinator (só existe um "ativo" recebendo consultas) e vários Workers. O Coordinator nunca toca nos dados das tabelas — ele só entende o SQL, monta o plano e distribui o trabalho. Quem realmente lê e processa os dados são os Workers, em paralelo. 🧒 Explicando para uma criança

Pensa numa obra de construção: o Coordinator é o engenheiro que olha a planta (seu SQL), decide quem faz o quê e em que ordem — mas ele não carrega tijolo. Os Workers são os pedreiros: cada um carrega e monta sua parte da parede (um pedaço dos dados) ao mesmo tempo que os outros, e no fim entregam a parede pronta para o engenheiro juntar tudo.

💡 Isso é bem diferente do modelo cliente-servidor de um PostgreSQL, onde um único processo atende cada conexão do início ao fim. No Trino, uma única consulta é atendida por vários processos ao mesmo tempo — daí vem a escala horizontal: para consultar mais rápido, basta adicionar mais Workers ao cluster.

O Motor por Dentro
⚙️ Como uma Consulta é Executada: Pipeline em Memória vs Hive/MapReduce

O motivo do Presto ter nascido é justamente este: o Hive clássico traduzia SQL em uma sequência de jobs MapReduce, e cada job escrevia seu resultado intermediário de volta no HDFS antes do próximo job poder começar — cada etapa pagava o preço de gravar e reler do disco. O Trino/Presto processa a consulta como um pipeline em memória: o resultado de uma etapa é trocado (exchange) diretamente para a próxima etapa, sem tocar o disco entre elas, sempre que possível. Compare os dois caminhos:

🐘 Hive clássico sobre MapReduce
Cliente envia HiveQL
Hive traduz em vários jobs MapReduce
Job 1 roda e grava resultado no HDFS
Job 2 lê do HDFS, processa, grava de novo
🚀 Trino / Presto (pipeline MPP)
Cliente envia SQL ao Coordinator
Coordinator monta um plano distribuído único
Workers trocam dados direto em memória (exchange)
Resultado final entregue ao cliente

🧒 Explicando para uma criança

É a diferença entre um correio com várias paradas (Hive/MapReduce: a carta para em cada agência, é registrada, guardada, e só depois segue para a próxima) e uma fileira de amigos passando baldes de água numa brincadeira de apagar incêndio (Trino: o balde passa direto de mão em mão, sem ninguém parar para guardá-lo no chão entre uma pessoa e outra).

ModeloOnde fica o resultado intermediárioLatência típicaMelhor para
Hive / MapReduce clássicoGravado em disco (HDFS) entre cada jobMinutos a horasJobs batch enormes, tolerantes a falha ponto a ponto

⚠️ Essa velocidade tem um custo: por padrão, se um Worker cai no meio da consulta, a consulta inteira falha e precisa ser reenviada — diferente do MapReduce, que só reexecuta a tarefa que falhou. Versões recentes do Trino resolvem isso com fault-tolerant execution, um modo opcional que grava dados de troca (exchange) num armazenamento externo (ex: S3) para permitir retomar consultas longas sem perder tudo — útil para cargas de ETL grandes, não só para consultas interativas.

Escala Horizontal
🧩 Paralelismo MPP: Splits, Tasks e Workers

Uma tabela grande no data lake é composta por vários arquivos (ex: centenas de arquivos Parquet). O Coordinator fatia essa tabela em pedaços chamados splits — cada split vira uma unidade de trabalho que um Worker processa. Quanto mais Workers disponíveis, mais splits são processados ao mesmo tempo, em vez de um atrás do outro.

Simule: distribuindo splits entre workers
Splits (pedaços de arquivo) a processar32
Workers disponíveis no cluster4
🧒 Explicando para uma criança

Imagine 32 caixas de brinquedo para guardar. Com 1 amigo ajudando, ele guarda uma caixa de cada vez — demora bastante. Com 8 amigos, cada um pega umas 4 caixinhas e todos guardam ao mesmo tempo — a arrumação termina muito mais rápido. É exatamente isso que acontece quando você aumenta o número de Workers no cluster: mais "amigos" carregando pedaços da mesma tarefa.

Coordenando Workers
🔀 Tipos de JOIN Distribuído: Broadcast vs Shuffle

Cada Worker só enxerga o pedaço (split) da tabela que recebeu. Para fazer um JOIN, as linhas com a mesma chave das duas tabelas precisam parar no mesmo Worker — senão ninguém consegue comparar nada. O otimizador escolhe entre duas estratégias principais para fazer isso acontecer, e a escolha certa muda drasticamente quanto dado trafega pela rede.

📡 Broadcast Join
A tabela pequena (ex: uma dimensão com poucas linhas) é copiada inteira para todos os Workers que têm pedaços da tabela grande. Cada Worker já fica com as duas metades que precisa comparar, sem mexer na tabela grande.
🔁 Partitioned (Shuffle) Join
Quando as duas tabelas são grandes, ambas são redistribuídas pela rede usando uma função hash da chave de junção — cada Worker passa a receber só as linhas, dos dois lados, cuja chave "pertence" a ele.
Simule: qual estratégia move menos dado pela rede?
Tabela pequena (dimensão)200 MB
Tabela grande (fatos)500 GB
Workers no cluster8
🧒 Explicando para uma criança

Pense em dois grupos trocando figurinhas para montar um álbum. Se um grupo tem poucas figurinhas raras, é mais fácil tirar cópias delas e entregar uma cópia pra cada colega (broadcast) do que fazer todo mundo se mexer. Mas se os dois grupos são enormes, o jeito mais justo é reorganizar todo mundo em times menores por tipo de figurinha, para que quem tem a mesma figurinha sempre fique junto (shuffle) — ninguém carrega o álbum do colega inteiro à toa.

💡 É por isso que estatísticas de tabela atualizadas (seção de tuning mais à frente) importam tanto: se o otimizador não souber que uma tabela é pequena, pode escolher shuffle onde um broadcast bem mais barato resolveria — ou pior, tentar um broadcast de uma tabela que na verdade é gigante.

O Superpoder do Trino
🔌 Conectores & Federação: Um SQL, Várias Fontes

Cada fonte de dados é acessada através de um conector — um plugin que sabe "traduzir" entre o SQL do Trino e o protocolo daquela fonte específica (JDBC de um banco relacional, API do MongoDB, protocolo do Kafka, arquivos Parquet/ORC/Iceberg no S3...). Cada instância configurada de um conector vira um catálogo, endereçado como catalogo.schema.tabela. Clique em cada fonte para ver como ela aparece no SQL.

O verdadeiro poder aparece quando você junta várias fontes numa única consulta federada — sem mover ou copiar nenhum dado antecipadamente:

sql — consulta federadacopiarSELECT c.nome, SUM(p.total) AS total_gasto, COUNT(e.evento_id) AS cliques FROM mysql.vendas.clientes c JOIN hive.lake.pedidos p ON p.cliente_id = c.id JOIN kafka.eventos.cliques e ON e.cliente_id = c.id WHERE p.total > 1000 GROUP BY c.nome; -- 3 catálogos diferentes, 3 tecnologias diferentes, 1 consulta só
🧒 Explicando para uma criança

É como uma reunião da ONU com tradutores simultâneos: cada país (fonte de dados) fala sua própria língua (MySQL fala "SQL relacional", MongoDB fala "documentos", Kafka fala "eventos em fila"). O Trino tem um tradutor (conector) para cada língua, e consegue montar uma única "ata da reunião" (o resultado da consulta) juntando o que cada país disse — sem que ninguém precise aprender a língua dos outros antes.

📚 Mais de 50 conectores
Data lakes (Hive, Iceberg, Delta Lake, Hudi), relacionais (MySQL, PostgreSQL, SQL Server, Oracle), NoSQL (MongoDB, Cassandra), streaming (Kafka, Pulsar) e mais.
🧩 Pushdown por conector
Cada conector decide o que consegue "empurrar" para a fonte (filtros, agregações, limites) — quanto mais inteligente o conector, menos dado bruto precisa trafegar até o Trino.
🏗️ Extensível
A interface de conector (SPI) é pública — qualquer empresa pode escrever um conector novo para uma fonte proprietária sem alterar o núcleo do Trino.
O Que Realmente Está no Data Lake
🧊 Formatos de Tabela do Lakehouse: Iceberg, Delta Lake e Hudi

Parquet e ORC são só formatos de arquivo — ótimos para armazenar colunas de forma compacta, mas sozinhos não sabem responder "quais arquivos formam a tabela agora?", nem "como ela estava ontem?", nem garantem que uma escrita no meio de uma leitura não corrompa o resultado. Os formatos de tabela (table formats) do lakehouse adicionam uma camada de metadados transacional por cima de arquivos Parquet/ORC comuns, trazendo recursos que só bancos de dados tinham: transações ACID, time travel e evolução segura de schema. Tanto o Trino quanto o Dremio leem (e em boa parte escrevem) esses formatos diretamente.

O time travel funciona porque cada mudança na tabela cria um novo snapshot imutável — os arquivos de dados antigos não são apagados na hora, só deixam de fazer parte do snapshot mais recente:

🧹 O problema dos "arquivos pequenos" e a compactação

Cada INSERT/MERGE incremental tende a criar arquivos Parquet novos e pequenos — com o tempo, uma tabela pode acumular milhares deles, o que deixa os scans mais lentos (mais arquivos para abrir, menos eficiência de I/O). Os três formatos oferecem um comando de compactação (ex: ALTER TABLE ... EXECUTE optimize no Iceberg via Trino) que reagrupa arquivos pequenos em arquivos maiores, sem mudar o dado lógico — só a organização física, gerando um novo snapshot.

🧒 Explicando para uma criança

Parquet puro é como fotos soltas jogadas numa gaveta: dá pra ver cada foto, mas não dá pra saber a ordem nem "voltar no tempo". Um formato de tabela é como um álbum de fotografias com data em cada página e um índice no início — você sempre sabe exatamente quais fotos existiam em cada momento, e pode folhear o álbum "como ele estava" há um mês, sem bagunçar as fotos novas que foram coladas depois. E de vez em quando alguém "reorganiza o álbum" (compactação), juntando fotos soltas em páginas cheias — sem jogar nenhuma foto fora.

🧊 Escolha Iceberg quando...
Vários motores diferentes (Trino, Spark, Flink, Dremio) precisam ler e escrever na mesma tabela, e você quer particionamento que não exige disciplina manual dos usuários.
🔺 Escolha Delta Lake quando...
Seu pipeline já vive majoritariamente no ecossistema Spark/Databricks, e Trino/Dremio entram principalmente como consumidores de leitura.
🟣 Escolha Hudi quando...
A carga é dominada por upserts incrementais de alta frequência vindos de CDC (ex: replicar um banco transacional quase em tempo real) via Spark ou Flink.
Inteligência do Planejamento
🎯 Otimizador de Custo & Pushdown

Antes de distribuir qualquer trabalho, o Coordinator usa um otimizador baseado em custo (CBO): com estatísticas das tabelas (linhas, tamanho, distribuição de valores), ele decide, por exemplo, a ordem de um JOIN ou se deve transmitir (broadcast) a tabela pequena para todos os Workers em vez de embaralhar (shuffle) as duas tabelas grandes pela rede. Outra técnica-chave é o pushdown: filtros e seleção de colunas são empurrados para o mais perto possível da fonte, para que menos dado precise viajar pela rede.

Simule: quanto dado precisa viajar até o Trino, com e sem pushdown?
Tamanho total da tabela200 GB
Seletividade do filtro (WHERE)5%
🧒 Explicando para uma criança

É como pedir para alguém trazer "só as maçãs vermelhas" do mercado, em vez de pedir para trazer o mercado inteiro para você escolher em casa. Sem pushdown, o Trino traz tudo e filtra depois; com pushdown, ele pede para a própria fonte (o "mercado") já separar só o que interessa antes de mandar — muito menos peso para carregar pelo caminho.

🧹 Predicate Pushdown
Condições do WHERE são enviadas para a fonte quando possível — um MySQL, por exemplo, já devolve só as linhas filtradas.
📐 Projection Pushdown
Só as colunas realmente usadas na consulta são lidas — essencial em formatos colunares como Parquet, onde colunas não lidas nem são abertas.
⚡ Dynamic Filtering
Durante um JOIN, os valores encontrados no lado menor são usados como filtro em tempo real no scan do lado maior, evitando ler dados que nunca vão casar no JOIN.
Operando em Produção
🎛️ Performance Tuning Avançado

Um cluster Trino é compartilhado por muita gente ao mesmo tempo — analistas rodando consultas rápidas, pipelines de ETL rodando consultas pesadas. Sem controle, uma única consulta gigante pode consumir toda a memória do cluster e travar todo mundo. Quatro mecanismos resolvem isso na prática.

🚦 Resource Groups
Filas de prioridade com cotas de memória e concorrência por grupo de consultas (ex: "etl" vs "analistas-adhoc") — uma consulta pesada de ETL não consegue sufocar o cluster inteiro.
💾 Spill to Disk
Quando um JOIN, agregação ou ORDER BY excede a memória alocada, o Trino pode derramar dados para disco temporário em vez de falhar com out of memory — mais lento, mas termina.
📊 Estatísticas (ANALYZE)
Sem estatísticas atualizadas (linhas, tamanho, distribuição de valores), o otimizador de custo "voa às cegas" — pode escolher a ordem errada de JOIN ou a estratégia errada (broadcast vs shuffle).
🗄️ Cache de resultados/segmentos
Camadas de cache adicionais (ex: Alluxio, ou aceleradores de vendors como o Starburst Warp Speed) guardam segmentos de dados já lidos, evitando reler o mesmo arquivo do S3 em consultas repetidas.
Simule: duas filas de resource group disputando a memória do cluster
Memória total do cluster100 GB
Cota do grupo "etl"60%
Consulta de ETL pedindo50 GB
🧒 Explicando para uma criança

É como uma cozinha de restaurante com duas filas separadas: uma para pedidos de banquete gigante e outra para quem só quer um lanche rápido no balcão. Se as duas filas dividissem o mesmo espaço sem regras, um banquete enorme travaria o lanche rápido de todo mundo. Com filas (e cotas) separadas, o banquete tem seu próprio espaço reservado e o balcão continua atendendo rapidinho, sem esperar.

A Outra Abordagem
🦉 O que é o Dremio?

O Dremio nasceu em 2015, fundado por Tomer Shiran e Jacques Nadeau — este último um dos criadores do Apache Arrow, o formato colunar em memória que virou padrão da indústria. Assim como o Trino, o Dremio é um motor de consulta MPP que se conecta a data lakes e bancos sem exigir cópia prévia dos dados. A diferença está no foco: o Dremio se posiciona como uma plataforma de self-service BI sobre o data lake, com duas peças centrais que o Trino não tem nativamente — Reflections (aceleração automática) e uma camada semântica (catálogo governado para usuários de negócio).

🏹 Apache Arrow nativo
O motor de execução do Dremio processa dados no formato colunar do Arrow do início ao fim, inclusive na troca de dados entre nós.
⚙️ Gandiva (LLVM)
Expressões de consulta (ex: preco * (1 - desconto)) são compiladas para código de máquina vetorizado em tempo real, em vez de interpretadas.
⚡ Reflections
Cópias otimizadas e pré-computadas dos dados, escolhidas automaticamente pelo otimizador para acelerar consultas — sem o usuário reescrever SQL.
🗂️ Camada semântica
Spaces, Folders e Virtual Datasets organizam o catálogo de forma amigável para analistas de negócio, com governança.

Se o Trino é o "bibliotecário que corre até os livros", o Dremio é o bibliotecário que, além de correr, vai anotando um resumo das perguntas mais frequentes num caderninho de respostas prontas — da próxima vez que alguém perguntar algo parecido, ele já entrega o resumo na hora, sem precisar correr de novo até os livros.

Aceleração Automática
⚡ Reflections: o "Cola de Prova" do Dremio

Uma Reflection é uma cópia física, otimizada (ordenada, particionada, às vezes pré-agregada) de um conjunto de dados, mantida automaticamente pelo Dremio. O usuário continua escrevendo SQL contra a tabela ou o Virtual Dataset original — é o otimizador quem decide, sozinho, se existe uma Reflection que responde à consulta mais rápido, e a usa no lugar da tabela crua, de forma completamente transparente.

Compare: mesma consulta, com e sem Reflection
📄 Raw Reflection
Uma cópia colunar do próprio dataset, geralmente reordenada/particionada por colunas comuns em filtros — acelera scans e filtros sem mudar a granularidade dos dados.
📊 Aggregation Reflection
Uma versão pré-agregada (ex: soma de vendas por mês e categoria) — se a consulta pedir algo que já está nesse nível de agregação (ou mais grosso), o Dremio responde direto dali.
sql — sintaxe ilustrativacopiarALTER TABLE s3.vendas.pedidos CREATE AGGREGATE REFLECTION agg_vendas_mes USING DIMENSIONS (mes, categoria) MEASURES (total_venda (SUM)); -- o analista continua consultando "pedidos" normalmente; -- o otimizador decide sozinho quando usar "agg_vendas_mes"
🧒 Explicando para uma criança

É igual uma cola de prova que o professor deixaria você usar — só que essa cola é feita com antecedência, com as contas mais difíceis já resolvidas. Quando cai uma pergunta parecida na prova, você não refaz a conta do zero: só olha a cola e copia a resposta certa. A Reflection é essa "cola", e o Dremio decide sozinho quando pode usá-la.

⚠️ Reflections não são mágica grátis: elas ocupam espaço em disco e precisam ser atualizadas (refresh) conforme os dados de origem mudam — criar Reflections demais, ou com frequência de atualização muito alta, pode gerar mais custo de processamento do que a economia que elas trazem nas consultas.

Governança para o Negócio
🗂️ Camada Semântica: Spaces, Folders e Virtual Datasets

Em vez de deixar analistas de negócio navegando direto pelas tabelas cruas do data lake (Physical Datasets), o Dremio organiza um catálogo de Spaces (áreas, ex: por time ou domínio) contendo Folders e Virtual Datasets — visões SQL reutilizáveis, com nomes de negócio, documentação e controle de acesso — construídas em cima dos dados físicos.

📂 Folder: Comercial

🧩 Virtual Dataset: vw_receita_liquida

🧒 Explicando para uma criança

Pense numa gaveta bagunçada de brinquedos (os dados crus do data lake) versus uma loja organizada, com prateleiras etiquetadas por categoria (a camada semântica). Você ainda pode ir até a gaveta se quiser, mas a loja organizada deixa muito mais fácil e seguro para qualquer pessoa — mesmo quem nunca viu a gaveta — encontrar exatamente o brinquedo certo.

💡 Virtual Datasets também podem receber Reflections próprias — ou seja, você pode acelerar não só a tabela física, mas uma visão de negócio inteira (com JOINs e agregações já embutidos), e ferramentas de BI que consultam essa visão ganham a aceleração automaticamente.

🔐 Segurança & Governança

Como o motor de consulta se torna a "porta de entrada" única para várias fontes, ele também precisa ser o lugar onde as regras de acesso são aplicadas de forma consistente — mesmo que a fonte original (um bucket S3, um MongoDB) tenha seu próprio controle de acesso separado. O controle costuma ser em camadas: catálogo → schema → tabela → coluna/linha. Clique em cada camada.

🧒 Explicando para uma criança

É como uma escola com crachás diferentes: o crachá de aluno abre a sala de aula (um schema), mas não abre a sala dos professores (outro catálogo); o crachá de diretor abre praticamente tudo. Além disso, algumas informações do boletim — tipo o CPF dos responsáveis — podem aparecer borradas mesmo para quem tem o crachá certo, a não ser que a pessoa tenha autorização especial para ver o valor de verdade. Isso é o "mascaramento de coluna".

⚠️ Federação amplia a superfície de governança: se uma consulta junta 4 fontes diferentes, as permissões de cada uma precisam ser respeitadas ao mesmo tempo — um usuário sem acesso a uma das tabelas não pode "vazar" dados dela através do resultado de um JOIN.

O Cano de Alta Vazão
✈️ Arrow Flight em Detalhe

JDBC e ODBC — os protocolos clássicos para conectar ferramentas de BI a bancos de dados — foram desenhados nos anos 90 para transferir resultados linha a linha: cada valor é serializado, enviado, e desserializado de volta no cliente, geralmente reconvertendo para um formato colunar do outro lado (ex: um DataFrame do Pandas). Para poucas linhas isso não importa, mas para milhões de linhas analíticas, essa conversão vira o próprio gargalo. O Apache Arrow Flight (usado pelo Dremio) transmite os dados já no formato colunar binário do Arrow, de ponta a ponta, sobre gRPC — sem essa dupla conversão.

Ordem de grandeza ilustrativa de vazão para extrair um resultado analítico grande — o ganho real depende do driver, da rede e do tamanho do resultado.
📦 Sem conversão de formato
Os dados já estão em memória no formato Arrow no servidor — a transmissão é praticamente uma cópia de bytes, não uma tradução linha a linha.
🚚 Streams paralelos
Um resultado grande pode ser dividido em múltiplos streams gRPC paralelos, lidos por várias threads do cliente ao mesmo tempo.
🔌 Flight SQL
Um padrão sobre o Arrow Flight, parecido em espírito com o JDBC, mas colunar — permitindo que qualquer driver "Flight SQL" converse com qualquer banco compatível.
python — pyarrow.flight (Dremio)copiarimport pyarrow.flight as flight client = flight.FlightClient("grpc+tls://meu-dremio:32010") info = client.get_flight_info(flight.FlightDescriptor.for_command( "SELECT categoria, SUM(total) FROM lake.vendas.pedidos GROUP BY 1" )) reader = client.do_get(info.endpoints[0].ticket) tabela_arrow = reader.read_all() # já chega como Arrow Table, sem conversão linha a linha
🧒 Explicando para uma criança

É a diferença entre transportar uma construção de Lego já montada direto num caminhão (Arrow Flight) e desmontar cada peça, numerar, jogar tudo solto numa caixa (serializar linha a linha via JDBC/ODBC), levar a caixa, e remontar peça por peça do outro lado. Para poucas peças não faz diferença — mas para uma construção gigante, montar tudo de novo do zero toma um tempo enorme.

Lado a Lado
🥊 Trino vs Dremio: Comparação

Os dois são motores MPP que consultam data lakes sem cópia prévia — mas resolvem prioridades diferentes. A pergunta certa não é "qual é melhor", e sim "qual problema estou resolvendo agora".

Dimensão🔵 Trino / Presto🟠 Dremio
ArquiteturaCoordinator + Workers, geração de bytecode JVMCoordinator + Executors, Apache Arrow + Gandiva (LLVM)
ConectoresEcossistema muito amplo (50+): relacional, NoSQL, streaming, lakehouseFocado em lakehouse + principais fontes relacionais/NoSQL
Aceleração automáticaNão nativa no núcleo open source (depende de cache externo/enterprise)Reflections, escolhidas automaticamente pelo otimizador
Camada semânticaNão tem — depende de catálogos externos (Hive Metastore, Iceberg)Nativa: Spaces, Folders, Virtual Datasets, lineage
Protocolo clienteJDBC / ODBC / API HTTPJDBC / ODBC / Arrow Flight (colunar, alta performance)
Tolerância a falhasFault-tolerant execution (opcional) para ETL longoFoco menor em ETL de longa duração
Melhor paraFederação ampla + consultas ad hoc + ETL em larga escalaSelf-service BI governado direto sobre o data lake
Pontuação ilustrativa/qualitativa (não um benchmark) para orientar a decisão — cada organização deve validar com sua própria carga de trabalho.
🔵 Escolha Trino quando...
Você precisa cruzar muitas fontes heterogêneas numa mesma consulta (RDBMS + NoSQL + streaming + lake), rodar ETL federado em larga escala, ou já tem um catálogo/camada semântica resolvidos por outra ferramenta (ex: dbt, Hive Metastore, uma ferramenta de BI própria).
🟠 Escolha Dremio quando...
A prioridade é self-service BI para analistas de negócio direto sobre o data lake, com governança (quem vê o quê) e aceleração automática sem precisar de um time de engenharia mantendo cubos OLAP ou extrações manuais.
Onde Cada Um Brilha
🎯 Casos de Uso
🔎 Consultas ad hoc federadas
Analistas cruzando dados do data lake com um banco transacional sem esperar um pipeline de ETL rodar — resposta em segundos.
🏭 ETL/ELT em larga escala
Trino como motor de transformação SQL sobre petabytes no lakehouse (Iceberg/Delta), muitas vezes acionado por ferramentas como dbt.
🌐 Motor único para várias equipes
Grandes empresas (Meta, Netflix, LinkedIn, Uber) usam Presto/Trino como o "SQL de entrada" comum para dezenas de fontes internas.
📊 Self-service BI
Dremio conectado direto a Tableau/Power BI via Arrow Flight, com analistas navegando pela camada semântica sem depender de extrações.
🏛️ Data lake governado
Camada semântica do Dremio como "porta de entrada" única e auditável para times de negócio acessarem dados do lake com segurança.
⚡ Substituição de cubos OLAP
Reflections eliminam a necessidade de manter cubos ou extrações pré-calculadas só para acelerar dashboards.

Checklist
✅ Boas Práticas
🔵 Trino
Particione/bucket tabelas no lake (idealmente Iceberg) para o otimizador conseguir podar partições inteiras; monitore a Web UI (porta 8080) para achar consultas com skew; ajuste query.max-memory-per-node conforme o tamanho do cluster; deixe o dynamic filtering ativo para JOINs seletivos.
🟠 Dremio
Curadoria da camada semântica é essencial — não deixe analistas acessando Physical Datasets crus por padrão; crie Reflections com propósito (não "para garantir"), monitorando custo de refresh; use Arrow Flight nas ferramentas de BI que suportarem, para menor latência que JDBC/ODBC tradicional.

⚠️ Nem Trino nem Dremio substituem um banco transacional (OLTP) — os dois são motores de leitura analítica sobre dados que já existem em outro lugar. E nenhum dos dois é, por padrão, um sistema de armazenamento durável: o dado "de verdade" continua sendo responsabilidade da fonte conectada (data lake, banco relacional etc.).
