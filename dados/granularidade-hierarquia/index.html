Toda tabela tem um tamanho de grão. A pergunta é: você sabe qual é o seu?

Granularidade é o nível de detalhe que uma única linha de uma tabela de fatos representa — pode ser "um item vendido", "um pedido inteiro" ou "o total do mês". Hierarquia é a forma como os atributos de uma dimensão se organizam em níveis, um dentro do outro — Ano contém Trimestres, que contêm Meses, que contêm Dias; País contém Regiões, que contêm Estados, que contêm Cidades. E drill down / drill up é o nome que se dá para navegar entre esses níveis: descer para ver mais detalhe, ou subir para ver o resumo. São três ideias que andam sempre juntas — e é exatamente isso que vamos destrinchar hoje, com muita analogia simples, árvores clicáveis e SQL de verdade.

Fundamentos
🧒 Primeiro, o básico: o que é Granularidade?

Imagine uma foto de satélite da sua cidade: de bem longe, cada "pontinho" da imagem (cada pixel) representa um bairro inteiro. Se você aproximar o zoom, cada pixel passa a representar uma rua. Se aproximar ainda mais, cada pixel representa uma casa. A foto é a mesma cidade — o que muda é quanto cada "unidade" da imagem representa. Em um Data Warehouse, essa "unidade" é a linha de uma tabela de fatos, e o nome que damos para "o que cada linha representa" é granularidade (ou simplesmente grão).

🧱
Pensando como criança

Pense em construir uma casa de Lego. Se você usar blocos gigantes, constrói rápido, mas não consegue fazer detalhes pequenos como uma maçaneta. Se usar blocos minúsculos, consegue fazer qualquer detalhe, mas precisa de muito mais peças e de muito mais tempo para montar. É a mesma casa — só muda o tamanho do bloco que você usa para descrevê-la. Granularidade é exatamente isso: o "tamanho do bloco" de informação que cada linha da sua tabela guarda.

Veja a mesma venda descrita em dois grãos diferentes — repare que as duas tabelas contam a mesma história, só que uma em blocos pequenos (fino) e a outra em blocos grandes (grosso):

📏 Definição técnica: granularidade é o nível de detalhe de uma linha de fato, definido a partir das dimensões que a descrevem. Quanto mais dimensões (e mais detalhadas) definem cada linha, mais fino é o grão; quanto menos, mais grosso.

Fundamentos
🪆 O que é Hierarquia?

Uma hierarquia organiza os atributos de uma dimensão em níveis, do mais geral para o mais específico (ou vice-versa), onde cada nível "contém" os níveis abaixo dele. É como uma boneca russa (matryoshka): abre a boneca grande e tem uma menor dentro, abre essa e tem outra ainda menor — até chegar na menor de todas.

🪆
Analogia

O Brasil (boneca grande) contém Regiões (Sudeste, Nordeste...), que contêm Estados (São Paulo, Bahia...), que contêm Cidades, que contêm Lojas. Do mesmo jeito, o Ano contém Trimestres, que contêm Meses, que contêm Dias. Cada boneca de fora sempre soma o valor de todas as bonecas de dentro dela.

📅 Hierarquia de Tempo
Ano → Trimestre → Mês → Dia (ou até Hora/Minuto). A mais comum de todas em qualquer Data Warehouse.
🗺️ Hierarquia Geográfica
País → Região → Estado → Cidade → Loja. Cada nível agrupa vários itens do nível de baixo.
📦 Hierarquia de Produto
Categoria → Subcategoria → Produto → SKU (a variação exata: tamanho, cor). Comum em varejo.

💡 Repare que subir um nível na hierarquia é sempre uma soma (ou outra agregação) dos níveis de baixo: o total do Estado é a soma das Cidades; o total do Trimestre é a soma dos Meses. É exatamente essa propriedade que torna o drill up/down possível.

O Conceito Central
🔍 Drill Down vs. Drill Up (Roll-up)

Com uma hierarquia pronta, dá para navegar por ela em duas direções. Drill down ("perfurar para baixo") é descer de um nível mais geral para um mais detalhado — de "Brasil" para "Região", de "Ano" para "Mês". Drill up (também chamado roll-up, "enrolar para cima") é o caminho inverso: subir de um nível detalhado para um mais resumido, somando os valores no caminho.

⬇️ Drill Down
Sai do resumo e vai para o detalhe. Pergunta típica: "Vendi R$ 1,24 mi este ano... mas em quais meses foi mais forte?"
⬆️ Drill Up / Roll-up
Sai do detalhe e vai para o resumo. Pergunta típica: "Essa loja vendeu R$ 180 mil... e a cidade toda, quanto vendeu?"

Modelagem Dimensional
🧮 O Grão da Fato — o "Grain Statement" de Kimball

Antes de criar qualquer tabela de fatos, Ralph Kimball recomenda escrever uma frase única e sem ambiguidade descrevendo exatamente o que representa uma linha — o chamado grain statement. Toda a equipe (engenharia, análise, negócio) precisa concordar com essa frase antes de desenhar colunas, porque é ela que decide se dá para responder certas perguntas depois ou não.

Veja o mesmo pedido do cliente Ana (loja Paulista, 10/03/2024: 2 Camisetas a R$ 50 + 1 Tênis a R$ 220) descrito em três grãos possíveis para a mesma fato_venda:

"Uma linha de fato_venda representa um produto específico dentro de um pedido específico."

4521Tênis1R$ 220
2 linhas. Dá para responder qualquer pergunta futura, inclusive as que ninguém pensou ainda.

💻 Drill Up em SQL — GROUP BY, ROLLUP, CUBE e GROUPING SETS

Partindo do grão mais fino disponível (fato_venda_item, 1 linha por produto vendido), qualquer nível mais grosso pode ser recalculado com GROUP BY — é o "drill up" acontecendo em SQL puro.

Drill up simples: do item para o pedido, e do pedido para a loja/dia:

sqlcopiar-- grão fino: 1 linha por item vendido SELECT id_pedido, produto, qtd, valor FROM fato_venda_item; -- drill up 1: soma para o grão de pedido SELECT id_pedido, COUNT(*) AS qtd_itens, SUM(valor) AS total_pedido FROM fato_venda_item GROUP BY id_pedido; -- drill up 2: soma para o grão loja + dia SELECT id_loja, data_venda, SUM(valor) AS total_dia FROM fato_venda_item GROUP BY id_loja, data_venda;

Quando se quer vários níveis da hierarquia de uma vez só — cada Cidade, o subtotal de cada Estado e o total geral, tudo na mesma consulta — usa-se GROUP BY ROLLUP(...). Ele agrega na ordem da hierarquia, de trás para frente, e insere uma linha de subtotal a cada nível que "fecha":

sqlcopiarSELECT COALESCE(dl.regiao, 'TOTAL BRASIL') AS regiao, COALESCE(dl.estado, ' (subtotal da região)') AS estado, SUM(fvi.valor) AS total FROM fato_venda_item fvi JOIN dim_loja dl ON dl.id_loja = fvi.id_loja GROUP BY ROLLUP(dl.regiao, dl.estado) ORDER BY GROUPING(dl.regiao), dl.regiao, GROUPING(dl.estado), dl.estado;

O resultado (simplificado, só com Sudeste e Nordeste) já sai com os subtotais de cada região e o total geral prontos — sem precisar rodar 3 consultas separadas e juntar na mão:

💡 A função GROUPING(coluna) retorna 1 quando aquela linha é um subtotal (a coluna foi "agregada para fora") e 0 quando é uma linha de detalhe normal — é assim que o ORDER BY acima consegue colocar os subtotais sempre por último dentro de cada grupo, e o COALESCE consegue trocar o NULL por um rótulo legível como "TOTAL BRASIL".

Quando as duas dimensões (não só uma hierarquia) precisam ser cruzadas em todas as combinações possíveis, existe o CUBE:

sqlcopiar-- todas as combinações: por ano+região, só por ano, só por região, e o total geral SELECT dt.ano, dl.regiao, SUM(fvi.valor) AS total FROM fato_venda_item fvi JOIN dim_tempo dt ON dt.id_tempo = fvi.id_tempo JOIN dim_loja dl ON dl.id_loja = fvi.id_loja GROUP BY CUBE(dt.ano, dl.regiao);

E quando só interessam algumas combinações específicas (nem todo o cubo, nem só uma hierarquia), usa-se GROUPING SETS, listando exatamente quais agrupamentos você quer:

sqlcopiarSELECT dl.regiao, dl.estado, dl.cidade, SUM(fvi.valor) AS total FROM fato_venda_item fvi JOIN dim_loja dl ON dl.id_loja = fvi.id_loja GROUP BY GROUPING SETS ( (dl.regiao), -- drill up até região (dl.regiao, dl.estado), -- drill up até estado (dl.regiao, dl.estado, dl.cidade), -- drill down até cidade () -- drill up total (grand total) );

✅ Repare no padrão: ROLLUP, CUBE e GROUPING SETS são apenas atalhos de SQL para fazer, numa única varredura da tabela, exatamente o que uma ferramenta de BI faz quando o usuário clica para expandir ou recolher um nível numa tabela dinâmica.

Panorama
⚖️ Grão fino x Grão grosso — os trade-offs
AspectoGrão fino (ex: item do pedido)Grão grosso (ex: total mensal por loja)
Nº de linhasMuito maiorMuito menor
Flexibilidade de análiseAltíssima — dá para recalcular qualquer agregação depoisBaixa — se o detalhe não foi guardado, não dá para "desagregar" depois
Performance de agregaçõesMais lenta (soma muitas linhas)Mais rápida (já vem pronto)
Espaço / custo de armazenamentoMaiorMenor
Rastreabilidade / auditoriaTotal — dá para chegar ao item exatoBaixa — perde-se a origem do detalhe
Regra de ouro de KimballGrave sempre no grão mais fino disponível. Use agregados (grão grosso) só como otimização adicional — nunca como substituto do grão fino.

⚠️ Uma vez que os dados são gravados só no grão grosso, o detalhe fino se perde para sempre — não existe consulta SQL capaz de "adivinhar" que uma venda de R$ 1.850 num dia era, na verdade, 12 pedidos diferentes de clientes diferentes.

Checklist
✅ Boas Práticas
📝 Escreva o grain statement antes de modelar
"Uma linha de fato_X representa ___" precisa ser uma frase que qualquer pessoa do time repita sem ambiguidade, antes de desenhar qualquer coluna.
🧱 Um grão único por tabela de fatos
Nunca misture linhas de grãos diferentes na mesma tabela (ex: não misturar "total do pedido" com "item do pedido" na mesma fato_venda) — isso quebra qualquer SUM() feito sem cuidado.
🪜 Modele a hierarquia como colunas da própria dimensão
Uma dim_tempo desnormalizada, com colunas ano, trimestre, mes, dia todas na mesma linha, é o que permite que ferramentas de BI ofereçam drill down/up automaticamente, sem SQL novo a cada clique.
🔀 Cuidado com hierarquias não balanceadas (ragged)
Nem toda categoria de produto tem subcategoria; em organogramas, alguns funcionários pulam o nível de gerente e reportam direto ao diretor. Trate esses "buracos" explicitamente, em vez de assumir que todo nível sempre existe.
📊 Agregados são otimização, nunca substituto
Tabelas de resumo (grão grosso) aceleram dashboards pesados, mas sempre devem poder ser recalculadas a partir do grão fino — nunca devem ser a única fonte da verdade.
🔍 Deixe a ferramenta de BI fazer o drill, não o usuário
Com a hierarquia bem modelada nas dimensões (ordem clara dos níveis), ferramentas de BI (Power BI, Tableau, Looker...) já oferecem clique para expandir/recolher — sem precisar escrever uma consulta nova para cada nível.
