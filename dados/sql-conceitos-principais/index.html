Dados são só uma tabela gigante. SQL é como você conversa com ela.

SQL (Structured Query Language) é a linguagem que usamos para perguntar coisas para um banco de dados: "quem são meus clientes de São Paulo?", "quanto eu vendi esse mês?", "qual produto mais vendeu?". Não é uma linguagem de programação como Python ou JavaScript — é mais parecida com inglês estruturado: você descreve o que quer, e o banco descobre como buscar. Nesta aula vamos construir, do zero e com muita analogia visual, os conceitos que sustentam praticamente qualquer consulta SQL que você vai escrever na vida — de um simples SELECT até JOINs, subconsultas e transações.

Fundamentos
🗂️ Primeiro, o básico: o que é uma tabela?

Uma tabela SQL é basicamente uma planilha organizada: um conjunto de colunas fixas (os "tipos de pergunta") e várias linhas (as "respostas" de cada registro). Ao longo desta aula inteira vamos usar sempre as mesmas duas tabelas — clientes e pedidos — para que cada conceito novo se encaixe no que você já viu antes, em vez de exemplos soltos e descartáveis.

🎒
Pensando como criança

Imagine um caderno de fichas da escola. Cada coluna é uma pergunta que se repete em toda ficha ("qual seu nome?", "qual sua cidade?"). Cada linha é a ficha preenchida de uma pessoa específica. E o id é tipo o número da carteirinha: ninguém mais na escola tem aquele número.

➡️ Uma LINHA (registro)
A ficha completa de um cliente: id, nome, cidade e categoria juntos. Em SQL, cada linha também é chamada de tupla ou registro.
⬇️ Uma COLUNA (atributo)
A mesma pergunta feita para todos os clientes — por exemplo, "cidade". Em SQL, uma coluna também é chamada de campo ou atributo.

O comando mais usado
🔍 SELECT & FROM — a pergunta básica

SELECT diz quais colunas você quer ver; FROM diz de qual tabela. É a espinha dorsal de toda consulta SQL — praticamente tudo que vem depois nesta aula é sobre refinar essa pergunta básica.

Organizando o resultado

🔢 COUNT
Conta quantas linhas. Como contar quantos passageiros embarcaram no ônibus.
➕ SUM
Soma os valores. Como juntar todas as moedinhas num cofre.
📊 AVG

Resumindo por grupo
📦 GROUP BY & HAVING — separando em cestos

GROUP BY separa as linhas em cestos de acordo com um valor em comum — aqui, a categoria do cliente — para então aplicar funções agregadas dentro de cada cesto. HAVING filtra cestos inteiros depois de agrupar (diferente do WHERE, que filtra linhas antes de agrupar).

🧺
Analogia

Imagine separar uma caixa de bolinhas coloridas em cestos por cor: um cesto de bolinhas douradas, um de prateadas, um de bronze. GROUP BY é essa separação. COUNT(*) depois conta quantas bolinhas caíram em cada cesto. HAVING COUNT(*) >= 2 é dizer "só me mostre os cestos que ficaram com 2 bolinhas ou mais".

O conceito mais poderoso do SQL
🔗 JOIN — juntando duas tabelas

JOIN junta linhas de duas tabelas usando uma coluna em comum — aqui, clientes.id com pedidos.id_cliente. Existem 5 variações, e a diferença entre elas é só uma pergunta: o que fazer com quem não tem par do outro lado? Clique nos botões para trocar o tipo de JOIN e observar o diagrama e a tabela de resultado mudando juntos.

🧦
Analogia

Imagine juntar pares de meias: INNER JOIN só mostra as meias que têm par. LEFT JOIN mostra todas as suas meias, mesmo as que perderam o par (com um buraco no lugar). RIGHT JOIN é o mesmo, olhando pela gaveta do outro lado. FULL JOIN mostra tudo — pares e meias soltas dos dois lados. CROSS JOIN é experimentar combinar cada meia com cada outra meia, mesmo sem nenhuma lógica de par.

Consulta dentro de consulta
🪆 Subconsultas (Subqueries)

Uma subconsulta é um SELECT dentro de outro SELECT — a consulta de dentro roda primeiro, e seu resultado vira um valor (ou uma lista de valores) que a consulta de fora usa para filtrar.

🪆
Analogia

É como uma boneca russa (matrioska): para abrir a boneca de fora, você primeiro precisa abrir a de dentro. Em SQL, o banco sempre resolve a subconsulta de dentro para fora.

Pergunta simples: quais clientes já fizeram algum pedido?

Combinando listas
➕ UNION, INTERSECT & EXCEPT

Esses três comandos combinam o resultado de duas consultas separadas (com o mesmo número de colunas) como se fossem conjuntos. Exemplo: as cidades dos nossos clientes comparadas com as cidades de uma tabela hipotética de fornecedores.

🧑 Cidades dos clientes
Recife, São Paulo, Salvador, Curitiba
🚚 Cidades dos fornecedores
São Paulo, Curitiba, Belo Horizonte, Fortaleza
🔗 UNION — junta tudo, sem repetir
RecifeSão PauloSalvadorCuritibaBelo HorizonteFortaleza
🎯 INTERSECT — só quem está nas duas
São PauloCuritiba
➖ EXCEPT — só clientes, tirando fornecedores
RecifeSalvador
sqlcopiarSELECT cidade FROM clientes UNION SELECT cidade FROM fornecedores; -- UNION ALL faria a mesma coisa, mas manteria as duplicatas

💡 UNION remove duplicatas automaticamente (como um conjunto matemático); UNION ALL mantém tudo, inclusive repetidos — e é mais rápido, por não precisar checar duplicidade.

Agregação sem perder linhas
🪟 Window Functions — calcular sem "achatar" a tabela

Diferente do GROUP BY, que reduz várias linhas a uma só por grupo, uma window function calcula algo por grupo mas mantém todas as linhas originais no resultado. PARTITION BY define a "janela" (o grupo), e OVER() é o que ativa esse modo especial.

🏁
Analogia

É como dar uma medalha de posição (1º, 2º, 3º lugar) para cada corredor dentro da sua própria categoria de idade, sem tirar ninguém da lista de resultados — todo mundo continua aparecendo, só que agora com uma posição ao lado do nome.

sqlcopiarSELECT c.nome, c.categoria, SUM(p.valor) AS total_gasto, RANK() OVER ( PARTITION BY c.categoria -- reinicia o ranking a cada categoria ORDER BY SUM(p.valor) DESC ) AS posicao_na_categoria FROM clientes c LEFT JOIN pedidos p ON p.id_cliente = c.id GROUP BY c.nome, c.categoria;

Definindo a estrutura
🏗️ CREATE TABLE — construindo a planta

Antes de guardar qualquer dado, alguém precisa definir a estrutura: quais colunas existem, que tipo de dado cada uma aceita, e quais regras (constraints) protegem a integridade dos dados.

sqlcopiarCREATE TABLE clientes ( id INTEGER PRIMARY KEY, nome VARCHAR(100) NOT NULL, email VARCHAR(150) UNIQUE, cidade VARCHAR(100), categoria VARCHAR(20) DEFAULT 'Bronze' CHECK (categoria IN ('Bronze','Prata','Ouro')) ); CREATE TABLE pedidos ( id INTEGER PRIMARY KEY, id_cliente INTEGER REFERENCES clientes(id), -- chave estrangeira produto VARCHAR(100) NOT NULL, valor DECIMAL(10,2) CHECK (valor > 0) );
🔑 PRIMARY KEY
Identifica cada linha de forma única. Não pode repetir, não pode ser nula.
🚫 NOT NULL
Obriga a coluna a sempre ter um valor — não aceita "vazio".
✨ UNIQUE
Não pode repetir entre linhas, mas (diferente da PK) pode ficar vazia.
🎚️ DEFAULT
Valor usado automaticamente quando ninguém informa um.
✅ CHECK
Regra customizada que todo valor precisa passar antes de ser aceito.
🔗 REFERENCES (FK)
Aponta para a chave primária de outra tabela — o assunto da próxima seção.
🔧 ALTER TABLE
Muda a estrutura de uma tabela que já existe: ALTER TABLE clientes ADD COLUMN telefone VARCHAR(20);
🗑️ DROP TABLE
Apaga a tabela inteira — estrutura e dados, sem volta: DROP TABLE clientes;
O elo entre tabelas
🔑 Chaves Primárias e Estrangeiras

A chave primária (PK) identifica cada linha de forma única dentro da própria tabela. A chave estrangeira (FK) é uma coluna que aponta para a chave primária de outra tabela — é o "elo" que permite fazer JOIN.

🎫
Analogia

A chave primária é como o número da carteirinha de um aluno — único, ninguém mais tem igual. A chave estrangeira é como escrever esse número no canto de cada prova que o aluno fez: a prova "aponta de volta" para o dono dela.

Consultas com nome próprio
👁️ VIEW — uma consulta salva com nome

Uma view é um SELECT guardado sob um nome, que pode ser consultado como se fosse uma tabela — mas sem duplicar dado nenhum: toda vez que você consulta a view, ela roda o SELECT original por trás dos panos.

🪟
Analogia

É como uma janela recortada na parede de um depósito cheio de caixas: você não move nenhuma caixa, só cria uma abertura que sempre mostra a mesma "fatia" da vista — e se as caixas lá dentro mudarem de lugar, a janela mostra a mudança na hora.

sqlcopiarCREATE VIEW vw_clientes_ouro AS SELECT id, nome, cidade FROM clientes WHERE categoria = 'Ouro'; -- a partir daqui, consulta-se como se fosse uma tabela normal SELECT * FROM vw_clientes_ouro;

💡 Views são ótimas para esconder complexidade — um JOIN complicado de 4 tabelas pode virar uma view simples que qualquer pessoa do time consulta com um SELECT * FROM view.

Tudo ou nada
💾 Transações — BEGIN, COMMIT e ROLLBACK

Uma transação agrupa vários comandos como se fossem um só passo: ou todos acontecem, ou nenhum acontece. Isso evita ficar "no meio do caminho" se algo falhar. Exemplo: transferir 100 pontos de fidelidade da Ana para o Bruno — clique nos passos abaixo para ver o estado dos saldos mudando:

🏦
Analogia

É como uma transferência bancária: tirar dinheiro da sua conta e não colocar na conta do amigo (por causa de uma falha no meio do caminho) seria um desastre. COMMIT é "confirmar a transferência de vez"; ROLLBACK é "desfazer tudo, como se nunca tivesse mexido em nada".

pontos de fidelidade

pontos de fidelidade
sqlcopiarBEGIN; UPDATE clientes SET pontos = pontos - 100 WHERE id = 1; -- debita Ana UPDATE clientes SET pontos = pontos + 100 WHERE id = 2; -- credita Bruno COMMIT; -- confirma as duas mudanças de vez -- se algo desse errado antes daqui, ROLLBACK desfaria as DUAS

⚠️ Sem transação, se o sistema falhasse entre os dois UPDATEs, a Ana perderia 100 pontos e o Bruno nunca os receberia — os pontos simplesmente sumiriam. É exatamente esse risco que BEGIN/COMMIT/ROLLBACK elimina.

Consulta que se chama de novo
🌲 Recursividade — WITH RECURSIVE

Uma CTE recursiva (WITH RECURSIVE) é uma consulta que se refere a si mesma, repetindo em "rodadas" até não sobrar mais nenhuma linha nova pra processar. Ela resolve algo que um JOIN comum não resolve: navegar uma cadeia de tamanho desconhecido — uma árvore genealógica, um organograma, categorias dentro de categorias, comentários de comentários.

📞
Analogia

É como o telefone sem fio: você pergunta "quem te indicou?", pega a resposta e faz a mesma pergunta de novo pra essa pessoa, e de novo, e de novo — até alguém responder "ninguém me indicou". Você não sabia de antemão quantas rodadas ia precisar; a recursão para sozinha quando a cadeia acaba.

Só para este exemplo, imagine que a tabela clientes ganhou uma coluna indicado_por, guardando quem indicou cada cliente:

idnomeindicado_por
1Ana— (raiz)
2Bruno— (raiz)
3Carla1 (Ana)
4Diego3 (Carla)
5Elis4 (Diego)
1Âncora — roda uma vez só, achando o início da cadeia
Pega quem não foi indicado por ninguém: Ana e Bruno, ambos no nível 1.
2Passo recursivo — repete, subindo um nível a cada rodada
Junta clientes com o resultado da rodada anterior, achando quem foi indicado por alguém que já apareceu. Para sozinho quando nenhuma linha nova aparece.
sqlcopiarWITH RECURSIVE cadeia AS ( -- âncora: clientes sem indicação (raiz da árvore) SELECT id, nome, indicado_por, 1 AS nivel FROM clientes WHERE indicado_por IS NULL UNION ALL -- passo recursivo: sobe um nível a cada rodada SELECT c.id, c.nome, c.indicado_por, cadeia.nivel + 1 FROM clientes c JOIN cadeia ON c.indicado_por = cadeia.id ) SELECT * FROM cadeia ORDER BY nivel;

O que o banco fez por baixo dos panos
🔬 EXPLAIN — o raio-x da consulta

EXPLAIN não devolve os dados — devolve o plano de execução que o banco escolheu pra rodar sua consulta: quais tabelas ele varre, em que ordem, se usa um índice ou lê a tabela inteira. É a ferramenta pra descobrir por que uma consulta está lenta, antes de sair mudando código no escuro.

🧾
Analogia

É como pedir a nota fiscal detalhada em vez de só o troco: normalmente você só quer o resultado, mas quando algo custou mais caro (ou demorou mais) do que devia, o "recibo" mostra exatamente onde o custo apareceu.

sqlcopiarEXPLAIN SELECT * FROM pedidos WHERE id_cliente = 1;
🐌 Sem índice
Seq Scan em pedidos — o banco lê a tabela inteira, linha por linha, e descarta quem não bate com id_cliente = 1. Com 6 linhas isso é instantâneo; com 6 milhões, não.
⚡ Com índice em id_cliente
Index Scan — o banco vai direto nas linhas certas, sem varrer as que não interessam. É a diferença entre procurar um nome numa lista telefônica com índice alfabético e ler página por página.

💡 EXPLAIN só mostra o plano — não necessariamente executa a consulta de verdade. EXPLAIN ANALYZE vai além: roda a consulta de fato e cronometra cada etapa do plano, mostrando o tempo real gasto em cada passo.

⚠️ O formato exato do plano varia de banco pra banco (PostgreSQL, DuckDB, MySQL...), mas a ideia é sempre a mesma: entender o caminho que a consulta percorreu antes de julgar se ela está "lenta" ou "rápida".
