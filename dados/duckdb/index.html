O SGBD analítico que cabe dentro do seu processo

DuckDB é um sistema de gerenciamento de banco de dados relacional, colunar e vetorizado, criado para cargas de trabalho analíticas (OLAP). Lançado em 2019 por Mark Raasveldt e Hannes Mühleisen, pesquisadores do CWI (Centrum Wiskunde & Informatica, em Amsterdã), o projeto nasceu com uma meta explícita: ser o "SQLite das análises" — um motor SQL completo, sem servidor, sem configuração, que roda embutido dentro da própria aplicação que o usa. Hoje ele é peça central do ecossistema Python/R de dados, dos notebooks às pipelines de produção, consultando arquivos Parquet, CSV e JSON diretamente — local ou na nuvem — sem precisar de um cluster.

Fundamentos
🦆 O que é o DuckDB?

A maioria dos bancos de dados que aparecem no dia a dia — PostgreSQL, MySQL, SQL Server — foi desenhada para OLTP (Online Transaction Processing): muitas transações pequenas e simultâneas, como "inserir um pedido" ou "atualizar o estoque de um produto". DuckDB ataca o problema oposto, OLAP (Online Analytical Processing): poucas consultas, cada uma tocando milhões de linhas, para responder perguntas como "qual a soma de vendas por categoria no último ano?". Essa diferença de propósito explica cada decisão de arquitetura que vamos ver na aula.

📊 Analítico (OLAP)
Otimizado para consultas complexas que agregam, filtram e cruzam grandes volumes — GROUP BY, JOIN, janelas — em vez de milhares de pequenas transações por segundo.
🧬 Colunar
Assim como o Parquet, guarda dados por coluna, não por linha. Uma consulta que soma 1 coluna entre 50 não precisa tocar nas outras 49 — menos I/O, mais velocidade.
📦 In-Process
Não existe um "servidor DuckDB" rodando à parte: a biblioteca é carregada dentro do próprio processo Python/Node/CLI que a usa — a mesma filosofia do SQLite.
DimensãoOLTP (ex: PostgreSQL, MySQL)OLAP (ex: DuckDB)
FocoMuitas transações pequenas (insert/update pontual)Poucas consultas grandes (agregações, scans)
Armazenamento físicoLinha (row-store)Coluna (column-store)
Exemplo de pergunta"Atualize o estoque do produto X""Some as vendas por categoria no último ano"

Como Funciona por Dentro
🏗️ Arquitetura In-Process (Embedded)

Bancos como PostgreSQL usam o modelo cliente-servidor: sua aplicação é um processo, o banco é outro processo (às vezes em outra máquina), e toda consulta viaja por uma rede ou socket entre os dois. O DuckDB usa o modelo in-process (embedded): o motor de banco de dados é uma biblioteca carregada dentro do mesmo processo da sua aplicação. 💡 É a mesma filosofia do SQLite (por isso a comparação é tão comum) — mas o SQLite foi otimizado para OLTP linha a linha, enquanto o DuckDB aplica essa ideia de "banco embutido" a cargas analíticas colunares. Resultado prático: con.sql(...) é uma chamada de função local, não uma requisição de rede — sem serialização, sem round-trip, sem processo extra para instalar ou manter no ar.

O Motor por Dentro
⚡ Execução Vetorizada

Muitos bancos tradicionais processam consultas no modelo Volcano/iterator: cada operador do plano pede "me dê a próxima linha", uma de cada vez, e essa chamada de função se repete para cada linha do resultado. O DuckDB usa execução vetorizada: os operadores processam lotes de até 2048 valores por chamada, organizados em colunas contíguas na memória. Menos chamadas de função, dados vizinhos na memória (cache-friendly) e abertura para o processador aplicar SIMD (uma instrução, vários valores de uma vez).

📉 Menos overhead por valor
Um lote de 2048 valores custa uma "volta" do executor, não 2048 — o overhead de despacho de função é diluído por todo o lote.
🧊 Cache-friendly
Como a coluna já está armazenada de forma contígua, processar um lote inteiro aproveita muito melhor o cache da CPU do que saltar entre campos de uma linha.
🧮 Aproveita SIMD
Operações simples (somar, comparar) sobre um vetor de valores do mesmo tipo podem ser paralelizadas em nível de instrução pelo próprio processador.

Modelo de execução em destaque
🧬 Unified Vector Format
Internamente, um vetor pode estar em diferentes representações — flat (valores expandidos normalmente), constant (o lote inteiro é um único valor repetido, ex: resultado de um filtro que zerou tudo) ou dictionary (índices apontando para um conjunto de valores únicos). O Unified Vector Format deixa os operadores lerem qualquer uma dessas formas de maneira uniforme, sem precisar descomprimir — o engine só materializa de verdade quando é estritamente necessário.
🎭 Validity Mask
Em vez de testar NULL valor a valor, cada vetor carrega um bitmap compacto (1 bit por posição) marcando nulos. Testar IS NULL num lote inteiro vira uma operação de bits sobre o bitmap inteiro, não um if repetido 2048 vezes.

💡 O DuckDB também é push-based: em vez do modelo clássico "pull" (Volcano), onde cada operador pede a próxima linha ao operador anterior, os vetores são empurrados de baixo para cima pelo pipeline assim que ficam prontos — menos chamadas de função encadeadas, melhor aproveitamento do pipeline da CPU. Combinado com o paralelismo morsel-driven (cada thread processa um bloco de vetores de forma independente), é isso que permite ao DuckDB saturar todos os núcleos disponíveis numa única máquina sem coordenação cara entre eles.

Mecânica da Velocidade
🧠 Por Que é Tão Rápido: Cache da CPU e Localidade de Memória

Todo o design do DuckDB — armazenamento colunar, vetorização, compressão — converge para um único objetivo de baixo nível: manter o processador alimentado pela cache em vez de esperar pela RAM. Entender a hierarquia de memória de um processador moderno explica por que "ser colunar" não é só sobre pular colunas inteiras (como vimos na aula de Parquet) — é também sobre aproveitar cada byte que já foi trazido para perto do núcleo.

A hierarquia de memória — quanto mais perto do núcleo, mais rápido e mais escasso
Latências ilustrativas (ordem de grandeza, escala logarítmica) — os números exatos variam por CPU, mas a proporção entre os níveis é o que importa aqui.

💡 Para sentir a diferença de escala: se um acesso à L1 durasse 1 segundo num relógio humano, a L2 levaria uns 4 segundos, a L3 uns 15 segundos, a RAM quase 2 minutos — e um SSD, mais de um dia inteiro. Toda vez que o processador "erra" a cache (cache miss) e precisa buscar na RAM, ele fica parado esperando o equivalente a centenas de instruções que poderia ter executado.

Uma cache line é a unidade mínima que a CPU move entre RAM e cache — tipicamente 64 bytes de cada vez, nunca um valor isolado. Isso significa que o que está fisicamente ao lado do dado que você quer também é trazido "de graça". A pergunta que decide se isso ajuda ou atrapalha é: o que está ao lado é útil para a consulta, ou é lixo que vai ser descartado?

🧱 Row-Store — a cache line vem contaminada
Numa tabela de vendas (produto, cliente, país, data, valor), uma cache line de 64 bytes carrega um pedaço de linhas inteiras. Se a consulta só precisa de valor, boa parte desses bytes é desperdício — ocupou espaço na cache e largura de banda de memória à toa.
📊 Column-Store — a cache line vem 100% útil
Na mesma consulta sobre uma tabela colunar, uma cache line de 64 bytes carrega 8 valores contíguos de valor (8 bytes cada). Nenhum byte desperdiçado — e o próximo bloco de 8 valores já está a caminho também.

É exatamente aqui que a execução vetorizada entra em jogo: o tamanho do lote padrão do DuckDB — 2048 valores — não foi escolhido à toa. É grande o suficiente para diluir o overhead por chamada de função, mas pequeno o bastante para o "working set" de cada operador (vetor de entrada + vetor de saída) caber confortavelmente nas caches L1/L2 do núcleo, em vez de estourar para a RAM no meio do processamento.

📦 Compressão reduz o "working set"
Vetores constant e dictionary (seção anterior) representam muitos valores com poucos bytes — mais dados úteis cabem em cada nível de cache ao mesmo tempo.
🔮 Prefetching de hardware
Acesso sequencial e previsível (como varrer uma coluna) é exatamente o padrão que o prefetcher da CPU sabe antecipar, trazendo a próxima cache line antes mesmo de ela ser pedida.
🧵 Cache por núcleo, dado por núcleo
Cada thread processa seu próprio morsel de dados (paralelismo morsel-driven) — mantendo a L1/L2 daquele núcleo "quente" com dados que só aquela thread usa, sem disputa entre núcleos.

Ergonomia
✨ SQL Amigável (Friendly SQL)

Além do SQL padrão, o DuckDB adiciona extensões de sintaxe que eliminam boilerplate comum — pensadas para quem escreve consultas ad hoc o dia inteiro, não só pipelines fixos.

SELECT * EXCLUDE — todas as colunas, menos algumas
SQL tradicionalSELECT id, nome, email, criado_em -- precisa listar manualmente cada coluna -- exceto "senha_hash" FROM usuarios;
duckdb friendlySELECT * EXCLUDE (senha_hash) FROM usuarios;
GROUP BY ALL / ORDER BY ALL — sem repetir a lista de colunas
SQL tradicionalSELECT categoria, regiao, SUM(valor) AS total FROM vendas GROUP BY categoria, regiao ORDER BY categoria, regiao;
duckdb friendlySELECT categoria, regiao, SUM(valor) AS total FROM vendas GROUP BY ALL ORDER BY ALL;
Sintaxe FROM-first — comece pela tabela, não pelo SELECT
SQL tradicionalSELECT categoria, SUM(valor) FROM vendas WHERE ano = 2024 GROUP BY categoria;
duckdb friendlyFROM vendas WHERE ano = 2024 SELECT categoria, SUM(valor) GROUP BY categoria;
🧩 Structs & Lists com açúcar sintático
Acesse campos aninhados como pessoa.nome e fatie listas como lista[1:3] — sem funções auxiliares.
🔤 COLUMNS() com regex
SELECT COLUMNS('venda_.*') aplica a mesma expressão a todas as colunas cujo nome bate com o padrão.
➕ Vírgula final permitida
Esquecer de tirar a vírgula do último item de um SELECT não quebra mais a consulta.

🐼 Integração com Pandas, Polars e Arrow

Por rodar no mesmo processo, o DuckDB consegue enxergar objetos já existentes na sua sessão — DataFrames, tabelas Arrow — e consultá-los sem copiar os dados (zero-copy sempre que o layout de memória já é compatível).

Pandas — consulte um DataFrame pelo nome
pythoncopiarimport duckdb, pandas as pd df = pd.read_csv("vendas.csv") duckdb.sql("SELECT categoria, SUM(valor) FROM df GROUP BY ALL").df()
Polars — LazyFrame direto no FROM
pythoncopiarimport polars as pl lf = pl.scan_parquet("vendas.parquet") duckdb.sql("SELECT * FROM lf WHERE valor > 100").pl()
Arrow — tabelas em memória colunar compatível
pythoncopiarimport pyarrow as pa tabela = pa.table({"categoria": ["a","b"], "valor": [10,20]}) duckdb.sql("SELECT * FROM tabela").arrow()

Estado e Volume
💾 Persistência & Processamento Maior que a Memória

O DuckDB pode viver inteiramente em memória (ideal para uma sessão de análise pontual) ou persistir num único arquivo .duckdb — com write-ahead log (WAL) para durabilidade, como qualquer banco de verdade.

Duas formas de conectar

E quando o dataset (ou o estado intermediário de uma consulta, como uma tabela de hash de um JOIN gigante) não cabe na RAM disponível? Diferente de engines puramente in-memory, o DuckDB implementa out-of-core processing: derrama (spilling) automaticamente os dados que excedem a memória para disco temporário, terminando a consulta em vez de falhar com out of memory.

📊 DuckDB vs. SQLite vs. PostgreSQL vs. Spark

Cada um resolve um problema diferente — a pergunta certa não é "qual é o melhor", e sim "qual carga de trabalho estou processando".

SistemaArquiteturaModelo de dadosEscala típicaMelhor para
SQLiteIn-processLinha (row-store)Um dispositivoOLTP embutido: apps mobile/desktop, config local
PostgreSQLCliente-servidorLinha (row-store)Um servidorOLTP de produção com muitos usuários concorrentes
DuckDBIn-processColuna (colunar) + vetorizadoUma máquina (multi-core)OLAP embutido: notebooks, ETL local, apps de dados
Spark (cluster)Distribuída (cluster)Coluna (via Parquet/Arrow)Muitas máquinasOLAP que não cabe em uma única máquina
Ordem de grandeza ilustrativa (não um benchmark) para uma agregação analítica típica sobre dezenas de milhões de linhas em uma única máquina — o overhead de coordenar um cluster só compensa quando o dado realmente não cabe em uma máquina.

Checklist
✅ Boas Práticas
📐 Prefira Parquet para persistir
Ao terminar uma etapa de transformação, exporte para Parquet (ou uma tabela em .duckdb) em vez de recomputar do CSV bruto toda vez.
🧵 Ajuste threads e memory_limit
PRAGMA threads=4; e SET memory_limit='8GB'; evitam que o DuckDB monopolize um container ou notebook com RAM limitada.
🔒 Um único processo escreve por vez
Um arquivo .duckdb aceita múltiplos leitores concorrentes em modo read_only, mas só um processo em modo de escrita.
🔌 Cuidado com autoload offline
Em ambientes sem internet, use INSTALL para pré-instalar as extensões necessárias — o autoload padrão tenta baixá-las na hora do primeiro uso.

⚠️ DuckDB não substitui um banco transacional de produção com muitos usuários concorrentes escrevendo ao mesmo tempo — para isso, PostgreSQL/MySQL continuam sendo a escolha certa. Use o DuckDB para a parte analítica do seu stack, não para o backend transacional da aplicação.
