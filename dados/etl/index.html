Dados não nascem prontos. Alguém precisa buscá-los, arrumá-los e guardá-los.

ETL (Extract, Transform, Load) e ELT (Extract, Load, Transform) são as duas formas mais comuns de montar esse "cano" que leva dados desde onde eles nascem — um sistema de vendas, um aplicativo, uma planilha — até onde eles viram informação útil: um Data Warehouse, um dashboard, um relatório. As duas siglas têm as mesmas três letras: Extrair, Transformar, Carregar (Load). A única diferença — mas ela muda tudo — é a ordem em que a transformação acontece. Hoje vamos destrinchar cada letra, comparar as duas ordens lado a lado, e simular um pipeline de verdade, com muita analogia simples e exemplo visual.

E — Extract T — Transform L — Load ETL — transforma antes ELT — transforma depois

Todo pipeline de dados é isso: pegar de um lugar, arrumar, e deixar em outro lugar — organizado para quem for usar depois.
Fundamentos
🧃 Primeiro, o básico: o que é um "pipeline de dados"?

Imagine uma fábrica de suco de laranja. Ninguém bebe a laranja direto do pé: alguém precisa colher as laranjas (em vários pomares diferentes), espremer, coar as sementes e misturar o suco na proporção certa, e depois engarrafar e guardar na prateleira certa do mercado, por tipo e validade. Um pipeline de dados faz exatamente isso, só que com informação: colhe dados de vários sistemas, limpa e organiza esses dados, e guarda tudo arrumado num lugar onde as pessoas (ou os robôs) vão "beber" essa informação depois — um dashboard, um relatório, um modelo de machine learning.

🍊
Pensando como criança

Se você desse uma laranja inteira, com casca e caroço, para alguém tomar de canudinho, a pessoa ia sofrer. É preciso descascar, espremer, coar antes. Dados brutos são a mesma coisa: cheios de "casca" (erros, duplicatas, formatos estranhos) que precisam ser tirados antes que alguém consiga "tomar" essa informação sem engasgar.

Todo pipeline — não importa a ordem das letras — é formado por essas três etapas. Veja o "cano" completo, com uma origem bagunçada de um lado e um destino organizado do outro:

E — Extract 🧺 Colher Buscar os dados nas fontes: bancos, APIs, planilhas, sensores.
→
T — Transform 🧑‍🍳 Preparar Limpar, corrigir, combinar e calcular — deixar pronto para uso.
→
L — Load 🏪 Guardar Colocar no destino final, organizado, pronto para consulta.

💡 A sigla não diz nada sobre o conteúdo de cada etapa — ela só diz a ordem. ETL faz E → T → L. ELT faz E → L → T. As três tarefas (colher, preparar, guardar) sempre acontecem — a pergunta é só: "preparo antes ou depois de guardar?"

Letra 1 de 3
E

Extract — Extrair

Buscar os dados onde quer que eles morem, sem alterar a fonte original.

Extrair é o ato de ler dados de um ou mais sistemas de origem — sem apagar nem modificar nada lá. Uma empresa raramente tem os dados que precisa num lugar só: parte está no banco do site de vendas, parte numa planilha do financeiro, parte numa API de um parceiro. A extração é a rede de pesca que recolhe tudo isso para um só lugar antes da próxima etapa.

🎣
Analogia

É como ir ao mercado com uma lista de compras em vários corredores: você não muda nada nas prateleiras, só pega uma cópia (os itens) e coloca no carrinho. A prateleira do mercado continua exatamente como estava.

Existem duas estratégias principais para decidir quanto extrair a cada execução do pipeline:

📦 Extração completa (Full Load)
Copia a tabela inteira toda vez, do zero. Simples de implementar, mas pesado — se a origem tem 50 milhões de linhas e só 100 mudaram, você ainda lê as 50 milhões de novo.
➕ Extração incremental (CDC)
Copia só o que mudou desde a última vez — usando uma coluna de data de atualização ou uma técnica chamada Change Data Capture. Muito mais leve e rápido para tabelas grandes.
sqlcopiar-- Extração completa: lê tudo, toda vez SELECT * FROM pedidos; -- Extração incremental: só o que mudou desde a última carga SELECT * FROM pedidos WHERE atualizado_em > '2026-08-04 00:00:00'; -- última execução do pipeline
Letra 2 de 3
T

Transform — Transformar

Limpar, corrigir, combinar e calcular — o coração do trabalho de arrumação.

Transformar é onde os dados brutos, cheios de imperfeições, viram informação confiável. É a etapa mais trabalhosa — e mais importante — do pipeline, porque é aqui que erros de digitação, formatos inconsistentes e regras de negócio são resolvidos de uma vez por todas, em vez de cada pessoa ter que "consertar na mão" toda vez que for usar o dado.

🥕
Analogia

É como preparar os ingredientes antes de cozinhar: lavar a sujeira, descascar o que não se come, cortar do mesmo tamanho para cozinhar por igual, e misturar os ingredientes de receitas diferentes numa saladeira só. Ninguém joga a cenoura suja e inteira direto na panela.

Letra 3 de 3
L

Load — Carregar

Colocar o dado no destino final, do jeito certo, para quem vai consultar.

Carregar é a etapa de escrever os dados no seu destino definitivo — quase sempre um Data Warehouse, um Data Lake ou um banco analítico. É aqui que a informação fica disponível para dashboards, relatórios e análises. Assim como na extração, existem estratégias diferentes de "como" gravar.

🗄️
Analogia

É como guardar as compras do mercado: você pode esvaziar a geladeira e recolocar tudo (full load), só adicionar o que comprou hoje na prateleira (append) ou trocar o item vencido pelo novo, mantendo o resto no lugar (upsert/merge).

🔄 Full Load
Apaga tudo no destino e regrava do zero a cada execução. Simples, mas caro para tabelas grandes — e perde o histórico se não houver controle à parte.
➕ Append (incremental)
Só adiciona linhas novas, sem tocar nas existentes. Ótimo para dados que nunca mudam depois de criados, como logs e eventos.
🔀 Upsert / Merge
Atualiza a linha se ela já existir, insere se for nova. O jeito mais comum de manter dimensões (clientes, produtos) sempre sincronizadas com a origem.
sqlcopiar-- Upsert / Merge: atualiza quem já existe, insere quem é novo MERGE INTO dw.dim_cliente AS destino USING staging.cliente AS origem ON destino.id_cliente = origem.id_cliente WHEN MATCHED THEN UPDATE SET nome = origem.nome, cidade = origem.cidade WHEN NOT MATCHED THEN INSERT (id_cliente, nome, cidade) VALUES (origem.id_cliente, origem.nome, origem.cidade);

💡 Antes de carregar no destino final, é comum passar por uma área de staging (uma "bancada de trabalho" temporária) — um espaço intermediário onde os dados ficam provisoriamente enquanto são validados, sem arriscar sujar as tabelas que os relatórios já usam.

O Coração da Aula
🔀 ETL vs ELT — a mesma receita, ordem diferente

As duas siglas usam exatamente as mesmas três letras. A diferença inteira está em onde a transformação acontece: antes ou depois de os dados chegarem ao destino. Clique nos botões abaixo para comparar as duas ordens lado a lado.

🏭 ETL — Extract, Transform, Load
Os dados são transformados num servidor separado (o motor de ETL), antes de chegar ao destino. Só o dado já limpo e pronto entra no Data Warehouse. É a abordagem clássica, usada desde os anos 1980-90, quando os bancos analíticos eram caros e lentos — então evitava-se ao máximo processar dado bruto dentro deles.
☁️ ELT — Extract, Load, Transform
Os dados brutos vão direto para o destino (um Data Warehouse ou Data Lake moderno), e a transformação acontece dentro dele, usando o próprio poder de processamento do Warehouse. Ficou popular com warehouses em nuvem (Snowflake, BigQuery, Databricks) que processam volumes gigantes muito rápido e barato.
✅ Quando ETL brilha
Dados sensíveis que precisam ser mascarados ou filtrados antes de tocar o destino (LGPD, dados médicos); destino com pouco poder de processamento; regras de transformação muito complexas que um motor dedicado resolve melhor.
✅ Quando ELT brilha
Data Warehouse moderno e barato para processar (nuvem); precisa de flexibilidade para reprocessar/mudar regras sem reextrair tudo de novo; equipe de análise quer acesso ao dado bruto também, não só ao transformado.

⚠️ Repare que em ambos, o dado passa pelas mesmas três etapas — a diferença não é "o que" é feito, é "onde" e "quando". No ETL, a transformação é um serviço à parte. No ELT, a transformação é só mais uma consulta SQL rodando dentro do próprio Warehouse (frequentemente orquestrada por uma ferramenta como o dbt).

Contexto Histórico
📈 Por que o ELT ficou tão popular na última década?

Nos anos 1990 e 2000, bancos analíticos eram caros e limitados — processar dado bruto neles era um desperdício de um recurso escasso. Por isso o ETL clássico transformava tudo fora do Warehouse, num servidor dedicado, antes de carregar só o essencial. A partir dos anos 2010, Data Warehouses em nuvem (Snowflake, BigQuery, Redshift, Databricks) passaram a separar armazenamento de processamento e cobrar por uso — de repente, processar dados brutos dentro do Warehouse ficou barato, rápido e elástico. O ELT nasceu para aproveitar esse poder computacional que passou a sobrar ali dentro.

Outra Dimensão da Escolha
⏱️ Batch vs Streaming — de quanto em quanto tempo?

Além de "ETL ou ELT", existe outra pergunta independente: o pipeline roda de tempos em tempos (batch) ou o tempo todo, dado a dado (streaming)? As duas abordagens de ordem (ETL/ELT) podem ser batch ou streaming — são decisões diferentes.

📦 Batch — em lotes
Roda de hora em hora, ou uma vez por dia/noite, processando um "lote" de dados acumulados. Mais simples e barato. Analogia: caminhão de lixo que passa uma vez por dia recolhendo tudo que acumulou.
🌊 Streaming — em tempo real
Processa cada evento assim que ele acontece, com atraso de segundos. Mais complexo e caro de manter. Analogia: esteira de caixa de supermercado, passando item por item, sem parar.

💡 A maioria das empresas usa batch para a maior parte dos relatórios (venda de ontem, estoque de hoje de manhã) e reserva streaming só para o que realmente precisa ser imediato — detecção de fraude, painel operacional ao vivo, alertas.

💻 Montando um pipeline ELT do zero, no DuckDB

Vamos simular o pipeline inteiro de pedidos de uma loja: extrair de uma "origem" simulada, carregar bruto numa staging, e só então transformar dentro do próprio banco — o jeitinho ELT. Cada passo pode ser colado e rodado em sequência.

1Extract — simular a origem (tabela bruta, cheia de sujeira)
sql · duckdbcopiarCREATE TABLE staging_pedidos ( id_pedido INTEGER, nome_cliente VARCHAR, -- vem sujo, com espaços e caixa inconsistente cidade VARCHAR, -- vem com grafias diferentes preco_texto VARCHAR, -- vem como texto, não número quantidade INTEGER ); INSERT INTO staging_pedidos VALUES (7734, ' joão silva ', 'sao paulo', '19,90', 2), (7735, 'MARIA souza', 'SP', '45,00', 1), (7736, 'ana lima', 'São Paulo', '12,50', 5);
2Load — o dado bruto já está "carregado" (é a própria tabela staging)
Na abordagem ELT, este passo já aconteceu: o dado sujo entrou direto no banco de destino. Não existe processamento externo antes disso.
sql · duckdbcopiarSELECT * FROM staging_pedidos; -- 7734 | " joão silva " | "sao paulo" | "19,90" | 2 ← tudo ainda sujo
3Transform — limpar e padronizar, agora dentro do próprio Warehouse
sql · duckdbcopiarCREATE TABLE dw_pedidos AS SELECT id_pedido, TRIM(INITCAP(nome_cliente)) AS nome_cliente, CASE WHEN UPPER(cidade) IN ('SP', 'SAO PAULO', 'SÃO PAULO') THEN 'São Paulo' ELSE INITCAP(cidade) END AS cidade, CAST(REPLACE(preco_texto, ',', '.') AS DECIMAL(10,2)) AS preco, quantidade, CAST(REPLACE(preco_texto, ',', '.') AS DECIMAL(10,2)) * quantidade AS total FROM staging_pedidos; SELECT * FROM dw_pedidos; -- 7734 | João Silva | São Paulo | 19.90 | 2 | 39.80 ← limpo, tipado, pronto para o dashboard

✅ Repare: o CREATE TABLE dw_pedidos AS SELECT ... é o coração do ELT moderno — é exatamente esse tipo de consulta que ferramentas como o dbt organizam, versionam e testam em produção, uma por uma, formando o pipeline de transformação inteiro dentro do Warehouse.

Checklist
✅ Boas Práticas
🛬 Sempre tenha uma área de staging/landing
Nunca escreva direto nas tabelas finais que os dashboards usam — um erro no meio do caminho não pode quebrar o que já está em produção.
🔁 Prefira extração incremental quando possível
Full load em tabelas grandes desperdiça tempo e recursos — use uma coluna de data de atualização ou CDC sempre que a origem permitir.
🧪 Teste os dados, não só o código
Verifique se chaves não se repetem, se valores não são nulos onde não deveriam, se totais batem — ferramentas como o dbt têm testes de dados prontos para isso.
📜 Documente e versione as transformações
Regras de negócio ("cliente ativo é quem comprou nos últimos 90 dias") mudam — trate a lógica de transformação como código, com histórico e revisão.
🔐 Trate dados sensíveis o quanto antes
Mascare ou anonimize CPF, e-mail e dados de saúde na extração ou logo na entrada — não espere chegar ao fim do pipeline.
📈 Monitore o pipeline como monitora uma aplicação
Alertas de atraso, falha ou volume anormal de dados evitam que um problema "silencioso" vire um relatório errado meses depois.
