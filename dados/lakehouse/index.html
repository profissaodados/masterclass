A jornada da aula: da biblioteca e da piscina até o lakehouse

Um Data Warehouse é organizado, mas caro e rígido. Um Data Lake é barato, mas vira bagunça. E se desse pra ter os dois de uma vez?

Lakehouse é a resposta: uma arquitetura que guarda os dados em armazenamento barato e aberto — como um Data Lake — mas adiciona uma "camada mágica" de controle por cima — transações ACID, regras de schema, histórico de versões — que só existiam em Data Warehouses. O resultado é um lugar só onde cabe tudo: tabelas estruturadas para o financeiro, dados brutos para o time de ciência de dados, e tudo isso consultado por qualquer motor SQL que você quiser. Hoje vamos desmontar essa ideia peça por peça, com muita analogia de criança, muito gráfico e simuladores para você clicar e ver funcionando.

Antes de Começar
🏠 O que vamos aprender hoje

Para entender por que o Lakehouse existe, primeiro precisamos entender os dois mundos que ele veio unir. Pense assim: de um lado tem a biblioteca (Data Warehouse) — tudo catalogado, mas rígida e cara para crescer. Do outro tem a piscina (Data Lake) — aceita qualquer coisa, barata, mas vira um pântano se ninguém organizar. O Lakehouse é o que acontece quando alguém coloca etiquetas inteligentes e regras de organização dentro da piscina, sem perder o preço baixo dela.

Fundamentos — Mundo 1
📚 Data Warehouse — a Biblioteca Organizadíssima

Um Data Warehouse (Teradata, Redshift, Snowflake, BigQuery clássico) é feito para receber dados estruturados — linhas e colunas, como uma planilha — e devolver respostas rápidas para relatórios e dashboards. Antes de qualquer dado entrar, ele precisa se encaixar num schema definido: nome das colunas, tipos, tamanhos. Isso se chama schema-on-write — o "molde" é verificado na entrada.

📚
Pensando como criança

Um Data Warehouse é como uma biblioteca com bibliotecário rigoroso: todo livro precisa ter capa, título, autor e código catalogado antes de subir na estante. Se você chegar com um brinquedo, uma foto ou uma pedra, o bibliotecário não deixa entrar — "isso não é livro, não tem onde catalogar". É extremamente organizado, mas só aceita o que já nasceu no formato certo.

✅ Pontos fortes
Consultas rapidíssimas, governança forte, dados sempre confiáveis e prontos para BI. Ótimo para o time financeiro que precisa de números exatos, todo dia, sem surpresa.
⚠️ Limitações
Caro para guardar grandes volumes, só aceita dados estruturados (nada de vídeo, imagem, texto livre, JSON aninhado), e crescer a capacidade costuma exigir contratos e hardware dedicados.
Fundamentos — Mundo 2
🏊 Data Lake — A Piscina Que Aceita Tudo

Um Data Lake nasceu para resolver o preço e a rigidez do Warehouse: é só um armazenamento de arquivos gigante e barato (Amazon S3, Azure Data Lake Storage, Google Cloud Storage) onde você joga qualquer coisa — planilhas, imagens, vídeos, logs, JSON, Parquet — sem precisar definir um schema antes. O schema só é verificado na hora de ler, se é que alguém verifica: é o chamado schema-on-read.

🏊
Pensando como criança

Um Data Lake é como uma piscina enorme e barata onde qualquer criança pode jogar qualquer brinquedo: bola, boneca, pedra, um pato de borracha. Não tem porteiro perguntando "isso é um livro catalogado?" — é só jogar dentro. Só que, sem ninguém organizando, depois de um tempo ninguém mais lembra o que tem lá no fundo da piscina, nem se aquele "brinquedo" ainda está inteiro.

✅ Pontos fortes
Armazenamento barato (centavos por GB), aceita qualquer tipo de dado, escala quase sem limite, e é ótimo para times de ciência de dados e Machine Learning que precisam de dados brutos.
⚠️ Limitações
Sem controle nenhum por padrão: ninguém garante que dois processos escrevendo ao mesmo tempo não vão se atrapalhar, que um arquivo corrompido não vai quebrar uma consulta, ou que os dados de ontem ainda batem com os de hoje.

Quando ninguém organiza a piscina por muito tempo, ela vira o que o mercado apelidou de "pântano de dados" (data swamp) — um amontoado de arquivos que ninguém mais confia:

Arquivo na piscinaProblema

⚠️ Sem transações, sem schema garantido e sem histórico de versões, a piscina vira pântano — e é exatamente esse conjunto de problemas que o Lakehouse foi criado para resolver.

A Grande Ideia
🏡 Nasce o Lakehouse

Por anos, empresas mantinham os dois sistemas ao mesmo tempo: um Data Lake barato para guardar tudo, e um Data Warehouse caro ao lado, alimentado por cópias já limpas do Lake, só para os relatórios de negócio funcionarem rápido e com confiança. Isso significa dados duplicados, pipelines de cópia constantes, e sempre a dúvida: "os dois lados estão mesmo sincronizados?"

🏡
Pensando como criança

O Lakehouse é o que acontece quando a piscina ganha um sistema de etiquetas e regras, como se um bibliotecário organizado se mudasse para dentro dela. Continua barata como a piscina — qualquer brinquedo pode entrar — mas agora cada brinquedo tem uma etiqueta, existe um caderno de registro dizendo o que entrou e quando, e ninguém consegue tirar um brinquedo de dentro d'água sem anotar. É a piscina virando um aquário organizado.

A peça-chave é a camada 2

Storage e Compute já existiam separados desde os primeiros Data Lakes. O que faltava — e é a verdadeira invenção do Lakehouse — é a camada de formato de tabela no meio: um "livro de regras" que transforma uma pasta cheia de arquivos Parquet soltos numa tabela de verdade, com transações, schema e histórico.

Superpotência 1 de 3
🔒 Transações ACID — Por Que Isso Importa

ACID é um conjunto de 4 garantias que um banco de dados de verdade oferece a cada escrita. O Lakehouse traz essas mesmas garantias para cima de arquivos num object storage — algo que um Data Lake puro, sozinho, nunca teve.

🧩 Atomicidade
Ou a escrita inteira acontece, ou nenhuma parte dela acontece. Nunca fica "meio caminho andado" — como pedir uma pizza e ela chegar inteira, ou não chegar.
📏 Consistência
As regras da tabela nunca são quebradas, nem no meio de uma escrita. Se toda linha precisa de uma chave, nunca aparece uma linha sem chave — nem por um segundo.
🚧 Isolamento
Duas pessoas escrevendo ao mesmo tempo não se atrapalham — é como se cada uma tivesse a mesa só para si até terminar sua tarefa.
💾 Durabilidade
Depois que a escrita foi confirmada, ela sobrevive a uma queda de energia. É como salvar o jogo de verdade, não só deixar pausado na tela.
Duas pessoas atualizando a mesma tabela ao mesmo tempo
Superpotência 2 de 3
🧬 Schema: Enforcement & Evolution

O Lakehouse controla dois momentos diferentes da vida de um schema. Enforcement (aplicação) é o porteiro que barra dados fora do formato esperado. Evolution (evolução) é a capacidade de mudar o schema — como adicionar uma coluna nova — sem quebrar nada que já existia.

🚪
Schema Enforcement — analogia

É como o porteiro de uma festa conferindo a lista de convidados: se seu nome não está lá (o dado não bate com o schema esperado), você não entra. Isso impede que um arquivo bagunçado corrompa a tabela inteira.

📋
Schema Evolution — analogia

É como a lista de convidados ganhar um campo novo — por exemplo "alergia alimentar" — sem expulsar ninguém que já estava dentro. Quem já entrou simplesmente fica com esse campo em branco.

Exemplo: a tabela pedidos ganha uma coluna nova (cupom_desconto) sem quebrar nenhuma linha antiga — as linhas antigas simplesmente recebem NULL nessa coluna:

id_pedidoclientevalorcupom_desconto
1001Ana199,90NULL (linha antiga)
1002Bruno89,00NULL (linha antiga)
1003Carla150,00DESC10 (nova coluna em uso)

✅ Sem essa evolução controlada, qualquer mudança de schema exigiria reescrever a tabela inteira do zero — no Lakehouse, é só uma operação de metadata.

Superpotência 3 de 3
⏳ Viagem no Tempo (Time Travel)

Toda escrita numa tabela Lakehouse cria uma nova versão (snapshot), sem apagar a anterior de imediato. Isso permite consultar a tabela exatamente como ela estava em qualquer ponto do passado — útil para auditoria, para desfazer um erro, ou para reproduzir exatamente o dado que treinou um modelo de Machine Learning há 3 meses.

📝
Analogia

É como o histórico de versões do Google Docs: você pode voltar e ver exatamente como o documento estava ontem às 15h, sem perder nada do que foi escrito hoje. Cada "salvar" vira um ponto no tempo ao qual você pode voltar.

Por Trás da Mágica
🗂️ Por Dentro do Metadata: Como a Mágica Acontece

O segredo de tudo isso é simples: os arquivos de dados (Parquet) nunca são editados diretamente. Toda escrita cria arquivos novos e registra num log de transações quais arquivos, somados, formam a versão vigente da tabela. Ler a tabela não é "escanear uma pasta" — é ler o log e saber exatamente quais arquivos abrir.

💡 Quando uma linha é "atualizada" no Lakehouse, na verdade um arquivo Parquet inteiro novo é escrito com a versão corrigida, e o log só marca o arquivo antigo como removido logicamente — ele continua existindo no armazenamento até uma limpeza (VACUUM) apagá-lo de vez, o que é o que possibilita voltar no tempo.

As 3 Implementações
⚔️ Delta Lake vs Apache Iceberg vs Apache Hudi

"Formato de tabela aberto" não é um conceito único — existem 3 implementações principais, todas open-source, todas resolvendo o mesmo problema (ACID + schema + time travel sobre arquivos), com diferenças de origem, ecossistema e pontos fortes.

🔺 Delta Lake
Criado pela Databricks, hoje projeto Linux Foundation. Integração mais profunda com Spark e com o ecossistema Databricks. É o formato com adoção mais ampla no mercado hoje.
🧊 Apache Iceberg
Criado na Netflix. Focado em ser neutro de motor — projetado desde o início para funcionar igualmente bem com Spark, Trino, Flink, Snowflake, entre outros, sem favorecer nenhum.
🌊 Apache Hudi
Criado no Uber. Focado em cargas de trabalho com muita atualização e upsert (CDC — Change Data Capture) em tempo quase real, como sincronizar um banco transacional.

Como Organizar as Tabelas
🥉🥈🥇 Arquitetura Medalhão (Medallion)

Dentro de um Lakehouse, é comum organizar as tabelas em 3 níveis de qualidade crescente, como uma cozinha de restaurante: os ingredientes chegam crus, depois são lavados e cortados, e só então viram um prato pronto para servir.

🥉
Bronze — Cru
Dado bruto, exatamente como chegou da origem. Sem limpeza, sem tipo definido, com duplicatas. Serve como "prova" auditável do que a origem enviou.
➜
🥈
Silver — Limpo
Dado validado, tipado corretamente, deduplicado, com regras de qualidade aplicadas e junções entre fontes já resolvidas. Pronto para análise técnica.
➜
🥇
Gold — Pronto
Dado agregado e modelado para uma pergunta de negócio específica: receita diária, clientes ativos, funil de vendas. É o que alimenta o dashboard.
🍳
Pensando como criança

Bronze é a sacola de compras chegando da feira — cenoura com terra, alface com bicho. Silver é a bancada depois de tudo lavado, descascado e cortado do jeito certo. Gold é o prato pronto, temperado, servido na mesa — exatamente o que o convidado (o time de negócio) pediu.

Um Problema Real
📦 O Problema dos Arquivos Pequenos & Compactação

Quando dados chegam em fluxo contínuo (streaming) ou em micro-lotes muito frequentes, cada escrita cria um arquivo Parquet novo e pequeno. Ler uma tabela com milhares de arquivos minúsculos é lento — o motor gasta mais tempo abrindo arquivos do que lendo dados. A solução é compactação (OPTIMIZE): juntar vários arquivos pequenos em poucos arquivos grandes, por trás dos panos, sem afetar quem está consultando.

🧱
Analogia

É como guardar Lego: 500 saquinhos com 2 peças cada demoram uma eternidade para abrir um por um. Compactar é despejar tudo numa caixa organizada só — mesma quantidade de peças, muito mais rápido de pegar o que precisa.

Checklist
✅ Boas Práticas
🧹 Rode compactação com regularidade
Agende OPTIMIZE (ou equivalente) periodicamente em tabelas com muita escrita frequente, para evitar o problema dos arquivos pequenos.
🗑️ Defina uma política de retenção para VACUUM
Arquivos antigos "removidos logicamente" continuam ocupando espaço até serem limpos de verdade — mas limpar cedo demais quebra o time travel.
🥉🥈🥇 Siga o padrão medalhão
Nunca deixe o time de negócio consultar direto a camada Bronze — ela existe para auditoria, não para dashboard.
🗄️ Use um catálogo central
Unity Catalog, AWS Glue, Nessie ou Polaris centralizam permissões e descoberta de tabelas — sem isso, o Lakehouse pode virar pântano de novo.
📐 Particione com moderação
Particionar demais (ex: por minuto) cria excesso de pastas pequenas — prefira particionar por dia/mês e usar Z-order/clustering para o resto.
🔐 Trate o Lakehouse como um banco de verdade
Controle de acesso em nível de tabela e coluna, auditoria de quem escreveu o quê — as garantias de ACID não substituem governança.
