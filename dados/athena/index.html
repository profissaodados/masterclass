Você nunca liga um servidor. Você só faz a pergunta.

O Amazon Athena é um serviço da AWS que deixa você rodar SQL padrão direto sobre arquivos guardados no Amazon S3 — sem copiar nada para dentro de um banco de dados, sem instalar nada, sem ligar nenhuma máquina. Por trás dos panos, ele usa um motor de consulta distribuído da família Trino/Presto (o mesmo tipo de motor que vimos na aula sobre Trino), só que 100% gerenciado pela AWS: você nunca vê um "Coordinator" ou um "Worker" — só manda a consulta e recebe a resposta. E você só paga pelos bytes que a consulta realmente leu.

Fundamentos
🤔 O que é o AWS Athena?

Athena é um serviço serverless de consulta interativa: você aponta para arquivos que já existem no S3 (o "data lake" da sua empresa), descreve o formato deles uma vez só, e a partir daí pode escrever SELECT, JOIN, GROUP BY como faria em qualquer banco relacional. Não existe "instância do Athena" para provisionar, escalar ou desligar — a AWS aloca um pedaço de um motor de consulta distribuído só durante os segundos em que sua consulta está rodando, e cobra apenas pela quantidade de dados escaneada nesse período (padrão de US$ 5,00 por terabyte lido).

🧒 Explicando para uma criança

Imagine uma biblioteca gigante (o S3) cheia de caixas de documentos empilhadas, sem nenhum bibliotecário morando lá dentro. O Athena é como um bibliotecário mágico que você chama por telefone só quando precisa: você liga, faz sua pergunta ("quantos livros de dinossauros temos?"), ele aparece do nada, corre até as caixas certas, conta só o que interessa, te entrega a resposta — e some de novo. Você nunca "contratou" um bibliotecário fixo (um servidor ligado 24 horas); você só paga pela ligação que fez, e só pelo tempo/trabalho daquela ligação específica.

🚫 Sem servidor para gerenciar
Não existe máquina para ligar, atualizar, redimensionar ou desligar. Você não escolhe "tamanho de cluster" — a AWS decide isso por trás dos panos a cada consulta.
💰 Paga por consulta
A cobrança é por bytes escaneados, não por hora de máquina ligada. Uma consulta que não roda, não custa nada — bem diferente de um data warehouse sempre ligado.
🔍 SQL direto no data lake
Os dados continuam no S3, no formato em que já estavam. Você não precisa de um pipeline de ETL só para "conseguir consultar" alguma coisa nova.

💡 O nome "Athena" é uma referência a Atena, a deusa grega da sabedoria e da estratégia — a ideia é uma ferramenta "sábia" o suficiente para você só perguntar, sem precisar planejar infraestrutura antes. Na prática, o serviço foi lançado pela AWS em novembro de 2016, construído sobre o motor open source Presto (o mesmo que deu origem ao Trino).

De Onde Veio
📜 A História do Athena

O Athena nasceu para resolver um problema muito comum: empresas já tinham montanhas de arquivos guardadas no S3 (logs, exports, eventos), mas para consultar qualquer coisa era preciso montar um pipeline, subir um cluster Hadoop/EMR ou copiar tudo para um banco. A AWS decidiu embrulhar um motor de consulta distribuído já existente — o Presto — numa experiência "sem clicar em nada de infraestrutura".

🧒 Explicando para uma criança

É como a diferença entre ter que montar sua própria bicicleta do zero toda vez que quiser andar (subir um cluster Hadoop) e simplesmente pegar uma bicicleta compartilhada já pronta na rua, andar até onde precisa, e devolvê-la sem se preocupar em consertar nada (Athena). Com o tempo, essas bicicletas compartilhadas foram ficando cada vez mais espertas: hoje elas "sabem" ler mapas de vários bairros diferentes ao mesmo tempo (Federated Query) e até ajudam a organizar seus próprios pertences (Athena for Apache Spark).

💡 Hoje o motor por trás do Athena é chamado de Athena engine version 3 — uma evolução própria da AWS, fortemente baseada em Trino, otimizada especificamente para rodar dentro do ambiente serverless da AWS (integração nativa com Glue, IAM, S3 e CloudWatch).

🧒 Explicando para uma criança

É a diferença entre ter carro próprio e usar aplicativo de carona. Com carro próprio, você é dono de tudo: compra, abastece, estaciona, faz manutenção — mesmo nos dias em que não usa. Com aplicativo de carona (Athena), você só diz "para onde quer ir" (o SQL); um carro aparece na hora, te leva, e vai embora. Você paga só pela viagem que fez, nunca pelo carro parado na garagem.

💡 Isso também significa que o Athena não tem "estado" entre consultas: cada consulta é isolada. Se você rodar a mesma consulta duas vezes seguidas, a segunda pode escanear exatamente a mesma quantidade de dados (e custar o mesmo) que a primeira, a não ser que você configure algum cache próprio (por exemplo, materializando o resultado em uma tabela).

O Caminho de uma Pergunta
⚙️ O Que Acontece Quando Você Aperta "Run Query"

Da sua perspectiva parece mágica, mas por dentro acontecem passos bem concretos, do texto SQL até o resultado aparecer na tela. Clique em cada etapa para entender o que acontece.

🔢 Passo a passo de uma consulta no Athena
1. Você escreve SQL no console, CLI, JDBC/ODBC ou boto3
2. Athena consulta o Glue Data Catalog: onde estão os arquivos, qual o schema, quais partições existem
3. O otimizador decide quais partições e colunas realmente precisam ser lidas (pruning)
4. Uma frota efêmera de workers é alocada e lê só os bytes necessários direto do S3, em paralelo
5. O resultado final é gravado como arquivo(s) num bucket de resultados no S3
6. Você recebe o resultado (console/API) e a frota de workers é desalocada

🧒 Explicando para uma criança

É parecido com pedir uma pizza por aplicativo: você faz o pedido (SQL); o app olha no mapa qual pizzaria fica mais perto e tem o que você quer (Glue Catalog); ele já sabe que não precisa mandar o entregador passar em bairros sem essa pizzaria (pruning de partição); o entregador pega só a pizza — não a pizzaria inteira — e traz até você (leitura otimizada no S3); a pizza chega na sua mesa (resultado); e o entregador vai embora para atender outro pedido, sem ficar esperando parado na sua porta (frota desalocada).

⚠️ Consultas que falham ou comandos de definição de estrutura (como CREATE TABLE apontando metadados, sem ler dados) normalmente não são cobrados pelos bytes escaneados — mas uma consulta mal escrita que efetivamente varre a tabela inteira, sim.

O Mapa dos Seus Dados
🗂️ AWS Glue Data Catalog: o Metastore do Athena

Antes de escanear qualquer byte, o Athena precisa saber três coisas sobre uma tabela: onde estão os arquivos no S3, qual o formato/schema deles (colunas e tipos), e quais partições existem. Quem guarda esse "mapa" é o AWS Glue Data Catalog — um metastore compatível com o Hive Metastore, compartilhado também por outros serviços AWS (Glue ETL, EMR, Redshift Spectrum). O Athena nunca "adivinha" nada sozinho: ele sempre consulta o catálogo primeiro.

🗂️ Glue Data Catalog
📁 Database: vendas
📄 Table: pedidos (aponta para s3://data-lake/vendas/pedidos/)
Schema: id BIGINT, cliente_id BIGINT, total DOUBLE, data_pedido DATE
Partições: ano=2026/mes=07/dia=30/ ...
📄 Table: clientes (aponta para s3://data-lake/vendas/clientes/)
🗄️ Databases & Tables
Uma table no Glue é só um "apontador" com metadados — não guarda dado nenhum, só descreve onde e como os arquivos reais estão organizados no S3.
🕷️ Crawlers
Um Glue Crawler varre um caminho no S3, infere schema e partições automaticamente, e mantém o catálogo atualizado sem você escrever o DDL na mão.
🧩 Partições
O catálogo guarda quais pastas de partição existem (ex: dia=2026-07-30), permitindo ao Athena pular pastas inteiras sem precisar "listar" o S3 toda vez.
🔗 Compartilhado
O mesmo catálogo é lido por Redshift Spectrum, EMR, Glue ETL Jobs e até o QuickSight — cadastre uma vez, use em vários serviços.
sql — registrando uma tabela externacopiarCREATE EXTERNAL TABLE vendas.pedidos ( id BIGINT, cliente_id BIGINT, total DOUBLE, data_pedido DATE ) PARTITIONED BY (ano STRING, mes STRING, dia STRING) STORED AS PARQUET LOCATION 's3://data-lake/vendas/pedidos/'; -- ensina o catálogo a "descobrir" as pastas de partição já existentes MSCK REPAIR TABLE vendas.pedidos;
🧒 Explicando para uma criança

O Glue Data Catalog é como o fichário de uma biblioteca: ele não tem os livros dentro dele, só fichas dizendo "livros de dinossauro ficam na sala 3, prateleira 2". Sem esse fichário, o bibliotecário (Athena) teria que correr sala por sala, prateleira por prateleira, abrindo tudo até achar o que você pediu. Com o fichário, ele vai direto no lugar certo.

O Que Realmente Custa Dinheiro
📦 Formatos Colunares: Por Que Parquet Custa Menos que CSV

Como o Athena cobra por bytes escaneados, o formato do arquivo tem impacto direto no seu bolso. CSV e JSON são formatos por linha: para ler uma coluna, o motor é obrigado a ler o arquivo inteiro, linha por linha. Parquet e ORC são colunares: cada coluna fica guardada separadamente e comprimida — se sua consulta só usa 2 colunas de uma tabela com 20, o Athena só precisa abrir os blocos daquelas 2 colunas. Clique para simular a mesma consulta nos dois formatos.

Simule: SELECT total FROM pedidos — quais dados o motor precisa abrir?
CaracterísticaCSV / JSONParquet / ORC
OrganizaçãoPor linha (row-based)Por coluna (columnar)
Leitura parcial de colunasImpossível — sempre lê a linha inteiraLê só as colunas usadas na consulta
Compressão nativaNenhuma, a não ser que você compacte manualmenteSim, por coluna (Snappy, GZIP, ZSTD)
Impacto no custo do AthenaEscaneia praticamente o arquivo inteiro sempre✅ Pode reduzir bytes escaneados em 80–95%
🧒 Explicando para uma criança

Pense num jornal impresso (CSV/JSON): se você só quer ler os classificados de emprego, ainda assim o jornaleiro entrega o jornal inteiro — capa, esportes, política, tudo junto, página colada em página. Já o Parquet é como se o jornal viesse separado por seções soltas, cada uma numa pastinha própria: você pega só a pastinha de "classificados" e nem precisa tocar nas outras. Menos papel carregado, resposta mais rápida, e no caso do Athena, menos dinheiro gasto.

Pular Pastas Inteiras
🧩 Particionamento: Nem Abrir a Gaveta Errada

Além de colunas, o Athena também pode evitar ler arquivos inteiros — se a tabela for particionada (ex: uma pasta por dia) e sua consulta filtrar por essa coluna de partição, o motor nem chega a listar os arquivos das pastas que não interessam. Esse comportamento se chama partition pruning (poda de partição). Simule abaixo o efeito de filtrar por poucos dias dentro de um ano inteiro de dados.

Simule: WHERE dia BETWEEN ... sobre uma tabela particionada por dia
Total de partições (dias) na tabela30
Dias filtrados pela consulta (WHERE)3
sql — filtro que aciona o pruningcopiarSELECT SUM(total) FROM vendas.pedidos WHERE ano = '2026' AND mes = '07' AND dia IN ('28','29','30'); -- só as pastas ano=2026/mes=07/dia=28|29|30 são lidas — o resto do ano é ignorado
🧒 Explicando para uma criança

Imagine um arquivo de gavetas, uma gaveta para cada mês do ano. Se você precisa só dos papéis de julho, você abre uma única gaveta — nem chega perto das outras onze. Sem particionamento, seria como ter todos os papéis do ano jogados numa caixa só, sem gavetas: para achar os de julho, você é obrigado a folhear a caixa inteira, mês por mês, até separar o que precisa.

⚠️ Particionar demais também tem custo: milhares de partições minúsculas (ex: particionar por minuto numa tabela pequena) deixam o catálogo mais pesado de consultar e criam muitos arquivos pequenos no S3, que também prejudicam a performance. Para tabelas com centenas de milhares de partições, a AWS recomenda Partition Projection — as regras de partição ficam declaradas na definição da tabela, sem precisar manter cada partição registrada individualmente no catálogo.

Menos Bytes, Menos Custo
🗜️ Compressão: o Mesmo Dado, Ocupando Menos Espaço

Formato colunar e compressão andam juntos, mas são coisas diferentes: o formato decide como organizar os dados; a compressão decide quantos bytes físicos eles ocupam no S3 — e, consequentemente, quanto o Athena cobra para lê-los. Compare o tamanho aproximado do mesmo conjunto de dados (1 GB de dados "crus") em diferentes combinações:

Proporções ilustrativas — a taxa de compressão real varia conforme a natureza dos dados (texto livre comprime menos que colunas repetitivas/categóricas).
🧾 CSV sem compressão
Texto puro, sem nenhuma otimização — o "pior caso" em tamanho e em custo de leitura no Athena.
📦 CSV + GZIP
Reduz bastante o tamanho em disco, mas o Athena ainda precisa descomprimir e ler a linha inteira — não resolve o problema de colunas desnecessárias.
🚀 Parquet + Snappy/ZSTD
Combina o melhor dos dois mundos: leitura só das colunas necessárias e compressão eficiente por coluna — normalmente o cenário mais barato para consultar.
🧒 Explicando para uma criança

É a diferença entre fazer uma mala jogando roupas soltas (CSV sem compressão) e usar aqueles saquinhos a vácuo que espremem o ar para fora (compressão). A mala fica bem mais leve para carregar — só que, se você quer só a camiseta azul, ainda vai ter que abrir o saquinho inteiro para achá-la. O Parquet comprimido é como ter um saquinho a vácuo separado para cada tipo de roupa: você pega só o saquinho das camisetas, sem mexer nas calças e meias.

A Calculadora
💰 Precificação: US$ 5 por Terabyte Escaneado

O modelo de cobrança do Athena é direto: US$ 5,00 por terabyte de dados escaneado por uma consulta, com cobrança mínima de 10 MB por consulta (consultas canceladas ou que falham antes de escanear dados não são cobradas). Formato, compressão e particionamento se combinam para determinar quantos bytes realmente precisam ser lidos — e é exatamente aí que mora a diferença entre uma consulta de centavos e uma de dezenas de dólares. 🧒 Explicando para uma criança

É como pagar por quilo de fruta que você realmente pegou na feira, não pela feira inteira. Se a feira tem 500 kg de fruta espalhados, mas você só pega as maçãs da barraca "julho" (partição) e ainda por cima leva num saquinho bem compacto (Parquet comprimido), você paga por muito menos quilos do que se andasse pela feira inteira enchendo um carrinho gigante (CSV sem filtro nenhum).

💡 Armazenamento no S3 é cobrado separadamente pelo próprio S3 (por GB/mês), independente de você consultar ou não. O Athena só cobra pelo ato de ler os dados numa consulta — por isso otimizar formato/partição impacta diretamente a fatura do Athena, mas não muda o custo de armazenamento em si (que, aliás, também cai bastante com Parquet comprimido).

Transformando sem Sair do SQL
🔄 CTAS: Convertendo Formato Direto no Athena

Você não precisa de uma ferramenta externa de ETL só para transformar uma tabela CSV legada em Parquet particionado — o próprio Athena resolve isso com CREATE TABLE AS SELECT (CTAS): você escreve um SELECT normal sobre a tabela de origem, e o Athena grava o resultado como uma tabela nova, já no formato e particionamento que você escolher.

sql — CTAS convertendo CSV em Parquet particionadocopiarCREATE TABLE vendas.pedidos_otimizado WITH ( format = 'PARQUET', parquet_compression = 'SNAPPY', partitioned_by = ARRAY['ano','mes'], external_location = 's3://data-lake/vendas/pedidos_otimizado/' ) AS SELECT id, cliente_id, total, data_pedido, year(data_pedido) AS ano, month(data_pedido) AS mes FROM vendas.pedidos_csv_legado; -- a tabela nova já nasce colunar, comprimida e particionada
🆕 CTAS
Cria uma tabela nova (com novos arquivos no S3) a partir do resultado de um SELECT — ideal para conversões de formato ou "instantâneos" de uma consulta pesada.
➕ INSERT INTO
Adiciona linhas a uma tabela já existente (criada via CTAS ou DDL manual), útil para cargas incrementais periódicas.
📤 UNLOAD
Exporta o resultado de uma consulta direto para arquivos no S3 (Parquet, ORC, JSON...) sem precisar criar uma tabela — útil para entregar um extrato pontual.
🧒 Explicando para uma criança

É como fotocopiar um caderno de anotações bagunçado (CSV cru) para dentro de um fichário organizado, com divisórias por assunto (Parquet particionado) — só que em vez de você copiar página por página à mão, você dá o comando "copie assim" e a fotocopiadora (Athena) faz tudo de uma vez.

Controlando Quem Gasta o Quê
🚦 Workgroups: Isolamento e Controle de Custo

Como qualquer pessoa com permissão pode escrever um SELECT * gigante sem querer, o Athena oferece Workgroups: grupos que isolam consultas de diferentes times, aplicam limites de bytes escaneados por consulta (ou por período), forçam criptografia dos resultados, e separam métricas/custo no CloudWatch — tudo sem mexer no código da consulta em si.

🧒 Explicando para uma criança

É como quando os pais dão um cartão pré-pago com limite diferente para cada filho: um irmão mais velho pode ter um limite maior para as compras da semana, e o mais novo, um limite menorzinho — mesmo os dois usando cartões ligados à mesma conta da família. Se alguém tentar gastar mais do que o combinado, a compra simplesmente não passa, antes mesmo de sair dinheiro da conta.

⚠️ O limite de bytes de um workgroup é aplicado antes de a consulta rodar de verdade (usando as estatísticas do planejamento) — então uma consulta bloqueada por estourar o limite não chega a gerar custo algum.

Além do S3
🔌 Athena Federated Query: SQL Também Fora do Data Lake

O Athena nasceu para consultar o S3, mas o Federated Query estende isso para fontes que não são arquivos: bancos relacionais (RDS/PostgreSQL, MySQL), NoSQL (DynamoDB), até outro data warehouse (Redshift) — numa única consulta, com JOIN entre fontes diferentes. Cada fonte é acessada por um Data Source Connector: uma função AWS Lambda que sabe "traduzir" entre o Athena e aquela fonte específica. Clique em cada fonte.

🏛️ ATHENA
👆 Clique em uma fonte de dados
Veja como o Athena alcança essa fonte através de um conector Lambda.
sql — consulta federadacopiarSELECT c.nome, SUM(p.total) AS total_gasto FROM lambda_postgres.vendas.clientes c JOIN data_lake.vendas.pedidos p ON p.cliente_id = c.id WHERE p.data_pedido >= DATE '2026-01-01' GROUP BY c.nome; -- "clientes" vive num PostgreSQL; "pedidos" vive como Parquet no S3 — uma única consulta
🧒 Explicando para uma criança

É como usar um fone de tradução simultânea numa reunião com gente de vários países. Você (Athena) continua falando só a sua língua (SQL); para cada país diferente (PostgreSQL, DynamoDB, Redshift), existe um tradutor especializado (uma função Lambda) que entende aquela língua específica e devolve tudo traduzido para você, na hora — sem que você precise aprender a língua de cada país.

⚠️ Cada linha lida de uma fonte federada passa por uma invocação de Lambda — isso tem seu próprio custo (Lambda) e costuma ser mais lento que ler Parquet direto do S3. Federated Query é ótimo para juntar um pedaço pequeno de um sistema operacional com o data lake, não para substituir o data lake como fonte principal de grandes volumes.

Lado a Lado
🥊 Athena vs Redshift vs EMR

Os três rodam SQL/processamento sobre grandes volumes na AWS, mas resolvem prioridades diferentes — a escolha certa depende do padrão de uso, não de qual é "mais rápido" isoladamente.

🏛️ Escolha Athena quando...
Você quer respostas rápidas sobre dados que já estão no S3, com uso esporádico ou imprevisível, sem manter infraestrutura ligada.
🔴 Escolha Redshift quando...
Dezenas de dashboards concorrentes precisam de latência baixa e previsível o dia inteiro — o custo de um cluster ligado se paga pela constância do uso.
🐘 Escolha EMR quando...
Você precisa de controle fino sobre o cluster (versões específicas de Spark, jobs de Machine Learning, processamento customizado) além de SQL puro.

💡 Eles não são mutuamente exclusivos: é comum usar Athena para exploração e ETL leve direto no data lake, Redshift Spectrum para juntar esse mesmo S3 com tabelas nativas do Redshift, e EMR/Glue para as transformações pesadas que alimentam o data lake que o Athena consulta depois.

Quem Pode Ver o Quê
🔐 Segurança & Governança

Como o Athena só "empresta" acesso aos seus dados no S3, a segurança acontece em camadas — combinando o controle de acesso da AWS (IAM) com regras mais finas de quem pode ver quais colunas ou linhas (Lake Formation).

🔑 IAM
Controla quem pode rodar consultas, em quais workgroups, e se tem permissão de leitura/escrita nos buckets S3 envolvidos (dados de origem + bucket de resultados). É o nível "grosso" de acesso.
🏛️ AWS Lake Formation
Adiciona controle fino por cima do Glue Catalog: permissões por tabela, por coluna (ex: esconder CPF) e até por linha (ex: cada vendedor só vê seus próprios pedidos), aplicadas automaticamente a qualquer consulta do Athena.
🔒 Criptografia em repouso
Dados no S3 e resultados de consulta podem ser criptografados com SSE-S3 ou SSE-KMS — configurável, e obrigatório em workgroups mais restritos.
🔐 Criptografia em trânsito
Conexões JDBC/ODBC e chamadas de API usam TLS por padrão entre o cliente e o serviço Athena.
📋 Auditoria (CloudTrail)
Toda chamada de API do Athena (quem rodou o quê, quando) fica registrada no CloudTrail, essencial para compliance.
🧒 Explicando para uma criança

É como uma escola com crachás (IAM) que abrem certas salas e não outras — mas além disso, alguns boletins têm partes borradas mesmo para quem tem o crachá certo, tipo o telefone dos pais (Lake Formation escondendo uma coluna), ou um aluno só consegue ver a própria nota, nunca a dos colegas (Lake Formation filtrando linhas).

⚠️ O bucket de resultados das consultas (onde o Athena grava cada saída) também guarda dado sensível — se ele não tiver as mesmas políticas de acesso e criptografia da fonte original, vira um "vazamento por atalho" mesmo com o Lake Formation configurado corretamente na tabela de origem.

Onde o Athena Brilha
🎯 Casos de Uso
📜 Análise de logs
Consultar diretamente logs de ALB, CloudFront ou CloudTrail que já caem no S3 — sem pipeline nenhum para "começar a analisar".
🔎 Exploração ad hoc do data lake
Analistas investigando uma pergunta pontual sobre dados que já existem, sem esperar um time de engenharia subir infraestrutura.
📊 Fonte para BI
Amazon QuickSight (ou Tableau/Power BI via JDBC) consultando o Athena como fonte de dashboards direto sobre o data lake.
🔄 ETL leve entre camadas
CTAS/INSERT INTO transformando uma camada "bronze" crua em camadas "prata/ouro" já otimizadas, sem cluster dedicado.
💵 Auditoria de custo (CUR)
Consultar o Cost and Usage Report da AWS direto no S3 para entender de onde vem cada centavo da fatura.
🧪 Exploração para Machine Learning
Cientistas de dados amostrando e explorando grandes datasets antes de decidir o que efetivamente vale a pena treinar.
Mão na Massa
📦 Primeiros Passos

Não existe "instalação" — só um bucket S3, uma tabela registrada no Glue, e você já pode consultar pelo console, CLI ou código.

Console — editor de SQL do Athena
sqlcopiar-- 1. defina um "query result location" nas configurações do workgroup -- 2. escreva e rode: SELECT categoria, COUNT(*) AS qtd FROM vendas.pedidos_otimizado WHERE ano = '2026' GROUP BY categoria ORDER BY qtd DESC;
AWS CLI
bashcopiaraws athena start-query-execution \ --query-string "SELECT COUNT(*) FROM vendas.pedidos" \ --work-group "analistas-adhoc" \ --query-execution-context Database=vendas # retorna um QueryExecutionId — use get-query-results depois
Python — boto3
pythoncopiarimport boto3 athena = boto3.client('athena') resp = athena.start_query_execution( QueryString='SELECT * FROM vendas.pedidos LIMIT 10', QueryExecutionContext={'Database': 'vendas'}, WorkGroup='analistas-adhoc', ) query_id = resp['QueryExecutionId']
Criando um crawler (infere o schema sozinho)
bashcopiaraws glue create-crawler \ --name crawler-vendas \ --role AWSGlueServiceRole \ --database-name vendas \ --targets '{"S3Targets":[{"Path":"s3://data-lake/vendas/"}]}' aws glue start-crawler --name crawler-vendas
Checklist
✅ Boas Práticas
📦 Use Parquet/ORC comprimido
A mudança de maior impacto em custo e performance. Converta camadas legadas em CSV/JSON via CTAS assim que possível.
🧩 Particione pelas colunas de filtro mais comuns
Data é o clássico. Evite granularidade excessiva (ex: por minuto) em tabelas pequenas — isso cria muitos arquivos pequenos.
🎯 Evite SELECT *
Liste só as colunas necessárias — em formato colunar, cada coluna a menos é literalmente menos byte escaneado (e menos custo).
🚦 Configure Workgroups com limite de bytes
Principalmente para times de analistas ad hoc — evita que uma consulta esquecida sem WHERE vire uma surpresa na fatura.
🗺️ Use Partition Projection em tabelas com muitas partições
Evita o overhead de manter (e consultar) centenas de milhares de partições registradas manualmente no catálogo.
📈 Monitore pelo CloudWatch
Acompanhe bytes escaneados e duração por workgroup/usuário para identificar consultas caras antes que virem hábito.

⚠️ O problema dos arquivos pequenos também afeta o Athena: milhares de arquivos Parquet minúsculos custam mais para abrir (overhead por arquivo) do que poucos arquivos maiores e bem compactados. Rode CTAS/compactação periodicamente em tabelas alimentadas por muitas cargas incrementais pequenas.
