Pare de recarregar a tabela inteira — capture só o que mudou

Change Data Capture (CDC) é a técnica de observar um banco de dados de origem e detectar, linha a linha, cada INSERT, UPDATE e DELETE — propagando apenas essas mudanças para outros sistemas, em vez de reler a tabela inteira a cada sincronização. Numa tabela de 200 milhões de linhas onde só três mudaram, um full reload periódico desperdiça I/O na origem, banda de rede e processamento no destino; o CDC inverte a pergunta de "como está a tabela agora?" para "o que mudou desde a última verificação?". Nesta aula vamos abrir as três técnicas clássicas — timestamp, trigger e log de transação — entender onde cada uma quebra, e como ferramentas como Debezium e Kafka viabilizam isso em produção.

Fundamentos
🔄 O que é Change Data Capture?

A motivação central do CDC é manter dois sistemas sincronizados — tipicamente um banco OLTP de produção e um data warehouse, lakehouse, cache ou índice de busca — com latência mínima e eficiência operacional. Em vez de perguntar periodicamente "quais são todos os dados agora?" (full reload), o CDC observa continuamente a origem e emite um evento explícito para cada mudança, contendo a operação (op), a chave primária afetada e os dados relevantes. O consumidor então aplica só essas mudanças no destino, via upsert.

📥 INSERT
Uma linha nova aparece na origem. O evento carrega a linha completa (NEW) — o destino simplesmente a adiciona.
✏️ UPDATE
Uma linha existente muda. O evento carrega a versão nova (e, em alguns formatos, também a antiga) — o destino substitui a versão anterior pela mesma chave.
🗑️ DELETE
Uma linha deixa de existir na origem. É o caso mais traiçoeiro de capturar — como veremos, nem toda técnica consegue enxergar algo que já não está mais lá.
A pergunta que o CDC inverte

Full reload pergunta "como está a tabela agora?" — o custo é proporcional ao volume total de dados, sempre. CDC pergunta "o que mudou desde a última verificação?" — o custo passa a ser proporcional ao volume de alterações, que normalmente é uma fração minúscula do total.

Por Que Isso Importa
📉 O Problema: Full Reload em Escala

A alternativa "ingênua" — recarregar a tabela inteira periodicamente — é simples de implementar, mas se torna impraticável assim que o volume cresce. Numa tabela de 200 milhões de linhas onde apenas três mudaram desde ontem, um full reload lê os 200 milhões de qualquer forma: I/O desperdiçado na origem, banda de rede consumida à toa e processamento redundante no destino. Técnica 1 — A Mais Simples
⏱️ Timestamp-Based (Polling)

Usa uma coluna updated_at e uma marca d'água (watermark): o timestamp da última leitura. A cada execução, roda SELECT * FROM orders WHERE updated_at > ? e avança a marca d'água para o maior updated_at retornado. Simples — só um SELECT, sem tocar no schema de produção — mas com um ponto cego estrutural.

sqlcopiar-- roda a cada N minutos, com watermark salva do ciclo anterior SELECT * FROM orders WHERE updated_at > :watermark; -- nova marca d'água = maior updated_at retornado watermark = MAX(updated_at) FROM resultado

⚠️ Linha fantasma detectada

O pedido #3 foi deletado da origem, mas uma linha deletada não deixa rastro — o SELECT ... WHERE updated_at > watermark simplesmente não enxerga algo que não existe mais. O destino continua com uma cópia "fantasma" do pedido #3 para sempre, a menos que a origem use soft delete (uma coluna deleted_at em vez de remover a linha de fato).

✅ Vantagens
Simples de implementar — apenas um SELECT parametrizado. Nenhuma modificação no schema de produção. Baixo custo de operação.
⚠️ Limitações críticas
Não captura DELETE — ponto cego estrutural. Vulnerável a múltiplas linhas com o mesmo timestamp. Exige soft deletes como workaround.
Técnica 2 — Captura Completa em Tempo Real
⚡ Trigger-Based

Gatilhos SQL interceptam cada mudança na hora em que ela acontece e gravam um evento numa tabela changelog, append-only. O gatilho de INSERT/UPDATE lê NEW (a linha depois da mudança); o de DELETE lê OLD (a linha antes de ser destruída) — por isso, ao contrário do polling, o DELETE deixa rastro.

sqlcopiarCREATE TRIGGER orders_after_delete AFTER DELETE ON orders FOR EACH ROW BEGIN INSERT INTO orders_changelog (change_id, op, order_id, dados) VALUES (NEXT_ID(), 'DELETE', OLD.id, TO_JSON(OLD)); END;

✅ Vantagens
Captura os três tipos de operação, incluindo deletes. Ordem cronológica garantida dentro de transações. change_id sequencial evita o problema de timestamps duplicados.
⚠️ Limitações
Trabalho extra em toda escrita — cada operação vira duas escritas. Gatilhos vivem em produção e exigem manutenção. Requer backfill manual para linhas já existentes antes do gatilho ser criado.

💡 Backfill: dados pré-existentes não têm registro de INSERT no changelog, porque o gatilho só passou a existir depois deles. A solução é injetar manualmente eventos INSERT sintéticos para cada linha já presente na tabela, antes de começar a consumir o changelog em produção.

Técnica 3 — A Escolha em Produção
📜 Log-Based (WAL / Binlog)

Todo banco relacional já mantém um log de transação nativo para recuperação de falhas e replicação — o CDC log-based simplesmente lê esse log em vez de tocar nas tabelas. Como o log já é escrito de qualquer forma, o custo adicional é praticamente zero, e como a leitura acontece no log (não na tabela), o impacto sobre a carga de produção é mínimo.

Mão na Massa
🐍 CDC na Prática com dlt (dlthub)

O dlt não substitui as técnicas de captura vistas nesta aula — ele implementa a metade downstream do pipeline: a marca d'água e a lógica de upsert, como código Python declarativo em vez de infraestrutura própria. Os exemplos abaixo cobrem desde o polling incremental até o consumo de eventos log-based publicados por um conector como o Debezium.

Instalação e pipeline básico
bash + pythoncopiar# instalação pip install "dlt[duckdb]" # pipeline básico import dlt pipeline = dlt.pipeline( pipeline_name="orders_cdc", destination="duckdb", dataset_name="vendas", )
Timestamp-based — incremental por cursor
pythoncopiarimport dlt # equivalente ao polling por updated_at, mas com o watermark # gerenciado automaticamente pelo dlt entre execuções @dlt.resource(primary_key="id", write_disposition="merge") def orders(updated_at=dlt.sources.incremental("updated_at")): yield from fetch_orders_since(updated_at.last_value) pipeline.run(orders())
write_disposition="merge" — o upsert idempotente da Arquitetura
pythoncopiar# merge = mesma lógica da seção Arquitetura Genérica: # casa pela primary_key, remove a versão antiga, insere a nova @dlt.resource(primary_key="order_id", write_disposition="merge") def orders_changed(): yield from get_changed_rows() pipeline.run(orders_changed())
Log-based na prática — consumindo eventos do Debezium via Kafka
pythoncopiarimport dlt from dlt.sources.kafka import kafka_consumer @dlt.resource(primary_key="id", write_disposition="merge") def orders_from_cdc(): for msg in kafka_consumer(topic="orders.public.orders"): event = msg.value # payload no formato Debezium yield event["after"] or event["before"] # before-only = DELETE pipeline.run(orders_from_cdc())

💡 Encadeando as três seções desta aula: o WAL do Postgres (Log-Based) é lido pelo Debezium, que publica no Kafka (Ferramentas), e o dlt consome esse tópico aplicando merge por primary_key no destino — a mesma arquitetura genérica (Origem → Método → Changelog → Upsert → Destino) vista mais acima, só que cada peça já resolvida por uma ferramenta madura do ecossistema.

Checklist
✅ Boas Práticas
🔑 Chave primária estável não é detalhe
É pré-requisito. Sem uma chave que identifique a mesma linha ao longo do tempo, o destino não consegue casar versões nem aplicar upsert corretamente.
🔁 Upsert idempotente no destino
O consumidor deve poder reprocessar o mesmo evento sem duplicar dados — eventos podem chegar mais de uma vez (at-least-once).
📸 Snapshot inicial + CDC incremental
É o padrão universal: uma carga completa única para popular o destino, seguida da captura incremental para manter tudo em dia.
📡 Monitore o lag entre origem e destino
Um consumidor lento ou parado acumula atraso — em log-based, isso também arrisca o log nativo expirar antes de ser lido.

⚠️ Em trigger-based, gatilhos vivem dentro da produção — cada mudança de schema na tabela de origem pode exigir atualizar o gatilho junto. Em log-based, um consumidor que fica offline por tempo demais pode perder eventos se o WAL/binlog for reciclado antes de ser lido — dimensione a retenção do log de acordo com o pior cenário de indisponibilidade do consumidor.
