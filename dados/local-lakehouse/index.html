Até pouco tempo atrás, o combo "DuckDB + arquivos Parquet" resolvia metade do problema: você conseguia consultar um data lake local em segundos, mas não conseguia escrever nele de verdade — não existia histórico, versão, nem jeito seguro de atualizar uma linha sem reprocessar tudo. Fundamentos
🏠 O que é um Lakehouse (e por que "local")?

Pensa em três jeitos de guardar brinquedos. O Data Warehouse é um cofre trancado: tudo super organizado, em caixinhas etiquetadas, mas só entra brinquedo novo se alguém arrumar um espaço certinho pra ele primeiro — é caro e lento pra mudar. O Data Lake é o baú gigante: joga qualquer brinquedo lá dentro, rapidinho e barato, mas depois de um tempo ninguém sabe mais o que tem lá no fundo nem se aquele brinquedo ainda funciona. O Lakehouse é o meio-termo esperto: um baú grande e barato (o lake, cheio de arquivos Parquet) só que com um caderninho de controle em cima dele — o table format — anotando exatamente o que tem, quando mudou, e uma cópia de segurança de cada estado anterior.

🏦 Data Warehouse
Tudo pré-organizado em tabelas rígidas, ótimo desempenho para relatórios — mas caro, fechado, e mudar o esquema (schema) dói. Geralmente vive só na nuvem.
🌊 Data Lake
Qualquer arquivo (CSV, JSON, Parquet) jogado numa pasta ou bucket. Barato e flexível, mas sem controle de versão, sem transação seguras: um UPDATE malfeito pode corromper tudo.
🛥️ Lakehouse
Arquivos abertos do Data Lake (Parquet) + um caderninho de metadados por cima (Iceberg/Delta) que dá transações, versões e schema — sem abrir mão do custo baixo.

O que muda quando ele é "local"?

Um lakehouse na nuvem normalmente envolve Spark, um catálogo gerenciado (Glue, Unity Catalog) e um bucket S3 — várias peças, várias contas, vários minutos de espera. Um lakehouse local troca isso por DuckDB (motor de consultas + agora também de escrita), Apache Iceberg (o caderninho de metadados) e uma pasta no seu disco — as mesmas ideias, sem infraestrutura para provisionar. É o mesmo "lakehouse", só que cabendo no seu laptop.

Como as Peças se Encaixam
🧱 Anatomia de um Lakehouse Local

Um lakehouse local é um sanduíche de três camadas, cada uma resolvendo um problema diferente. Da base para o topo: onde os bytes moram, o que descreve a história da tabela, e o motor que fala SQL com você. Clique em cada camada para ver o papel dela.

🥪 De cima para baixo
🦆 Motor de consultas — DuckDB
🧊 Table format — Apache Iceberg
📦 File format — Parquet
💽 Armazenamento — disco local / bucket
🦆 Motor de consultas — DuckDB
Roda dentro do seu processo Python (in-process): lê e agora também escreve nas camadas de baixo via SQL comum — SELECT, INSERT, UPDATE, DELETE. É o "rosto" com quem você conversa.
💽 Armazenamento — só bytes
Uma pasta, um disco, um bucket S3. Não sabe nada sobre "tabelas" — só guarda arquivos.
🧊 Table format — a memória
Iceberg (ou Delta Lake) anota quais arquivos formam a tabela agora, e guarda o registro de como ela era antes — sem isso, um data lake nunca teria "antes".
🦆 Motor — a conversa
DuckDB traduz seu SQL em leituras/escritas dessas duas camadas — e faz isso na sua própria máquina, sem round-trip de rede.

Essa última parte — "sem round-trip de rede" — parece detalhe, mas é a diferença entre perguntar pro coleguinha do lado (resposta na hora) e escrever uma carta pra nuvem e esperar o correio voltar. Veja a escala:

O Caderninho de Metadados
📸 Apache Iceberg por Dentro: Snapshots e Manifests

Imagina que sua caixa de brinquedos (a tabela) é fotografada toda vez que algo muda — um brinquedo entra, sai, ou troca de lugar. Cada foto é um snapshot: uma versão completa e válida da tabela num instante exato. O Iceberg não guarda a foto inteira de novo a cada vez (isso seria um desperdício) — ele guarda uma lista do que mudou e aponta para os arquivos de dados que continuam valendo. É esse índice de fotos + apontadores que transforma um monte de arquivos Parquet soltos em uma tabela com histórico de verdade.

Clique e desça pela pilha de metadados — de "qual é a foto atual?" até o arquivo de dados de verdade

📚 Lista de snapshots — o álbum inteiro
🗂️ Manifest list — o índice desta foto
📋 Manifest file — quais caixas (arquivos) entram

📇 metadata.json
O ponteiro raiz da tabela: diz qual é o snapshot atual, o schema vigente e o histórico de schemas. É o único arquivo que qualquer leitor precisa achar primeiro.

🔎 Consultando o álbum de fotos
Toda tabela Iceberg expõe seu próprio histórico via SQL — sem precisar de nenhum log externo.
sqlcopiarSELECT * FROM iceberg_snapshots(iceberg_catalog.default.vendas); -- snapshot_id | timestamp_ms | operation | summary
A sacada do Iceberg

Nada de reescrever a tabela inteira a cada mudança. Um INSERT pequeno cria só um arquivo de dados novo + um manifest novo + um metadata.json novo apontando pra ele — os arquivos antigos continuam lá, intactos, formando o snapshot anterior. É "controle de versão" (tipo git) aplicado a tabelas.

A Virada Recente
✍️ DuckDB Como Escritor no Iceberg

Por muito tempo, o DuckDB era um ótimo leitor de tabelas Iceberg (via iceberg_scan) mas não um escritor. O fluxo comum era: prototipar localmente e depois "entregar" para outro sistema (Spark, um serviço gerenciado) fazer a escrita de verdade. Isso mudou — o DuckDB agora participa do caminho de commit do Iceberg como um escritor de primeira classe, não um "exportador" por fora. Um INSERT/UPDATE/DELETE no DuckDB agora produz arquivos de dados, arquivos de delete (quando necessário) e um novo snapshot de metadados — igualzinho a qualquer outro motor Iceberg faria.

O caminho de uma escrita, do seu script até o snapshot novo
📄 Arquivos/streams locais (CSV, Parquet, JSON)
🦆 DuckDB — SQL in-process
📖 Catálogo REST do Iceberg
💽 Armazenamento de objetos (dados + deletes + metadados)
📄 Arquivos/streams locais
Tudo começa num CSV bagunçado, num Parquet já limpo, ou num stream de eventos — a matéria-prima que ainda não tem histórico nenhum.
1. Conectar num catálogo REST Iceberg
sqlcopiarLOAD httpfs; CREATE SECRET iceberg_secret ( TYPE iceberg, TOKEN 'bearer_token' ); ATTACH 'warehouse' AS iceberg_catalog ( TYPE iceberg, SECRET iceberg_secret, ENDPOINT 'https://rest_endpoint.com' );
2. Criar, inserir, atualizar, apagar — SQL comum
sqlcopiarCREATE TABLE iceberg_catalog.default.simple_table ( col1 INTEGER, col2 VARCHAR ); INSERT INTO iceberg_catalog.default.simple_table VALUES (1, 'hello'), (2, 'world'); UPDATE iceberg_catalog.default.simple_table SET col1 = col1 + 5 WHERE col1 = 1; DELETE FROM iceberg_catalog.default.simple_table WHERE col1 = 2;

💡 Note que cada um desses comandos é SQL padrão — nada de API especial. A mágica acontece nos bastidores: o DuckDB conversa com o catálogo REST para reservar o próximo número de snapshot, escreve os arquivos Parquet (e de delete, quando aplicável) no armazenamento de objetos, e só então comita o novo metadata.json — tornando o lakehouse compartilhado mesmo com a computação ficando local.

Quem Sabe Onde Cada Coisa Está
📖 Catálogos REST: o Bibliotecário do Lakehouse

Se o metadata.json é o "índice" de uma tabela, o catálogo é o bibliotecário que sabe, entre todas as tabelas do lakehouse, qual é o metadata.json mais recente de cada uma — e garante que só um commit vence quando duas escritas competem ao mesmo tempo. Sem catálogo, cada motor teria que adivinhar sozinho qual arquivo é o "atual". Escolha uma opção para ver como rodar (ou usar) um catálogo REST.

Script Completo
🧪 Construindo seu Lakehouse Local, do Zero

O mesmo fluxo, em dois sabores: um script Python completo e o equivalente digitado direto no shell interativo do DuckDB. Os dois fazem exatamente a mesma coisa — lêem um CSV bagunçado, criam uma tabela Iceberg versionada, inserem/atualizam dados e confirmam que virou um snapshot de verdade.

Python
pythoncopiarimport duckdb con = duckdb.connect() con.sql("INSTALL iceberg; LOAD iceberg; LOAD httpfs;") # conecta no catálogo REST (local via Docker ou remoto) con.sql(""" ATTACH 'warehouse' AS lakehouse ( TYPE iceberg, ENDPOINT 'http://localhost:8181' ) """) # cria a tabela versionada a partir de um CSV cru con.sql(""" CREATE TABLE lakehouse.default.vendas AS SELECT * FROM read_csv_auto('vendas_bruto.csv') """) # operações do dia a dia viram novos snapshots automaticamente con.sql("INSERT INTO lakehouse.default.vendas VALUES (101, 'Ana', 250.0)") con.sql("UPDATE lakehouse.default.vendas SET valor = valor * 1.1 WHERE cliente = 'Ana'") # consulta comum — igual a qualquer tabela con.sql("SELECT * FROM lakehouse.default.vendas").show() # prova de que existe histórico agora con.sql("SELECT * FROM iceberg_snapshots(lakehouse.default.vendas)").show()
CLI — shell interativo do DuckDB

O que aconteceu nos bastidores

Cada CREATE TABLE, INSERT e UPDATE gerou um snapshot novo no catálogo — três "fotos" da tabela vendas, cada uma reconstruível a qualquer momento. Nada disso precisou de Spark, de um cluster, ou de subir a tabela pra nuvem antes de poder trabalhar nela. E não importa se você chegou lá pelo Python ou pelo CLI — o histórico gerado no catálogo é exatamente o mesmo.

O Preço de Mudar uma Linha
📝 Copy-on-Write vs. Merge-on-Read

Quando você faz UPDATE ou DELETE numa tabela versionada, alguém precisa registrar "essas linhas não valem mais". Existem duas filosofias para isso — pensa em duas formas de corrigir um caderno de anotações:

📓 Copy-on-Write — reescreve a página inteira
1101, Ana, 250.0 2102, Bruno, 180.0 3103, Carla, 90.0
Pra mudar só a linha da Ana, um novo arquivo de dados inteiro é escrito do zero, sem ela — mesmo que o arquivo tenha 100 mil outras linhas intocadas. Simples de ler depois, caro de escrever.
🩹 Merge-on-Read — cola um post-it
1101, Ana, 250.0 2102, Bruno, 180.0 3103, Carla, 90.0
🗒️ delete file: linha 1 não vale mais
O arquivo de dados original não é tocado — só nasce um pequeno "arquivo de delete" apontando quais linhas ignorar. Quem lê depois junta (faz o merge) os dois na hora. Escrita barata, leitura com um pouquinho mais de trabalho.
Simule: quantos bytes são reescritos ao atualizar linhas de uma tabela de 1 milhão de linhas em 10 arquivos?

⚠️ Hoje, o suporte de escrita do DuckDB para UPDATE/DELETE só funciona em tabelas sem particionamento e sem ordenação, usando exclusivamente positional deletes (merge-on-read) — não copy-on-write. Veremos mais no bloco de Limitações.

O Preço de Nunca Apagar Fotos
📈 Crescimento do Histórico e Limpeza (expire_snapshots)

Se você nunca joga fora fotos antigas do álbum, ele fica gigante — mesmo que ninguém mais olhe pra maioria delas. É a mesma coisa com snapshots: cada escrita deixa arquivos antigos intactos no disco (é assim que o time travel funciona!), mas isso significa que o armazenamento só cresce, a menos que você rode uma limpeza periódica que "esquece" fotos velhas demais para importar.

Simule: quantos snapshots antigos você decide manter?

Linha vermelha: sem limpeza, o armazenamento cresce sem parar a cada escrita. Linha verde: rodando expire_snapshots periodicamente, o tamanho se estabiliza.
sqlcopiar-- "esquece" snapshots mais antigos que N dias, liberando os arquivos órfãos CALL lakehouse.system.expire_snapshots('default.vendas', older_than => 7);

Nem Tudo São Flores (Ainda)
⚠️ Limitações Atuais

Escrita Iceberg no DuckDB é uma capacidade recente — poderosa, mas com bordas. Vale conhecer antes de depender dela em produção.

🚫 Tabelas particionadas/ordenadas
UPDATE e DELETE só funcionam hoje em tabelas sem particionamento e sem ordenação.
📍 Só positional deletes
Somente merge-on-read via arquivos de delete posicionais — nada de copy-on-write nas operações de escrita.
🚫 Sem MERGE INTO
A sintaxe upsert clássica não é suportada ainda — é preciso desenhar em torno dela.
🚫 Sem ALTER TABLE
Mudanças de schema exigem um padrão de create/replace em vez de alterar a tabela existente.

⚠️ Contorno prático: use padrões de append (só inserir), create/replace (recriar a tabela quando o schema muda) e UPDATE/DELETE controlados apenas onde as regras acima permitem. Para operações mais avançadas (merge, tabelas particionadas), combine com outro motor Iceberg (Spark, Trino) enquanto o suporte do DuckDB amadurece.

Checklist
✅ Boas Práticas
🧹 Rode expire_snapshots periodicamente
Sem isso, cada escrita deixa arquivos órfãos acumulando — seu "lago" vira um baú sem fundo.
📐 Prefira append quando possível
Dado o suporte ainda parcial a UPDATE/DELETE, padrões de inserção (append) e create/replace são mais previsíveis hoje.
📖 Combine com um catálogo REST desde cedo
Mesmo em experimentos locais, anexar um catálogo (mesmo que local via Docker) já te acostuma com o fluxo "de verdade" de commit.
🔍 Use iceberg_snapshots() para auditar
Antes de confiar num pipeline, confira se cada etapa está de fato gerando um snapshot novo — é sua prova de que a escrita comitou.

💡 Um lakehouse local não substitui um lakehouse compartilhado em produção com muitos escritores concorrentes — para isso, um catálogo remoto de verdade (Glue, Nessie, Polaris) continua sendo a peça central. Use o modelo local para desenvolver, prototipar e depurar mais rápido, sabendo que o mesmo formato de tabela funciona nos dois mundos.
